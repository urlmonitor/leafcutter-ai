## Implementation Notes

```yaml
- THE WARN LIST LIVES IN commit_guardian.json UNDER THE `frontend_ac_declaration`
  SECTION (key `warn_paths`, as the mock record gf-commit-cart-summary-warn already
  names), in BOTH the templates/scripts/commit_guardian/ and scripts/commit_guardian/
  copies. A list in a new bespoke config file would be a second configuration surface
  for one hook and would miss the build parity check.
- MATCHING IS PATH-PREFIX ON REPO-RELATIVE, FORWARD-SLASH-NORMALISED PATHS, ANCHORED
  AT A DIRECTORY BOUNDARY. `storefront-jsx/src/components/` must not match `storefront-jsx/src/components-legacy/Foo.jsx`.
  Normalise before comparing — a Windows-style separator or a leading `./` slipping
  through would silently widen or narrow the list.
- 'ABSENT AND EMPTY BOTH MEAN ''NOTHING IS ON WARN''. The default for a missing `warn_paths`
  key, an empty list and a null value is identical: every path blocks. An implementation
  that reads a missing key as ''unconfigured, therefore permissive'' silently repeals
  the L0 — this is the second scenario and it is a real default-handling bug, not
  a hypothetical.'
- WARN DOWNGRADES THE VERDICT FIELD ON THE EXISTING FINDING; IT DOES NOT SUPPRESS
  THE FINDING AND DOES NOT CREATE A SECOND ONE. A warn that suppresses the finding
  is indistinguishable from the file being out of scope, and an area on the warn tier
  is meant to be visibly unfinished, not invisible. GE-124d-3 fixes the exclusivity.
- THE MESSAGE MUST NAME THE LIST AND THE DEFAULT — that this path is on frontend_ac_declaration.warn_paths
  and that every other path blocks — so a reader of the output learns the tier is
  an opt-in rather than assuming the check is advisory everywhere.
- A warn-tier finding must not change the exit code. Collect warn findings alongside
  block findings and decide the exit from the block set alone; an implementation that
  returns early on the first warn will also skip the block findings after it.
```
