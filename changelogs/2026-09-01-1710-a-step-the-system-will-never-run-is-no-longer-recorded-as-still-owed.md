description: "When a piece of work belongs to a group, the system handles one particular step once for the whole group rather than separately for each member. The generator did not know that, so every member was created claiming that step was still owed by it individually — and each one then refused to be recorded as finished, waiting on a step nobody was ever going to perform for it. Twenty-five were corrected by hand, three hundred and fifteen more by a migration written for the purpose; this change makes the generator produce them correctly in the first place, which is the only version that does not need doing again. Which steps are skipped for which kind of location is now a written declaration rather than something inferred, and the generator reads it from the item's own final location — not from whatever the caller happens to say. That distinction is load-bearing: a generator that accepts the caller's word about what to skip has stopped checking, and the whole failure being fixed here was a generator that did not check. If the declaration is missing the generator refuses outright rather than guessing, because quietly guessing is how the original problem stayed invisible for so long. A skipped step is recorded in two places that must agree: it is marked as excluded, and its line is removed from the checklist. Setting one without the other is its own defect — a leftover checklist line reads to a person as outstanding work and is rejected by the existing consistency check, while removing the line without recording the exclusion loses the reason. The tempting shortcut is worse than either: marking the step as completed also unblocks the item, and is a false statement that work was performed. That route is now closed, and the test that closes it asserts the false record is rejected by the checker that already existed for exactly this purpose. One finding from the run is recorded rather than quietly fixed. The automated test author wrote a test that could never pass — it checked a helper it had itself defined in the test file, which always failed. Because a failing test is what the first quality gate wants to see before implementation begins, that gate approved it; the second gate, which requires everything to pass afterwards, then blocked all seven pieces of work even though every one had been implemented correctly. The run returned all seven to the unstarted pile, which is the right call on the merits and still leaves a completed implementation looking exactly like a run that achieved nothing. The underlying gap is that a failing test proves the test is connected to something, not that it is connected to the code being built, and nothing currently asks the second question."
