## Acceptance Criteria

```gherkin
Given a merge commit that has already been made, so no record of an operation in progress
  remains, and the author now revises it — restaging the same merged content plus one edit
  of their own,
When a check that works out its own change set runs on that commit,
Then the change set it inspects holds the author's edit and not the merged-in work,
And the absence of an operation record does not cause the whole staged tree to be
  attributed to the author,
And the verdict is identical to the verdict on the original merge commit plus that same
  edit made as an ordinary follow-up commit.

Coverage note: perform the revision as a real repository operation — the states the commit
is built on are still discoverable from the commit being revised even though the operation
record is gone, and an implementation that reads only the operation record fails this case
while passing every merge fixture in this L1. Execute the check as a process and assert
result status and output text in both arms.
```

## Implementation Notes

```yaml
- SIGNAL ORDER IS THE DEFECT. The states the commit is built on must be consulted
  FIRST; the operation record refines the answer. The named anti-pattern is 'if there
  is no operation record, treat this as an ordinary commit and use the whole staged
  tree' — it reads as a sane default and it fails only on this case, because every
  other fixture in this L1 has the record present.
- THE PARENTS OF THE COMMIT BEING REVISED ARE STILL DISCOVERABLE after the operation
  record has expired. Derive them from the commit under revision, not from the expired
  marker. When the commit being amended has two parents, the derivation must use both.
- 'VERDICT EQUALITY IS AN ASSERTION ABOUT TWO REAL RUNS, not an inference: the revised
  merge plus the edit must produce the same result status and the same objected-to
  content as the original merge followed by the same edit as an ordinary commit. Both
  arms in one case.'
- This case must hold in the deployed layout after build.py (ADR-001), and it must
  hold inside a git worktree — resolve git state through plumbing rather than filesystem
  assumptions.
```
