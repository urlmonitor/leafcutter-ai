## Acceptance Criteria

```gherkin
Given the same run is started three times against the same project -- once with
  the process working directory set to the project root, once set to a git
  worktree of the project, and once set to a directory that contains neither the
  project nor any installed copy of the route's support files,
When each run starts,
Then all three reach the same point -- the first question the route puts to the
  user,
And no run stops before that point reporting a file it could not find or a
  directory that is not a repository,
And every support file each run read or executed before that point resolves to a
  file inside the project it was pointed at.
```

## Implementation Notes

```yaml
- The change must land under templates/. This record's evidence must be gathered against
  the source copy; ACD-2100d-1 is where the deployed copy is exercised.
- The class must be closed by a single resolution used by every support-file access
  on the startup path -- not by five per-site repairs. A per-site repair leaves the
  sixth site to be added the same way the last five were written.
- The last Then clause must be established from what the process actually did -- the
  files it opened or the commands it issued, as recorded by the run itself or by the
  operating system -- never from a source scan. A scan for the literal string passes
  on a path that is never executed and fails on a correct path built by concatenation.
- All three runs must complete their startup path with no network available, so a
  transport failure cannot be mistaken for a resolution failure.
- Must satisfy the repository error-handling policy across every resolution site touched.
- The startup path must reach its first question in under 2 seconds from each of the
  three directories on a cold run, so that a resolution built on a filesystem search
  does not become the new startup cost.
```
