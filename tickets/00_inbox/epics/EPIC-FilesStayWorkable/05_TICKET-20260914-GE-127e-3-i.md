  Plain-list spec form, and no config_schema_fragment invented to satisfy the structured-spec
  validator — the BP-100k-4 / BP-100k-4-i fictional-key precedent is not repeated.'
- 'THE UNAVAILABILITY VOCABULARY IS REUSED, THE EXIT STATUS IS NOT — THIS IS THE DECISION
  THE BA DEFERRED AND IT IS TAKEN HERE, WITH ITS REASONING. GE-127a-1-i pinned BP-1600a-2-ii''s
  contract for a file whose LENGTH could not be established: an "INDETERMINATE: reason=<text>"
  line naming which situation occurred, at exit 2, alongside exit 0 clean and exit
  1 for a measured finding. That contract is reused HERE IN ITS LINE SHAPE AND ITS
  NAMING DISCIPLINE — a single machine-readable token, followed by `reason=` and a
  specific reason, naming the situation that actually occurred — and is NOT reused
  in its exit status. The substantive difference decides it: a failure to MEASURE
  leaves the verdict unknown, which is what exit 2 means; a failure to DESCRIBE leaves
  the verdict perfectly known — the file''s length was established and found over
  — and only the advice missing. This record positively requires the commit to be
  refused in that case, so the run must exit 1 with the ordinary refusal for that
  file, carrying the could-not-be-described line INSIDE that file''s refusal block
  on the same stream. Routing it to exit 2 would be a defect three times over: it
  would move the verdict, which the title of this record forbids; it would collapse
  the very distinction GE-127a-1-i''s third clause exists to hold, by making a known-over
  file report as indeterminate; and structurally the exit-2 paths in main() print
  to stderr and return immediately, suppressing the refusal block this line is required
  to be attached to.'
- 'THIS IS NOT A THIRD VERDICT SET, AND THE GUARD ALREADY DEMONSTRATES WHY. check_file_size
  already emits "EMPTY HISTORY: reason=<text>" — the same token-and-reason line shape
  as INDETERMINATE, deliberately named distinctly, and deliberately NOT carrying exit
  2, because an empty previous-length history is a legitimate completing result. The
  could-not-be-described state is the same construction applied to a different step:
  one shared line grammar, one naming discipline, and a status decided by the VERDICT
  rather than by the token. Choose a token in that grammar which cannot be misread
  as either of the existing two, and record it in the guard''s own module docstring
  alongside them.'
- NAME THE REASON SPECIFICALLY, AND DO NOT COLLAPSE DISTINCT CAUSES. "Could not be
  described" will have more than one cause — content that will not parse into parts,
  a part set that cannot account for half the quoted length (GE-127e-1 routes that
  state here), a kind for which no extractor exists. These are different facts about
  the world and the reason text must say which occurred, exactly as GE-127a-1-i requires
  the two measurement situations to be named separately. A single shared sentence
  for all causes costs the author the only information that tells a genuinely unparseable
  file from a gap in the gate.
- 'THE DESCRIPTION STEP MUST BE STRUCTURALLY INCAPABLE OF MOVING THE VERDICT. The
  verdict is computed from length alone and must be fixed BEFORE the description step
  runs, so no outcome of that step — success, failure, or an exception — can change
  whether the commit completes. Do not compute the verdict from anything the description
  produced, and do not let the description step raise into the classification loop.
  The recorded defect on this guard''s measurement step is the same shape one step
  earlier, and this one would be quieter: a caught exception in the description step
  turning a refusal into a completed commit silently undoes GE-127a and GE-127b for
  exactly the files hardest to describe, and no test in either of those records would
  notice, because their fixtures describe cleanly.'
- THE STATEMENT IS AN ATTACHMENT TO A REFUSAL, NEVER A FINDING OF ITS OWN. A file
  that is within its permitted length produces no could-not-be-described line even
  when it is undescribable, and no exit-status change. Gate the emission on the file
  already having been refused, not on the description step having been attempted —
  the cheap implementation reports the failure wherever it occurs and would break
  GE-127a-1's silence arm from a direction that record cannot see.
- 'Must follow the repo error-handling policy: the description step performs I/O and
  parsing, so specific-exception try/except, and log at WARNING or higher or re-raise.
  The re-raise-equivalent here is the could-not-be-described line itself. A swallowed
  error must never become an absent description that also relaxes the verdict, and
  must never become an empty parts list that reads to the author as "this file has
  no parts".'
- 'EXERCISE THE UNDESCRIBABLE STATE FOR REAL. Make the content genuinely unresolvable
  into parts at run time — a covered file whose bytes do not parse, or whose structure
  yields no locatable part — never by asserting that an error branch exists in the
  source. BP-100k-4-i''s standing constraint applies unchanged, and this record''s
  own notes say so: a source assertion stays green on precisely the swallow-and-continue

**Design ruling 1 — where "plainly" lives.** The stated could-not-describe
line belongs in `check_file_size.py`'s `_print_file_description()` — the
single call site both `_print_too_large_file` and `_print_grown_file`
already route through, exactly the pattern already used for
`_print_measures_line()` and `_print_asymmetry_advice()` so wording cannot
drift between the two refusal printers. Today `_print_file_description`
returns silently on `describe_file() is None`; that silent early return is
confirmed (read in full) as this AC's subject. The gate this ticket's notes
require — "attach only to an existing refusal, never to describing itself" —
is ALREADY structurally satisfied: `_print_file_description` is called only
from the two refusal printers, both of which are only reached for a file
already classified `too_large`/`grew` in `main()`'s classification loop, so
no separate gating condition needs to be added for that half. What must
change is `_file_description.py`'s `describe_file()` return contract: a bare

(unparseable content, no extractor registered for the kind, located parts

code already collapses "no extractor" and "zero parts found by a real
extractor" into the same `parts == []` branch; python-coder must split

itself belongs beside `format_description_lines()` in `_file_description.py`
(formatting stays in that module), while the print call and the
already-satisfied refusal-only gate stay in `check_file_size.py` — this
mirrors the existing architecture split stated in both modules' docstrings.

output — this is the arm that catches an implementation that reports the
