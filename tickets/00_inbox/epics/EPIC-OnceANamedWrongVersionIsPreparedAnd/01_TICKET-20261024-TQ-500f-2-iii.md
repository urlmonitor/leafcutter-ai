## Acceptance Criteria

```gherkin
Given the code-aware test designer is naming the wrong versions for
  test_report_only_branch_announces_finding, which guards requirement R4, a
  rule that announces a finding when a proof enters its entry point, and its
  candidate names are —
    C1 "a fixture on which no entry point resolves, so the report-only
       branch is never reached and the test passes vacuously",
    C2 "an assertion that reads the source file rather than the emitted
       line",
    C3 "a rule that is never reached on any fixture",
    C4 "a rule that passes the verdict through but announces nothing",
  and for requirement R5, whose code under test itself inspects test files,
  the candidate C5 "assertions matched by position, so an inserted assertion
  shifts the strict one",
When it produces the test design for R4 and R5,
Then C1 and C2 are left out of must_catch, because no change to the code
    under test is a wrong fixture or a wrong assertion,
  And for each of them the design names instead the wrong version of the
    code that the defective test would let through, C3 for C1 and C4 for
    C2, and a name already in the list is not added a second time,
  And the concern behind C1 and C2 stays on record in the description of
    that test entry, where review sees it, without becoming a wrong version
    a drive must prepare,
  And C3, C4 and C5 are kept as must_catch names: a name that mentions a
    fixture, an assertion or a test is a test defect only when no change to
    the code under test can be that name,
  And a name of the C1 kind that reaches a drive anyway is reported by the
    preparer as could not be prepared, with the reason that it names a
    defect in a test rather than in the code, so a reader sees that the
    requirement must be corrected rather than the code or the tests.
```
