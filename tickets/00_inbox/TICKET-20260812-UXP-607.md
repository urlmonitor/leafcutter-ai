# The mock-mode badge always tells the truth about what you are looking at

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `UXP-607` — The mock-mode badge always tells the truth about what you are looking at — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `UXP-607`. Component: `ux-prototyping`. Assigned agent: `frontend-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given the Atlas has resolved, at request time, which data source is in effect — the runtime
  mock decision produced by the data-layer seam (resolution order: production lock > runtime
  override > LEAFCUTTER_MOCK env default),
When a page renders the mock/live badge,
Then the badge is derived from that resolved runtime decision, not from the build-time
  NEXT_PUBLIC_ mock flag,
And when the resolved decision is "mock" the badge reads "mock" and every view on the page is
  served from bundled fixtures,
And when the resolved decision is "live" the badge reads "live"/real and every view is served
  from the real repo,
So the badge and the data actually served can never disagree.
```

- [ ] AC-1: the badge is derived from that resolved runtime decision, not from the build-time
- [ ] AC-2: when the resolved decision is "mock" the badge reads "mock" and every view on the page is
- [ ] AC-3: when the resolved decision is "live" the badge reads "live"/real and every view is served

## Implementation Notes

```yaml
- The badge value must be derived from the single resolved runtime mock decision returned
  by the data-layer seam in leafcutter-web/lib/data/mock.ts (resolution order production
  lock > runtime override > LEAFCUTTER_MOCK env default), never from the build-time
  NEXT_PUBLIC_ mock flag.
- The badge component in leafcutter-web/components/shell/sidebar.tsx and the view
  data must both read from that one resolved decision so they are computed from a
  single source and cannot diverge.
- Resolution must be evaluated per request on the server so a runtime override is
  reflected in the same response that serves the overridden data (no stale build-time
  value).
- No fallback code path may re-read the NEXT_PUBLIC_ build-time flag for the badge;
  the build-time flag must not be able to re-introduce badge/data divergence.
```
