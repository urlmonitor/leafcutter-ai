# KI-BO-20261009-1832 — /build-feature refuses a handoff to a phase the handing phase has just added, because it checks the target against the planner's opening snapshot of the agents map instead of the live record it re-read a moment earlier

- **Severity:** medium. The drive halts loudly and commits nothing wrong, and a re-run gets
  past it because by then the ticket carries the new key. But the halt reason is false: the
  target *is* on the ticket, and the driver's own read-back from the same iteration says so.
  Every ticket where `architect-review` adds an ADR phase costs one wasted run, and the
  operator is told to "fix the emitter or the ticket's agents map" when neither is wrong.
- **Status:** open. No AC. The handoff checks are BO-3000a (2026-10-06); the mid-drive
  promotion is BO-3700. Each is right on its own; they read different copies of the phase list.
- **Occurrences:** 2 (2026-10-09). `/build-feature EPIC-OneDurableLogRootForEveryWorkspace`,
  ticket `01_TICKET-20261009-INF-500d-4-iii`, runs `wf_6eeb35a5-324` (worktree
  `feedback-sink-scaffold`) and `wf_20325042-622` (worktree `EPIC-OneDurableLogRootForEveryWorkspace`).
  The third run, `wf_0648a71b-2ac`, advanced: its ticket-planner reported
  `{"agent":"adr-author","status":"needed"}` in `ordered_phases`, and adr-author returned `ok`.
- **First seen:** 2026-10-09 · **Last seen:** 2026-10-09
- **Where:** `templates/workflows-js/build-feature.js` on origin/main `282117ab5`:
  - the snapshot: `const orderedPhases = plan.ordered_phases;` (:1936), filled by the
    `ticket-planner` dispatch (:1910-1925) before any phase runs, and never reassigned;
  - the live re-read and promotion, in the same iteration and *before* the handoff branch:
    `readTicketRecordBack` (:2257) then `absorbPromotedPhases(phaseRecord, pendingPhases,
    plannedPhaseNames, ...)` (:2269-2275), which adds a newly `needed` phase to `pendingPhases`
    and to the `plannedPhaseNames` set (function body :611-636);
  - the refusal: the handoff branch (:2349) computes `unfit` at :2389-2396, and the
    "not on this ticket" arm is `!orderedPhases.some((p) => p.agent === normalizedTarget)`
    (:2392-2393), refused at :2397-2403.

  The deployed copy (`.claude/workflows/build-feature.js`, built 2026-10-08) has the same
  logic: snapshot :1898, read-back :2236, promotion :2248, handoff branch :2334, the
  `orderedPhases.some` arm :2377-2378. Not fixed on origin/main; this is not a stale deploy.

## Symptom

`architect-review` returned:

```text
{"status": "handoff", "handoff_target": "adr-author", "message": "Classified LARGE: 7 files
(over 5) across 3 components ... I set requires_adr: true and added `adr-author: needed` to
the ticket, with a matching Sign-offs row. I handed off to adr-author ..."}
```

The driver halted with:

```text
Phase 'architect-review' returned 'status: handoff' but it names 'adr-author', which is not
on this ticket (not a key of its agents map). Nobody was dispatched and the ticket did not
advance; fix the emitter or the ticket's agents map, then re-run /build-feature.
```

## Cause

The journal of `wf_6eeb35a5-324` shows the two lists side by side:

- `ticket-planner` (journal line 11) returned `ordered_phases` with `architect-review`,
  `test-writer`, `python-coder`, ... and **no `adr-author` entry**: the ticket's agents map had
  no such key when the drive started.
- `signoff-readback` after `architect-review` (line 15) returned
  `needed_phases: [..., "adr-author", ...]`.

So the driver had the right answer. `absorbPromotedPhases` consumed it and queued
`adr-author`. The handoff check, a few lines later, ignored it and consulted `orderedPhases`.
The comment at :2386-2387 says that check exists for "a target that is not on this ticket
(orderedPhases keeps not_needed keys)". That holds for keys present at plan time. It fails for
a key the handing phase added itself, which is exactly what `architect-review` is chartered to
do when it sets `requires_adr`.

This is the shape `KI-BO-20260901-1000` closed for dispatch: a list frozen before the first
phase runs, read after phases have changed the record. BO-3700 fixed the dispatch loop. The
BO-3000a handoff checks, added later, took the older snapshot.

## Detection

A refusal reading "which is not on this ticket (not a key of its agents map)" where the
journal's `signoff-readback` *after* the handing phase lists the target in `needed_phases`, or
where the ticket file on disk now has the key. The `ticket-planner` result in the same journal
will lack it.

## Workaround

Re-run `/build-feature`. The ticket now carries the key, so the new planner snapshot has it and
the check passes. Confirmed on the third run, `wf_0648a71b-2ac`.

## Fix direction

Check the target against the live set, not the snapshot: `plannedPhaseNames` (which
`absorbPromotedPhases` has already updated by the time the handoff branch runs), or the
`phaseRecord` read-back's agents map. Keep the refusal for a target that is genuinely absent
from both. A behavioural test should drive one iteration in which a phase writes a new
`needed` key and hands off to it, and assert that the target is dispatched, not refused.

**Related:** `KI-BO-20260901-1000` (resolved; the same frozen-snapshot defect in the dispatch
loop, fixed by BO-3700); `KI-BO-20260901-1045` (resolved; handoffs halted because nothing
emitted `handoff_target`). `KI-BO-20261009-1833`, filed the same drive.

**Pattern:** a correct live signal and a stale snapshot of the same fact both in scope, with the
newest check reading the snapshot.
