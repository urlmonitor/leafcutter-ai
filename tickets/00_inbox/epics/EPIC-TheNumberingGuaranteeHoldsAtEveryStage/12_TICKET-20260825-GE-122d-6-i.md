# A pass states what it inspected, so a pass is distinguishable from a hook that never ran

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-122d-6-i` — A pass states what it inspected, so a pass is distinguishable from a hook that never ran — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-122d-6-i`. Component: `guardrail-engine`. Assigned agent: `python-coder`. Estimated complexity: `S`. Complexity: `low`.

## Acceptance Criteria

```gherkin
Given a built working copy in which the numbering check is registered as GE-122d-6 requires,
And each namespace the check holds itself responsible for contains a known number of
  artifacts, with no number claimed twice anywhere,
And a change staged that claims no contested number,
When a commit is attempted through the ordinary commit path,
Then the commit completes,
And the check's output carries one inspected count per namespace it is responsible for,
And each reported count equals the number of artifacts actually present in that namespace,

And given one further artifact is then added to exactly one of those namespaces and the same
  clean commit is attempted again,
Then that namespace's reported count is one higher than before and the other namespaces'
  counts are unchanged, so the counts are read from the collection on each run rather than
  emitted as fixed text,

And given the check is deregistered and the working copy rebuilt,
When the same clean commit is attempted,
Then the commit completes and NO inspected counts are produced at all,
And a reader comparing the two runs can tell the two situations apart from the output alone,
  without inferring anything from the absence of an error.

Coverage note: covered only by executing all three runs against a real built working copy and
comparing their outputs. A test asserting that the output contains the word "inspected", or
that a count field is present in a returned value, covers none of this — a constant satisfies
it. The count must be shown to MOVE with the collection, and the deregistered run must be
performed, because "the commit succeeded and nothing was said" is precisely what this
repository's four unregistered guards produce today and it is currently indistinguishable
from a clean pass.
```

## Implementation Notes

```yaml
- THE COUNTS ARE THE PROOF OF EXECUTION, so they must be emitted on the PASSING path,
  at the commit-time stage, where nobody is looking. A count emitted only on the failing
  path proves nothing about a green commit, and a green commit is the state the repository
  has been in for four unregistered guards.
- 'One count per namespace, never a single total. A total hides the case this criterion
  is about: three namespaces read and one skipped sums to a plausible-looking number,
  and the blind spot is invisible.'
- The count must be the number of artifacts the pass ATTEMPTED to read in that namespace,
  tracked during the walk — the same counter GE-122d-3 requires for the degraded path,
  not a second one. Two independently-maintained counts will disagree, and the disagreement
  will be settled by whichever is quieter.
- 'THE NAMESPACE SET IS DERIVED, NEVER LISTED (IT-PO 2026-08-25). The set of namespaces
  the count line spans must come from the same declaration the pass resolves its roots
  from — ADR-037''s responsibility set as it is expressed in configuration — so that
  a namespace added tomorrow gets a count line without an edit here. A per-namespace
  count emitted from a literal sequence written into the reporting code is the same
  always-green shape this AC exists to defeat, one layer up: the fifth namespace would
  silently have no line and nobody would miss it.'
- Keep the output legible on a passing commit without making it noise. The commit-time
  stage prints on every commit in the repository; a per-namespace count line is the
  budget, and a per-artifact listing is not.
- OUTPUT STREAM AND VISIBILITY ARE PART OF THE DELIVERABLE. The count line must land
  where a reader of an ordinary successful commit actually sees it, under the hook
  framework's normal passing-hook presentation — not on a stream the framework swallows
  on success, and not behind a verbosity flag nobody sets. A count that is emitted
  but not shown satisfies the letter of this AC and none of its purpose; the deregistered-run
  comparison is what proves it is visible, because the comparison is made on captured
  commit output.
- 'FILE SCOPE: this AC edits the check and its scanner module (both under templates/scripts/commit_guardian/,
  with their scripts/commit_guardian/ counterparts regenerated by build.py per ADR-001,
  never hand-edited) plus the new test module. It does not touch the registry — registration
  is GE-122d-6''s surface, and this AC consumes it.'
- Error handling per CLAUDE.md Rules 1-4. This criterion covers the clean path only;
  the could-not-establish and terminated-abnormally outputs are GE-122d-3's and GE-122d-3-i's
  and are not re-specified here.
```
