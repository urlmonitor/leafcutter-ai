## Acceptance Criteria

```gherkin
Given the staged set contains five screen component files that each declare
  the criterion UXP-100d-2, written in the comment syntax native to the file:
  - a `.tsx` file whose first tokens are a `/** ... @ac UXP-100d-2 ... */`
    block comment
  - a `.jsx` file whose first tokens are a `/** ... @ac UXP-100d-2 ... */`
    block comment
  - a `.vue` file whose first tokens are an `<!-- ... @ac UXP-100d-2 ... -->`
    comment placed above its first `<template>`, `<script>` or `<style>` block
  - a `.svelte` file whose first tokens are an
    `<!-- ... @ac UXP-100d-2 ... -->` comment placed above its first markup or
    `<script>` block
  - an `.html` file whose first tokens are an
    `<!-- ... @ac UXP-100d-2 ... -->` comment placed above its first element
When the frontend declaration reader evaluates the staged set
Then all five files record the declared list ["UXP-100d-2"]
And all five files record the declaration verdict "declared"
And each file records the framework derived from its extension —
  .tsx as react-tsx, .jsx as react-jsx, .vue as vue-sfc, .svelte as svelte,
  .html as html
```

## Implementation Notes

```yaml
- TWO COMMENT DIALECTS, ONE MARKER. Implement exactly two leading-comment extractors
  — a JS block-comment extractor for .tsx/.jsx and an HTML comment extractor for .vue/.svelte/.html
  — both feeding GE-124a-1's single @ac grammar. Do not write five per-extension parsers;
  the marker, the list shape and the separators are identical across all five and
  duplicating them is how the five drift apart.
- 'THE EXTENSION-TO-FRAMEWORK MAP IS A SINGLE DATA STRUCTURE, not a chain of if-statements,
  and it is the same structure GE-124a-3 consults for the in-scope extension test.
  One map, two readers: a second copy would let a file be in scope with no framework,
  or carry a framework while being out of scope.'
- THE `html` FRAMEWORK VALUE IS NEW AND HAS NO WORKED RECORD. docs/product-truth/mock-data/guardrails/frontend-ac-declarations.mock.json
  declares framework as the five-value enum including `html`, but its FrontendComponent
  records cover only react-tsx, react-jsx, vue-sfc and svelte — there is no .html
  record in the dataset. The .html path must therefore be built and tested from a
  purpose-written fixture, and the implementer must not assume a mock record exists
  to copy. If the user removes .html from scope, this AC and GE-124a-4's five-shape
  how-to are the two places to change.
- SFC LEADING REGION IS 'ABOVE THE FIRST BLOCK TAG'. For .vue and .svelte the region
  ends at the first `<template>`, `<script>` or `<style>` tag; for .html it ends at
  the first element; for .tsx/.jsx it ends at the first non-comment, non-blank token
  (typically the first import). Encode the region boundary once per dialect and expose
  it to GE-124a-2-i, which asserts the negative from outside it.
- Byte-order marks, shebangs, blank lines and consecutive comment blocks must not
  push a valid declaration out of the leading region. A single leading blank line
  is the most common real-world form and must pass.
- Must handle errors gracefully per the project error handling policy; an unparseable
  file is GE-124c-3-i's named-and-skipped path, not a crash and not a silent pass.
```
