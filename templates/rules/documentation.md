## 4. Mandatory Architectural Diagrams (Mermaid.js)
Diagrams should follow a 3-tier strategy to prevent context bloat:
1.  **`docs/` Directory:** Macro architecture, major system components, and ADRs (Architecture Decision Records). *Ensure these are linked in the document's frontmatter using the `architecture_diagrams` field.*
2.  **Folder `README.md`:** Shows how the files in that specific folder orchestrate and interact.
3.  **File Docstrings/Headers:** Shows the internal sequence flow of a single heavy script or procedure.

**Deterministic Triggers for Embedded File Diagrams:**
Whenever you (the AI) or a developer create or refactor code meeting these conditions, a Mermaid.js diagram MUST be included directly inside the docstring or SQL header `ARCHITECTURE: ` field. 
*If the condition is not met, explicitly state `ARCHITECTURE: Not needed.`*

- **Python/Backend Components require a `graph TD` diagram if:**
  - **Orchestration:** The code coordinates 3 or more distinct systems (e.g., API + Database + Queue).
  - **Workers/Loops:** The component follows the Calculate-Batch-Sleep pattern.
  - **State Machines:** The code manages transitions between 3 or more distinct states.
  - **Data Transformation / Complex Logic:** The code handles significant data transformations, logic branching, or fractal/pattern scanning.

- **SQL Procedures require a `flowchart TD` diagram if:**
  - **Data Pipelines:** Uses Temporary Tables or multiple CTEs to stage data before a final merge.
  - **Orchestrators:** The primary purpose is `CALL`ing other SQL procedures.

*Note: The commit checker applies regex to verify that Temp Tables and Called Procedures described in SQL are actually represented in your Mermaid diagram!*

## 5. File-Level Decision History (Micro-ADRs)
To prevent "concept ping-pong" (repeatedly reverting or changing structural decisions without context), any source file must include an implementation history at the very bottom of the file.

Currently, this is strictly enforced for **all SQL and Python files** (excluding `__init__.py`). 

**Format Example (Place at the end of the file):**
```sql
/*
====================================================================
DECISION HISTORY
====================================================================
- 2026-04-23 09:15 [Hendrik]: Switched from Lateral Joins to Parameterized 
  function to prevent deep chunk scanning on hypertable targets.
- 2026-03-01 10:00: Initial implementation.
====================================================================
*/
```
If you modify an existing complex SQL procedure, you **must append a new entry** to its `DECISION HISTORY` block explaining what you changed and why, to ensure context remains attached to the code.

## 6. Function & Class Docstrings (Google Style)
All Python functions, methods, and classes **MUST** have Google-style docstrings. This is enforced by `check_docstrings.py` in the pre-commit hooks.

**Required Format:**
```python
def fetch_data(symbol: str, interval: str = "1m") -> pd.DataFrame:
    """Fetch candle data from the database for a given symbol.

    Args:
        symbol: Trading symbol (e.g., 'BTCUSDT').
        interval: Candle interval. Defaults to '1m'.

    Returns:
        pd.DataFrame: DataFrame with OHLCV columns indexed by open_time.

    Raises:
        ValueError: If symbol is not found in the database.
    """
```

**Rules:**
- **Summary line**: First line must be a one-line description.
- **Args section**: Every parameter (except `self`/`cls`) must be listed.
- **Returns section**: Required when the function has a non-None return annotation or returns a value.
- **Raises section**: Recommended but not enforced.
- **Stale params**: Documented params that don't match the signature will be blocked.
- **Type annotations** *(new)*: Every parameter must have a type hint (e.g., `symbol: str`) and every function must have a return type annotation (e.g., `-> None`). Controlled by `enforce_type_annotations` in `commit_guardian.json`.

**Exemptions:**
- Functions with ≤ 5 body lines OR 0 non-self/cls params (trivial getters/setters).
- Dunder methods (except `__init__`): `__str__`, `__repr__`, `__eq__`, etc.
- Files in excluded dirs: `unit_tests`, `alembic`, `debugging`, `legacy`, `tests`.
- `__init__.py` files.

**Parsing**: Docstrings are parsed by the `docstring-parser` library for machine-readable extraction. This enables future automated tooling (data flow graphs, API docs).

## 7. SQL Headers & Dependency Tags
Every SQL file (including views, materialized views, functions, procedures) **MUST** begin with a block comment containing metadata.

**Required Format:**
```sql
/*
MODULE: filename.sql
Object Name: object_name
Dependencies: other_view, other_function  -- OR "none"
GOAL: What this object does
BUSINESS CONTEXT: Why it exists
ARCHITECTURE: Not needed.
*/
```

**Rule for Views and Materialized Views:**
The `Dependencies:` tag is strictly enforced by pre-commit hooks for all views and materialized views. This tag is critical as it enables the `DatabaseManager` to parse and build a topological sort for initializing the database securely without manual ordering hacks.

> ⚠️ **CRITICAL — Tables Are NOT Dependencies:**
> The `Dependencies:` tag must ONLY list other **SQL objects loaded from `sql_functions/`** — i.e. views, materialized views, functions, or procedures. **NEVER list base tables** (e.g., `candles`, `candle_strategy_performance`, `strategy_templates`). Tables are managed by Alembic and already exist before the DatabaseManager loads SQL objects. The dependency resolver only knows about objects it discovers in `sql_functions/views/` and `sql_functions/materialized_views/`, so listing a table name will crash the application with `Unknown dependency`.
>  - ❌ **WRONG:** `Dependencies: strategy_templates, view_profitable_strategies`
>  - ✅ **CORRECT:** `Dependencies: view_profitable_strategies`

## 8. Markdown Documentation Frontmatter
All documentation files located in the `docs/` directory (or its subdirectories) **MUST** include a YAML frontmatter block at the very beginning of the file. This ensures consistent cataloging and structure.

**Required Format:**
```yaml
---
title: "Document Title"
type: "concept|tutorial|how-to|reference|adr|cross-cutting"
status: "draft|active|deprecated|migrating"
created: "YYYY-MM-DD"
last_updated: "YYYY-MM-DD"
components:
  - "component_id_from_registry"
---
```
*Note: Ensure that the `components` list entries strictly match keys defined in `docs/components.json`.*

## 9. Code-to-Doc Traceability (DOC_LINKS)
To achieve bidirectional traceability, all Python files (except `__init__.py`) and SQL object headers must include a `DOC_LINKS:` section in their top-level docstring or header comment.

**Required Format (Python):**
```python
"""
MODULE: path/to/module.py
GOAL: Short description.
BUSINESS CONTEXT: ...
ARCHITECTURE: ...
DOC_LINKS:
  - docs/architecture/relevant_document.md
"""
```

**Required Format (SQL):**
```sql
/*
MODULE: filename.sql
Object Name: object_name
Dependencies: other_view, other_function
GOAL: What this object does
BUSINESS CONTEXT: Why it exists
ARCHITECTURE: Not needed.
DOC_LINKS:
  - docs/database/table_schema.md
*/
```
*If a file does not map to any existing documentation, use `DOC_LINKS: None`.*

## 10. ADR Linking via DOC_LINKS

When code implements a decision from an ADR, add a `DOC_LINKS:` reference to that ADR in the implementing code file.

**Rule:** Any Python module or SQL procedure that directly implements an architectural decision documented in `adr/` MUST include a `DOC_LINKS:` entry pointing to that ADR.

**Example (Python):**
```python
"""
MODULE: database_manager.py
GOAL: Central database connection and SQL loading manager.
BUSINESS CONTEXT: ...
ARCHITECTURE: ...
DOC_LINKS:
    - adr/0001-hybrid-schema-management.md
    - docs/database-domain.md
"""
```

**Example (SQL):**
```sql
/*
Object Name: procedure_populate_features
Doc Links: adr/0005-sql-files-idempotent-objects.md
           docs/logic/strategy_discovery.md
*/
```

**When to add an ADR DOC_LINK:**
- The code introduces or enforces a specific pattern described in the ADR (e.g., idempotent migrations, pre-commit hook pattern)
- The code is a primary implementation of the ADR's decision
- Removing this code would violate the ADR's accepted decision

**When NOT to add an ADR DOC_LINK:**
- The ADR is only tangentially related
- The code predates the ADR and doesn't specifically implement its decision
- The ADR is superseded by a newer one

## 11. Component Registry Workflow

The project maintains a **machine-readable component registry** at `docs/components.json`. This registry is the single source of truth for what logical components exist, their types, code paths, and relationships. It is validated by pre-commit hooks and referenced by documentation frontmatter (`components:` field).

### A. Before Creating a New Module — Check the Registry First

**Mandatory first step:** Before creating a new folder, service, worker, or significant module, you **MUST** consult `docs/components.json` to determine whether:
1. The functionality already exists as a registered component → **reuse it**.
2. It belongs inside an existing component as a sub-component → **add it there**.
3. It is genuinely new and independent → **register a new component** (see Section C below).

### B. When to Create a New Component vs. Sub-Component

| ✅ Create a **NEW Component** when... | ❌ Keep as a **Sub-Component** when... |
|---|---|
| It has its own **lifecycle** — can be deployed, tested, or deprecated independently | It only makes sense **in the context of its parent** |
| It has a **distinct owner** or could be owned by a different team | It shares the same **lifecycle** as the parent |
| You would **talk about it in a meeting** as a separate thing | Removing it wouldn't change the **architectural diagram** |
| It has its **own primary documentation** (a dedicated spec doc) | Its documentation is a **section within** the parent's doc |
| It introduces a **new data entity** (table) that others depend on | It reads/writes to the parent's table only |

**Applied examples:**
- `candle_context` → **COMPONENT** (own table, own doc, own lifecycle)
- `vp_levels_populator` → **SUB-COMPONENT** (only exists within candle_context)
- `strategy_miner` → **COMPONENT** (own lifecycle, own doc, could run independently)
- `live_trader` → **COMPONENT** (entire subsystem)
- `position_manager` → **SUB-COMPONENT** of live_trader

### C. How to Add a New Component

Follow these steps when registering a new component:

1. **Choose a unique `id`**: Use `snake_case`, descriptive, no spaces (e.g., `order_book_collector`).
2. **Select a `type`** from the allowed enum: `data_pipeline`, `data_table`, `service`, `engine`, `utility`, `infrastructure`, `model`, `api_integration`.
3. **Add the entry** to the `components` array in `docs/components.json` with at minimum:
   ```json
   {
     "id": "your_component_id",
     "name": "Human Readable Name",
     "type": "service",
     "description": "What this component does and why it exists.",
     "detail_ref": "relative/path/to/main/folder/or/file",
     "status": "reviewed"
   }
   ```
4. **Set optional fields** as appropriate:
   - `primary_code`: Array of key file paths (e.g., `["collector/services/my_service/worker.py"]`)
   - `depends_on`: Array of other component IDs this component depends on
   - `data_tables`: Array of database tables this component owns or writes to
   - `contains`: Array of sub-component IDs
5. **Update frontmatter**: Any documentation files related to this component must include its `id` in their `components:` frontmatter list.
6. **Run validation**: The pre-commit hook `check_doc_frontmatter` will verify that all `components:` references in frontmatter match valid entries in the registry.
