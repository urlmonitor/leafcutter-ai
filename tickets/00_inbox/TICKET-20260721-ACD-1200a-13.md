## Acceptance Criteria

```gherkin
Given an AC whose implemented_by list already contains a legacy ABSOLUTE
  filesystem path (or a cross-worktree path with a per-checkout prefix) that
  points at the SAME ticket now being regenerated — a path whose repo-relative
  form equals the ticket the generator is about to record,
When a ticket is generated again from that AC and the back-reference is written
  by _write_implemented_by,
Then the legacy absolute/cross-worktree entry is recognised as the same ticket
  and collapsed so the AC's implemented_by list contains exactly one entry for
  that ticket, and that surviving entry is the repo-relative form (no leading "/",
  no absolute or per-checkout prefix),
And the dedup comparison and the relativisation both run through ONE shared
  repo-root-relative canonicaliser applied to both the incoming path and each
  existing entry — not two different path forms — so an absolute existing entry
  and a repo-relative incoming entry for the same ticket are treated as equal.
```
