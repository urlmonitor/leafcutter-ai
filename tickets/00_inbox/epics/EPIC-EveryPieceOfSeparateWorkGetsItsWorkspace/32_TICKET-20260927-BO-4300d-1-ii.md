# Two requests for the same work at the same moment never make two workspaces

## Actor / Goal

## Context

## Acceptance Criteria

```gherkin
Given no workspace exists for "alpha",
When two requests for "alpha" are started at the same moment from two different
  routes,
Then exactly one workspace for "alpha" exists afterwards, and it meets every
  part of readiness,
And each request is answered either ready with that one workspace's location,
  or refused stating that the same work is already being prepared,
And neither request is answered ready with a location other than that one.
```

- [ ] AC-1: exactly one workspace for "alpha" exists afterwards, and it meets every
- [ ] AC-2: each request is answered either ready with that one workspace's location
- [ ] AC-3: neither request is answered ready with a location other than that one.

## Implementation Notes

```yaml
- 'Mutual exclusion per (project, work identity): an exclusively created lock outside
  the workspace folder, holding pid, host and start time; a lock whose holder is dead
  is detectably stale and reclaimed; a waiter waits a bounded time (configurable,
  default no more than the expected ensure duration) and then answers refused IN_PROGRESS
  -- never an indefinite block, never a second workspace.'
- Proof starts two real maker processes concurrently (the stub build holds a barrier
  so both are genuinely in flight).
- Proof runs the DEPLOYED maker -- the copy an install delivers, resolved through
  the shared test locator delivered by BO-4300f-4 -- as a separate process against
  real temporary git repositories with a real bare hub. No mock of git, no import
  of the maker module, no grep of its source (CLAUDE.md 'Gate / Workflow ACs -- Verify
  Behaviorally, Not by Grep'); a test never falls back to the templates/ source copy.
- 'Tests must not spawn the package''s own scripts/build.py (CLAUDE.md ''Tests must
  not spawn their own build.py''): the deployed maker comes from the shared deployed
  layout, and fixture projects carry a minimal stub build entry point that installs
  a real, rejecting hook in well under a second. A test that must mutate the package
  and build its own copy says so and justifies it in its ticket.'
- All temporary projects, hubs and workspaces live under the test's temp directory
  and run git with an isolated global and system config; afterwards the developer's
  own repository's branches, registered worktrees and local git config are unchanged
  (BO-4300f-4-i, F14, KI-TQ-012).
```
