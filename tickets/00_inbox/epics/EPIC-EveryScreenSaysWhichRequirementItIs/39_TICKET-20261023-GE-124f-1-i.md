## Implementation Notes

```yaml
- 'ENFORCE THE MOCK-DATA IFF DIRECTLY: FrontendComponent.screen != null iff role ==
  ''page-root''. Both halves are violations — a leaf carrying data-screen is reported,
  and a page root''s design name must attach to the page root record and nowhere else.
  Implement the check on the record, so the invariant is enforced once rather than
  at each consumer.'
- 'THE FINDING NAMES THE FILE AND THE ELEMENT (line and opening tag, already on the
  element record from GE-124b-1), and states the rule — a design name belongs on the
  page root. It is its own finding code, distinct from an unresolvable design name
  (GE-124f-1): here the name may be perfectly valid, it is in the wrong place.'
- THE LEAF MUST NOT BE RECORDED AS REALISING THE DESIGN even though the name resolves.
  Detecting the misplacement and then also recording the link would give the chain
  two answers to 'what design is this page?', which is the consequence the PO names.
- EXACTLY ONE DESIGN PER PAGE, ENFORCED AS CARDINALITY. Two data-screen attributes
  on one page root, or a page root plus a leaf both carrying one, must not produce
  two chain records for that page — every comparison built on the chain (GE-124f-2)
  breaks when the page has two answers.
- This rule depends entirely on the page-root identification rule GE-124f-1 is required
  to state explicitly. If that rule is fuzzy, this AC becomes a source of false findings
  on legitimate nested route layouts — check the two against each other before implementing.
```
