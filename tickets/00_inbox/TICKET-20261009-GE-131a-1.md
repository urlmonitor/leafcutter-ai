## Acceptance Criteria

```gherkin
Given the complexity limit is 15, and a tracked file scripts/planner.py whose
  committed version holds plan_batches scoring 30 and load_rules scoring 12,
When a staged change leaves plan_batches at 30, or lowers it to 22,
Then the check allows the change, though plan_batches is still over the limit.

Given the same committed file,
When a staged change raises plan_batches to 31,
Then the check refuses it, naming plan_batches, its score 31 and the ceiling 30.

Given the same committed file,
When a staged change adds a new function parse_rules scoring 16, or raises
  load_rules from 12 to 16,
Then the check refuses each against the ceiling 15, and a new function scoring
  exactly 15 is allowed.

Given plan_batches is staged at 31 while the working-tree copy has been put back
  to 30,
When the check runs,
Then it refuses, because the staged version is what is judged.

Given a merge in progress where plan_batches scores 30 in HEAD and 40 in the
  branch being merged,
When the staged merge result scores it 40, and separately 41,
Then the check allows 40 and refuses 41, naming 40 as the ceiling.

Given a committed file whose function encode holds a nested visit scoring 20 and
  whose function decode holds a nested visit scoring 9,
When a staged change raises decode's visit to 18,
Then the check refuses it, naming decode.visit against the ceiling 15; the ceiling
  of 20 that belongs to encode.visit is not lent to it.

Given a staged Python file that cannot be parsed or cannot be read,
When the check runs,
Then it never reports that file as within the limit: it either refuses the commit
  naming the file, or states that it could not check the file, naming it.
```
