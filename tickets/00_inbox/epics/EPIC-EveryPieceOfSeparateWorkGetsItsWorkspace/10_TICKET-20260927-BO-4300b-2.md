# A project that installed the tools gets its workspaces the same way

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `BO-4300b-2` — A project that installed the tools gets its workspaces the same way — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `BO-4300b-2`. Component: `build-orchestration`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given a project "shop" that installed these tools, whose installed copy of the
  workspace maker lives in a folder outside shop's version history,
When a workspace for the work "alpha" is requested from shop's top folder, and
  again from the folder above shop,
Then both requests are answered ready with the same location,
And the workspace is a copy of shop, started from shop's shared main line tip,
  with shop's own tools installed inside it,
And that location is the same on every request for "alpha" in shop, and lies
  in the one place set aside for shop's workspaces.
```

- [ ] AC-1: both requests are answered ready with the same location
- [ ] AC-2: the workspace is a copy of shop, started from shop's shared main line tip
- [ ] AC-3: that location is the same on every request for "alpha" in shop, and lies

## Implementation Notes

```yaml
- Consumer layout (the maker deployed in a folder outside shop's version history)
  resolves shop by the BO-4300b-1 order, never from the maker's own location (F11,
  KI-ACD-004).
- 'The landing place is ONE rule owned by the maker and reported as layout (Q5 open:
  inside the project and ignored by git, or in the parent folder). Whichever is chosen,
  it is derived from the resolved project, stable across requests, and -- if shared
  by several projects -- keeps them apart (BO-4300b-2-i).'
- shop's install inside the workspace is built from the workspace's own contents with
  shop's own derived config.
- Answers conform to the result contract delivered by BO-4300c-2 (one JSON object
  on stdout, status/code/exit mapping, workspace_path absent on every non-ok answer).
- Proof runs the DEPLOYED maker -- the copy an install delivers, resolved through
  the shared test locator delivered by BO-4300f-4 -- as a separate process against
  real temporary git repositories with a real bare hub. No mock of git, no import
  of the maker module, no grep of its source (CLAUDE.md 'Gate / Workflow ACs -- Verify
  Behaviorally, Not by Grep'); a test never falls back to the templates/ source copy.
- 'Tests must not spawn the package''s own scripts/build.py (CLAUDE.md ''Tests must
  not spawn their own build.py''): the deployed maker comes from the shared deployed
  layout, and fixture projects carry a minimal stub build entry point that installs
  a real, rejecting hook in well under a second. A test that must mutate the package
  and build its own copy says so and justifies it in its ticket.'
- All temporary projects, hubs and workspaces live under the test's temp directory
  and run git with an isolated global and system config; afterwards the developer's
  own repository's branches, registered worktrees and local git config are unchanged
  (BO-4300f-4-i, F14, KI-TQ-012).
```
