# A trigger that matches nothing because the project holds no file of that kind is a gate with nothing to do, not a gate that cannot fire — the two are told apart by what a checkout could ever produce, never by what it holds today

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `BP-100k-4-ii` — A trigger that matches nothing because the project holds no file of that kind is a gate with nothing to do, not a gate that cannot fire — the two are told apart by what a checkout could ever produce, never by what it holds today — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `BP-100k-4-ii`. Component: `build-pipeline`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

### This is one half of a pair — do not build it in isolation

`check_hook_trigger_reachability.py` fails in two opposite directions at once, and this
ticket fixes only one of them.

| Direction | Owned by | State |
|---|---|---|
| **Too strict** — a kind-based condition matching nothing yet is reported unreachable, so an adopter tracking no Python cannot commit at all | **this ticket** (`BP-100k-4-ii`) | being built |
| **Too blind** — the check walks only *registered* hooks, so a script the registry never mentions is invisible to it | `BP-1600a-2`, `BP-1600a-2-i`, `BP-1600a-2-ii` | `todo` on `main`, not yet built |
| **Detection** — the consumer simulation never presents a language-absent adopter | `BP-900h-6-iii` | authored alongside this, same PR |

**Narrowing the verdict without widening the input population makes the gate quieter while
leaving it blind.** That combination is strictly worse than today: fewer false blocks *and*
the same silent gap, with the appearance of a fix. If `BP-1600a-2` is not being built in the
same stretch, say so at sign-off rather than closing this as complete.

These are not listed in `depends_on` because that field resolves to sibling **ticket
filenames** within an epic, and the paired ACs have no tickets yet — an AC id there would
fail the dependency-resolution guard. The constraint is recorded here instead, deliberately.

### Why a green suite here proves less than usual

The defect is **invisible in this repository by construction**: the gate misfires only where
no Python is tracked, and this repo always tracks Python. `BP-100k-4` and `BP-100k-4-i` are
both `done` with passing tests, and both remain correct — the blocker sits outside what they
specify. Any verification that runs only against this tree will pass on the broken code.
Verify in a **built consumer layout**, and treat
`test_removing_the_distinction_restores_the_blocker` as load-bearing: without it, an
implementation that simply never reports anything satisfies every other assertion.

The gate is `always_run: true`, `pass_filenames: false`, so a regression here blocks **every
commit in every adopter**, not just this repo's.

```yaml
config_schema_fragment:
  hook_trigger_reachability_nothing_to_match:
    description: 'Third reachability outcome, alongside reachable and unreachable:
      a registered gate whose activation condition selects files by kind and which
      the project currently holds none of. Distinguished from unreachable by whether
      any checkout of the project could ever produce a matching path, and reported
      by name with the kind left unmatched, so a gate reclassified this way is visible
      in the run''s summary rather than silently omitted from the unreachable list.'
    type: object
constraints:
- PARENT SCOPE IS THE DEFECT. BP-100k-4's criteria say 'no path THIS REPOSITORY is
  able to stage' — written from the package repository's own perspective, where Python
  is always present. The gate inherited that framing and applies it to whatever project
  it runs in, so in an adopter that tracks no Python the two registered conditions
  selecting Python files are classified exactly like a condition naming a directory
  that cannot exist. This constraint supplies the missing distinction; it does not
  overturn the parent.
- The line to draw is COULD-EVER versus DOES-NOW. A condition selecting files by kind
  is reachable while any checkout of the project could produce such a file. A condition
  naming a location absent from every layout, or naming only ignored locations, could
  never be activated by any checkout and stays a blocking finding.
- Do NOT fix this by exempting the two conditions that select Python files, and do
  NOT fix it by narrowing the gate to run only when the project holds Python. Both
  leave the class intact and both re-break the moment another kind-based condition
  is registered.
- Do NOT fix it by making the gate advisory or by loosening it to always pass when
  anything is unclear. BP-100k-4-i already forbids the fail-open shape, and an inability
  to determine reachability must remain a named failure.
- The classification must be reported, not merely acted on. A gate silently reclassified
  as 'nothing to match' is indistinguishable from a gate that was never evaluated
  — the failure this whole L1 exists to prevent.
- Verify against a BUILT CONSUMER LAYOUT, not only the package's own tree. The defect
  is invisible in this repository by construction, because this repository holds Python;
  a source-tree-only verification cannot observe it.
- 'Must follow the repo error-handling policy: specific-exception try/except around
  file, JSON and subprocess I/O, log at WARNING or higher or re-raise; no bare or
  blind excepts.'
```
