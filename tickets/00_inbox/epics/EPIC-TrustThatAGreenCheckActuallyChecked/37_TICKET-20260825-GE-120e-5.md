## Acceptance Criteria

```gherkin
Given the reference documentation an author consults before adding a check to the
  guardrail engine,
When that author reads it,
Then it states the attribution rule in the form this L1 defines it: a check reports only
  on content the author of this commit introduced, and never on work they merely brought
  across,
And it states that a check must take its change set from the shared authored-change source
  rather than working out its own, and names where that source is and where the choice is
  recorded per check,
And it states the limit of the rule in the same place: a fault introduced by the author's
  own resolution is still the author's, and a merge is never grounds for a check to skip
  its inspection,
And it carries the observed case as the worked example — a mainline merge on which one
  check objected to test deletions the branch never made and another to frontmatter faults
  in tickets the branch never touched, both bypassed with an override,
And it states plainly that a routine override is the damage this rule prevents, so a
  future author reads the rule as a guardrail property rather than as a convenience,
And any existing guidance that tells a reader to override these checks when merging is
  corrected in place rather than left standing beside the rule.

Coverage note: the last clause is the one that can be quietly skipped — cover it by
searching the documentation surfaces for override guidance aimed at merge-time blocks and
asserting none remains. This is a documentation criterion, so a content assertion is the
appropriate form; the behavioural criteria in this L1 are covered by GE-120e-3 and its
children.
```
