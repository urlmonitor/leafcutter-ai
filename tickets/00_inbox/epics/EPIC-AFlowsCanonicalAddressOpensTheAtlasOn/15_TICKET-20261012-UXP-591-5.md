## Implementation Notes

```yaml
- Selecting a flow, drilling (on the node or with 'Open sub-flow' in the drawer) and
  clicking a breadcrumb each add exactly one history entry at flowHref(targetFlowId)
  with no ?step=, written with window.history.pushState (owner decision 2026-10-09).
  The App Router (Next.js 14.1+) integrates pushState with no server round-trip or
  remount; router.push is not used, because it re-renders the server route and remounts
  view state.
- 'Each pushed entry stores its view state {crumbs: string[] (Flow ids, entry flow
  first), filters: {source: ''real'' | ''mock'', kind: ''user'' | ''data'' | ''architecture'',
  realization: ''all'' | ''built'' | ''spec'' | ''mock''}}: select -> [target], drill
  -> previous crumbs + [target], crumb -> previous crumbs cut after the target; filters
  unchanged. The state is kept in history.state under one namespaced key, merged into,
  never overwriting, the App Router''s own keys (__NA, __PRIVATE_NEXTJS_INTERNALS_TREE);
  not sessionStorage (owner decision 2026-10-09).'
- 'No in-memory history stack: dropping Forward entries on a new push is the browser''s
  own behaviour, and a reload or a Back from another Atlas page works from the URL
  plus the stored entry state alone.'
- The push decision lives in the same pure navigation function as the drawer replace
  (proposed leafcutter-web/components/flows/flow-navigation.ts) and is tested by replaying
  the dataset's FlowNavigation sessions.
- A pushed URL reloaded in place renders the same flow through the catch-all route
  (UXP-591-1).
- jsdom does not run the App Router's history integration, so the real-browser behaviour
  (history length under the App Router, Back/Forward without a page reload) is proven
  by this AC's Playwright spec in leafcutter-web/e2e/, run in CI against `next build`
  + `next start` (owner decision 2026-10-09; harness set up under UXP-591-1).
```
