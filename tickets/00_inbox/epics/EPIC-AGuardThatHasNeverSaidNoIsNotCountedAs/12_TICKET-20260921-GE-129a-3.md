# The input arrives as the tool call the guard actually sees, and the refusal counted is the tool call not happening — a rejection the event it is wired to cannot produce is unusable rather than satisfied

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-129a-3` — The input arrives as the tool call the guard actually sees, and the refusal counted is the tool call not happening — a rejection the event it is wired to cannot produce is unusable rather than satisfied — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-129a-3`. Component: `guardrail-engine`. Assigned agent: `python-coder`. Estimated complexity: `L`. Complexity: `high`.

## Acceptance Criteria

```gherkin
Given a guard wired at a kind of tool call that can stop the call from happening, whose
  declaration names a known-bad input and names its observable rejection as that call
  not happening,
When the liveness run examines that guard,
Then the declared input is presented to the guard in the form the editor presents one —
  the event's own account of the tool call being attempted and the arguments it was
  attempted with, delivered the way the editor delivers it — and not as a path handed to
  a command,
And what is read back is what the protected surface reads back: whether the tool call
  was allowed to proceed or was stopped,
And a guard that stops the declared input is reported as having demonstrated its
  refusal,
And a guard that allows the declared input to proceed is reported as not having
  demonstrated a refusal, naming it, in the same run as the guard above, so that neither
  verdict is the only answer the run is able to give,
And given a guard wired at a kind of tool call that cannot stop the call from happening,
When the liveness run examines it,
Then a declaration naming that call not happening as its rejection is reported as
  unusable on that guard, naming it, and is never reported as satisfied,
And a declaration naming a rejection that kind of tool call can produce is examined in
  the same way as any other, and a guard that produces it is reported as having
  demonstrated its refusal,
And a guard for which no known-bad input is meaningful is reported under the
  not-applicable alternative together with the ground given for it, and is reported in
  neither of the two classes above.
```

## Implementation Notes

```yaml
- 'THE INPUT IS DELIVERED THE WAY THE EDITOR DELIVERS IT, AND THAT IS A PROTOCOL,
  NOT A PREFERENCE. Per docs/how-to/creating-a-claude-code-hook.md, the editor launches
  the entry''s own command and writes a JSON payload describing the attempted tool
  call and its arguments to the guard''s STDIN. The adapter must reproduce that: run
  the entry''s own command string as written on the surface, from a working directory
  the walk-up resolves from, with the payload on stdin. It must NOT import the guard,
  must NOT call a helper inside it, and must NOT pass a path in argv — GE-129a-3-i
  owns the last of those and it is the cheapest wrong implementation available here.'
- ESTABLISH THAT THE GUARD SAW ITS INPUT BEFORE READING ITS VERDICT — ADR-045 §5,
  inherited and load-bearing on this surface for the mirror-image reason it is load-bearing
  on the commit one. There, checks ignore argv and read the index; here, a guard reads
  only what the editor sends it, so handing it nothing produces a clean exit that
  is indistinguishable from approval. The run must have positive evidence of receipt
  before it records anything other than never-attempted or blocked — the guard's own
  output, its observable effect, or the payload having been accepted on the channel
  the editor uses. A clean exit with no such evidence is `unverified` or `blocked`,
  never `passing`.
- THE VERDICT IS READ THE WAY THE PROTECTED SURFACE READS IT, WHICH IS NOT THE EXIT
  STATUS ALONE. On this surface the observable rejection is the tool call being denied,
  and the editor's decision protocol — not the process's return code — is what decides
  whether it was. A guard that objects in a way the event discards has not refused
  anything, and an implementation that reads exit status alone will record it as having
  demonstrated a refusal. That is the named mutation on this record; the implementation
  must be written so it fails.
- 'EVENT CAPABILITY IS DERIVED FROM THE EVENT, AND THE UNUSABLE CLASS IS A THIRD OUTCOME,
  NOT A FAILURE. Classify each subject''s event by whether it can stop the tool call,
  take the classification from the same place the protocol is taken from rather than
  from a list hard-coded beside the adapter, and report a declaration naming a rejection
  its event cannot produce as UNUSABLE on that guard, by name. Unusable is never reported
  as satisfied and never reported as not-demonstrated: the first is a false pass and
  the second reads as a weak guard when the truth is a misplaced declaration. Nothing
  in config/verification_flow.schema.json''s four values covers this, because on the
  surface it was written for every check reaches the same commit-time verdict — so
  the class is reported alongside the state rather than as a fifth state value, and
  no synonym set is minted.'
- A LIVE EXAMPLE OF THE UNUSABLE CLASS ALREADY EXISTS ON THIS SURFACE AND IS THE OBVIOUS
  REAL-SURFACE PAIRING CANDIDATE — verify it before relying on it, and do not encode
  its verdict. check_exception_handling_hook is wired PostToolUse on the Edit|Write
  matcher and is reported in this workspace as announcing a blocking error on essentially
  every edit while the edit proceeds. Whether that is a guard whose declared rejection
  its event cannot produce, or a guard doing exactly what a PostToolUse hook can do
  and being misread, is what this record's machinery exists to state. Either answer
  is useful; asserting either one in a test by name is forbidden by the same rule
  GE-129a-4's last clause imposes.
- THE NOT-APPLICABLE ALTERNATIVE IS THE SCHEMA'S OWN HATCH AND MUST CARRY ITS GROUND.
  A guard for which no known-bad input is meaningful is reported under negative_control.not_applicable
  with its stated reason, and is reported in neither the demonstrated nor the not-demonstrated
  class. An exemption with no ground is not an exemption; a postponement is not a
  ground.
- THE ADAPTER MUST NOT MUTATE THE REPOSITORY IT IS EXAMINING. A declared known-bad
  input for a guard on the Edit|Write matcher describes an edit that must be refused;
  if the guard allows it, the edit must not actually land. Present the attempt in
  a disposable working copy, or in a form the editor's protocol lets the adapter abandon
  after the decision is read. A sweep that leaves the tree dirty will be made to skip
  subjects, and a sweep that skips subjects to stay safe is the narrowing this record
  exists to prevent.
- 'HOST, DEPLOYMENT AND STRICTNESS. The adapter goes inside templates/scripts/commit_guardian/;
  anything imported from outside it goes into the scripts/build_phases.py deploy map
  in the same change. AC_ENFORCE_STRICT=1 on every pytest invocation below. Error-handling
  policy applies to the subprocess and stdin/stdout I/O: specific exception types,
  logged at WARNING or higher or re-raised. A swallowed invocation error must never
  become an absent record or a silent demonstration; it is `blocked`.'
```
