# Fail the build on template deploy-path collisions (BP-100m collision guardrail)

## Actor / Goal

In order to never ship the wrong artifact, we need `build.py` to fail loudly when
two or more source templates would deploy to the same target output path, so that
a later build phase can never silently overwrite an earlier phase's file.

## Context

This is the systemic fix for the `/build-feature` command-deployment-collision bug.
`build_commands` deploys `templates/commands/*.md` to `<root>/commands/`, and for
the `claude` platform `build_workflows` also deploys `templates/workflows/*.md` to
`<root>/commands/` (`platform_dirs["claude"] = "commands"`). Because the
`artifact_phases` loop in `scripts/build.py` runs `build_commands` **before**
`build_workflows`, when a filename exists in both source dirs the later phase
silently overwrites the earlier one. The live victims are `build-feature.md`,
`create-ticket.md`, and `finalize-feature.md` (all present in both
`templates/commands/` and `templates/workflows/`) — the clean workflow-invoking
`build-feature` command is replaced by a 21 KB prose file.

This ticket adds a collision detector to the build. It does NOT change which
template should win (that routing fix is BP-300d) — it only makes any many-to-one
target mapping a hard, named build failure.

## AC References

Implements the **BP-100m** family (docs/acceptance-criteria/build_pipeline/BP-100-reliable-builds/):
- BP-100m-1 — collision on `build-feature.md` (and create-ticket/finalize-feature) fails the build, naming both sources + the shared target.
- BP-100m-1-i — collision fails even when the two colliding sources are byte-identical (path-keyed, content-agnostic; the only sanctioned exception is an explicit allowlist).
- BP-100m-2 — general rule: any N≥2 sources → one target; the message names ALL colliding sources.
- BP-100m-2-i — a single template fanned out to DIFFERENT per-platform dirs is NOT a collision (no false positive).
- BP-100m-3 — the no-silent-overwrite invariant is ordering-independent: a collision is always fatal, never last-write-wins.

**Coupled scope (added at build time — the guardrail cannot land green while the real collisions exist):**
- BP-300d — de-conflict the three real collisions by retiring the shadowing prose workflow templates (`templates/workflows/{build-feature,create-ticket,finalize-feature}.md`) so the clean `templates/commands/` versions are the sole source deployed to `commands/`.
- BP-900g-1 — repoint those clean command templates from the non-resolving `Workflow("scripts/workflows/…​.js")` path to the name-based `Workflow("…")` form so the command resolves post-deploy.

## Acceptance Criteria

```gherkin
Scenario: real collision fails the build (BP-100m-1)
  Given a build for the claude platform where templates/commands/build-feature.md
    and templates/workflows/build-feature.md both resolve to commands/build-feature.md
  When build.py runs
  Then the build exits non-zero
  And the message names both colliding source templates and the shared target path
  And the same collision is reported for create-ticket.md and finalize-feature.md

Scenario: byte-identical sources still collide (BP-100m-1-i)
  Given two colliding source templates whose contents are byte-identical
  When build.py runs
  Then the build still exits non-zero (detection is path-keyed, not content-based)

Scenario: N-way collision names all sources (BP-100m-2)
  Given three or more source templates that resolve to one target path
  When build.py runs
  Then the build exits non-zero and the message names every colliding source

Scenario: cross-platform fan-out is not a collision (BP-100m-2-i)
  Given one template deployed to different per-platform directories (e.g. commands/ and gemini/workflows/)
  When build.py runs
  Then no collision is reported

Scenario: detection is ordering-independent (BP-100m-3)
  Given a collision between an earlier-phase and a later-phase artifact
  When build.py runs in any phase order
  Then the collision is fatal — never resolved by last-write-wins
```

## Implementation Tasks

- [x] Build a `(source_template → resolved_target_path)` map across ALL artifact phases (before any file is written), keyed by the final deployed path per active platform.
- [x] Detect any target path claimed by ≥2 distinct source templates; raise a build failure naming every colliding source and the shared target.
- [x] Ensure cross-platform fan-out (same template → different platform dirs) is NOT flagged.
- [x] Make detection path-keyed (content-agnostic); byte-identical sources still fail.
- [x] Wire the check so it runs deterministically regardless of phase order (fail-closed, before/independent of last-write-wins).
- [x] Add `unit_tests/build/test_deploy_collision_guard.py` covering all five scenarios above (behavioral: run the build/detector against a temp target, assert exit + message).

## Risk & Safety

- Touches money? No.
- Touches data? No — build-time check only.
- Reversibility? Fully reversible (additive guard). Risk: a false-positive collision could block legitimate builds — the cross-platform fan-out case (BP-100m-2-i) is the guard against that; test it explicitly.
