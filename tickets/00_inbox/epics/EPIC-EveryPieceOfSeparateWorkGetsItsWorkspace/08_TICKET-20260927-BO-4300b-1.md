# The same request from any folder in or around the project gives the same workspace

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `BO-4300b-1` — The same request from any folder in or around the project gives the same workspace — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `BO-4300b-1`. Component: `build-orchestration`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given a project "proj" whose parent folder is not itself a project, and a ready
  workspace W1 for the work "alpha",
When a workspace for the work "beta" is requested, one request at a time, from
  each of: proj's top folder; a folder three levels down inside proj; the parent
  folder above proj; a sibling folder beside proj; inside W1; and inside the
  "beta" workspace itself once it exists,
Then every request is answered ready with the same location for "beta",
And every request found the same project, proj,
And in every case the "beta" workspace is in proj's landing place for
  workspaces, never inside the folder the request was started from.
```

- [x] AC-1: every request is answered ready with the same location for "beta"
- [x] AC-2: every request found the same project, proj
- [x] AC-3: in every case the "beta" workspace is in proj's landing place for

## Implementation Notes

```yaml
- 'Project resolution is performed by the separate resolver module delivered by BO-4300a-1
  (duplication audit C4; KI-CG-20260925-shared-root-resolver-accepts-non-repo-workspace-parent),
  in exactly this order: (1) --repo-root when given; (2) otherwise the parent of `git
  rev-parse --path-format=absolute --git-common-dir` run from cwd -- and when that
  folder holds the maker''s own marker record, the project is the marker''s recorded
  project_root, never the workspace clone itself; (3) otherwise a bounded search of
  cwd''s immediate children, then of cwd''s siblings, where a candidate counts only
  when git itself confirms it is a repository (an empty .git folder is not one), a
  maker-made workspace counts as its recorded project, and candidates are de-duplicated
  by resolved project before exactly one match is required (AMBIGUOUS_REPO with candidates
  on more than one); (4) otherwise NO_REPO naming searched_from.'
- A workspace identifies its project ONLY through the maker's own marker record. The
  landing-place convention (inferring the project from a folder's position under worktrees/
  or any other landing place) is NOT a resolution step. When a marker's recorded project_root
  is missing or is not a repository, the answer is NO_REPO naming the marker -- never
  the clone itself, never a folder guessed from the path.
- 'Forbidden in resolution: any anchor on the file location of the maker or resolver
  (__file__ or equivalent; the deployed copy lives outside every repository in the
  dev layout and inside the consumer project in the consumer layout, so either would
  give a cwd-independent wrong answer); any upward walk that accepts a folder because
  ".git exists" or "CLAUDE.md exists" (the dev-layout workspace parent has both and
  is not a project); any caching of an answer (module global, file, environment) --
  every call recomputes from its own inputs; and any reuse, import, wrapping or copy
  of templates/scripts/commit_guardian/_resolve_root.py, which does all three.'
- The landing place is derived from the resolved project only, never from cwd (F3).
  git is run with its working directory set to the target, or with -C <path> for verbs
  other than commit only; a commit is never spelled `git -C <path> commit` (KI-CG-20260925-commit-delegation-hook-misses-git-dash-c).
- Answers conform to the result contract delivered by BO-4300c-2 (one JSON object
  on stdout, status/code/exit mapping, workspace_path absent on every non-ok answer).
- Proof runs the DEPLOYED maker -- the copy an install delivers, resolved through
  the shared test locator delivered by BO-4300f-4 -- as a separate process against
  real temporary git repositories with a real bare hub. No mock of git, no import
  of the maker module, no grep of its source (CLAUDE.md 'Gate / Workflow ACs -- Verify
  Behaviorally, Not by Grep'); a test never falls back to the templates/ source copy.
- 'Tests must not spawn the package''s own scripts/build.py (CLAUDE.md ''Tests must
  not spawn their own build.py''): the deployed maker comes from the shared deployed
  layout, and fixture projects carry a minimal stub build entry point that installs
  a real, rejecting hook in well under a second. A test that must mutate the package
  and build its own copy says so and justifies it in its ticket.'
- All temporary projects, hubs and workspaces live under the test's temp directory
  and run git with an isolated global and system config; afterwards the developer's
  own repository's branches, registered worktrees and local git config are unchanged
  (BO-4300f-4-i, F14, KI-TQ-012).
```
