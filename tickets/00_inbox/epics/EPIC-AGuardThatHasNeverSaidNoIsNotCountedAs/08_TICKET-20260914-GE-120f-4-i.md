# A check that was already registered when the requirement arrived is subject to it identically, and a ground that is a fact about when a check was registered is no ground at all

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-120f-4-i` — A check that was already registered when the requirement arrived is subject to it identically, and a ground that is a fact about when a check was registered is no ground at all — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-120f-4-i`. Component: `guardrail-engine`. Assigned agent: `python-coder`. Estimated complexity: `S`. Complexity: `low`.

## Acceptance Criteria

```gherkin
Given protective checks that were already registered before the declaration became a
  condition of registration,
When the registration surface is read and the run examines the population,
Then each of them is subject to the requirement in the same way as one registered
  afterwards: one carrying no declaration is named as carrying none, and one carrying a
  declaration whose rejection has not been observed is named as not demonstrated,
And a claimed exemption whose stated ground is a fact about when the check was registered
  — that it predates the requirement, that it is inherited, that it is long-standing — is
  refused in the same way as an exemption stating no ground at all, because a ground must
  be about what the check does,
And a record that exempts a group of checks at once, by when they were registered or by
  where they live rather than by a ground stated for each check, is refused, and every
  check it names stays in the class its own record puts it in,
And the run's first report over the population as it stands is not made quiet by any such
  record, and the checks that report as never demonstrated on that first run are reported
  by name rather than summarised.
```

- [ ] AC-3: a record that exempts a group of checks at once, by when they were registered or by
- [ ] AC-4: the run's first report over the population as it stands is not made quiet by any such

## Implementation Notes

```yaml
- 'THE REQUIREMENT APPLIES TO THE WHOLE REGISTERED POPULATION, NOT TO WHAT COMES NEXT.
  The parent is fully satisfiable by a gate that polices new registrations and leaves
  the existing family alone, and that reading is attractive precisely because it makes
  the first run quiet. It also makes the regime worthless: the checks that cannot
  refuse are the ones already registered. A rule that applies only to what comes next
  certifies everything already broken.'
- A GROUND MUST BE A FACT ABOUT WHAT THE CHECK DOES. Refuse a ground that is a fact
  about when it was registered — that it predates the requirement, that it is inherited,
  that it is long-standing — in the same way as an exemption stating no ground at
  all. Today's vocabulary permits any non-empty string, which is the same weakness
  the postponement rule already has to defeat one form over; a minimum-length rule
  is not a ground rule.
- HOLD THE VOCABULARY OF REFUSED GROUNDS AS DATA A FIXTURE CAN EXTEND, NEVER AS A
  FIXED SET THE TEST ALSO CARRIES. If the test restates the refused-ground set, the
  test and the implementation agree with each other and with nothing else, and the
  next form of evasion passes both. Assert instead by extending the fixture's refused-ground
  data and observing the run's behaviour change with no test edit.
- 'AN EXEMPTION IS PER CHECK, WITH ITS OWN GROUND. A record exempting a group at once
  — by when its members were registered, by where they live, by a shared prefix or
  directory — is refused, and every check it names stays in the class its own record
  puts it in. This is the same rule GE-120c-6 already states one axis over: an exemption
  must be a property read from the candidate or from a declared record, never a match
  against an identifier written into the thing applying the rule, so nothing inherits
  an exemption by resemblance. Registration date is resemblance by another name —
  it says nothing about whether the check can refuse.'
- CONSUME GE-126b-5-i's EXEMPTION VOCABULARY; DO NOT BUILD A SECOND. What a ground
  is, that a groundless exemption is reported and fails, and that a postponement is
  not a ground are that record's clauses. This record adds two further groundless
  forms and adds nothing to the disposition itself. One vocabulary — the schema's
  `negative_control.not_applicable` + `reason` — across this record, its parent, and
  BP-1600a-2-i's neighbouring register.
- THE FIRST REPORT NAMES CHECKS INDIVIDUALLY, NOT AS A SUMMARY. A summarised first
  report is how a group exemption gets granted afterwards without anyone reading what
  it covers. Name them; the noise is the correct outcome.
- DAY-ONE BLAST RADIUS IS MADE MECHANICAL HERE RATHER THAN ADVISORY. It must not be
  pre-suppressed by seeding exemption records, by a dated cut-off, or by a single
  record covering everything registered so far. The natural remedy for the noise is
  to weaken the rule until it goes quiet, and that remedy is the failure mode this
  whole tree is designed against. Repairing, declaring, or honestly exempting each
  check is the work, not a follow-up. The component's own known-issues register records
  a detector that already existed, reported unreachable checks, and was skipped rather
  than acted on because its verdict arrived as a blocker — which is why a grandfathering
  hatch is the most likely way this regime is neutralised on the day it lands.
- AC_ENFORCE_STRICT=1 on every pytest invocation; exercise the DEPLOYED gate out of
  process, and confirm it saw its input before reading its verdict. Any module imported
  from outside templates/scripts/commit_guardian/ goes into the scripts/build_phases.py
  deploy map in the same change.
- 'Error-handling policy: specific-exception try/except around registry and file I/O,
  logged at WARNING or higher or re-raised. A malformed exemption record is a reported
  finding, never a crash that leaves the rest of the population unexamined.'
```
