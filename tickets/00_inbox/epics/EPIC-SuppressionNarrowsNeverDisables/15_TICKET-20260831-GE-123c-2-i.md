## Acceptance Criteria

```gherkin
Given the security allowlist contains, on separate lines, three entries whose
  rule id is not one the scanner can report:
  - a first line beginning with a byte-order mark before "ENTROPY_HIGH", left
    there by an editor that saved the allowlist with one,
  - "ENTROPY-HIGH:secrets.py:*", written with a hyphen instead of an underscore,
  - "ENTROPY_HIGH :secrets.py:*", with a space before the first separator,
And "secrets.py" contains a high-entropy token the ENTROPY_HIGH rule reports,
When the allowlist is loaded and the file is scanned through the multi-file
  entry point,
Then the finding is reported — none of the three entries suppressed it,
And each of the three lines produces its own warning on the error stream naming
  the allowlist file, its own 1-based line number, and its own verbatim text,
And each of the three entries is skipped,
Because a rule id that is neither the wildcard nor a rule the scanner can report
  can never equal the rule id of any finding, and all three of these read as
  something other than what their author typed.

Given the security allowlist contains one well-formed entry for each rule the
  scanner can report — the sensitive-filename rule, the private-key rule, the
  cloud-access-key rule, the api-key rule, the generic-secret rule and the
  high-entropy rule — and one entry whose rule id is the literal wildcard,
When the allowlist is loaded,
Then no warning is emitted for any of those lines and every one of them is
  loaded and applied,
Because every rule the scanner can report, and the wildcard that stands for all
  of them, must remain writable without complaint.
```

## Implementation Notes

```yaml
- 'The set of reportable rule ids currently has no single home: some are declared
  in the module''s rule table and the rest are emitted directly by the per-file scan.
  Establish ONE canonical set inside the scanner, derived from those declarations
  rather than hand-copied, and make it the set both the load-time check and the test
  read. A hand-written second copy is a duplicated source that will drift the moment
  a rule is added, and the drift shows up as valid new suppressions being rejected.'
- Reject by data property — the value is not in the canonical reportable set, and
  is not the wildcard — never by enumerating the specific mis-spellings observed.
  A branch that names the hyphen variant, the byte-order mark or the trailing space
  by hand leaves the next variant to escape.
- 'No case-insensitive, whitespace-tolerant or fuzzy matching of the rule id, and
  no invisible-character stripping: a mis-cased or byte-order-mark-prefixed id is
  reported and skipped, not quietly repaired.'
- Reuse the single allowlist-diagnostic convention — error stream, allowlist file
  path, 1-based line number, verbatim line text, one message per offending line —
  and do not add a second shape.
- Classification is never fatal and never alters the scan's exit status.
- Edit the canonical template at templates/skills/security-scanner/scripts/scan_secrets.py
  and propagate with build.py; never edit a deployed copy (ADR-001).
- Tests must never create, modify or delete a .security-allowlist at any real project
  root, workspace root or worktree root; every fixture allowlist lives under tmp_path/tempfile.
- Fixture files must use ordinary source filenames — the per-file scan short-circuits
  environment-named files and never reads their content.
```
