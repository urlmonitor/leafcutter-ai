summary: "Files KI-BO-019 and KI-BO-020, both found by running the fast lane against a real target: the context bundle cannot cross the agent boundary at realistic size, and the release-on-failure path is dead."
description: "Both were found the only way they could be found — by pointing the lane at a real acceptance criterion and watching where it stopped. Run wf_bd4984e8-438, target BO-2400f-13. Five agents, none errored: the worktree was created, the connected set resolved to the correct five ids, all five were claimed, and the context bundle was assembled. Then the run halted. KI-BO-019 is the halt itself, and the gate is not at fault. The lane asks its bundle agent to return the assembled bundle verbatim in a JSON string field. On a real target that bundle is about 149 KB, so the agent wrote it to disk and returned a 47-character file pointer instead. The gate checked the returned string for the cache-breakpoint marker, did not find one in a path, and halted fail-closed exactly as BO-2400c-1-iii requires. The bundle on disk was fine: 148891 bytes, 2232 lines, five layers, marker present at line 958. What failed is the transport, not the assembly and not the check. This is structural rather than a flake, because the E2 workflow engine has no filesystem access and therefore cannot follow the pointer it was handed — the bundle must arrive in-band or not at all, while being large is the entire point of a prompt-cache payload. A re-run might happen to succeed and make this look intermittent; the contract is simply unsound at this size. The operator-facing message also needs work: it says the bundle was not obtained while its own detail block says obtained true and assembled successfully, because obtained and usable are conflated in the text. KI-BO-020 was found while checking what the halt left behind, and is the worse of the two. When a phase fails after the claim step the lane dispatches a release agent to put the claimed ACs back to todo. The prompt opens with You are the release-phase agent and the dispatch passes agentType status-checker. status-checker refuses, correctly, because no message may reassign its role — and the lane discards the reply because the release is best-effort. So the release ran, did nothing, and reported nothing. All five ACs were still in_progress afterwards, verified by direct read rather than assumed. The damage was contained only by luck: a fast-lane run claims in its own worktree's copy of the store, which is discarded with the worktree, so origin/main still read todo. Any path where a claim reaches a shared store strands those ACs in_progress, and BO-2400f-8 will then correctly refuse to rebuild them — a failed run silently making its own target unbuildable. This also invalidates a premise already in use: BO-2400f-13's reasoning, and the decision to refuse rather than reuse an occupied workspace, rest on BO-2400f-10 releasing the claim on abort. That criterion is specified and believed working, but its only invocation path is dead. The refuse decision still holds and arguably holds harder, since a leftover workspace may now also carry stranded claims, but the stated reason should not be quoted as established behaviour until this is fixed. The same status-checker refusal already breaks plan-feature's gates, where it is dispatched to ask the user and returns a well-formed cancel that reads as a real decision. The general lesson is recorded in the entry: dispatching an agent under a role name that is not its own is not a prompt-style choice, the agent will refuse, and a caller that ignores the reply turns that refusal into a silent no-op."
