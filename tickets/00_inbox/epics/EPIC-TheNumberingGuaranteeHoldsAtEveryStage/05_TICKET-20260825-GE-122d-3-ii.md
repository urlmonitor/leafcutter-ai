# A new project's first commit works because the roots are there, not because absence is excused

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-122d-3-ii` — A new project's first commit works because the roots are there, not because absence is excused — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-122d-3-ii`. Component: `guardrail-engine`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given a brand-new project — an empty directory holding only a minimal skills_config.json —
  into which the package has been installed and the install run once, with no opt-in
  documentation-seeding step performed,
And that project therefore holds none of the artifacts any of the numbered namespaces
  collect,
When the adopter makes their first commit through the ordinary commit path,
Then the commit completes,
And every namespace root the uniqueness pass holds itself responsible for exists in that
  project as a real directory,
And the pass reports an inspected count of zero for each of those namespaces, so the first
  commit carries a positive statement that nothing was claimed twice rather than a silence
  that could equally mean nothing was examined,

And given that same project, with one of those namespace roots then renamed, moved or removed
  while the pass still holds that namespace responsible,
When a commit is attempted,
Then the commit does not complete,
And the output names the root that was not found and the place the pass expected to find it,
And it states that uniqueness for that namespace was not established — the same
  could-not-establish disposition GE-122d-3 requires for a collection the pass could not see,
And an absent root is never reported as an inspected count of zero, and never contributes to
  a clean verdict,

And given a project whose collection legitimately lives somewhere other than the default
  location, and which declares that location in its own path configuration,
When a commit is attempted,
Then the pass resolves that namespace at the declared location rather than at an assumed one,
And every namespace root the pass is responsible for is resolved through that same declared
  configuration, with no namespace resolved by a location written into the pass itself.

Coverage note: the first block and the second block must be exercised in the SAME test module,
against a real installed project on disk, because this criterion is a boundary and a boundary
demonstrated from one side is not demonstrated. Creating the project by copying this
repository does not cover it — a copy already contains every root, which is the condition
under which the defect cannot reproduce. A test that asserts the pass returns zero for a
missing directory covers the opposite of this criterion.
```

## Implementation Notes

```yaml
- 'THE BINDING DESIGN DECISION, and the one an implementer will be tempted to undo:
  an absent root is NOT an empty collection. Satisfy the first block by having the
  install CREATE the roots, never by teaching the pass to treat absence as zero. The
  two mechanisms are indistinguishable on a green first commit and opposite on every
  other day — a consumer whose store lives elsewhere, a renamed directory, or a hook
  invoked from an unexpected working directory all present as an absent root, and
  under the absence-is-empty reading every one of them passes silently. That is the
  fail-closed contract of GE-122d-3 reopened. The second block of the criteria exists
  specifically so this shortcut fails the AC.'
- Because git cannot commit an empty directory, each scaffolded root needs a real
  placeholder file. docs/reference/architecture-docs-layout.md carries a drafted README
  for the diagrams root and records that the adrs root already has a seed source.
  Scaffolding belongs on the BASE install path, not behind the opt-in documentation-seeding
  flag — a gate that is only safe for consumers who happened to run an optional flag
  is not safe to register.
- DO NOT RENUMBER, RENAME OR MOVE THE ELEVEN GRANDFATHERED UNNUMBERED DIAGRAM FILES.
  That exemption is a binding, permanent scope decision taken by the user at the PO
  gate on 2026-08-17 and recorded in GE-122e and GE-122b. They do not match the filename
  pattern and are therefore invisible to the uniqueness scan by construction; scaffolding
  a root must not disturb them, and the inspected count for that namespace counts
  what the pass examined, which is not the same as the number of files in the directory.
- 'The third block is a real change of mechanism, not a restatement: KI-CG-13 records
  that the diagrams root is hardcoded in the check while adrs and components resolve
  through config/paths.json, which today has no architecture_diagrams key. Add it
  as a non-optional entry mirroring architecture_adrs — the gate hard-requires the
  root, so an optional declaration would be a third way for the root to go missing
  quietly.'
- 'THE CONFIG CHANGE, STATED CONCRETELY SO IT CANNOT BE READ AS OPTIONAL (IT-PO 2026-08-25).
  Add `architecture_diagrams: "docs/architecture/diagrams/"` to the `paths.docs` object
  in config/paths.json, sitting alongside the existing `architecture`, `architecture_adrs`
  and `architecture_components` keys. Do NOT add a companion `architecture_diagrams_optional`
  flag: `architecture_components_optional: true` exists because nothing fails when
  that root is absent, and the whole premise of this criterion is that the diagrams
  root is not in that class.'
- 'DELETE THE HARDCODED ROOT, DO NOT LEAVE IT AS A FALLBACK. Once the key exists,
  the literal `root / "docs" / "architecture" / "diagrams"` in check_identifier_uniqueness.py
  must be REMOVED, and all four namespace roots must resolve through the one declared-path
  resolver. A hardcoded default retained ''just in case the key is missing'' is a
  duplicated source of truth: it makes a project that relocated its diagrams store
  silently scan the wrong directory and report a clean count of zero — the exact silent-pass
  this criterion forbids — and it makes a missing key unobservable instead of could-not-establish.
  One resolver, one source, no fallback.'
- THE FOUR ROOTS RESOLVE BY ONE MECHANISM, INCLUDING tickets/. ADR-037's fourth namespace
  resolves via tickets/ticket_lifecycle.json rather than a paths.json key. 'Every
  namespace root is resolved through that same declared configuration' means no root
  is resolved from a location written into the pass — it does not mean all four must
  be declared in the same FILE. State which declaration each root reads and make the
  resolver read it; if the tickets root is judged to need a paths.json key too, that
  is a decision to record, not to assume silently.
- 'Distinguish the three conditions in the pass''s outcome vocabulary rather than
  in prose: a resolved root with nothing in it is clean with a count of zero; a declared
  root that does not resolve is could-not-establish and blocks; an artifact inside
  a resolved root that cannot be read or parsed is GE-122d-3''s condition and also
  blocks. Do not collapse the first into the second or the second into the first.'
- Build the fixture project from an EMPTY directory, never from a copy of this repository.
  A copy already contains every root, so it cannot reproduce the condition — the same
  source-tree bias BP-900h-1's constraints call out and the reason the seven consumer-install
  defects of 2026-08-13..17 all shipped.
- SCAFFOLDING MUST BE IDEMPOTENT AND MUST NOT OVERWRITE. Running the install a second
  time over a project whose diagrams or adrs README the adopter has since edited must
  leave that file byte-identical — create-if-absent, never rewrite. BP-900h-2 already
  asserts install idempotency for the tree as a whole; a scaffold step that re-seeds
  a placeholder on every run turns every subsequent install into a silent content
  revert.
- 'FILE SCOPE: config/paths.json, scripts/build.py (base install path — NOT scripts/seed_project_docs.py,
  which is the opt-in seeding path this criterion deliberately excludes), the two
  commit_guardian modules under templates/scripts/, the new templates/docs/architecture/diagrams/README.md,
  and one new test module. Deployed copies under scripts/commit_guardian/ are build
  outputs regenerated by build.py per ADR-001 and are never hand-edited.'
- 'Error handling per CLAUDE.md Rules 1-4: the root-resolution branch catches the
  specific filesystem exception, logs at WARNING or above, and converts to the could-not-establish
  outcome rather than raising an unhandled traceback. A traceback at an adopter''s
  first commit is not the same as a stated could-not-establish result.'
```
