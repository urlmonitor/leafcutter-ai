# A check whose declared rejection was not observed is named and fails the run, and a check that has never been asked to refuse is never counted among the things keeping the work safe

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-120f-2` — A check whose declared rejection was not observed is named and fails the run, and a check that has never been asked to refuse is never counted among the things keeping the work safe — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-120f-2`. Component: `guardrail-engine`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given the liveness run has examined the checks and written each one's record from what
  was observed when its declared known-bad input was put through the entry point the
  protected surface invokes,
When the run reports,
Then every check whose record says the rejection was not observed is named, together with
  the input it declared and the rejection it declared, and the run fails,
And every check whose record says the attempt has never been made is named as a check
  whose refusal has never been demonstrated, and the run fails,
And no check whose record says either of those things appears in any statement the system
  makes about what is protecting the work, and none of them is reported as though its
  refusal had been demonstrated,
And a check whose record says the rejection was observed is named in no failing class,
And a check exempted on a ground the exemption rule accepts is named in no failing class
  and does not by itself fail the run,
And the reasons the run gives are reasons about that check: a check is never named as not
  demonstrated on the strength of another check's record, and the run states nothing about
  how many checks in the family have the condition beyond the figures it measured itself.
```

- [ ] AC-2: every check whose record says the attempt has never been made is named as a check
- [ ] AC-3: no check whose record says either of those things appears in any statement the system
- [ ] AC-4: a check whose record says the rejection was observed is named in no failing class
- [ ] AC-5: a check exempted on a ground the exemption rule accepts is named in no failing class
- [ ] AC-6: does not by itself fail the run

## Implementation Notes

```yaml
- 'THE SECOND FAILING CLASS IS LOAD-BEARING AND MUST BE IMPLEMENTED FIRST. Naming
  a check whose declared rejection was not observed is the easy half — that check
  at least tried. The class that changes behaviour is never-attempted (`currently.state:
  unverified`). If never-attempted does not fail the run, the whole regime is discharged
  by never asking, and the difference between a guard that refuses and a guard that
  has never been given anything to refuse survives into every report the system produces.'
- 'ENUMERATE, IN THE TICKET, EVERY SURFACE THAT STATES WHAT IS PROTECTING THE WORK
  — THIS IS THE LEAST-SPECIFIED CLAUSE IN THE RECORD AND THE MOST LIKELY TO BE PARTIALLY
  IMPLEMENTED. The criterion says an undemonstrated check appears in NO statement
  the system makes about what is protecting the work. Candidate surfaces to enumerate
  and then either cover or explicitly exclude with a stated reason: the run''s own
  summary; the commit-guardian README and docs/pre-commit-hooks.md; any generated
  hook inventory or coverage rollup; and any agent-facing or CI-facing summary that
  counts registered gates. The enumeration itself is a deliverable — a clause covering
  one surface and silently missing three is the same coverage-by-omission the parent
  L1 was amended on 2026-09-07 to stop.'
- EVERY FIGURE THE RUN STATES IS DERIVED FROM THE RUN'S OWN PER-CHECK RECORDS. No
  figure may be a literal, a carried-forward value, or a count of anything the run
  did not itself observe. The parent records the population count as disputed and
  forbids one below it; GE-120f-3 owns the stated figure and its movement, and this
  record must not restate that — it owns only that the run states nothing it did not
  measure.
- A CHECK'S CLASS IS DERIVED FROM ITS OWN RECORD AND NOTHING ELSE. Never from a family-level
  summary, never from a group's worst member, never from a directory or naming resemblance.
  A demonstrated check that inherits a neighbour's finding is the same shape as quoting
  a disputed population figure as though it were measured.
- 'CONSUME GE-126b-5-i''s EXEMPTION VERDICT; DO NOT RE-DERIVE IT. What counts as a
  ground, that a groundless exemption is refused, and that a postponement is not a
  ground are all that record''s clauses. This record states only the consequence for
  its own failing classes: an accepted exemption falls into neither of them and does
  not by itself fail the run. Keep ONE exemption vocabulary — the schema''s `negative_control.not_applicable`
  + `reason`.'
- 'THE STANDING FAIL-OPEN CONVENTION IS NOT REPEALED HERE, AND MUST NOT BE FLATTENED.
  This component deliberately does not hard-block when a guard hits an internal error
  while still running (GE-116a-1-iii). The line this record draws is narrower: a run
  that COMPLETED and observed that a check did not refuse is not an internal error,
  and reporting it as a success is the failure. The could-not-reach-a-verdict case
  is GE-120f-2-i''s and is not decided here.'
- DO NOT ENCODE THE EXPECTED DAY-ONE LIST. Record the first run's output as evidence
  on the implementing ticket, never as a test assertion — an expected list becomes
  false on the day the guards are repaired, which is the day the run starts earning
  its place. Assert by count-and-membership over the run's own reported classes.
- AC_ENFORCE_STRICT=1 on every pytest invocation; the report must be produced by the
  DEPLOYED copy out of process. Any module imported from outside templates/scripts/commit_guardian/
  goes into the scripts/build_phases.py deploy map in the same change.
- 'Error-handling policy: specific-exception try/except around I/O and subprocess
  calls, logged at WARNING or higher or re-raised. A swallowed read error must never
  empty a failing class — an empty failing class is the greenest possible result and
  is exactly what GE-120f-3''s examined-none clause exists to refuse.'
```
