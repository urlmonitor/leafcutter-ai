# A dependency cycle in one subtree degrades the store-wide scan to a warning, while a real intra-scope cycle still hard-fails a scoped epic build

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `ACD-1200c-3` — A dependency cycle in one subtree degrades the store-wide scan to a warning, while a real intra-scope cycle still hard-fails a scoped epic build — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `ACD-1200c-3`. Component: `ac-driven-dev`. Assigned agent: `python-coder`. Estimated complexity: `M`.

## Acceptance Criteria

```gherkin
Given the AC store contains a dependency cycle confined to one component subtree
  (for example BO-1100a-3 depends_on BO-1100d-1 and BO-1100d-1 depends_on BO-1100a-3),
And the rest of the store is acyclic,
When the store-wide scan / ready-AC ranking runs over the whole store,
Then it does NOT hard-abort the entire scan,
And it surfaces the cycle as a warning that names the cyclic AC ids,
And it continues to rank and emit the ready ACs from the acyclic remainder of the store,
And the store-wide scan exits with status 0 (the cycle is reported as a warning,
  not a fatal error) when the only problem is a cycle outside the requested scope.

And given a goal-scoped goal-mode run whose OWN collected leaf set contains a
  genuine intra-epic dependency cycle among the leaves being built,
When the scoped topological sort over that leaf set runs,
Then it still raises the cyclic-dependency error for that scoped build
  (the scoped pre-write guard specified by ACD-1200c-1-i is preserved and not weakened),
And no epic folder is created and no ticket files are generated for that scoped build,
And the distinction is explicit: store-wide ranking degrades gracefully and keeps going,
  whereas a scoped epic build with a real intra-scope cycle still fails fast before any write.
```
