# The AC-schema check reports a non-authoritative result when it cannot load the schema it validates against

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-120a-3` — The AC-schema check reports a non-authoritative result when it cannot load the schema it validates against — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-120a-3`. Component: `guardrail-engine`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given the AC-schema pre-commit check is invoked on staged AC YAML files,
And the authoritative AC store schema document cannot be resolved from the working copy
  the check is running in,
When the check runs,
Then it states that authoritative schema validation did not happen and names the schema
  document it could not reach,
And any clean finding produced by its reduced manual field validation is labelled as not
  authoritative, per GE-120a-1-ii,
And the reduced finding is not presented with the same result value as a run in which
  the authoritative schema was loaded and satisfied,
And a staged AC file that authoritative validation would reject is never reported as
  clean without that label,
And the label appears on the reduced run even when the reduced validation finds nothing
  at all to report.

Coverage note: covered only by running the check with the schema document genuinely
unreachable and asserting the observed output and result value. Asserting that a fallback
branch exists in the source does not cover it, and neither does a test that makes the
schema unreachable by monkey-patching an import inside the same process — the observed
defect is a path-resolution failure, so the unreachability must be real.
```
