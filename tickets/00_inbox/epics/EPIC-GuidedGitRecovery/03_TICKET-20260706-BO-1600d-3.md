## Acceptance Criteria

```gherkin
Given the human has confirmed execution of the recovery plan against a shared
  repository that the BO-1600c detection identified as damaged (for example a
  zero-byte loose object, a branch ref pointing at a corrupt commit, and a
  poisoned index cache-tree)
When recovery executes
Then it detects and lists the zero-byte loose objects, removes those specific
  listed objects, and re-fetches the authoritative objects from origin so the
  removed objects are restored from the remote
And when a branch ref points at a corrupt commit, it resets that branch ref to the
  branch's own reflog tip (the last known-good entry), not to a hardcoded branch
And when the index cache-tree is poisoned, it rebuilds the index cache-tree so a
  fresh status/read succeeds with no cache-tree error
And after execution the repository reads cleanly (a fresh integrity read reports no
  remaining corruption for the items the plan addressed)
```

### High-Confidence Findings

[H-1] templates/scripts/git_recovery.py:698,715 — `verify_recovery_integrity` exceptions propagate uncaught through `main()`
      `verify_recovery_integrity` calls `detect_corrupt_branch_refs` (which re-raises `subprocess.CalledProcessError`) and `detect_poisoned_index` (which re-raises `OSError`) without any try/except wrapper of its own. Both call sites in `main()` — the `--execute` path (line 698) and the interactive path (line 715) — are also unguarded. If git fails during the post-check after a successful recovery (e.g., a transient git crash or missing binary), the script exits with a Python traceback and never prints "Recovery complete."; the operator cannot determine whether recovery succeeded or failed. The AC requires the integrity read to "report" its result; an unhandled exception is not a report. Fix: wrap the `verify_recovery_integrity(...)` call at each call site in `main()` with `try/except (subprocess.CalledProcessError, OSError)`, log a warning, and continue to "Recovery complete." so the operator knows recovery ran.
      Sub-skill: code-reviewer (error handling analysis)

### Medium-Confidence Findings

[M-1] templates/scripts/git_recovery.py:233 — inner `except subprocess.CalledProcessError:` in `detect_corrupt_branch_refs` has no log or re-raise
      When `git cat-file -t <sha>` exits non-zero for a branch tip, the code silently appends `(branch_name, sha)` to the corrupt list without any WARNING log entry. Per Error Handling Policy Rule 3, every except block must log at WARNING or re-raise. The detection intent is correct (the failure IS the signal), but a non-corruption subprocess failure (e.g., temporary git crash) would silently misclassify a healthy branch as corrupt and queue it for a ref reset. Adding a `logger.debug` or `logger.warning` call with the sha and reason would satisfy the policy and provide a diagnostic trace. Ruff rules E722/BLE001 do not fire on this pattern (specific type, not bare except).
      Sub-skill: code-reviewer (error handling policy)

[M-2] templates/scripts/git_recovery.py:293 — inner `except subprocess.CalledProcessError:` in `get_reflog_tip` has no log or re-raise
      Same pattern as M-1: when `git cat-file -t <sha>` fails for a reflog entry, the code silently calls `continue` without any log. If `cat-file` fails for reasons other than object corruption, the reflog tip SHA is silently skipped, potentially causing `get_reflog_tip` to return a further-back entry or raise `ValueError` when a valid tip actually exists. Adding a `logger.debug` call before the `continue` would satisfy the policy and help operators diagnose recovery.
      Sub-skill: code-reviewer (error handling policy)
