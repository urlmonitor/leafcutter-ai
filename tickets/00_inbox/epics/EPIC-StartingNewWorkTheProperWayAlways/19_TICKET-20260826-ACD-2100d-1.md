## Implementation Notes

```yaml
- Evidence must come from executing the deployed artifact in the deployed layout in
  a fresh process. A file diff, a checksum comparison or a build-manifest assertion
  is explicitly not evidence and does not satisfy this record.
- The installer must be run into a temporary target rather than against a developer's
  own project, so the check is repeatable and leaves nothing behind.
- Both runs must be started under the same directory conditions. The only variable
  is which copy is running -- ACD-2100a's behaviours are directory-sensitive and varying
  two things at once makes a failure unattributable.
- Both runs must complete their startup path with no network available, so a transport
  failure in one run cannot be read as a parity difference.
- This record must not restate what ACD-2100a, b or c require. Its subject is that
  the copy the user runs is the copy that does it; a child that reads as 'sibling
  behaviour X but in the deployed layout' duplicates coverage and splits one behaviour's
  evidence across two L1s.
- Must satisfy the repository error-handling policy in any harness code that ships
  under scripts/ or unit_tests/.
- Any dependency the deployed route needs at runtime must be in the build deploy manifest.
  A dependency that is not deployed raises at runtime while every source-tree test
  passes -- this repo has that failure twice over in CLAUDE.md.
- 'THE DEPLOY GAP THIS RECORD IS ABOUT IS ALREADY LIVE, AND IT IS WHY scripts/build_phases.py
  IS AN EDIT SURFACE HERE. The deployed route resolves the charter that guards its
  workspace-setup step by reading .leafcutter/config/agent_registry.json at startup,
  and no build phase deploys that file -- a real build leaves the deployed config directory
  holding only the commit-guardian tree and the feedback categories. The gate fails
  closed on an unreadable registry, so the installed copy halts before the first user
  question while the source copy, which resolves the same registry from the package
  root, does not. Until the deploy declarations in scripts/build_phases.py carry that
  dependency, the Then clause above cannot hold for any consumer install.'
- 'THE TWO RUNS MUST BE STARTED UNDER EQUAL HARNESS CONDITIONS, NOT MERELY EQUAL DIRECTORY
  CONDITIONS. unit_tests/_workflow_engine_harness.py resolves its built-in default response
  for the workspace-setup permission gate by walking up from the script''s own directory
  looking for the package''s agent registry. That walk succeeds for the source copy
  and fails for a copy installed under a temporary target, so an unmodified harness
  would start the two runs against different gate conditions and report a parity failure
  that is an artifact of the harness rather than of the installed artifact. Equalise
  the harness environment across both runs, or the verdict is unattributable -- the
  same defect the same-starting-conditions clause exists to prevent.'
- The harness is this record's principal deliverable and ACD-2100d-3 consumes it, so
  it must be importable from the portability test package without living inside it.
  Place it at the unit_tests root beside the repository's existing shared harnesses,
  and give it a stopping-point vocabulary stable enough for ACD-2100d-3 to compare two
  of its results against each other.
```
