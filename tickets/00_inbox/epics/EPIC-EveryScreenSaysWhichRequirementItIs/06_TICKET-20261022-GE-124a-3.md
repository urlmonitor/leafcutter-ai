## Acceptance Criteria

```gherkin
Given the staged set contains `components/coverage/gaps-callout.tsx`, which
  returns a JSX element
When the frontend declaration reader decides which staged files are screen
  components
Then `gaps-callout.tsx` is in scope
And the reader records the reason it is in scope — an in-scope extension plus
  rendered markup

Given the staged set contains `lib/coverage-format.tsx`, which has an in-scope
  extension and exports only a type alias and a formatting constant, with no
  JSX element, no `<template>` block and no markup of any kind
When the frontend declaration reader decides which staged files are screen
  components
Then `lib/coverage-format.tsx` is out of scope
And no declaration verdict of any kind is recorded for it
And the reader records the reason it is out of scope — an in-scope extension
  with no rendered markup

Given the staged set contains a file whose extension is not one of
  `.tsx`, `.jsx`, `.vue`, `.svelte`, `.html`
When the frontend declaration reader decides which staged files are screen
  components
Then the file is out of scope and no declaration verdict is recorded for it
```

## Implementation Notes

```yaml
- 'THE IN-SCOPE DECISION IS ITS OWN FUNCTION WITH ITS OWN RETURN VALUE — {path, in_scope:
  bool, reason: <enumerated code>} — not a filter predicate whose reasoning is discarded.
  GE-124d''s opt-outs are the pressure valve for this rule being wrong at the edges,
  and the PO''s instruction is that clustered opt-outs are evidence the rule needs
  narrowing. That evidence is only collectable if the decision records WHY, so `reason`
  must be a small closed enum (in-scope-markup, no-markup, extension-not-in-scope,
  re-export-only, story-file, test-file, generated-file), never free prose.'
- THE EXTENSION TEST READS GE-124a-2'S SINGLE EXTENSION-TO-FRAMEWORK MAP. Do not hard-code
  a second extension list here; a second list lets a file be in scope with no framework,
  or carry a framework while being out of scope.
- MARKUP DETECTION IS HEURISTIC AND MUST FAIL TOWARDS IN-SCOPE, NOT OUT. Detecting
  JSX/`<template>`/markup in a text scan (no JS AST is available to a Python hook)
  will be imperfect; when the scan is genuinely ambiguous the file must be treated
  as IN scope, because a false in-scope is survivable — the author writes a visible
  opt-out reason (GE-124d-2) that a reviewer can argue with — whereas a false out-of-scope
  is a silent exemption, indistinguishable from the check not running (GE-120's standing
  rule for this component).
- OUT OF SCOPE MEANS NO RECORD AT ALL, not a record with a passing verdict. Every
  downstream count (GE-124c-3's pass records, GE-124g-3's declared axis) treats an
  absent record and a passing record differently, and conflating them inflates every
  figure built on this check.
- The in-scope decision runs BEFORE the declaration and pin readers, so an out-of-scope
  file is never parsed. This is both the latency lever for a large staged set and
  the reason no verdict can leak from an out-of-scope file.
- Must handle errors gracefully per the project error handling policy; a file that
  cannot be read for the markup test is GE-124c-3-i's named-and-skipped path.
```
