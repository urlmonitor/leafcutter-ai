# One allowlist line cannot silence every file in the repository

## Actor / Goal

## Acceptance Criteria

```gherkin
Given three files — "secrets.py", "helpers.py" and "src/deep/secrets.py" —
  each containing the same four lines the scanner's content rules recognise: a
  cloud access key in the AWS_KEY form, a private-key header line, a quoted
  twelve-character value assigned to a field named password, and a
  high-entropy token,
And the allowlist contains exactly one entry, in which both the rule field and
  the path field are written as the wildcard,
When all three files are scanned through the scanner's multi-file entry point
  — the same entry point the pre-commit secrets check calls,
Then all twelve findings are reported and the run's exit status reports
  findings present,
Because a line that names no particular rule and no particular path leaves
  every file it reaches with nothing able to report on it, which is the same
  collapse this guarantee forbids, applied to the whole repository at once.

Given the same three files,
And the allowlist instead contains exactly one entry naming the single rule
  that recognises the password assignment, with the path field written as the
  wildcard,
When the run completes,
Then nine findings are reported — the cloud access key, the private-key header
  and the high-entropy token in each of the three files — and no
  password-assignment finding is reported for any of them,
Because suppressing ONE rule across the repository leaves five rules able to
  report on every file, so it is a narrowing and must keep working; a fix that
  satisfies the first arm by refusing repository-wide entries as a class is a
  regression, not a fix.

Given the same three files,
And the allowlist contains two entries — the all-rules, all-paths entry on one
  line, and on another an entry naming the single rule that recognises the
  password assignment together with the path "helpers.py",
When the run completes,
Then "helpers.py" reports three findings rather than four,
Because refusing one over-broad line never withdraws the other lines the
  author wrote in the same file.
```

## Implementation Notes

```yaml
- THIS IS A DIFFERENT SEAM FROM GE-123b-1, not a bigger example, and the distinction
  dictates the implementation. An entry whose path field is the wildcard names no
  file at all, so an implementation that asks 'which named path would this entry empty?'
  never sees it and passes GE-123b-1 with this hole wide open. The decision must be
  reached PER SCANNED FILE in the run — every entry in force for that file, path-naming
  or path-wildcard alike — and never per named path enumerated from the allowlist.
- 'DO NOT REFUSE REPOSITORY-WIDE ENTRIES AS A CLASS. Arm 2 is the regression guard
  on exactly that cheap fix: a rule-scoped entry with the path wildcard silences one
  of six rules on every file, leaves five, and is documented behaviour the repository''s
  own allowlist relies on heavily today. Refusal is triggered by the state the allowlist
  would leave a FILE in, never by how broad a line looks.'
- 'PER-FILE INDEPENDENCE, both ways: the refusal reached for one file must not change
  the outcome for any other file in the run, and each file''s decision must be reached
  against its own path. The nested third file deliberately shares a basename with
  the root file — it distinguishes ''the entry was correctly scoped'' from ''the entry
  happened to miss'', and the GE-113c-3 exact / segment-suffix path semantics must
  be used unchanged when deciding which entries are in force for it.'
- Refusing one over-broad line never withdraws the other lines in the same allowlist
  (arm 3). This is GE-113c-3-v's per-line-not-per-file precedent applied to a declined-for-effect
  entry rather than a rejected-for-shape one.
- 'COMPLEMENT OF GE-113c-3-v, NOT REOPENED WORK: -v closed the malformed spelling
  (wildcard rule plus a zero-segment path) and deliberately preserved the literal
  wildcard path as the legitimate repository-wide form. Do not re-specify -v''s scenarios,
  and do not close this criterion by banning the wildcard path at parse time — that
  would repeal -v''s fourth scenario.'
- 'VERIFICATION STANDARD, non-negotiable: every arm must be exercised through `scan_files`
  with three real files on disk — one of them at a nested path sharing a basename
  with another — and a real `.security-allowlist` in the same temporary root. Calling
  `_is_suppressed` with hand-built tuples discharges nothing; an audit in the sibling
  GE-113c-3 family found two criteria that passed unit-level tests while describing
  scenarios the real entry point can never produce.'
- 'Fixture reachability: ordinary `.py` filenames throughout. `scan_file` short-circuits
  an environment-named path to a single name-based finding and returns before any
  content rule runs, so the four-findings fixture is unreachable at such a path. The
  environment-filename collapse is GE-123a''s subject.'
- 'Commit hot path: the per-file decision must not turn a repository-wide entry into
  a per-file re-scan. At most one pass over (scanned files x allowlist entries), no
  additional file reads.'
- 'ADR-001 parity: edit the canonical `templates/skills/security-scanner/scripts/scan_secrets.py`
  only and let `build.py` propagate. Never hand-edit the copies under `.claude/`,
  `.gemini/`, `.leafcutter/`, `EPIC-*/` or `worktrees/**`.'
- 'RED-FIRST LABELLING: arm 1 is red (measured 0 findings across all three files,
  clean exit, no warning; target 12 and a findings-present exit) and arm 3 is red
  (measured 0; target three findings for the middle file). Arm 2 is a declared REGRESSION
  GUARD and is GREEN ON ARRIVAL by design (measured 9) — that is expected and is not
  a TDD-order violation.'
```
