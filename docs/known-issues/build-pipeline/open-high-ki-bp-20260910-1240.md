# KI-BP-20260910-1240 — build.py writes CRLF on Windows and then cannot see that it did, so every deployed script silently diverges from its template and a plain re-run never repairs it

> One known issue, split out of `docs/known-issues/build-pipeline.md` on
> 2026-09-14. Index: [build-pipeline.md](../build-pipeline.md).
> Filename severity is the three-level index bucket (`high`); the
> original grading is the `**Severity:**` line below, unchanged.

- **Severity:** high
- **Status:** **OPEN (reopened 2026-09-25)** — partially resolved: the shared writer `build_phases._write()` is fixed (BP-1000a-7, commit `3f0d1ba1`, merged in PR #774 `012b6412`), which clears the commit-blocking hook-parity case. The other text-mode writers are still unfixed on main `d2fe85a1` (see the 2026-09-25 re-verification below). This file had been filed under `resolved/` although its own status said "partially". It is moved back to `open-`.
- **Occurrences:** 5 (found 2026-09-10 while landing EPIC-TruthfulProjectRecord; 2026-09-25 on every fresh worktree bootstrap, see Occurrence 2; 2026-09-27 a CRLF template working copy, see Occurrence 3; 2026-09-27/28, the leftover diff aborts commits through pre-commit's stash, see Occurrence 4; 2026-10-08, the product-truth generator, see Occurrence 5)
- **First seen:** 2026-09-10 · **Last seen:** 2026-10-08 (Occurrence 5). On 2026-09-14, two more text-mode writers seen producing CRLF: `docs/product-truth/scripts/generate_product_truth.py` `_write_text()` (regenerated journeys land CRLF in the working tree; git normalises on add, so the churn is invisible until a byte-level check reads them), and an unidentified step in the `unit_tests/portability` run that rewrote `templates/scripts/commit_guardian/_authored_change.py` with CRLF-only changes
- **Where:** `scripts/build_phases.py` `_write()` · every `check-hook-parity` / `check-output-drift` consumer

**Symptom.** On Windows, `check-hook-parity` blocks the commit reporting that every script under `.leafcutter/scripts/commit_guardian/` and `scripts/commit_guardian/` diverges from its canonical template in `templates/scripts/commit_guardian/`. Running `python scripts/build.py` — the remedy the hook names — reports `580 files unchanged` and repairs nothing. The commit stays blocked, and no number of re-runs moves it.

**Why the build cannot see it.** `_write()` writes with `Path.write_text(content, encoding="utf-8")`. That opens in text mode with `newline=None`, so Python translates every `\n` to `os.linesep` — `\r\n` on Windows. The canonical templates are LF-only, so every deployed file lands byte-different from its source. The build's own compare-before-write guard then reads the deployed file back with `read_text()`, which applies universal-newline translation on the way in and hands back LF. The comparison is LF-vs-LF, matches, and the file is skipped as up to date. The corruption and the blindness to it are the same line:

```python
>>> p.write_text("a\nb\n", encoding="utf-8"); p.read_bytes()
b'a\r\nb\r\n'
>>> p.read_text(encoding="utf-8")
'a\nb\n'          # the CRLF is invisible from here
```

**Why it is worse than a cosmetic diff.** Three consequences compound. (1) The repair the hook advertises is a no-op, so the contributor is told to run a command that cannot work. (2) `--force` does NOT repair it either, despite appearances. A forced run reaches the compare-before-write guard, whose text-mode read normalises the CRLF file to LF, compares equal, and skips the write. (This entry originally claimed `--force` was the working repair; that was wrong. The repairs observed while filing it came from byte-copying templates over the deployed copies by hand, and from `--force` refreshing `.build_manifest.json`, which is a different defect.) (3) `.build_manifest.json` records the hash of what the build believes it wrote; when the build skips a file it never refreshes that entry, so `check-output-drift` later reports the file as hand-edited. A contributor following the error messages is walked toward editing hashes inside a build-integrity manifest to make a drift check pass — which is exactly the action that should never be taken, arrived at by following the tool's own advice.

**Detection.**

```bash
python -c "import pathlib,tempfile; p=pathlib.Path(tempfile.mkdtemp())/'t'; p.write_text('a\nb\n',encoding='utf-8'); print(p.read_bytes())"
# b'a\r\nb\r\n' on Windows, b'a\nb\n' on Linux
python scripts/build.py --target-dir .        # reports "unchanged", repairs nothing
python scripts/build.py --target-dir . --force # also reports "unchanged": the guard compares decoded text
```

Any `check-hook-parity` failure that survives a plain `build.py` re-run on Windows is this.

**Fix direction.** *Landed for the shared writer (BP-1000a-7, 2026-09-13):* `_write()` in `scripts/build_phases.py` now encodes once, compares `read_bytes()` against those bytes, and writes with `write_bytes()`, so the guard and the writer act on the same value with no newline translation. Every commit-guardian script, config and manifest is deployed through it, so the hook-parity failure that blocked commits is gone: after the fix a deployed `run_hook.py` holds zero CRLFs and is byte-identical to its template. *Still open:* the build has roughly twenty other text-mode writers with the identical defect that do not route through `_write()` — among them `generate_agent_cards.py` (every tracked `docs/agents/cards/*.card.md`), `build.py`'s `LEAFCUTTER_VERSION` write, the CLAUDE.md glossary and roadmap-phase injections (`build_glossary.py`, `build_roadmap_phase.py`), and the scaffold writers (`build_ac_store_scaffold.py`, `build_architecture_scaffold.py`, `build_config_scaffolds.py`, `build_precommit.py`). On Windows these leave every freshly built checkout showing dozens of tracked files as modified, purely by line endings. The right fix is one shared byte-exact writer that every phase calls, not twenty local patches — which is why it was scoped out of the quick-fix rather than folded in.

**Re-verification 2026-09-25 (main `d2fe85a1`): reopened.** A probe on Windows showed three results:
- `build_phases._write(p, "x\ny\n", ...)` writes `b'x\ny\n'`. That writer is fixed.
- `build.write_file(p, "x\ny\n", False, False)` still writes `b'x\r\ny\r\n'`. It is still a text-mode `write_text` behind a `read_text` compare guard.
- A second call to `build.write_file` with `force=True` returns `False` and leaves the CRLF in place. This is the original "cannot see it, cannot repair it" defect, unchanged, in `scripts/build.py:226-238`.

`grep` still finds direct `write_text(..., encoding="utf-8")` writers that do not route through `_write()`:
- `scripts/build_precommit.py:377` (`.pre-commit-config.yaml`)
- `scripts/build_helpers.py:1327` (`.build_manifest.json`)
- `scripts/build_ownership.py:532` (clean-mode ledger)
- `scripts/build.py:237`, `:1369` and `:1780`
- `scripts/build_glossary.py:106`, `:172`, `:271` and `:299`
- `scripts/build_roadmap_phase.py:136`, `:155` and `:192`
- `scripts/build_ac_store_scaffold.py:83`
- `scripts/build_architecture_scaffold.py:119`
- `scripts/build_config_scaffolds.py:192`
- `scripts/generate_agent_cards.py:1142`
- `docs/product-truth/scripts/generate_product_truth.py:341` (`_write_text`)

**Pattern:** the writer and the change-detector disagree about what a file's content IS, so the component's self-check validates a normalised view of its own output rather than the output. **Related:** `GE-120` (green means it was checked — here the build reports "unchanged" about a file it corrupted), and `docs/reference/false-green-mechanisms.md`.

**Occurrence 2 — 2026-09-25, every fresh worktree starts dirty, and the drift gate's remedy
regenerates the same noise.** Windows 11, workspace-parent layout. `setup_ticket_worktree.py
create-only` bootstraps each new worktree by running `build.py`
(`templates/scripts/setup_ticket_worktree.py` `_bootstrap()`, `:1393`). On this machine that left
about 60 **tracked** generated files modified in a worktree that had just been created:

- `docs/agents/cards/*.card.md`, written by `scripts/generate_agent_cards.py:1142` (`write_text`)
- `LEAFCUTTER_VERSION`, written by `scripts/build.py:237` (`write_file`)
- `docs/INDEX.md`, written by `scripts/build.py:1369`, the doc-index writer at `:1332-1369`
- once, `templates/scripts/commit_guardian/_authored_change.py` (already noted above, cause unidentified)

Most of the diff was line endings only, and `git add` reported `CRLF will be replaced by LF`. Some
files also differed in content, which is observed and not yet traced (likely generated values
such as the version or index ordering, but not confirmed).

The consequence is procedural, and it compounds. Every commit on such a worktree has to exclude
or `git restore` these files by hand. The `check-build-drift` pre-commit hook
(`.pre-commit-config.yaml:16-22`) then asks for `build.py --force`. That runs the same text-mode
writers and recreates the same CRLF diff, so the remedy the gate names cannot clear the condition
the bootstrap created. Every writer named here is already on this entry's 2026-09-25 re-verification
list, so this occurrence adds a new consequence, not a new cause. It is also the most common way to
hit the defect: once per worktree, before any work is done.

**Occurrence 3 — 2026-09-27, the other direction: the template's working copy was CRLF, not the deployed copy.**
While committing the GE-120f-1 family, `templates/scripts/commit_guardian/check_negative_control_liveness.py`
was found with 767 CR bytes in the working tree, although its staged blob was LF and byte-identical
to both deployed copies. Most likely a checkout or restore under `core.autocrlf=true` rewrote the
file; the exact step was not identified. `check-hook-parity` compares working-tree bytes, so it
reported the canonical template and the deployed copy as diverged even though the content being
committed was identical. Rewriting the working copy from the staged blob fixed parity, but then
`check-build-drift` reported the template as modified without a rebuild, and only a
`scripts/build.py` run cleared it. A pre-commit dry run (`pre-commit run --files <staged>`) caught
both before a real attempt. The same run left `docs/INDEX.md` with CRLF in the working tree after
`scripts/generate_doc_index.py` regenerated it. Git normalised both on `git add` (`eol=lf`), so the
staged content was never wrong. **Pattern:** the parity and drift hooks read the working tree while
the commit contains the index, so line-ending noise that the commit will never carry can still block it.

**Occurrence 4 — 2026-09-27/28, the bootstrap diff now aborts commits, not just clutters them.**
Reported by session leafcutter-6d (closed PR #928, carried over with its user's approval).
Windows 11, leafcutter-ai. Session observation unless marked verified.

`python scripts/build.py --target-dir .` in a fresh worktree left about 60 tracked files modified again: `docs/agents/cards/*.card.md` and `LEAFCUTTER_VERSION`. Most were CRLF-only. Some cards also had real content changes for ACs unrelated to the work (that half is `KI-BP-015`, Occurrence 6).

New consequence: commits then failed inside pre-commit. pre-commit stashes unstaged changes before running hooks and re-applies them afterwards. `transform-doc-index` (`.pre-commit-config.yaml:57-63`, `files: ^docs/.*\.md$`) regenerates `docs/INDEX.md` whenever a staged file is under `docs/`. When the stashed diff and the hook's rewrite touch the same files, the re-apply fails with `patch does not apply`, pre-commit rolls back, and the commit aborts. The only way through was to `git checkout --` the generated files before committing. Hook config verified on main `8ed47463`.

Reproduced incidentally while filing this entry (verified): a `git merge --ff-only origin/main` in a clean worktree ran the post-merge hooks and left seven `docs/agents/cards/*.card.md` modified. Those changes were real content (new AC lines, and skill links rewritten from `templates/skills/...` to `.leafcutter/gemini/skills/...`), not only line endings, and were restored by hand.

Workaround: after any `build.py` run or merge in a worktree, `git status`, then `git checkout -- docs/agents/cards LEAFCUTTER_VERSION docs/INDEX.md` unless the change is intended, before staging.

**Occurrence 5 — 2026-10-08, the product-truth generator still writes CRLF and every author converts by hand.**
Reported while filing the 2026-10-06..08 follow-ups (Windows 11, main `6ccbd14ea`). Same cause as the
2026-09-14 note and the 2026-09-25 list above. Still unfixed, now at a different line:
`docs/product-truth/scripts/generate_product_truth.py` `_write_text()` (:301-306) is
`path.write_text(text, encoding="utf-8")`, with no `newline="\n"`.

- **What it rewrites.** Each run that changes `docs/product-truth/index.json` (:517-521), a flow
  (`write_flows`, :388-405) or an AC's `product_truth` block (`write_ac_product_truth`, :411-437,
  which writes AC YAML files) rewrites that whole file with CRLF. The change checks compare text-mode reads,
  which fold CRLF back to LF, so the next run sees nothing to repair (the pattern of this entry).
- **Two more writers in the same scripts folder** do the same:
  `docs/product-truth/scripts/apply_flow_backlinks.py` `_write_text()` (:57-59) and
  `docs/product-truth/scripts/validate_product_truth.py` (:503, the behind-mark sync).
- **Harm.** Git normalises on add (`.gitattributes` `* text=auto eol=lf`), so the commit is
  clean. But the working tree shows every regenerated file as modified, and every author on
  Windows has to convert the files back before staging or a byte-level check reads them.
  `generate_product_truth.py` measures 425 lines against the 400-line limit, so a fix there must
  also shrink the file.
- **Fix direction, unchanged.** One byte-exact writer (encode once, compare bytes, `write_bytes`)
  used by all three product-truth scripts, as `build_phases._write()` already does. Component
  `ux_prototyping` owns these scripts. Note for the coder: write `newline="\n"` as the two
  characters backslash and n, and `ast.parse` each edited file before committing.
