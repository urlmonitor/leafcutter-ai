## Acceptance Criteria

```gherkin
Given a request offered for a split,
When the host's proposal for it holds one part or none,
Then no split gate is shown and no part is created,
And the request goes on exactly as a single question would: with trigger bundled_accepted it goes

  clarification question it asks today for an ambiguous request, instead of ending blocked,
```

## Implementation Notes

```yaml
- The part count is taken after set-aside (DK-400c-3-i) and before the five-part cut.
  Fewer than 2 means no gate, no part, no Decomposition in the run's output and no
  split section in report.md; the split record is closed with a run event and a limitation
  naming why.
- 'The request then goes on by its trigger, deterministically: bundled_accepted resumes
  from kept_routing as one decision from the precedent step; mid_run resumes the item
  as one decision or research step from its own routing result; jev_none records today''s
  capability gap (DK-400a-1-ii) and ends blocked with today''s blocked report; ambiguous
  falls back to today''s insufficient_context path, unchanged: with routing.on_insufficient_context
  ''human'' today''s clarification question is opened (the same template and choices
  as today) and the run is waiting_human; follow-ups count against intent.max_clarifications;
  today''s ambiguous gap is recorded only if the request ends unresolved (the person
  cannot be asked, or the follow-up limit is reached), and only then does the run
  end blocked.'
- 'No second decomposition is requested for the same item. A request that falls back
  to the clarification question after a rejected or too-small ambiguous split is never
  offered a split again in the same run: the item keeps its split_checked flag (see
  the closed-split marker below), so the bundle check is skipped for it even after
  the person''s answer changes its effective goal, and it routes normally from there.
  This holds even when the clarification answer itself bundles several questions:
  the user chose today''s clarification, and today''s clarification path never splits;
  the person can start a new run to get a split.'
- 'Tests enable splitting explicitly: split.enabled true through a config override
  (false only where a test compares with the off switch). None relies on the shipped
  default, which stays false until E3 merges (dec-9925ebf1895222f4, see DK-400a-1).
  A test asserting that no split starts must run with splitting on, or it passes for
  the wrong reason.'
- 'Closed-split marker (ADR-067 Open Question 1, settled by the IT PO): the WorkItem
  carries a split_checked flag (IT PO default name), set in the route pass that asks
  the item''s bundle question, whatever the answer, and checkpointed with the item;
  it defaults to false, so existing checkpoints load unchanged. While a proposal is
  pending, the open split record (state null) in run state holds the item''s split,
  and the flag is already set. When the proposal leaves fewer than two parts or is
  abandoned, the split record is not kept as a Decomposition (it never reaches the
  envelope, the output or report.md); a run event and a limitation keep the trace,
  and the flag stays set. The flag is not a product state, so product truth keeps
  its eight user-visible states. The bundle check is skipped for every item whose
  flag is set.'
```
