# The web-app build/type-check check is required only for pull requests that change the web app

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `BP-1400a-2` — The web-app build/type-check check is required only for pull requests that change the web app — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `BP-1400a-2`. Component: `build-pipeline`. Assigned agent: `python-coder`. Estimated complexity: `S`. Complexity: `low`.

## Acceptance Criteria

```gherkin
Given the web-app build/type-check check defined for the repository,
When a pull request is opened that changes one or more files under the web-app
  directory (leafcutter-web/),
Then the web-app build/type-check check runs for that pull request and its
  result is required for the pull request to merge,
And when a pull request changes no files under the web-app directory
  (leafcutter-web/), the web-app build/type-check check is not required for that
  pull request to merge.
```

- [ ] AC-1: the web-app build/type-check check runs for that pull request and its
- [ ] AC-2: when a pull request changes no files under the web-app directory

## Implementation Notes

```yaml
- Scope the web-app job with a pull_request `paths:` filter on `leafcutter-web/**`
  in .github/workflows/ci.yml so the job is triggered only by PRs that change web-app
  files. This is the single triggering rule shared by all three web-app checks (build/type-check,
  style, route-render).
- 'KNOWN GOTCHA (reconcile with BP-1400a-4): a GitHub required status check that is
  path-filtered will sit as ''expected/pending'' forever on a PR where the job never
  runs, permanently blocking non-web-app PRs. Choose ONE consistent mechanism and
  apply it identically across all three web-app checks: EITHER (a) required-checks-on-changed-paths
  / a job that always runs but no-ops (reporting success) when no leafcutter-web/
  file changed, OR (b) rely on GitHub''s ''skipped required check counts as neutral/passing''
  behavior — and verify the chosen mechanism actually lets a clean non-web-app PR
  merge.'
- The path filter MUST treat 'touches ANY leafcutter-web/ file' as in-scope (not 'touches
  ONLY leafcutter-web/ files') — see the mixed-change boundary in BP-1400a-2-i.
- Path-scoping must be authored so the SAME filter definition is reused (or kept identical)
  across the a-1 build/type-check, b-1 style, and c-1 route-render jobs — divergent
  filters would let one check fire while another silently skips on the same web-app
  change.
```
