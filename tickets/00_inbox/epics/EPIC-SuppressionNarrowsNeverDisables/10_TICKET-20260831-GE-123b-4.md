## Acceptance Criteria

```gherkin
Given a file "secrets.py" containing four lines the scanner's content rules
  recognise — a cloud access key in the AWS_KEY form, a private-key header
  line, a quoted twelve-character value assigned to a field named password,
  and a high-entropy token,
And the allowlist contains six entries, one naming each of the scanner's six
  rules, every one of them naming the path "secrets.py" and every line,
When the file is scanned through the scanner's multi-file entry point — the
  same entry point the pre-commit secrets check calls,
Then at least one finding is still reported for "secrets.py",
And the run's exit status reports findings present,
And the author is told which file the entries would have left with nothing
  able to report on it,
Because the guarantee is about the state the allowlist leaves a file in, not
  about how many lines it took to get there; an implementation that only ever
  inspects one line at a time is defeated by writing two.

Given the identical six entries written into the allowlist in the reverse
  order,
When the run completes,
Then the same number of findings is reported for "secrets.py" as in the first
  arm,
Because which entry is declined must be settled by the state the allowlist
  would leave the file in, and not by the order the author happened to write
  the entries in.

Given the same file "secrets.py",
And the allowlist contains five entries naming five of the scanner's six
  rules, every one of them naming the path "secrets.py" and every line, with
  the high-entropy rule left unnamed,
When the run completes,
Then exactly one finding is reported for "secrets.py" — the high-entropy
  token — and no lost-coverage warning is emitted,
Because narrowing a file all the way down to one remaining rule is still
  narrowing; only the step that would take it to none is declined.
```

## Implementation Notes

```yaml
- THE DECISION IS TAKEN AGAINST THE WHOLE ALLOWLIST IN FORCE FOR THE FILE, never against
  one entry in isolation. Six individually unremarkable per-rule lines reach exactly
  the same zero as the one over-broad line in GE-123b-1 — measured today at 0 findings.
  A per-line reading of GE-123b's title ships a guarantee that anyone defeats by writing
  their suppression out longhand, which is the form the existing how-to guidance actually
  encourages.
- 'DETERMINISM AND ORDER-INDEPENDENCE: the outcome must be a function of the SET of
  entries in force for the file — not of the order they appear in the allowlist file,
  and not of the iteration order of whatever container holds them. Note the current
  hazard profile: `_load_allowlist` returns an unordered `set`, so no ordering is
  observable today; the moment GE-123b-1-i''s provenance plumbing turns that container
  into an ordered sequence, or a sequential apply-then-refuse loop is introduced,
  order becomes observable and this constraint starts to bite. Design for it up front
  rather than discovering it.'
- 'ARM 2 PASSES VACUOUSLY TODAY AND MUST NEVER BE RUN OR REPORTED AS A STANDALONE
  PASS. Both orders currently yield zero findings, so an order-equality assertion
  on its own is green while the defect is fully live (0 == 0). Arm 2 is meaningful
  only asserted together with arm 1: the same test method must assert that the count
  is identical in both orders AND that the count is at least one. Do not split it
  into its own test, do not sign it off separately, and do not let a coverage report
  credit it in isolation.'
- THE RESOLUTION MUST LEAVE THE FILE ACTUALLY REPORTED ON, NOT MERELY NOMINALLY COVERED
  — this is the constraint that eliminates the naive fix. Arm 1 requires at least
  one finding to be reported. Two of the six rules (the exchange-key rule and the
  env-filename rule) fire zero times on an ordinary source file, so a resolution that
  restores one of THOSE satisfies 'a rule is live again' while the file still reports
  nothing, and fails arm 1. Any resolution strategy is acceptable that simultaneously
  (a) is a deterministic function of the entry set for that file, (b) leaves at least
  one declared rule able to report, and (c) causes at least one finding to be reported
  for that file. Declining the entire collapsing group for that file is one shape
  that satisfies all three with no ordering hazard at all; the choice is the implementer's,
  the three constraints are not.
- 'DO NOT IMPLEMENT AS ''decline any entry once more than one is in force for a file''.
  Arm 3 is the regression guard on exactly that: five entries leaving the high-entropy
  rule unnamed must still narrow the file to exactly one reported finding, with no
  lost-coverage warning.'
- 'THE COLLAPSE THRESHOLD MUST FOLLOW THE DECLARED RULE INVENTORY (the single declared
  source required by GE-123b-1''s it_requirements), not a hard-coded six. The consequence
  is testable and must be tested: if the declared inventory gains a seventh rule,
  these same six entries stop being a collapse automatically and the file is suppressed
  to zero. A hard-coded count passes every other arm here and silently weakens the
  guarantee the day a rule is added.'
- The accumulated-collapse announcement reuses GE-123b-1-i's warning contract without
  variation — error stream, allowlist file path, 1-based line number, verbatim text
  — and additionally names the affected file. Where several entries jointly cause
  the collapse, every declined line must be identifiable; still at most one warning
  per declined entry per affected file per run.
- 'VERIFICATION STANDARD, non-negotiable, and sharper here than elsewhere in the batch:
  the accumulation behaviour cannot be observed by calling the suppression predicate
  once, and the order arm cannot be observed AT ALL through an unordered in-memory
  set. Every arm must be driven through `scan_files` with a real fixture file on disk
  and a real `.security-allowlist` whose lines are written in the specified order.'
- 'Fixture reachability: ordinary `.py` filenames throughout. `scan_file` short-circuits
  an environment-named path to a single name-based finding and returns before any
  content rule runs. The environment-filename collapse is GE-123a''s subject, not
  this one''s.'
- 'ADR-001 parity: edit the canonical `templates/skills/security-scanner/scripts/scan_secrets.py`
  only and let `build.py` propagate. Never hand-edit the copies under `.claude/`,
  `.gemini/`, `.leafcutter/`, `EPIC-*/` or `worktrees/**`.'
- 'RED-FIRST LABELLING: arm 1 is red (measured 0 findings, clean exit, no warning
  on any stream; target at least one finding and a findings-present exit). Arm 2 is
  vacuous today and inherits arm 1''s red status only because it is asserted with
  it. Arm 3 is a declared REGRESSION GUARD and is GREEN ON ARRIVAL by design (measured
  1 finding, the high-entropy token) — expected, and not a TDD-order violation; without
  it the criterion is satisfied by an implementation that declines every entry once
  more than one is present.'
```
