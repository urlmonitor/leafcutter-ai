# KI-BP-20260922-0620 — setup_ticket_worktree.py resolved the repository from its own file location

> Filed 2026-09-22 after the fast lane refused four consecutive runs against `BP-1500g-2`.
> Index: [build-pipeline.md](../build-pipeline.md).

- **Severity:** high — it makes the fast lane unusable in the dev layout, and every
  `create-*-worktree` subcommand depends on this resolution
- **Status:** open — the resolution defect is **fixed** (PR #866, AC `BO-4100d-4`); the
  residual described under *What remains* is what keeps this entry open
- **Occurrences:** 1 (reproducible on demand)
- **Where:** `scripts/setup_ticket_worktree.py` and `templates/scripts/setup_ticket_worktree.py`
  — `_git_toplevel()`, reached from `cmd_create_fastlane_worktree` /
  `cmd_create_ac_worktree` / `cmd_create_only`

**The assumption, stated in the code's own docstring:**

> "When *anchor* is omitted, the script's own directory is used — the script always lives
> physically inside the repository it operates on."

True of the source copy, false of every deployed copy. `build.py` deploys this file to
`.leafcutter/scripts/`, which is not inside `leafcutter-ai/`.

**Two symptoms, and the quiet one is why this is high.** In the dev layout the anchor is not
inside any repository, so it aborts:

```
$ python /home/henzeh/projects/leafcutter/.leafcutter/scripts/setup_ticket_worktree.py \
    create-fastlane-worktree probe-deployed-copy
SubprocessError: Failed to resolve git toplevel from .../.leafcutter/scripts:
  Command '['git','-C','.../.leafcutter/scripts','rev-parse','--show-toplevel']'
  returned non-zero exit status 128
```

The source copy — identical code — succeeded immediately. Location was the entire difference.

In a **consumer install** `.leafcutter/scripts/` *is* inside a git repository: the adopter's.
So `rev-parse --show-toplevel` succeeds, returns the **consumer** repo, and the script creates
leafcutter-ai worktrees against the wrong repository with no error at all. The dev layout gets
the loud version and is the lucky one.

**How it presented, which is the part worth remembering.** The fast lane's worktree phase
invokes a deployed copy, so it hit the crash on every run — but it did not report the
traceback. It composed a structured refusal blaming "a symlink at
`/home/henzeh/projects/leafcutter/.leafcutter`", and cited the operator's own memory file as
corroboration. That path is a plain directory (`ls -ld` → `drwxr-xr-x`); there is no symlink;
the cited memory entry describes a different path whose fix is already in place. Acting on its
stated remediation ("remove the parent symlink") would have deleted a directory roughly eighty
live worktrees resolve through.

So the agent was **right that the script fails and wrong about every stated reason**. The
refusal was byte-identical across two runs, which is what finally distinguished it from a
one-off hallucination and prompted running the script by hand. That confabulation is itself an
instance of `KI-BO-20260921-fastlane-worktree-agent-acts-on-leaked-conversation` — the phase
agent building a diagnosis out of the parent session's context — reached here through reading
rather than through acting.

**What PR #866 fixed.** Both copies now resolve through an ordered candidate list — explicit
anchor, then process working directory, then the script's own directory — returning the first
that is a git repository. An explicit anchor is authoritative and never falls through, so a
caller that names a subject which fails to resolve gets a refusal rather than some other
repository silently substituted. Failure names every candidate tried and says the copy appears
to be deployed outside the repository it manages. The silent consumer-layout half is closed.

Deliberately **not** a plain cwd default:
`KI-BO-20260921-worktree-base-resolver-defaults-to-cwd` is that exact shape in a sibling file,
right in one layout and silently wrong in the other.

**What remains, and why this entry stays open.** Verified by running the fixed template from a
simulated deploy location rather than assumed:

```
$ env --chdir=/home/henzeh/projects/leafcutter python /tmp/dep-sim/setup_ticket_worktree.py \
    create-fastlane-worktree probe-sim
SubprocessError: Could not resolve a git repository from any candidate anchor. This copy of
setup_ticket_worktree.py appears to be deployed outside the repository it manages.
Candidates tried:
  - process working directory (/home/henzeh/projects/leafcutter): ... exit status 128.
  - script's own directory (/tmp/dep-sim): ... exit status 128.
```

In the dev layout *neither* candidate is a repository — the workspace parent is deliberately
untracked and the deployed copy sits inside it. So the deployed copy now fails **clearly
instead of opaquely**, which is a real improvement and nothing more: it still cannot create a
worktree, and the fast lane remains unusable in this workspace.

**Fix direction for the residual.** The deployed copy needs to be told where it came from,
because it cannot infer it. `build.py` already knows — it is the thing doing the deploying.
`KI-BP-011` records that `.build_manifest.json` is written to the package that ran the build
rather than to the target it describes, so a consumer install has no local copy to read.
Fixing KI-BP-011 and having the deployed script read its package root from the target's own
build manifest would close this entry. Note the same dependency closes
`KI-BP-20260921-1630` — three entries now wait on that one piece of missing provenance.

**Related.** `KI-BP-011` (the blocker on the fix direction) ·
`KI-BP-20260921-1630` (also waiting on deploy-time provenance) ·
`KI-BO-20260921-worktree-base-resolver-defaults-to-cwd` (same family, sibling file) ·
`KI-BO-20260921-fastlane-worktree-agent-acts-on-leaked-conversation` (explains the fabricated

**Pattern:** code that derives its context from its own file location, then gets copied
elsewhere by the build — correct in the tree it was written in, wrong everywhere it runs.
