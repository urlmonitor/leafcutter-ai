# A blocking route-render check headlessly loads every web-app route and fails on a non-200 or a console/render error

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `BP-1400c-1` — A blocking route-render check headlessly loads every web-app route and fails on a non-200 or a console/render error — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `BP-1400c-1`. Component: `build-pipeline`. Assigned agent: `python-coder`. Estimated complexity: `L`. Complexity: `high`.

## Acceptance Criteria

```gherkin
Given the continuous-integration configuration for the repository,
When a pull request is opened or updated with one or more changed files under
  the web-app directory (leafcutter-web/),
Then a dedicated web-app route-render check headlessly loads each of the web
  app's routes automatically,
And the check reports a failing (non-passing, blocking) result whenever any
  route returns a non-200 HTTP status or emits a console error or render error
  while loading,
And the check reports a passing result only when every route loads with a 200
  status and no console or render error,
And the check is a hard, blocking check — not an advisory or informational one
  that a pull request can be merged despite.
```

- [ ] AC-1: a dedicated web-app route-render check headlessly loads each of the web
- [ ] AC-2: the check reports a failing (non-passing, blocking) result whenever any
- [ ] AC-3: the check reports a passing result only when every route loads with a 200
- [ ] AC-4: the check is a hard, blocking check — not an advisory or informational one

## Implementation Notes

```yaml
- Add a Playwright-based route-smoke harness UNDER leafcutter-web/ (e.g. leafcutter-web/tests/route-smoke.spec.ts
  + a playwright config). @playwright/test is a NEW devDependency to add to leafcutter-web/package.json
  (also add a lockfile entry and, in CI, `npx playwright install --with-deps chromium`
  for the browser binary). No test framework is currently installed in leafcutter-web/,
  so this is net-new tooling.
- The harness MUST enumerate the app's routes and iterate them (include /about explicitly
  — see BP-1400c-1-i). Prefer deriving routes from the Next.js app-router filesystem
  (leafcutter-web/app/**) so new routes are covered automatically rather than a hard-coded
  list that silently drifts; where a route needs params, provide a representative
  concrete path.
- For each route the harness MUST assert HTTP status == 200 AND capture browser console
  errors (page.on('console'...') / pageerror) and fail the route if any console error
  or uncaught render error is emitted while loading. The check passes only when EVERY
  route is 200 with no console/render error.
- 'The harness runs against a real running instance of the built app: `npm ci` ->
  `next build` -> `next start` (or Playwright webServer) so it exercises the production
  build, then run the Playwright spec against that server.'
- Add a NEW blocking route-render job to .github/workflows/ci.yml that invokes the
  harness. The job MUST be blocking (no continue-on-error), reuse the BP-1400a-2 leafcutter-web/**
  paths filter, use actions/setup-node with npm cache, and pin a stable `name:` —
  the cross-AC contract added to the required-status-checks list by BP-1400a-4.
- 'Harness<->CI-job contract: the harness MUST signal overall pass/fail via process
  exit code (Playwright exits non-zero on any failing spec); the CI job consumes that
  exit code as the check result. A non-200 or console/render error on ANY route yields
  a non-zero exit; the CI job must not mask it (fail loudly).'
- 'PREREQUISITE: every current route must already render clean (200, no console error)
  on the built app before the check is made blocking, or every web-app PR is blocked.
  Establish a clean baseline first.'
```
