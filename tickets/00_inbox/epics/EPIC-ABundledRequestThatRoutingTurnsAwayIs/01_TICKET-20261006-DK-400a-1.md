## Implementation Notes

```yaml
- 'Detection follows the ADR-053 order. Deterministic gates run first and skip the
  check entirely when any fails: split.enabled is true; host operations are enabled
  and the host-operation budget can fund one decomposition; the item is routed semantically
  (request kind capability, not a fixed, continued or retried binding, not a deterministic
  no_match with no eligible candidate, not a part of an approved split); its payload
  is not a caller-supplied leafcutter.decision_request.v1; the run''s remaining part
  allowance (split.max_parts_per_run) is at least 2; the resolved answer kind is decision
  or evidence, or unresolved (ideas, change and out_of_domain roots are never split).'
- 'The ''one question or several?'' judgment is one literal Jev noul per checked item
  (versioned template id kernel.split.bundled) that rides the item''s first existing
  Jev batch: the intent batch for a root without an explicit output contract, otherwise
  the routing batch. It adds no Jev provider request: a checked run makes exactly
  as many provider calls as the same run with split.enabled false, unless the added
  question pushes a batch past jev.max_questions_per_call.'
- A subject counts as bundled only at or above split.bundle_threshold (default 0.8,
  biased against false positives). Below it the item goes on exactly as today; the
  probability and threshold are recorded in the routing assessment, a run event and
  the trace, so an uncertain answer is visible but never starts a split (ADR-053 section
  6).
- For a bundled root whose routing ended no_match because Jev chose none (jev_none),
  the split replaces today's gap recording and host fallback rebinding; the gap decision
  is deferred until the split's outcome is known (DK-400a-1-ii, DK-400d-3-i). Split
  detection takes precedence over the no_match fallback for a bundled subject.
- The split record is checkpointed before the run returns waiting_host; its id is
  derived from the owning work item, so a re-executed node or a resumed run never
  creates a second split for the same item.
- The item's split_checked flag (DK-400c-3) is set in the same route pass, so a re-executed
  node or a resumed run never asks the bundle question twice.
- subject_text equals the submitted goal with only whitespace runs collapsed, using
  one shared normalisation helper that the quote check (DK-400c-2) also uses.
- 'subject_kind is derived deterministically: research_request when the item''s requested
  or classified output is leafcutter.evidence_bundle.v1, decision_question for a mid-run
  item whose request asks a decision question, goal otherwise.'
- Every new tunable lives in config/kernel_config.default.json under a split section
  (split.enabled, split.bundle_threshold, split.max_parts, split.max_parts_per_run
  and the per-part budget keys of DK-400e-1), with config/kernel_config.schema.json
  regenerated from the config model and kept equal by the existing config test; no
  threshold or bound is hard-coded in node code, and every value used is recorded
  in the trace.
- 'Shipped default of split.enabled: on, as approved at the final gate. While DK-400
  is built in three dependency-checked epics (dec-9925ebf1895222f4: E1 = DK-400a +
  DK-400c except c-5; E2 = DK-400b + DK-400d except d-5, plus c-5; E3 = DK-400e +
  DK-400f + d-5), E1 and E2 ship split.enabled: false in config/kernel_config.default.json
  and as the config model''s default, so main stays usable for daily kernel runs between
  merges. DK-400e-1 (E3) returns both to on. Every split test enables splitting explicitly
  through a config override and never relies on the shipped default.'
- 'split.enabled false (the off switch) restores today''s behaviour exactly on the
  same inputs: no bundle question in any Jev batch, no split record, today''s gap,
  fallback, clarification and report.'
- The split lifecycle emits run events and tracer events (split.started and the later
  split.* events) carrying the split id, trigger and subject kind; subject text in
  telemetry obeys the data_policy redaction rules.
- 'Handle failures per the project error handling policy: catch specific exceptions,
  log at WARNING with the run, work item and split ids involved, and never swallow
  a failure silently; a rejected submission leaves run state unchanged.'
```
