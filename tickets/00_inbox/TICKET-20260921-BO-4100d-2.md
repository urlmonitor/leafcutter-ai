# A kind that cannot be honoured is refused, never quietly swapped for one that can

## Acceptance Criteria

```gherkin
Given a request for a workspace naming a kind of work that creation does not
  support,
When creation is attempted,
Then creation refuses and reports failure,
And no branch is created and no workspace is registered,
And the refusal names the kind that was asked for and lists the kinds that can
  be honoured,
And no workspace is created under a different kind from the one requested.
```

- [ ] AC-2: no branch is created and no workspace is registered

## Implementation Notes

```yaml
- Acceptance must derive from MEMBERSHIP of the declared supported-kind set, never
  from a hard-coded name list in the refusal path. A fifth kind added to the declared
  set must become acceptable with no edit here -- the same data-driven rule BO-4100d-1
  establishes, read rather than duplicated.
- No fallback kind may exist anywhere on the creation path. An implementation that
  maps an unknown kind onto a default IS the defect this record closes, and it will
  reproduce the 2026-09-14 failure on the fifth kind while passing every test written
  for the four.
- The listed honourable kinds must be rendered FROM the declared set, so the list
  cannot go stale when the set changes.
- The refusal must be inert -- no branch, no directory, no registration entry -- and
  must reach that guarantee through BO-4100a-3-i's no-debris refusal behaviour rather
  than re-deriving it.
- The refusal must be a discriminated structured outcome in the shape ADR-039 established,
  distinguishable from the unreadable-shared-line refusal of BO-4100a-3 and from the
  post-condition failure of BO-4100a-2.
- Template and deployed copies change together and are verified in parity via the
  build.py round-trip (ADR-001).
```
