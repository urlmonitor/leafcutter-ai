## Acceptance Criteria

```gherkin
Given a reporting period during which phase agents completed work and no
  knowledge record was produced,
When a person asks whether the capture step is working,
Then a report is available that states, for that period and separately: how
  many agent runs reached the knowledge-capture step, how many recorded a
  learning, and how many attempted to record one and could not,
And a period in which runs reached the step, none recorded a learning and
  none failed is reported as agents having had nothing to record,
And a period in which runs reached the step and one or more failed to record
  is reported as the capture path being broken, naming what was missing,
And those two periods are distinguishable from each other by reading the
  report alone, without opening a template or a source file,
And the report is derived from durable records rather than from the console
  output of runs that have already ended,
And a period in which no agent run reached the step at all is reported as a
  third, distinct case rather than being merged into either of the other two.
```

## Implementation Notes

```yaml
- 'NON-COLLISION WITH INF-700a — the BA''s escalation, resolved. The two counters
  do NOT collide, and may share a reporting surface, provided three rules hold. (1)
  DIFFERENT INPUTS: this report reads the capture-attempt ledger (per-run records
  written at sign-off time by INF-700b-1-i and INF-700b-1-ii); INF-700a''s backlog
  reads the knowledge-emission sink minus the harvest watermark. (2) DIFFERENT DENOMINATORS:
  this report counts AGENT RUNS, INF-700a counts EMITTED RECORDS, and one run may
  emit zero or more records — so the two numbers must never be summed, equated, or
  cross-validated against each other. (3) SHARED SURFACE ALLOWED, SHARED NUMBER FORBIDDEN:
  presenting both in one command with two labelled sections is desirable, because
  ''is the loop working'' needs both; deriving either figure from the other is not.'
- 'The discriminating case, and the one to test: on 2026-08-26 the backlog INF-700a
  reports is unaffected by capture health, while capture health is broken. A period
  of 5 runs that all recorded and were all harvested gives this report 5 reached /
  5 recorded / 0 failed and gives INF-700a a backlog of 0. A period of 5 runs that
  all failed gives this report 5 reached / 0 recorded / 5 failed and ALSO gives INF-700a
  a backlog of 0. Identical backlogs, opposite health — a report that could not tell
  them apart would be the defect this AC exists to close.'
- MUST NOT read the harvester's counters. skipped_unknown, unroutable_by_kind, write_failures
  and state_persist_failed in scripts/knowledge/harvest_learnings.py describe the
  ROUTING side and would mislabel a healthy capture as a broken one — all 28 records
  on disk are currently unroutable while capture itself is merely silent.
- 'The three cases must be a partition, decided by data and not by presentation: (a)
  attempt records exist for the period, none with outcome ''recorded'', none with
  outcome ''failed'' → agents had nothing to record; (b) attempt records exist and
  at least one has outcome ''failed'' → capture path broken, naming each distinct
  missing target; (c) NO attempt record exists for the period → third case, reported
  as ''no run reached the step'', never collapsed into (a). Case (c) is only derivable
  because INF-700b-1-i requires an attempt record even on the nothing-to-record path.'
- Period selection must be by the records' own timestamps, not by file position or
  by the time the report runs, so a period can be re-reported later and produce the
  same numbers. Timestamps are ISO-8601; a record with an unparseable or absent timestamp
  must be reported in a separate malformed count and excluded from every period, never
  silently attributed to the current one.
- 'ARCHITECT-REVIEW CORRECTIONS (2026-10-23), binding on test-writer and python-coder. (1) Record shape is what emit_event.py writes: event_type=capture_attempt, timestamp, agent_name, ticket_path (null for ticketless v3 agents), payload.{phase, outcome, retry_count, missing_target}; there is no separate failure record, failed is an outcome. Read payload.missing_target with .get: records written before 2026-10-21 12:18 have no such key. (2) Four verdicts, not three: add learnings-recorded (recorded >= 1, failed = 0). The three-case partition above leaves it undefined. Order: no attempts -> no-run-reached-the-step; any failed -> capture-path-broken; else any recorded -> learnings-recorded; else nothing-to-record. (3) The counted unit is the attempt: a run recording two learnings writes two recorded attempts and no run id exists. Label it attempts, never agent runs. (4) Window is half-open [since, until); naive since/until/record timestamps are read as UTC; a record whose timestamp is not parseable ISO-8601 is malformed. A record whose outcome is not in the closed set is also malformed, not dropped. Lines that are not JSON objects, objects with no event_type, and event types other than capture_attempt (agent_start, legacy knowledge_captured, probes) go to the unrecognised count. (5) Locate the stream by importing sink_resolution.read_usable_stream (plus the enduring-root check that --print-location telemetry uses) from the sibling deployed module; do NOT copy the rule (A2.7, INF-500d-4-ix). (7) The report prints the A2.6 limit once: a failed attempt can only exist where telemetry was still writable.   with no access to any run's console output, and must not read a log file that is

- 'Resilient to a mixed stream. The operational telemetry sink is shared: it currently
```
