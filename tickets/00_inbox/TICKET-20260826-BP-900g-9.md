## Acceptance Criteria

```gherkin
Given a deploy phase iterating the entries it has been declared to ship,
And an entry whose source file cannot be found at the path the declaration names,
When the phase runs,
Then the build exits non-zero and the failure names the phase, the entry, and the
  source path that was not found,
And the phase does not emit a warning and proceed to the next entry, because a
  build that completes with a success verdict while silently omitting a declared
  file reports a consumer install that was never produced,
And the build reports EVERY unresolvable entry in the run, not only the first, so a
  single build tells the author the whole remediation set rather than revealing it
  one commit at a time,
And a declaration listing zero entries, and a declaration all of whose entries
  resolve, both complete without a failure, so the rule distinguishes "nothing to
  ship" and "everything shipped" from "something was promised and dropped",
And the demonstration invokes the build's real entry point as a subprocess against a
  package tree carrying a declared-but-absent source, and asserts the non-zero exit
  and the naming — a test that calls the phase's helper directly does not satisfy
  this criterion, because the fail-open branch is reached through the build's own
  iteration, not through the helper,
Because at HEAD 339b0981c the build_ac_store deploy loop in scripts/build_phases.py
  (~lines 878-883) logs a warning and continues when a declared source is missing.
  That is fail-open in the same direction as the loader defect BP-900g-8 addresses,
  in the same loop, so the one mechanism that could have caught a hand-maintained
  map going stale is itself configured not to.
```
