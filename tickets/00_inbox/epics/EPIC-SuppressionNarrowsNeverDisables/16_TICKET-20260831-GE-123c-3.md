## Acceptance Criteria

```gherkin
Given a security allowlist whose lines 2, 3 and 4 are one entry of each
  unmatchable shape — an appended note after a three-field entry, an appended
  note after a two-field entry, and a rule id the scanner cannot report — and
  whose lines 6 and 7 are two well-formed entries covering findings in
  "src/config/foo.py" and "secrets.py",
And both of those files contain findings for the rules their entries name, and
  "secrets.py" additionally contains a private-key header that no entry covers,
When the developer commits those files and the pre-commit secrets check runs,
Then the developer sees three warnings in the terminal, one per offending line,
  each naming the allowlist file, its 1-based line number and its verbatim text,
And the two well-formed entries still suppress their findings — skipping is per
  line, never per file,
And the private-key finding is reported and the commit is blocked on that
  finding alone,
Because the warning has to reach the person on the path a real commit takes; a
  message that only appears when the allowlist is loaded directly is a
  correction nobody receives.

Given the same allowlist, and a set of files in which no finding survives
  suppression,
When the pre-commit secrets check runs,
Then the three warnings are still shown,
And the check reports a clean result and the commit proceeds,
Because an entry that cannot match is a mistake in the author's instruction, not
  a secret in the repository — this check runs on every commit, so treating a
  cosmetic mistake as a failure would turn one typo into a repository-wide
  outage.

Given the same allowlist,
When the pre-commit secrets check runs,
Then every warning about it is carried on the error stream and none of them
  appear among the reported findings the check consumes,
And each warning has the same three-part shape as the warnings this file
  already emits for entries that are outright malformed — same stream, same
  information, one message per line — with no second warning convention
  introduced for the new class,
Because the findings report and the diagnostics about the allowlist are read by
  different consumers, and two message shapes describing the same file would
  each teach the author to ignore the other.
```

## Implementation Notes

```yaml
- 'There are two places the scanner exists and only one of them gates a commit: the
  pre-commit check imports the DEPLOYED copy, resolved as a sibling of its own deployed
  location, and falls back to the configured scanner directory. A change present only
  in the templates/ source is inert on the real path. Edit the canonical template,
  run build.py, and verify the behaviour through the deployed layout (ADR-001).'
- The warning must be delivered on the error stream and the findings report on the
  standard output stream must remain free of it — the pre-commit check parses that
  stream, and a diagnostic leaking into it would read as a finding.
- The unmatchable-entry warning must never, on its own, change the check's exit status.
  The commit is blocked if and only if a finding survives suppression.
- 'Exactly one allowlist-diagnostic convention exists for this file after the change:
  the shape already established for outright-malformed entries, extended to the new
  class. Two shapes describing the same file is itself the defect.'
- 'Per-line skipping is preserved: every well-formed entry in the same allowlist still
  loads and still suppresses, whatever its neighbours look like.'
- This runs on every commit in this repository and in every project the package is
  installed into. Loading must stay a single linear pass and must not measurably lengthen
  the hook's runtime.
- The verification harness must run the pre-commit check as its own process against
  a temporary tree it owns — its own git repository, its own project root, its own
  allowlist — and must never create, modify or delete a .security-allowlist at any
  real project root, workspace root or worktree root. The live file is what the hook
  actually reads, so a stray write would disable the real gate as a side effect.
- Fixture files must use ordinary source filenames — the per-file scan short-circuits
  environment-named files to a single filename-based finding and never reads their
  content, so such a fixture cannot produce the content findings these criteria depend
  on.
- The blocking-finding fixture must use a rule the pre-commit check never post-filters.
  Its prose exemption removes high-entropy findings for files under certain path prefixes,
  so a high-entropy finding is the wrong choice for the arm that proves the commit
  is blocked.
```
