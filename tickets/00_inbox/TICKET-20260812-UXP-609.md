# The mock-mode safety check cannot pass unless it is really reading fixtures

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `UXP-609` — The mock-mode safety check cannot pass unless it is really reading fixtures — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `UXP-609`. Component: `ux-prototyping`. Assigned agent: `frontend-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given the CI drift-guard that checks the bundled fixtures for drift against the same schemas
  and loaders used for real data,
When it runs,
Then it first asserts that mock mode is genuinely active (isMockActive() is true — the app is
  really reading the fixtures, not the live repo) before it evaluates drift,
And it reports a clean result only when that assertion holds AND no drift is found,
And if mock mode is not genuinely active it exits with a failure that names the reason instead
  of reporting clean,
So a mis-configured environment can never produce a false "all clear".
```

- [ ] AC-1: loaders used for real data
- [ ] AC-2: it first asserts that mock mode is genuinely active (isMockActive() is true — the app is
- [ ] AC-3: it reports a clean result only when that assertion holds AND no drift is found
- [ ] AC-4: if mock mode is not genuinely active it exits with a failure that names the reason instead

## Implementation Notes

```yaml
- The drift-guard route (leafcutter-web/app/api/drift-guard/route.ts, invoked by leafcutter-web/scripts/run-mock-toggle-check.sh
  in .github/workflows/fixture-drift.yml) must assert isMockActive() from leafcutter-web/lib/data/mock.ts
  is true BEFORE evaluating drift; the mock-active assertion must gate the drift evaluation,
  not run after it.
- 'The guard must fail closed: it may report a clean result only when the mock-active
  assertion holds AND no drift is found; any other state must be a non-clean failure,
  never a silent pass.'
- On failure it must name the reason (e.g. mock mode not active) in its output per
  the project error handling policy, so a mis-configured CI environment is diagnosable
  rather than falsely green.
- The mock-active check must use the same isMockActive() seam the app uses, so the
  guard cannot pass while the app would read the live repo.
```
