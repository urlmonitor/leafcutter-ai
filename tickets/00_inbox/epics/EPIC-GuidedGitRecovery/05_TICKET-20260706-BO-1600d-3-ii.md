# When origin genuinely lacks the missing objects, recovery reports it as unrecoverable and does not loop

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `BO-1600d-3-ii` — When origin genuinely lacks the missing objects, recovery reports it as unrecoverable and does not loop — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `BO-1600d-3-ii`. Component: `build-orchestration`. Assigned agent: `python-coder`. Estimated complexity: `S`.

## Acceptance Criteria

```gherkin
Given the objects needed to repair the store are not present on origin (origin
  cannot supply them, so a re-fetch cannot restore them)
When the recovery step engine attempts the re-fetch-from-origin action
Then after the fetch completes without restoring the needed objects, recovery
  reports the situation as unrecoverable-by-this-tool and names the objects that
  could not be restored from origin
And it stops rather than retrying the same fetch indefinitely — it does not loop
And it does not leave the store in a worse state than the halt (it does not delete
  objects it cannot restore)
```
