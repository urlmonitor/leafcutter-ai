# Source, configuration and any location not on the list never inherit the exemption

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-123d-4` — Source, configuration and any location not on the list never inherit the exemption — so that the acceptance criterion is satisfied.

## Acceptance Criteria

```gherkin
Given a source file named "secrets.py" staged for commit contains, inside a
  code comment, the exact credential-shaped sentence that is exempt when it
  appears in a ticket file — its quoted value being a run of ordinary words,
When the staged file is checked by the pre-commit secrets check,
Then the generic-credential finding IS reported and the commit is blocked,
Because the exemption is granted by a file's location and kind, and a source
  file has neither: a comment inside code is still code.

Given a Markdown file staged for commit sits in a documentation area that is
  not one of the five enumerated prose areas — for example the how-to area —
And it contains that same credential-shaped sentence,
When the staged file is checked by the pre-commit secrets check,
Then the finding IS reported,
Because the list of prose locations is closed: a location is exempt only by
  being named on it, never by resembling one that is.

Given a YAML file staged for commit sits in the configuration area,
And it contains that same credential-shaped sentence,
When the staged file is checked by the pre-commit secrets check,
Then the finding IS reported,
Because configuration is read by a running program, and nothing a running
  program reads may ever be treated as prose.

Given the same credential-shaped sentence appears in a ticket Markdown file
  staged in the same commit as all three files above,
When the pre-commit secrets check runs over the whole staged set,
Then exactly three findings are reported — one for the source file, one for
  the documentation file, one for the configuration file — and none for the
  ticket file,
And the commit is blocked,
Because the exemption is decided per file from that file's own location and
  kind, and never spreads across the staged set.
```

## Implementation Notes

```yaml
- 'Exclusion must arise from absence from the closed location and kind lists, never
  from an explicit deny list. An implementation containing a hard-coded exclusion
  for the how-to area, the configuration area or source directories satisfies the
  letter of the first three scenarios and fails their intent. The observable test
  of this is a cost invariant: adding a sixth prose location must require exactly
  one edit — an entry on the location list — and no edit to any exclusion anywhere.'
- The verdict for a staged file must be computed only from that file's own repository-relative
  path and its own kind. No run-level or set-level state may influence it; a cache
  keyed on anything coarser than the individual path is forbidden, because the fourth
  scenario is precisely the case that distinguishes a per-file decision from a per-run
  one.
- The default for a path that is on no list is to report. This must be exercised against
  a directory name that appears nowhere in the implementation, so that the default
  cannot be confused with a hard-coded three-directory deny list passing by coincidence.
- The location gate must be anchored at the repository root, not satisfied by a same-named
  directory at any depth. This is the same constraint GE-123d-2 carries and must be
  met by the same shared mechanism, not solved a second time here.
- The how-to area's exclusion is a recorded decision, not an oversight. Whatever holds
  the location list must make it possible to see that the how-to area was considered
  and left off — a bare list of five strings with no accompanying reason invites the
  next author to add it by analogy, which is the failure this AC exists to prevent.
- This AC changes the boundary of one rule only; no other rule's behaviour in any
  location may change.
- 'ADR-001 parity: edit the canonical copy under templates/ and verify through the
  build.py round-trip.'
```
