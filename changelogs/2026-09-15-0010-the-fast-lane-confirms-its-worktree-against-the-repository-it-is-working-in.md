description: "Two fast-lane runs on 2026-09-14 reported their worktree as /mnt/c/Users/henzeh/Documents/Scripts/leafcutter/leafcutter-ai -- a second, stale clone of this repository on the Windows mount -- and died at the resolve phase looking for fast_lane.py there. The lane had in fact created the correct worktree, on the correct branch, in the right place; only the reported location was wrong. The guard added on 2026-09-07 for this exact class of failure checked that the reported path appeared in the raw git output supplied alongside it, which proves the agent quoted from some git invocation but not that the invocation ran in the repository the run is operating in -- an answer is only evidence about the repository it came from. The stale clone holds no fast-lane branches, so a probe running there found no record for the branch and returned the contract's empty result, which took the deliberate 'git said nothing, fall back to the claim' path. The wrong-repository case was therefore the one case the guard structurally could not catch: the probe failed to contradict the claim because it was looking somewhere the claim could not be contradicted, and the fallback exists to forgive precisely that silence. The fix makes a three-way decision where there were two. An answer that is ABSENT still falls back to the claim, unchanged, because that fallback's stated rationale -- one flaky dispatch should not halt the lane -- is sound, and a test now asserts it survives. An answer that is EMPTY OF THIS RUN'S OWN BRANCH now halts, naming both the branch that could not be confirmed and the location the worktree phase claimed: the run created that branch moments earlier, so an answer omitting it is information rather than silence. The pre-existing self-consistency check is kept verbatim, since it catches a fabricated path, which is a different failure added after two recorded occurrences. The probe is additionally pinned with git -C to the location the worktree phase already claimed rather than running in the dispatched agent's ambient working directory; containment is the substantive half of the fix, because checking the answer harder while leaving the probe free to run anywhere reproduces the defect with more steps. Five tests run through unit_tests/_workflow_engine_harness.py against the real control flow in a Node subprocess, following the precedent of test_bo2400f_13_workspace_refusal_workflow.py; none greps the workflow source, because the defect being fixed was a present, correct-looking check that produced the wrong decision, so the presence of source text is exactly the evidence that already misled. Two of the five assert invariants the fix had to preserve and were green beforehand. One asserts the resolve phase is never dispatched rather than trusting the terminal status, because the observed failure reported success and had already taken that step. Reverting the workflow to its pre-fix content turns three of the five red again and reproduces the /mnt/c path in the run payload together with the resolve dispatch against it. One sibling fixture was corrected in passing: test_bo2400c1vi_bundle_layer_set.py declared branch fast-lane/bo2400c1vi-real-worktree-probe in its worktree stub while its verify stub's raw output listed refs/heads/fast-lane/bo-stub-1, a self-contradiction its own comment already prohibited and which the old lenient guard could not see. The whole unit_tests/workflows/ suite is green at 634 passed. fast-lane-ship.js is over its size limit at 1573 content lines against 1000, so the GE-127b-1 ratchet refuses any growth; the change is net-neutral at 1573 before and after."
