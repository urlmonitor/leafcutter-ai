## Acceptance Criteria

```gherkin
Given a developer whose commit has just been blocked by the secrets check on a
  value they know is not a secret,
And they open the how-to guide that explains how to work with the commit-time
  checks,
When they look for how to stop that one finding being reported,
Then they find a section on suppressing a finding that names the file
  suppressions are written in, describes an entry as three parts — which check,
  which file, which line — and says what each part may contain, including that
  the third part is either a single line number or the marker meaning every
  line,
And they can write a working entry from that section alone, without opening the
  file to copy an existing line,
Because the accepted forms are learned by imitation today, and imitation is
  exactly how the observed mistake was made.

Given the same section,
When the developer wants to record why they added the entry,
Then the section states that an explanatory note cannot be appended to the end
  of an entry and must be written on its own line above it, and shows both
  spellings side by side — the appended note that is rejected and the note on
  its own line that is accepted,
Because the whole point of the note is that its author believed it was harmless,
  and a rule they never read cannot correct them.

Given the same section,
When the developer wants to know what happens if they get an entry wrong,
Then the section states that an entry which cannot match anything is reported in
  the terminal, naming the file and the line, and is then ignored — and that the
  commit is not blocked by that warning on its own,
And the wording of the warning shown matches what the check actually prints,
Because a described correction that does not happen, or happens differently, is
  worse than none: this component already contains one guard documented as doing
  something it does not do, and authors believed it.
```
