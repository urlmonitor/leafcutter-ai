# In a named prose location, a credential-shaped line whose value is recognisably not a credential is not reported

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-123d-2` — In a named prose location, a credential-shaped line whose value is recognisably not a credential is not reported — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-123d-2`. Component: `guardrail-engine`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given a file staged for commit sits inside one of the five enumerated prose
  areas — the ticket tree, the retrospectives area, the acceptance-criteria
  store, the skill-prompt area, or the changelog area,
And the file is of one of the four admitted non-executing kinds — .md, .yaml,
  .yml or .txt,
And it contains three separate lines that the generic-credential rule matches
  today, whose quoted values are one each of these recognised non-credential
  shapes:
  - a value containing whitespace, that is, a run of ordinary words,
  - a bracketed placeholder value — enclosed in angle brackets or in braces,
    or containing an ellipsis of three or more dots,
  - a value made only of masking characters, that is, asterisks or a single
    letter repeated,
When the staged file is checked by the pre-commit secrets check,
Then none of the three lines is reported,
And the commit is not blocked.

Given a file in the acceptance-criteria store staged for commit contains a
  credential-shaped line whose quoted value is a ticket identifier of the
  form TICKET-YYYYMMDD-Name, and a second whose quoted value is an epic name
  of the form EPIC-Name,
When the staged file is checked by the pre-commit secrets check,
Then neither line is reported,
Because the project already classes those two identifiers as benign for the
  high-entropy rule, and two rules looking at the same token must not reach
  opposite conclusions about it.

Given a ticket Markdown file staged for commit contains a credential-shaped
  line whose quoted value matches NONE of the recognised non-credential
  shapes — no whitespace, no placeholder brackets or ellipsis, no masking
  characters, no recognised text-file extension, and not a project
  identifier,
When the staged file is checked by the pre-commit secrets check,
Then the finding IS reported and the commit is blocked,
Because the exemption is a closed list of shapes that are recognisably not
  credentials, and a value that matches nothing on the list is treated as a
  credential.

Given the same three exempt lines are moved, unchanged, into a file that sits
  in one of the five prose areas but is of a kind outside the four admitted
  kinds,
When the staged file is checked by the pre-commit secrets check,
Then all three findings ARE reported,
Because both conditions must hold together: a named location AND an admitted
  non-executing kind. Neither alone grants the exemption.
```

- [ ] AC-4: the commit is not blocked.

## Implementation Notes

```yaml
- The location gate must be anchored at the repository root and evaluated against
  the repository-relative path. The existing prose-prefix test in the pre-commit check
  accepts a prefix that appears at any depth, so a nested directory whose name happens
  to equal a prose-location name inherits the exemption today. Reusing that matching
  form for the new gate would import the same silent inheritance the AC forbids; the
  new gate must not.
- The five locations and the four admitted kinds must each be held as named, closed
  data at a single site, separator-normalised once rather than enumerated twice for
  POSIX and Windows spellings. Extending either list must be a one-line deliberate
  edit.
- The kind gate must be decided from the final extension of the staged path only,
  compared case-insensitively; a compound suffix resolves to its last component, and
  a file with no extension is never admitted. Unadmitted means reported — the closed
  list fails closed in both directions.
- 'Location, kind and value shape must be evaluated as a conjunction per finding.
  No file-level short-circuit and no caching keyed on anything coarser than the individual
  finding: GE-123d-3 and GE-123d-4 both depend on the per-finding granularity and
  are unsatisfiable without it.'
- The exemption decision must carry the NAME of the shape that granted it back to
  the caller. A boolean-only decision does not satisfy the delivers_to contract, because
  GE-123d-5 has to report which shape was responsible.
- The project-identifier shape must reuse the one recogniser the high-entropy path
  already applies to ticket-identifier and epic-name tokens, referenced from a single
  definition. A second, independently written recogniser is the mechanism by which
  two rules come to disagree about the same token, which the second scenario exists
  to prevent.
- The path form must be normalised before the location gate runs. The hook receives
  repository-relative paths from git diff --cached, whereas the scanner CLI may be
  handed absolute or dot-slash-prefixed paths; the same file must receive the same
  verdict from either entry point.
- The rule reports at most one finding per line, so when a line contains more than
  one credential-keyword match the exemption may be granted only if every match on
  that line is a recognised non-credential shape. Granting on the first match alone
  lets a real credential ride in beside a placeholder.
- The value-shape decision must be computed from the full matched value, not from
  the 120-character-truncated finding excerpt the post-filter reads today (same constraint
  as GE-123d-1, and it must be satisfied by the same shared mechanism rather than
  solved twice).
- Adding the changelog area is a deliberate widening beyond the existing high-entropy
  location list. It must be introduced as a named entry in the location data with
  the reason recorded alongside it, not as an unremarked extra string.
- 'Per-finding cost must stay proportionate to a pre-commit hot path: no extra file
  reads, and no matcher whose worst case is superlinear in line length.'
- 'ADR-001 parity: edit the canonical copies under templates/ and verify through the
  build.py round-trip; never hand-edit the deployed copies under scripts/ or .leafcutter/.'
```
