# Prose-tolerant reply reading is applied uniformly across every delivery workflow script

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `BP-300e-5` — Prose-tolerant reply reading is applied uniformly across every delivery workflow script — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `BP-300e-5`. Component: `build-pipeline`. Assigned agent: `python-coder`. Estimated complexity: `L`. Complexity: `high`.

## Acceptance Criteria

```gherkin
Given the delivery commands are backed by multiple workflow scripts
  (/plan-feature, /build-feature, /finalize-feature, and the epic and ticket
  workflows behind them),
And each script reads structured results from the agents it dispatches at every
  such reply-reading point,
When any of these scripts reads an agent reply that wraps a valid JSON object or
  array in surrounding prose,
Then every reply-reading point in every one of these scripts tolerates the extra
  wording identically — a /build-feature or /finalize-feature run is exactly as
  resilient as a /plan-feature run,
And no reply-reading point retains the brittle behavior of stopping on prose around
  otherwise-valid JSON.
```

## Implementation Notes

```yaml
- 'Every agent-reply parse site across plan-feature.js, build-feature.js, finalize-feature.js,
  build-epic.js and build-ticket.js must route through the single tolerant reader;
  no residual inline `typeof x === ''string'' ? JSON.parse(x) : x` ternary or bare
  JSON.parse of agent output may remain.'
- Coverage must be asserted by a structural audit test that enumerates agent-reply
  parse sites (not a hard-coded count); the authoring-time surface is 26 JSON.parse
  sites in plan-feature.js, 5 in finalize-feature.js, 1 each in build-epic.js and
  build-ticket.js, and 0 in build-feature.js (it dispatches via schema-enforced agent()
  calls, so it is trivially compliant).
- 'HELPER PLACEMENT (open design decision — recommendation, needs ratification at
  the gate): E2 workflow scripts are self-contained — the engine forbids require()/import
  in the script body — so the tolerant reader cannot be a shared import. Choose either
  (a) inline a byte-identical parseAgentJson into each workflow script, guarded by
  a parity test asserting the helper body is identical across all scripts, or (b)
  have build.py inject a shared prelude at deploy time. RECOMMEND (a): the test harness
  (unit_tests/_plan_feature_e2_runner.py / _workflow_engine_harness.py) executes the
  TEMPLATE source directly via vm.Script, so a deploy-time-only prelude (b) would
  leave templates/workflows-js/*.js non-runnable and break the harness; inlining keeps
  each script independently runnable and neutralizes drift via the parity test, matching
  the repo''s established source<->template parity pattern (BP-1000).'
- Edit only the canonical source templates/workflows-js/*.js; rebuild via build.py
  so every deployed .claude/workflows/*.js copy stays byte-identical (BP-100k drift
  guard).
- Resilience must be verified by per-script runtime behavioral tests (replay a prose-wrapped
  reply through build-feature and finalize-feature and assert each run continues),
  not a source string-scan.
```
