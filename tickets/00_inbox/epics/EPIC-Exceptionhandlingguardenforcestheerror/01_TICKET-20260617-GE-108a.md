# Exception-handling guard treats subprocess calls as a mandatory I/O boundary

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-108a` — Exception-handling guard treats subprocess calls as a mandatory I/O boundary — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-108a`. Component: `guardrail-engine`. Assigned agent: `python-coder`. Estimated complexity: `M`.

## Acceptance Criteria

```gherkin
Scenario: Unwrapped subprocess.run is reported as an I/O-boundary violation
  Given a production Python file containing `subprocess.run(["ls"])` at module
    or function scope that is NOT enclosed in a try/except block,
  When the exception-handling guard analyses the file,
  Then it emits an io-boundary (IO-001) violation for that call,
  And the violation names the call site by line and column,
  And the guard exit status reports the file as having violations.

Scenario Outline: Every subprocess entry-point form is detected when unwrapped
  Given a production Python file containing an unwrapped `<call_form>` at
    module or function scope,
  When the exception-handling guard analyses the file,
  Then it emits an io-boundary (IO-001) violation for that call.

  Examples:
    | call_form                     |
    | subprocess.run(...)           |
    | subprocess.Popen(...)         |
    | subprocess.call(...)          |
    | subprocess.check_call(...)    |
    | subprocess.check_output(...)  |
    | subprocess.getoutput(...)     |

Scenario: A wrapped subprocess call produces no violation
  Given a production Python file in which each of `subprocess.run`,
    `subprocess.Popen`, `subprocess.call`, `subprocess.check_call`,
    `subprocess.check_output`, and `subprocess.getoutput` appears inside the
    body of a try block with a matching except clause,
  When the exception-handling guard analyses the file,
  Then no io-boundary (IO-001) violation is emitted for any of those calls.

Scenario: Configuration and detection are in parity for subprocess forms
  Given the commit-guardian configuration's declared list of I/O-boundary call
    forms,
  When that list is compared against the call forms the guard actually
    detects,
  Then the configuration lists every subprocess form the guard detects —
    `subprocess.run`, `subprocess.Popen`, `subprocess.call`,
    `subprocess.check_call`, `subprocess.check_output`, and
    `subprocess.getoutput` —
  And no subprocess form is detected by the guard without being declared in
    the configuration, and none is declared without being detected.

Scenario: Self-hosting code stays clean under the widened detection
  Given the guard analyses leafcutter's own production Python files whose
    subprocess usage is already wrapped in a try/except (or is exempted by an
    accepted architecture decision),
  When the widened subprocess detection runs across those files,
  Then no io-boundary (IO-001) violation is emitted for that legitimately
    wrapped or exempted subprocess usage,
  And the guard exit status reports those files as clean.
```
