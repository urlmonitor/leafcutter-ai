## 2. Becoming a CALLER of the store's record check (question 2)

What is true in the code, which differs from ACD-2500a-1's "no-ops when pointed at a path":
- Only `main()` and the staged-file discovery of the two hooks read the git index. Their per-file functions are path-based: `templates/scripts/commit_guardian/check_ac_schema.py::_validate_file(path, schema, all_ac_data, repo_root)` and `scripts/ac_store/validate_ac_schema.py::_validate_file(path, registry_ids, schema, declared_files_reports)`.
- Both return bare strings, not structured findings, and ONE rule is double-reported INSIDE a single function. Verified by running it: a record with `components: []` returns two messages from `validate_ac_schema._validate_file` ("Field 'components' must be a non-empty list..." from `_ac_components.components_field_errors`, AND "schema violation at components - [] should be non-empty" from `_schema_field_errors`, because config/ac_store_schema.json has `minItems: 1` and an `enum` for the same field). An unknown component value does the same (registry check plus schema enum). So "one finding per rule" cannot be met by merely calling the function; it needs a subject-keyed collapse.
- The two hooks and `validate_ac_schema.py` are all over the 400 limit (check_ac_schema 551, check_ac_parent_covered_by 521, validate_ac_schema 418): none of them can grow, so do not edit them.

Decision: call `scripts/ac_store/validate_ac_schema.py` (same directory, already in AC_STORE_DEPLOY_MAP, no commit_guardian sys.path hack), through new `_rc_record_schema.py`:
1. `schema, warn = validate_ac_schema.load_ac_store_schema(path)`; `registry = _ac_components.load_registry_ids(path)`; call `validate_ac_schema._validate_file(file, registry, schema, reports_sink)` per record. Pass the arguments explicitly; do not rely on the defaults (see below).
2. Classify each message to a SUBJECT: for the jsonschema form `<path>: schema violation at <dotted.path> - ...` the subject is the first path segment (`components`, `readiness`, `<root>`, ...); for `components_field_errors` messages and the other hand-written ones it is the quoted field in `Field '<x>'` / `Missing required field '<x>'`; anything else gets subject `record`. Then keep exactly one message per (file, record_id, subject), preferring the non-schema producer (it names the registry and the fix).
3. The `components` subject is NOT emitted by the adapter; it is handed to the components family (`_rc_components.py`), which owns the repair and the "needs a decision" wording. This is how B in ACD-2500a-2-ii and C in ACD-2500a-2-ii each yield exactly one finding.
4. `declared_files_reports` (informational, ACD-1600c-4-i) are dropped, not findings.
5. The adapter's family name is "record schema"; it is report-only.

Two traps the coder must know:
- Deployed layout. `_ac_components.default_registry_path()` and `validate_ac_schema._default_schema_path()` resolve from `__file__` (three parents up). Deployed at `.leafcutter/scripts/ac_store/`, that is `.leafcutter/`, which contains `config/ac_store_schema.json` but NO `docs/components.json`. So `load_registry_ids()` returns an empty set there, and `components_field_errors` then silently skips the membership check ("a broken registry never blocks all commits"). The rule check must pass `<repo-root>/docs/components.json` explicitly and treat an empty or unreadable registry as a `failed` finding, never a skip. The schema default (script-relative) is correct in both layouts; keep it unless `--schema` is given.
- Fixture stores. `_infer_repo_root(path)` in validate_ac_schema falls back to `Path.cwd()` when no `docs/acceptance-criteria` ancestor exists, which silently changes where declared-files existence is judged. Tests must build fixtures as `<tmp>/docs/acceptance-criteria/<component>/<feature>/` and pass `--repo-root`.

Gap to accept knowingly: `validate_ac_schema._validate_file` lacks three commit-hook-only checks (`validate_test_contract`, `validate_declares_side_effect`, the pattern-binding gates). Its docstring claims parity with the hook; the code does not deliver it. The rule check therefore will not flag those, and the commit hook still does. The alternative (importlib-load `check_ac_schema._validate_file` from the commit_guardian directory) buys parity at the cost of a cross-directory path hack, a fail-open `__main__` neighbour, and a second layout to deploy-test; not recommended for G2.

Parent back-link rule: the hook's logic is three lines inside `check_ac_parent_covered_by._check_file` (immediate parent derived from the child id, parent must appear in the child's `depends_on`, child id must be in the parent's `covered_by`). Do NOT extract it from the hook (over the limit, 2-for-1). `_rc_backlinks.py` restates the predicate once and imports the id derivation from `scripts/ac_store/ac_parent_id.py::derive_parent_id`. Two deliberate differences from the hook, both required by ACD-2500a-2-i: (a) a parent that is absent from the checked folder is `needs a decision` naming child and parent, where the hook fails OPEN with a stderr warning; (b) the parent is looked up inside `--location` only, so a repair can never write outside the checked folder (a parent that exists only elsewhere in the store is also `needs a decision`). Note on "the one parent-id derivation": there are three, not one: `ac_parent_id.derive_parent_id` (canonical, `[0-9]{3,}`), `scan_ac_store.derive_parent_id` (`\d+`), and `check_ac_limits._derive_parent_id` (a private copy that says it "mirrors" ac_parent_id). Use the first; do not add a fourth; the consolidation is a separate ticket.

Repairable fields are exactly `{covered_by, components, readiness}`. Write-locked fields (check_ac_governance.py `_PROTECTED_FIELDS` = criteria, title, req_status, depends_on; `_OPEN_FIELDS` = work_status, implemented_by, covered_by) are guaranteed untouched by five stacked layers:
1. `_rc_edit.REPAIRABLE_FIELDS = frozenset({"covered_by","components","readiness"})` is the single allowlist and `_rc_edit.apply_edit` raises `ProtectedFieldError` for any other field. Families cannot write; only the orchestrator calls `_rc_edit`.
2. A unit test reads `_PROTECTED_FIELDS` from templates/scripts/commit_guardian/check_ac_governance.py by `ast` (do not import the hook; it pulls `_ac_governance_baseline`) and asserts `REPAIRABLE_FIELDS.isdisjoint(...)`. If someone later protects `components` or `readiness` the test goes red.
3. Pre-write verification inside `_rc_edit`: parse old and new text with `yaml.SafeLoader`; the two dicts must be equal except for the one target key; otherwise abort the write and return a `failed` finding. The original file is untouched until the verified temp file replaces it (`os.replace`, as `mark_ac_done._atomic_write` does).
4. Byte-level test: after every repair test, the text outside the target key's line span is byte-identical (this is AC "every other field byte-identical", test_parent_other_fields_byte_identical).
5. Property test over a mixed fixture folder: for every file, YAML-level diff keys subset of REPAIRABLE_FIELDS.

Writer rules (field-targeted, never load/dump): read and write with `newline=""` (the ticket files and many records are CRLF on Windows); act only on column-0 key lines (as `mark_ac_done._set_work_status` does, so prose in a `|` block that quotes `covered_by:` is never edited); the key's value extends over every following line that is indented OR starts with `- ` at column 0 (this store has both `covered_by:\n  - X` and the unindented `implemented_by:\n- x` style in the same record, so a naive "next column-0 line ends the block" cuts the list short and corrupts it); append a list item in the style already used (flow `[a, b]` -> `[a, b, c]`; `[]` -> `[c]`; block -> same indent as the last item; null/absent key -> insert after the `id:` line as `backfill_components._insert_after_id_line` does). Do NOT reuse `backfill_components._backfill_file` for components: it treats `components: []` as "missing" and inserts a SECOND `components:` key (PyYAML SafeLoader accepts duplicate keys silently, last wins), so for the present-but-empty case the writer must replace in place.

Readiness before-state (ACD-2500a-2-iv). The workflow cannot snapshot (no fs), and the stage agent's report is not allowed. plan-feature commits every approved stage before the next one starts (BO-1500b-1 invariant), and an `edit` retry re-runs with the stage's output still uncommitted, so the committed `HEAD` of the authoring worktree IS the stage-start state. `--before-ref HEAD` reads each record's readiness with `git show <ref>:<path>` (one `git cat-file --batch`, as check_ac_schema does); `--before-snapshot FILE` (JSON `{id: value|null}`) exists for tests and non-git callers. Rule: after-state `approved` and before-state not `approved` -> restore. `--stage approval` skips the family (stage identity, not value inspection); the workflow never calls the check after `apply-approval`, but the CLI must support the stage for the ACD-2500a-2-iv paired case and for `approve_acs.py`.

Component candidates (ACD-2500a-2-ii). ACD-2500a-2 says to reuse "the mapping backfill_components.py applies".
