# Installing into a project where the route starts leaves the route still able to start

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `ACD-2100d-3` — Installing into a project where the route starts leaves the route still able to start — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `ACD-2100d-3`. Component: `ac-driven-dev`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given a project in which a run reaches the first question the route puts to the
  user before the installer is run,
When the current installer is run against that project,
Then a run started in that project afterwards still reaches that first question,
And it does not stop at any check that did not stop it before the install,
And the finding comes from starting a run in that project after the install
  rather than from inspecting what the installer copied.
```

- [ ] AC-1: a run started in that project afterwards still reaches that first question
- [ ] AC-2: it does not stop at any check that did not stop it before the install
- [ ] AC-3: the finding comes from starting a run in that project after the install

## Implementation Notes

```yaml
- THE VERDICT MUST BE A RELATION BETWEEN TWO RECORDED OBSERVATIONS of the same project
  -- one taken before the installer runs and one after. It must not be an assertion
  about the after-state alone. An implementation that measures only the after-state
  and compares it to a constant passes on a project that was already broken, which
  is the one outcome this record exists to exclude.
- A PROJECT THAT DOES NOT REACH THE FIRST QUESTION BEFORE THE INSTALL MUST NOT PRODUCE
  A PASS. The Given is a precondition, so the correct verdict there is precondition-not-met,
  reported as such and distinguishable in the output from a pass. This is the mechanically
  checkable form of the requirement above -- it is the single case that separates
  a real before-and-after from an after-only check wearing its name.
- Reuse ACD-2100d-1's harness -- install into a temporary target project and observe
  how far a run started there gets -- rather than writing a second one. Two harnesses
  observing 'how far the run got' by different means will eventually disagree, and
  when they do one of these two records reports green on the condition the other reports
  red. The temporary target must be created and torn down by the harness so the check
  is repeatable and leaves nothing behind; it must never be run against a developer's
  own project.
- Both observations must be taken on the same project under the same starting directory
  conditions. The only variable is that the installer ran in between -- ACD-2100a's
  behaviours are directory-sensitive and varying two things at once makes a regression
  unattributable.
- The observation must be the run's own recorded stopping point, not its exit code.
  A run can exit zero having halted at a startup check, and which check stopped it
  is this record's entire subject.
- Both runs must complete their startup path with no network available, so a transport
  failure in one of the two measurements cannot be read as an install-induced regression.
- The finding must be produced by starting a run in the project after the install.
  An assertion over what the installer copied, a file manifest or a checksum is not
  evidence -- the same real-artifact rule ACD-2100d-1 is held to, for the same reason.
- STANDING GUARANTEE MEANS IT HAS TO KEEP RUNNING. Wire the check where a change to
  the startup path or to the installer will re-run it, and have its verdict read by
  whatever decides that change is deliverable. A script that proved the property once
  and is never invoked again satisfies the words and not the record -- the inert-gate
  shape this repo keeps rediscovering.
- Must satisfy the repository error-handling policy in any harness code that ships
  under scripts/ or unit_tests/.
- Any dependency the check needs at runtime must be in the build deploy manifest.
  A check that runs only from the source tree is not the check a consumer's install
  would run, and this record is about what happens to a consumer.
- 'THE GATE THAT ACTUALLY RUNS ON AN INSTALLER CHANGE ALREADY EXISTS -- WIRE INTO IT
  RATHER THAN ADDING A SECOND ONE. scripts/ci/check_consumer_install.py already creates
  a temporary target project, runs the real installer into it as a subprocess, and
  has its exit code consumed by the consumer-install simulation job in the repository''s
  CI workflow. That is the deliverability decision the standing-guarantee requirement
  above names. Extend that script with the before-and-after startup measurement so
  the verdict is read where an installer change is already gated. The CI workflow definition
  itself needs no edit, because the job already invokes this script -- and a new standalone
  script that nothing invokes is the inert-gate shape the requirement forbids.'
- 'THE DEPLOY-MANIFEST REQUIREMENT IS ABOUT THE ROUTE, NOT ABOUT THE CHECKER, AND THE
  TWO MUST NOT BE CONFLATED. Neither the CI check directory nor the test tree is deployed
  into a target install, and that is correct: both are package-development tooling.
  What must be present in a consumer install is everything THE ROUTE reads at startup,
  and closing that gap is ACD-2100d-1''s surface. If reusing ACD-2100d-1''s probe from
  the CI check turns out to be awkward because the probe lives under the test tree,
  resolve it by having the consumer-install job reach the probe through the test runner,
  or by relocating the single shared probe. Do NOT resolve it by writing a second probe
  -- that is the exact outcome the reuse requirement above exists to prevent.'
```
