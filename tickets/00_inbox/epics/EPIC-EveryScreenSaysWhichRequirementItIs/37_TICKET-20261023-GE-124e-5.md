## Acceptance Criteria

```gherkin
Given a person's build has just failed the reverse-direction gate on a
  criterion id
When they open the how-to named in the failure
Then it states the two ways to satisfy the gate — name the criterion in a
  component-level declaration, or pin it on a rendered element — and shows
  both
And it states that satisfying this gate does not mean the criterion is proven,
  and names the separate obligation that a test still has to assert it
And it shows how this failure differs on the page from a test-proof failure,
  which the reader may be looking at the same day
And it states that a criterion still in progress is skipped rather than
  checked, so the reader does not mark work done to clear the gate

Given a reader asks why a criterion that has been undeclared for months has
  only now failed the gate
When they open the same how-to
Then it states that the gate evaluates only the criteria a change touched —
  the criterion's own record, or a front-end file that declares or pins it
And it states that an untouched criterion is not evaluated rather than passed,
  so its silence on earlier runs was never a clean bill
```

## Implementation Notes

```yaml
- 'Author under docs/how-to/ with check_doc_frontmatter-compliant frontmatter for
  docs/** (title, type: how-to, status, created, last_updated, components, description)
  and stay within the check_doc_length budget.'
- THE PAGE MUST BE NAMED IN THE GATE'S FAILURE MESSAGE, and the test contract asserts
  that routing from the real check's output. A remediation page nobody is sent to
  might as well not exist.
- SHOW THE TEST-PROOF FAILURE SIDE BY SIDE, using the real text check_done_proof emits,
  not a paraphrase. The two failures look superficially identical on a CI page and
  appear on the same criterion; a reader who cannot tell them apart will 'fix' the
  wrong one. Reproducing both real messages next to each other is the only form of
  this that works.
- 'STATE BOTH DIFF-SCOPING FACTS, not just the first: the gate evaluates the criteria
  a change touched via EITHER route (the criterion''s own record, or a changed front-end
  file that declares or pins it), AND an untouched criterion was never evaluated rather
  than passed. The second is what turns an apparent regression into the backfill it
  actually is — without it the likeliest reaction is to hunt for a recent change that
  caused it, and the next likeliest is to ask for the gate to be turned off.'
- 'STATE THE IN-PROGRESS RULE AND WHY IT IS NOT AN ESCAPE: a UI criterion that is
  not done is skipped, and it comes straight back the moment it is finished (GE-124e-1).
  Stating it removes the incentive to mark work done to silence the gate, and naming
  its expiry removes the incentive to leave work unfinished to avoid it.'
- CARRY GE-124g'S LANGUAGE UNCHANGED — declared, never verified, covered or proven.
  This page is where a reader most wants the two obligations to be one thing.
- change_target stays `code` under the L0's tree-wide instruction; the deliverable
  is the how-to document.
```
