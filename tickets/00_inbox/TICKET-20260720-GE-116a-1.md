# Verification-required agent with no edit ability is blocked at commit

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-116a-1` — Verification-required agent with no edit ability is blocked at commit — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-116a-1`. Component: `guardrail-engine`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given a staged agent definition whose settings declare that it must verify
  the changes it makes (requires_verification is true),
And that agent's declared abilities include neither the ability to edit files
  nor the ability to create files (tools lists only read-and-inspect abilities
  such as Read and Bash),
When the commit is attempted,
Then the commit is blocked fail-closed,
And the block is reported as a failure of the consistency guard,
And the offending agent definition is not committed.
```

- [ ] AC-1: that agent's declared abilities include neither the ability to edit files
- [ ] AC-2: the commit is blocked fail-closed
- [ ] AC-3: the block is reported as a failure of the consistency guard
- [ ] AC-4: the offending agent definition is not committed.

## Implementation Notes

```yaml
- 'Mirror the existing sibling guard templates/scripts/commit_guardian/hooks/check_agent_spawn_consistency.py:
  same module structure, staged-file scan (git diff --cached), run_hook.py invocation,
  and non-zero-exit fail-closed convention. Place the new script in the hooks/ subdirectory
  alongside it (not the commit_guardian/ root).'
- 'Fail CLOSED only on a clearly-detected contradiction (requires_verification: true
  AND tools lacks both Edit and Write): exit non-zero so the commit is blocked; any
  consistent or non-target staged set must exit 0.'
- Scope the scan to STAGED templates/agents/*.md by file identity only; never full-tree
  scan and never content-grep unrelated files.
- Must complete within the interactive pre-commit budget (well under 1s for a typical
  staged set) so it does not slow commits.
- 'Follow the project error-handling policy: wrap file/git I/O in typed try/except
  and log at WARNING or higher; the fail-open parse path (GE-116a-1-iii) must never
  let an exception propagate out of the hook.'
- 'This ticket covers the FULL python-coder AC set for the guard: GE-116a-1/-2/-3/-4/-5,
  GE-116b-1, GE-116c-1/-2/-3 and the L3 edges GE-116a-1-i/-ii/-iii, GE-116a-2-i, GE-116b-1-i.
  (GE-116a-6 — the reference doc — is a separate documentation-expert ticket.)'
- 'Rule detail: the requirement is satisfied by Edit OR Write (GE-116a-2 / GE-116a-2-i);
  requires_verification false or absent → allowed (GE-116a-3/-4); tools present-but-empty
  → blocked (GE-116a-1-i).'
- 'Block message (GE-116b-1 / GE-116b-1-i): name the offending template path(s) and state
  BOTH fixes (add Edit/Write to tools, or set requires_verification: false). When multiple
  templates offend, enumerate EVERY one, not just the first.'
- 'Scope (GE-116c-1/-2/-3): trigger by file identity on STAGED templates/agents/*.md only
  (git diff --cached); no-op/exit 0 when none staged; never inspect non-agent files by
  content; never scan the full tree (pre-existing unstaged contradictions are ignored).'
- 'Registration (GE-116a-5): register the hook in the SOURCE manifest
  templates/scripts/commit_guardian/commit_guardian.json (run_hook.py entry + files regex
  ^templates/agents/.*\.md$) and rebuild via build.py so it lands in the generated
  .pre-commit-config.yaml. CRITICAL (BP-300e trap): a NEW commit_guardian script must also
  be added to ALL build deployable-set/parity lists — build_phases.py deploy_scripts,
  build.py _manifest_* helpers, AND _get_source_paths_for_guard — or the
  test_guard_source_paths_match_deployable_set guard fails. Edit SOURCE (templates/…),
  never the deployed copy.'
```
