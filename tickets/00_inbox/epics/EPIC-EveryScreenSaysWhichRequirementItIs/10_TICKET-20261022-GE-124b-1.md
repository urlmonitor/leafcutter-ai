## Acceptance Criteria

```gherkin
Given a staged screen component file containing the element
  `<span className={styles.badgeLive} data-ac="UXP-607-1 UXP-607">` on line 51
When the element-pin reader evaluates the file
Then one pin is recorded for that element with the criteria
  ["UXP-607-1", "UXP-607"], the line number 51, and the opening tag as written
And the recorded attribute name is `data-ac`

Given a staged screen component file containing two pinned elements
When the element-pin reader evaluates the file
Then two separate pins are recorded, each with its own line number and
  criteria list

Given a staged screen component file that carries a component-level
  declaration and contains no `data-ac` attribute anywhere
When the element-pin reader evaluates the file
Then no pins are recorded for the file
And the absence of pins produces no finding of any kind
```

## Implementation Notes

```yaml
- THE PIN READER LIVES IN THE SAME SHARED MODULE AS THE DECLARATION READER (templates/scripts/commit_guardian/_frontend_declaration_reader.py
  plus its deployed twin, deploy_map entry in scripts/build_phases.py) and emits pins[]
  as a collection SEPARATE from declares[], never unioned with it (GE-124a-1-ii).
  Both the commit tier and the CI tier read pins from this one place.
- ATTRIBUTE VALUE GRAMMAR IS SPACE-SEPARATED, ORDER-PRESERVING. Split the data-ac
  value on runs of whitespace; keep the authored order; do not de-duplicate distinct
  ids. Note this grammar deliberately differs from the comma-tolerant @ac line grammar
  in GE-124a-1, because the value must also be consumable by the CSS attribute-membership
  selector `[data-ac~="<id>"]` that GE-124f-3 derives — and `~=` matches whitespace-separated
  tokens only. Document the difference where both grammars are specified (GE-124b-5).
- EACH PIN RECORDS {id, file, line, element, attribute, ac_ids[], state} — a 1-based
  line number for the opening tag and the opening tag verbatim. A pin known only as
  'somewhere in this component' cannot be argued with in a review, and the line number
  is what GE-124c-2's unresolved-pin finding points at. The stable slug `id` is what
  a criterion's pinned_by list stores (GE-124g-1), so it must be deterministic for
  a given file, line and value rather than a run-ordinal.
- 'ONE PIN PER ELEMENT, EVEN WHEN MULTI-VALUED. `data-ac="UXP-607-1 UXP-607"` is ONE
  pin carrying two ids, not two pins. Cardinality matters downstream: GE-124c-3''s
  pass record counts pinned elements, and GE-124e-2 reports the file and line of the
  pinned element.'
- OPTIONALITY IS A POSITIVE BEHAVIOUR. A file that declares at component level and
  pins nothing must produce zero findings of any kind — no advisory, no 'consider
  pinning' note, no warn. An implementation that nudges here makes the optional surface
  compulsory in practice and contradicts GE-124b-2 scenario 2.
- Read the attribute only in the framework's markup, not in arbitrary strings. Pure
  text scanning is required (no JS AST in a Python hook), so anchor the match to an
  attribute occurrence inside an opening tag rather than to the bare substring `data-ac`,
  or a comment or string literal mentioning the attribute will be read as a pin.
- Must handle errors gracefully per the project error handling policy; an unparseable
  file is GE-124c-3-i's named-and-skipped path.
```
