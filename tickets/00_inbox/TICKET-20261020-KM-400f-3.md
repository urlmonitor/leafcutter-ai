# Capacity headroom is measured and an unsafe publication is refused before it starts

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `KM-400f-3` — Capacity headroom is measured and an unsafe publication is refused before it starts — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `KM-400f-3`. Component: `knowledge-management`. Assigned agent: `python-coder`. Estimated complexity: `L`. Complexity: `high`.

### Implementation notes (added 2026-10-20, before the build)

- **Where the gate sits.** In `publish()` (`knowledge/adapters/neo4j_projection.py`), after the
  snapshot is prepared (its node/relationship counts are known, after
  `collapse_identical_edges`) and BEFORE the first write of the new generation. The test double
  must record every call so "no write before refusal" is asserted, not inferred. A refusal
  leaves the active pointer and every generation untouched and reports
  `generations reclaimed: 0` like the other pre-switch failures (KM-400f-2).
- **Measured usage** is whole-database (the Aura cap is per database, not per repository):
  `MATCH (n) RETURN count(n)` and `MATCH ()-[r]->() RETURN count(r)`. The result states the
  figures were measured, e.g. `basis: measured`.
- **The ceiling is declared, never built in.** Neo4j/Aura does not report its capacity over
  Bolt. "The backend reports a ceiling" is therefore satisfied by an operator declaration for
  that backend: `sync --capacity-max-nodes N --capacity-max-relationships M
  --capacity-refuse-percent R --capacity-warn-percent W`, declared all together or not at all
  (a partial declaration is a `ValueError` before any network access), the same pattern as the
  retention bound flags. No flags → ceiling unknown → headroom `unknown`, measured usage
  still reported, never counted as a fit. An unknown ceiling does NOT refuse publication (that
  would break every install that declares none); it is reported as unknown.
- **Thresholds per axis.** Refuse when `usage + snapshot > refuse% x ceiling` on EITHER nodes
  or relationships; warn when it exceeds `warn%` on either. Report all four figures (usage,
  ceiling, snapshot size, shortfall or remaining headroom) separately per axis. AC scenario 1
  figures: nodes 189,950 + 9,850 = 199,800 > 180,000 → refused.
- **Read-only latch.** Detect before writing via `SHOW DATABASE <db> YIELD access` on the
  `system` database where permitted (Aura reports `read-only` once latched). If that query is
  not permitted, classify the write rejection (`DatabaseError` naming read-only) as the same
  capacity condition. Either way the result names `read-only` and the measured usage, and is
  never an empty/successful result.
- **Workflow.** `.github/workflows/knowledge-sync.yml` declares the Aura Free ceiling
  (200,000 nodes / 400,000 relationships) with refuse 90 / warn 75 and passes the flags. The
  workflow stays disabled.
- **Layout limits.** `knowledge/adapters/` is at 14 files (density cap 15) and
  `neo4j_projection.py` is near the 400-line cap: put the headroom logic in
  `knowledge/adapters/retention/capacity.py`. New live tests go under
  `tests/knowledge_live/publication/` (the parent directory is at the density cap).
- **Reachability test** entry point: `python -m knowledge sync` (cli_sync), not a direct
  function import.

## Acceptance Criteria

```gherkin
Given the backend reports a capacity ceiling of 200,000 nodes and 400,000 relationships
And the declared safe-headroom threshold is 90 percent of that ceiling and the declared warning threshold is 75 percent
And measured current usage is 189,950 nodes and 304,498 relationships
And the prepared snapshot contains 9,850 nodes and 26,100 relationships
When publication is requested
Then publication is refused before any part of the snapshot is sent to the backend
And the refusal names the measured usage, the reported ceiling, the snapshot size and the shortfall, separately for nodes and for relationships
And the active generation, every retained generation and the active pointer are unchanged
And the refusal states that the usage figures were measured from the backend rather than estimated

Given the same ceiling and thresholds, measured usage of 150,000 nodes and 300,000 relationships, and the same prepared snapshot
When publication is requested
Then publication proceeds
And a warning is reported naming the measured usage, the reported ceiling, the snapshot size and the remaining headroom, separately for nodes and for relationships

Given the same ceiling and thresholds, measured usage of 20,000 nodes and 50,000 relationships, and the same prepared snapshot
When publication is requested
Then publication proceeds without a headroom warning

Given the backend does not report a capacity ceiling
When publication is requested
Then the headroom result is reported as unknown, naming the measured usage and stating that the ceiling could not be determined
And the result is never reported as fitting within the ceiling
And an unknown ceiling is not counted as a satisfied headroom check

Given the backend has latched read-only because it is full
When publication is requested
Then the refusal names the read-only condition and the measured usage as the reason
And it is not reported as an absence of knowledge or as an empty result
```
