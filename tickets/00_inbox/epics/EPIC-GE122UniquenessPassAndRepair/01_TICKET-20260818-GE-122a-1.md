# A whole-collection pass reports every number claimed by two artifacts

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-122a-1` — A whole-collection pass reports every number claimed by two artifacts — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-122a-1`. Component: `guardrail-engine`. Assigned agent: `python-coder`. Estimated complexity: `L`. Complexity: `high`.

## Acceptance Criteria

```gherkin
Given a collection fixture that contains, across three numbered namespaces:
  - two acceptance-criterion records that both declare the identifier "GE-119" — one a
    goal-level record owning a folder of children, the other a parentless detail-level
    record at the namespace root,
  - two decision records whose filenames both claim the integer 029,
  - two architecture diagrams whose filenames both claim the level-and-sequence "c2-003",
And several thousand further artifacts across those same namespaces that each claim a
  number no other artifact claims,
When the uniqueness pass runs over the whole collection,
Then it terminates with a failing result,
And it reports exactly three findings — one per contested number, not one per claimant
  file,
And each finding states the contested number and the path of EVERY artifact claiming it,
  so a reader can identify both sides of the collision without searching the collection,
And no artifact whose number is claimed only once appears in the report.

And Given the same collection with those three contested numbers resolved so that every
  number is claimed once,
When the same pass runs,
Then it terminates with a passing result,
And it states, per namespace, how many artifacts it inspected — so a passing result is
  distinguishable from a pass produced by inspecting nothing.

Coverage note: this criterion is covered only by a test that EXECUTES the pass over a real
on-disk collection and asserts on the result value, the number of findings, and the paths
named in the emitted output. A test that searches the implementation for a function name,
a constant, or a message string does not cover it — a grep-only test passes on dead code
(CLAUDE.md, "Gate / Workflow ACs — Verify Behaviorally, Not by Grep").
```

## Implementation Notes

```yaml
- This is the load-bearing PRODUCER of the tree — six ACs (GE-122a-1-i, GE-122c-1,
  GE-122c-2, GE-122d-1, GE-122d-3, GE-122e-3) consume its verdict. It MUST be a single
  importable module with a callable entry point, not logic inlined into one hook script.
  Three stages invoking one evaluation is GE-122d-1's behavioural requirement, and
  it is unsatisfiable if the pass lives inside a stage.
- 'The verdict object MUST carry, per namespace: an outcome value, every contested
  number with EVERY claimant path for that number, and the count of artifacts inspected.
  The inspected count is not optional output — GE-122d-3 and GE-122e-3 both assert
  on it, and it is the only thing that distinguishes a pass from a pass over nothing.'
- 'REGISTRATION TARGET — the single most likely way this work ships inert. `.pre-commit-config.yaml`
  is a BUILD OUTPUT: `scripts/build_precommit.py` strips every `@package-managed`
  block and re-renders it from `hooks_manifest.hooks` in `templates/scripts/commit_guardian/commit_guardian.json`
  on every `build.py` run. A hook added by hand-editing `.pre-commit-config.yaml`
  works locally and then VANISHES in CI, because the `AC store valid` job runs `python
  scripts/build.py --target-dir .` before it runs any hook. The canonical registration
  edit is the `hooks_manifest.hooks` array in `templates/scripts/commit_guardian/commit_guardian.json`;
  `.pre-commit-config.yaml` is then regenerated by running build.py and the regenerated
  file committed.'
- DEPLOY MANIFEST (CLAUDE.md, 'New Hook / Gate Dependencies Must Be in the Build Deploy-Manifest').
  Every new module this pass introduces, and every existing module it starts importing,
  MUST be added to the matching build deploy list BEFORE the gate is registered —
  commit-guardian scripts under `templates/scripts/commit_guardian/`, AC-store helpers
  via the `build_ac_store` deploy_map in `scripts/build_phases.py`, and any `scripts/*.py`
  helper via `AGENT_SUPPORT_SCRIPT_FILES` in the same file. An undeployed dependency
  raises ModuleNotFoundError in the deployed layout while source-tree unit tests stay
  green; once the CI gate is required, that crash blocks every merge (the done_proof.py
  precedent).
- 'ADR-001 parity: the canonical source is `templates/scripts/commit_guardian/`; the
  `.leafcutter/` copy is a build output. Edit the template, run build.py, and let
  `check-hook-parity` confirm — never edit the deployed copy.'
- 'The decision-number namespace is largely REGISTRATION, NOT NEW IMPLEMENTATION.
  `templates/scripts/commit_guardian/check_adr_collision.py` already exists, is deployed
  to `.leafcutter/scripts/commit_guardian/`, and already compares staged decision
  numbers against origin/main plus in-flight branches. Verified 2026-08-17: it is
  registered in NEITHER `.pre-commit-config.yaml`, NOR either `commit_guardian.json`
  manifest, NOR `ci.yml` — it has never executed. Reuse its comparison logic rather
  than reimplementing it. This AC''s complexity is driven by the acceptance-criterion
  and diagram namespaces, not by this one.'
- check_adr_collision.py's fail-open contract MUST be changed as part of adopting
  it. It is fail-open by design (exit 0 on any internal error), while GE-122d-3 requires
  a could-not-read-the-collection condition to block at commit time; registering it
  unchanged satisfies neither AC. Its fail-open behaviour is an ACCEPTED DECISION
  recorded in ADR-029 ('The guard is fail-open ... It must never become a deployment
  blocker'), so changing it requires an ADR amendment or superseding ADR authored
  by adr-author — not a silent code change. ADR-029's false claim that the hook is
  already wired must be corrected in the same edit.
- 'The whole-collection load must reuse the existing precedent rather than adding
  a second store loader: `check_ac_circular_deps.py` already builds a store-wide adjacency
  list from every on-disk record and then overlays the staged set. Reuse means EXTRACT
  that loader into a shared importable module both scripts depend on — not import-from-CLI,
  not copy-paste — with a no-regression guarantee on the existing hook''s behaviour.'
- Must complete a full pass over the present collection (~2,975 requirement records,
  33 decision records, 23 diagrams) in under 5 seconds at commit time. A commit-time
  gate slower than that gets bypassed, and a bypassed gate is precisely the failure
  GE-122d-2 exists to backstop. Prefer one directory walk per namespace over a per-file
  git invocation.
- 'Error handling per CLAUDE.md Rules 1-4: every filesystem and subprocess boundary
  wrapped with a specific exception type; every handler logs at WARNING or above or
  re-raises; no bare except; no try/except around pure comparison helpers. Ruff E722/BLE001/TRY
  are enforced at commit time.'
- 'Adding a new whole-collection guard is a structural change: `check-adr-coverage`
  and `check-structural-change` will demand an architecture-doc update and an ADR.
  Budget for an ADR authored by adr-author, and allocate its number by ADR-029''s
  rule (free only when it has neither a file nor a citation) rather than max+1.'
```
