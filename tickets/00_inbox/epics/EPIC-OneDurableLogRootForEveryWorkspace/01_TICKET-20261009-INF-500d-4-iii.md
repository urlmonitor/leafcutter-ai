## Acceptance Criteria

```gherkin
Given the same drive also reads its own configuration and also runs commit-time
  guards,
When the durable report location is determined,
Then the configuration still resolves to the workspace the drive is actually
  running under, and the commit-time guards still resolve to the tree they are
  judging,
And the durable report location is determined independently of both, resolving to
  the enduring project location rather than to the workspace root.

Given the operational log directory also holds the agent-telemetry log and the
  knowledge-emission log, which are written by the same drives with the same
  workspace-relative lifetime and are destroyed the same way,
When the durable location is adopted for the report sink,
Then the same durable location is adopted for every log in that directory, so the
  directory is not split across a disposable root and an enduring one.
```

## Implementation Notes

```yaml
- EXTEND THE ONE DECLARATION. build_knowledge_sink_declaration (scripts/build_phases_knowledge.py)
  must additionally write operational_log_root (absolute directory) and feedback_sink
  (<operational_log_root>/feedback.jsonl) into <output_root>/config/knowledge_sink.json.
  knowledge_emission_sink and operational_telemetry_stream stay, and every file-valued
  key must sit directly under operational_log_root. For an ordinary build the two
  existing values must stay byte-identical to today's (<target_root.parent>/debugging/logs/...),
  so existing installs and INF-400c-4-iii's identical-results invariant are unaffected.
  No second declaration artefact.
- 'THE ROOT IS AN INPUT TO THE BUILD, NEVER SOMETHING IT DISCOVERS. Default: <target_root.parent>/debugging/logs,
  as today. In addition the build must accept an explicit inherited log root (for
  example a --log-root argument) and record it verbatim. The value must be absolute;
  a relative value is refused with an error naming it. The build must not invoke git,
  walk upward, or look for marker files to choose the root (INF-400c-4-v: decide from
  what was recorded, never from what is around).'
- 'PROVISIONING: THE WORKTREE BOOTSTRAP PASSES THE ROOT THE MAIN INSTALL ALREADY RECORDED.
  templates/scripts/setup_ticket_worktree.py runs build.py --target-dir <worktree>
  in every new worktree. It must pass, as the inherited log root, the value read from
  the main install''s existing declaration at <main_repo>/.leafcutter/config/knowledge_sink.json
  — operational_log_root, or for a pre-feature declaration the parent directory of
  knowledge_emission_sink. It must NOT compute the root from main_repo''s path. In
  the development workspace main_repo is leafcutter-ai/ while the main install''s
  declared root is /home/henzeh/projects/leafcutter/debugging/logs, so computing it
  would create a fourth location. Mirror the change into scripts/setup_ticket_worktree.py,
  which is a tracked build output of the template, and never resync the whole file.'
- WHEN THE MAIN INSTALL'S DECLARATION CANNOT BE READ, SAY SO. If the bootstrap cannot
  read an enduring root from the main install (declaration absent, unreadable, keyless
  or relative), it must print a stderr WARNING naming the path it tried and stating
  that logs written in this worktree will not survive its removal. It must not leave
  behind a declaration that silently names the worktree's own root as operational_log_root.
  Whether that means omitting the root, so writers refuse per INF-500d-4-i, or refusing
  the bootstrap is the implementer's choice; the outcome must be loud either way.
- NO REGRESSION FOR SYMLINKED WORKTREES. A worktree whose .leafcutter is a symlink
  to the main install already reads the main install's declaration and must keep doing
  so.
- 'A bare manual build pointed at a worktree with no inherited root keeps INF-400c-4-v''s
  existing behaviour: it declares that directory and prints the NOTE. That NOTE must
  now also name the operational log root it declared.'
- SIDE-EFFECT-FREE LOCATION QUERY. Ship one CLI query, through sink_resolution.py
  or an entry point backed by it, that prints the absolute declared path for a named
  stream (feedback, telemetry, knowledge) or for the root. It must create no file,
  directory or record, and must refuse with a non-zero exit and a stderr message naming
  the expected declaration when the declaration is absent or the key is missing —
  the same refusal semantics as INF-400c-4-i's --print-sink. It is the one surface
  the BO-100d pre-drive probe, the prompt surfaces (INF-500d-4-vi) and plan-feature.js
  (INF-500d-4-iv) use to obtain a location, so none of them restates a path.
- PARITY CHECK EXTENDED, EXISTING BRANCHES UNTOUCHED. scripts/ci/check_sink_parity.py
  must also fail when operational_log_root or feedback_sink is missing or not absolute,
  when any file-valued key does not sit directly under operational_log_root, or when
  feedback_sink equals another stream. It must name the offending key and value. Branches
  1-3 (INF-400c-4) keep their current behaviour.
- RULES (a) AND (b) ARE NOT TOUCHED. Configuration still resolves to the workspace's
  own .leafcutter/ (INF-100c-1-i) and the guard root to the worktree toplevel (GE-113c-1-iv).
  The declaration FILE is read from the workspace's own deployed config, which is
  rule (a); only the VALUE it holds names the enduring root, which is rule (c). That
  is how the first scenario's 'determined independently of both' holds.
- The declaration holds a machine-specific absolute path, so it stays untracked (generated
  under the gitignored output root) and must be carried by the deploy manifest for
  any deployed reader.
- 'File-size ratchet: build_phases_knowledge.py (749 lines), build.py (2223) and setup_ticket_worktree.py
  (2379) are over the 400-line limit. Extract rather than grow, and never SKIP check-file-size.'
- 'Must handle errors gracefully per the project error handling policy: the declaration
  read in the bootstrap and the build-input validation must use typed except and report
  at WARNING or above.'
```
