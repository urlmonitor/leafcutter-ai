# A file whose name marks it as sensitive is still reported for its name — de-privileging the name signal must not delete it

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-123a-3` — A file whose name marks it as sensitive is still reported for its name — de-privileging the name signal must not delete it — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-123a-3`. Component: `guardrail-engine`. Assigned agent: `python-coder`. Estimated complexity: `S`. Complexity: `low`.

## Acceptance Criteria

```gherkin
Given a file whose name marks it as environment configuration, containing only
  ordinary configuration text that no content rule recognises,
And no suppression entries are in force,
When the file is scanned through the scanner's multi-file entry point — the
  same entry point the pre-commit secrets check calls,
Then exactly one finding is reported for that file, recording that the name
  itself marks the file as sensitive,
And the run's exit status reports findings present,
Because the name is a signal in its own right: a file of that kind is worth
  a second look even when nothing inside it is recognisable, and that is why
  the rule exists.

Given the same environment-configuration file, now also containing four lines
  the scanner's content rules recognise — a cloud access key in the AWS_KEY
  form, a private-key header line, a quoted twelve-character value assigned to
  a field named password, and a high-entropy token of at least twenty
  characters,
And no suppression entries are in force,
When the file is scanned through the same entry point,
Then the filename finding is reported alongside all four content findings,
And the filename finding is reported as its own separate result, not merged
  into, replaced by, or downgraded relative to any content finding,
Because reading the contents was added to the name check, not substituted for
  it — an implementation that reaches the content findings by dropping the
  name finding has traded one blind spot for another.

Given one file of every filename form the sensitive-filename rule recognised
  before this change, each containing only ordinary configuration text,
And no suppression entries are in force,
When all of them are scanned in a single run,
Then each of them reports its filename finding,
Because narrowing the set of names the rule recognises is the same deletion by
  another route, and it would be invisible to any criterion that exercises a
  single example name.
```

- [ ] AC-1: no suppression entries are in force
- [ ] AC-2: exactly one finding is reported for that file, recording that the name
- [ ] AC-3: the run's exit status reports findings present
- [ ] AC-4: no suppression entries are in force
- [ ] AC-5: the filename finding is reported alongside all four content findings
- [ ] AC-6: the filename finding is reported as its own separate result, not merged
- [ ] AC-7: no suppression entries are in force
- [ ] AC-8: each of them reports its filename finding

## Implementation Notes

```yaml
- 'The third arm''s filename set must be a FROZEN BASELINE captured from the sensitive-filename
  rule as it stands BEFORE this change, written into the test with its provenance
  recorded. It must NOT be derived at test time from the rule under test: a derived
  set narrows whenever the rule narrows and therefore cannot detect narrowing, which
  is the only thing this arm exists to catch.'
- The frozen baseline must include the bare dotted name, the dotted-name-with-suffix
  form, the stem-plus-extension form, and at least one case variant. A single example
  name cannot detect narrowing, and the criterion says 'every filename form' for that
  reason.
- Widening the recognised set is explicitly NOT a failure of this criterion; only
  narrowing is. Write the third arm so that a newly recognised form does not break
  it.
- The filename finding must be observed as its own separate result identified by its
  rule id and its own line number — never inferred from a total count. A count-only
  assertion cannot distinguish 'reported separately' from 'merged into, or downgraded
  relative to, a content finding', which is the exact failure the second arm exists
  to catch.
- All arms must run through the multi-file entry point scan_files over real files
  in a tempfile-backed directory, and the third arm must scan every baseline filename
  in a SINGLE run. Coverage of the filename matcher in isolation does not discharge
  any arm — that is how two sibling criteria in this family came to describe situations
  the real entry point can never produce.
- Exit-status arms must run the scanner's CLI entry point in a fresh subprocess with
  the fixture directory as the working directory, and must assert the process exit
  code. A returned list of findings is not an exit status.
- Test fixtures must assemble every credential-shaped string at runtime from concatenated
  fragments rather than writing it as a source literal, so this repository continues
  to need no PRIVATE_KEY or AWS_KEY suppression anywhere. The existing suppression
  test module does this deliberately; do not collapse the fragments back into literals.
- The ordinary configuration text used by the first and third arms must contain no
  token of twenty or more characters and no keyword-followed-by-quoted-value line,
  or 'exactly one finding' becomes an accident of the fixture rather than a statement
  about the scanner.
- The module under test must be loaded from the canonical templates/ path via importlib.util.spec_from_file_location,
  never from a deployed copy, which can be stale.
- No test may write a .security-allowlist to any real project root. Every arm of this
  criterion runs with no allowlist present in the fixture directory.
- Fixture files must not be placed under tickets/, docs/retrospectives/, docs/acceptance-criteria/
  or templates/skills/. The pre-commit consumer post-filters entropy findings for
  those path prefixes, which would silently change the expected counts.
- Reporting the filename finding on a file whose contents are innocuous is a deliberate
  accepted cost here. Whether that noise should be reduced is GE-123d's subject; no
  implementation of this criterion may reduce it by ceasing to report the finding.
```
