# A pass that could not see the whole collection never reports success

## Actor / Goal

## Acceptance Criteria

```gherkin
Given the collection contains an artifact belonging to a namespace the uniqueness pass is
  responsible for, which the pass cannot read or cannot parse — a record whose content is not
  well-formed, or a file the process is not permitted to open,
When the pass runs at the commit-time stage,
Then it does NOT report success,
And its output names the artifact it could not read,
And it states that uniqueness for that namespace was therefore not established,
And it states how many artifacts in that namespace it did read, so the size of the blind spot
  is visible rather than implied,
And the commit does not complete,

And when the same condition occurs at the shared-build stage, the build fails carrying the same
  three statements,

And when the same condition occurs at the authoring-time stage, the author is told the same
  three statements in-session, and the write they just made is not reverted,

And in all three cases the reported outcome is distinguishable by a caller from an ordinary
  clean pass without parsing prose — a could-not-establish result, not the value a clean run
  produces.

Coverage note: covered only by a test that creates the genuine unreadable or unparsable
condition on disk and executes the pass against it, asserting the outcome value, the named
artifact, and the read count. Simulating the condition by patching the pass's own return value
tests the caller, not the pass, and does not cover this criterion.
```

## Implementation Notes

```yaml
- The outcome must be a distinct VALUE in the pass's return type — three states at
  minimum (clean, contested, could-not-establish) — not an exit code plus prose. GE-119a-1
  requires machine-distinguishability independently of the exit code, and GE-122d-3-i
  then adds a fourth (terminated-abnormally) whose disposition differs at commit time.
  A boolean return makes both criteria unsatisfiable and is the shape to reject at
  review.
- The read count must be tracked per namespace DURING the walk, not derived afterwards
  from what was successfully parsed. A count computed from the successes is the same
  number in both the clean and the degraded case, which defeats the entire clause
  — the blind spot is precisely the difference between attempted and succeeded.
- 'DIRECT CONFLICT WITH AN ACCEPTED DECISION, to be resolved rather than absorbed:
  ADR-029 records that the decision-number guard is fail-open and ''must never become
  a deployment blocker'' — meaning git unavailable, directory absent or network failure
  warns and exits 0. Under this criterion, an inability to read the origin/main side
  of the decision namespace is a could-not-establish condition and must block at commit
  time. Adopting that guard into this pass requires an ADR amendment or superseding
  ADR authored by adr-author, landed with the behaviour change, not after it.'
- 'Distinguish cannot-read-the-subject from cannot-run-at-all with care: a git invocation
  that fails while resolving the in-flight side of the decision namespace is a cannot-read
  condition (part of the collection was not seen), whereas a defect in the pass''s
  own reporting code after every namespace was read is GE-122d-3-i''s case and does
  not block. The pass already knows which it is, because it tracks the per-namespace
  read counts this criterion requires.'
- The authoring-time disposition — announce in-session, do not revert — must be implemented
  through the PostToolUse block-decision channel, the same channel GE-122c-1 uses
  to reach the session. There is no other way for that stage to say anything, and
  the author's file must remain on disk.
- 'Error handling per CLAUDE.md Rules 1-4: the unreadable-file branch catches a specific
  exception type (OSError / PermissionError for access, the parser''s own error for
  malformed content), logs at WARNING or above, and converts to the could-not-establish
  outcome rather than re-raising into an unhandled traceback. A traceback at commit
  time is not the same as a could-not-establish result and does not satisfy the criterion.'
- The test fixture must create the real conditions on disk — a genuinely malformed
  record and a genuinely unreadable file (mode 000) — per the coverage note. Note
  that a mode-000 fixture behaves differently when tests run as root (in some CI containers
  the read succeeds), so the unreadable-file test must either skip explicitly with
  a stated reason on that platform or use a condition that holds regardless; a silently-passing
  permission test is a false green.
```
