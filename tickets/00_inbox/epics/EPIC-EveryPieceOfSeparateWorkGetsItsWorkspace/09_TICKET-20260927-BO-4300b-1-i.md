# Starting inside another workspace never nests the new one there or roots it on that work

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `BO-4300b-1-i` — Starting inside another workspace never nests the new one there or roots it on that work — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `BO-4300b-1-i`. Component: `build-orchestration`. Assigned agent: `python-coder`. Estimated complexity: `S`. Complexity: `low`.

## Acceptance Criteria

```gherkin
Given the request for "beta" is started from inside workspace W1, whose line of
  work carries one commit not on the shared main line, and which has one
  uncommitted change,
When the request is answered ready,
Then the "beta" workspace sits beside W1 in the landing place, not inside W1,
And "beta"'s line of work starts at the shared main line tip, and W1's commit
  is not reachable from it,
And W1's files, its uncommitted change and its line of work are identical
  before and after the request.
```

- [ ] AC-1: the "beta" workspace sits beside W1 in the landing place, not inside W1
- [ ] AC-2: "beta"'s line of work starts at the shared main line tip, and W1's commit
- [ ] AC-3: W1's files, its uncommitted change and its line of work are identical

## Implementation Notes

```yaml
- Starting inside a workspace resolves to the project it was made from (see BO-4300b-1);
  the new workspace's base is the hub's main tip, never the current workspace's HEAD
  or branch.
- Proof runs the DEPLOYED maker -- the copy an install delivers, resolved through
  the shared test locator delivered by BO-4300f-4 -- as a separate process against
  real temporary git repositories with a real bare hub. No mock of git, no import
  of the maker module, no grep of its source (CLAUDE.md 'Gate / Workflow ACs -- Verify
  Behaviorally, Not by Grep'); a test never falls back to the templates/ source copy.
- 'Tests must not spawn the package''s own scripts/build.py (CLAUDE.md ''Tests must
  not spawn their own build.py''): the deployed maker comes from the shared deployed
  layout, and fixture projects carry a minimal stub build entry point that installs
  a real, rejecting hook in well under a second. A test that must mutate the package
  and build its own copy says so and justifies it in its ticket.'
- All temporary projects, hubs and workspaces live under the test's temp directory
  and run git with an isolated global and system config; afterwards the developer's
  own repository's branches, registered worktrees and local git config are unchanged
  (BO-4300f-4-i, F14, KI-TQ-012).
```
