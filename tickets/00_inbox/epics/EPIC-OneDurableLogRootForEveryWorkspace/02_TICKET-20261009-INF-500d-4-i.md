# When the enduring location cannot be determined, the sink says so rather than quietly using the disposable one

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `INF-500d-4-i` — When the enduring location cannot be determined, the sink says so rather than quietly using the disposable one — so that the acceptance criterion is satisfied.

## Context

## Acceptance Criteria

```gherkin
Given the durable report location cannot be determined because the install's
  build-time declaration of its durable log location is unusable in one of these
  ways: it is absent, it cannot be read, it cannot be parsed, it lacks the report
  sink or log root entry, it records a location that is not absolute, or it is
  stale (the enduring project root it records no longer exists),
When a report is filed and the durable report location is resolved,
Then no file and no directory is created anywhere: not in the temporary workspace
  directory, not at a location derived from where the caller is running, and not
  at or above the declared log location,
And the write is refused with a failure reason that names the expected declaration
  and which of those conditions failed,
And no record identifier is returned to the caller,
And the agent's verdict is still delivered.

Given the install's build-time declaration is usable, recording an absolute
  durable log location beneath an enduring project root that exists,
And the project is not under version control at all, or the version-control
  tooling is unavailable to the caller,
When a report is filed,
Then the report is written to the declared location, and the sink location the
  writer reports lets the caller confirm it is not the disposable workspace,
So that version control plays no part in deciding where reports are kept.

Given a project that uses no temporary workspaces at all, so the drive runs
  directly in the ordinary project checkout,
When a report is filed,
Then it is written to the same durable location that a workspace-based drive
  would have used, and is readable there,
So that consumer projects without the worktree-per-drive convention are not
  given a second, divergent storage location.
```

## Implementation Notes

```yaml
- 'WHAT ''CANNOT BE DETERMINED'' MEANS UNDER THE ADOPTED MECHANISM. The enduring location
  is the build-time declaration (INF-500d-4, rule (c) as superseded), so it is undeterminable
  exactly when <output_root>/config/knowledge_sink.json is absent, unreadable or unparseable,
  lacks the feedback_sink or operational_log_root key, holds a value that is not absolute,
  or is STALE in INF-400c-4-v''s sense (the declared directory''s enduring project
  root no longer exists). Each of these must take the refusal branch. Version control
  plays no part in resolution any more: a project with no repository, or a caller
  with no git on PATH, resolves normally from its declaration. The criteria''s first-scenario
  examples (''not under version control'', ''tooling unavailable'') are therefore
  exercised as SUCCESS cases that land in the declared location — the caller confirms
  it is not the disposable workspace from INF-500d-4-ii''s ''[submit_feedback] sink:
  <path>'' line — and the refusal branch is exercised through the declaration cases
  above. See caveat: the Given wording should be updated by the BA.'
- NO SILENT FALLBACK, IN ANY FORM. In every undeterminable case the writer must not
  write to a path derived from __file__ (the _find_project_root walk for .claude/
  that KI-FC-001 identifies as the root cause), from the current working directory,
  or from the worktree root. Nothing is written anywhere.
- 'THE REFUSAL MUST BE LOUD AND LEGIBLE: one stderr line naming the expected declaration
  path and which condition failed (absent, unreadable, missing key, not absolute,
  stale), a non-zero exit, nothing on stdout, and no sidecar id file. An empty stdout
  is what stops every FB_ID=$(...) caller from mistaking a refusal for a captured
  id.'
- 'The refusal reason must map to INF-500d-3''s ''the destination could not be written''
  reason, or to a distinct closed-set reason if INF-500d-3 adds one. It must never
  present as ''written but the identifier was not captured'', because nothing was
  written: that keeps the submission eligible for INF-500d-5''s hold queue, where
  a written-but-uncited record must never go.'
- 'THE VERDICT IS STILL DELIVERED (bounded by INF-500d-3). A refusal must not raise
  into its callers: emit_hook_finding.py''s in-process call must stay failure-isolated,
  and the signoff path''s existing submit-failed marker route must keep working unchanged.'
- DO NOT CONJURE THE ENDURING ROOT. The writer may create only the final log directory
  beneath an enduring project root that already exists (the ordinary first-write case).
  It must never create the project root or any directory above the log directory,
  because that turns a stale install into a healthy-looking empty one (INF-400c-4-v).
- SECOND SCENARIO, NO SECOND LOCATION. A plain-checkout install's build declares <target_root.parent>/debugging/logs,
  and a worktree-based drive of that install inherits the same recorded value (INF-500d-4-iii),
  so both resolve to one location without any branch on whether worktrees are in use.
  The writer must not contain a worktree-detection branch.
- An explicit --jsonl override stays the caller's responsibility and is never refused
  (the same rule as the harvester's --sink), and INF-500d-4-ii's sink line still reports
  where it went.
- 'templates/scripts/feedback/submit_feedback.py is over the 400-line check-file-size
  limit (637 lines): resolve and refuse through an extracted helper or a shared declaration
  reader, leave the file within the ratchet, and never SKIP check-file-size.'
- 'Must handle errors gracefully per the project error handling policy: wrap the declaration
  read in typed except, report at WARNING or above, and never swallow silently.'
```
