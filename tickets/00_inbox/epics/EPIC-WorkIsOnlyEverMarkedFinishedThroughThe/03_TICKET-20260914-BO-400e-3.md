# One door: the finished state is only ever written by the mechanism that checks it, and the blanket override is not the way through

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `BO-400e-3` — One door: the finished state is only ever written by the mechanism that checks it, and the blanket override is not the way through — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `BO-400e-3`. Component: `build-orchestration`. Assigned agent: `python-coder`. Estimated complexity: `L`. Complexity: `high`.

## Acceptance Criteria

```gherkin
Given a ticket that a drive is about to close,
  And two routes by which its recorded state could today be set to finished -- the
    mechanism that reads the ticket's record and checks it, and a direct edit of that
    record by whoever was asked to close the ticket,
When the drive closes the ticket,
Then the ticket's record is written to the finished state by the checking mechanism and
  by nothing else,
  And the instruction under which the close is carried out names that mechanism as the
    route and does not describe editing the recorded state directly,
  And the close is carried out without the blanket override -- the one that switches off
    the allowed-transition rules along with the check -- so a close that only succeeds
    because the override was passed is not a close through this door,
And given the same ticket and a run in which the checking mechanism refuses,
When the drive reaches the close,
Then no finished state appears on that ticket by any route: the recorded state is
  unchanged, and the run reports the ticket as not closed rather than closing it another
  way,
And given the same ticket carried instead by the driver that carries a single ticket
  rather than a whole epic,
When that driver closes it,
Then the close goes through the same mechanism and produces the same recorded state,
So there is exactly one way the finished state is ever reached, and the route that
  bypasses the check is closed rather than discouraged.
```

**1. Impact summary.** Confirmed by direct inspection: `build-feature.js` (~line 1305)
and `build-ticket.js` (~line 1145) both dispatch `status-checker` with the literal
instruction "Edit the ticket's frontmatter so that 'status:' reads done. Change nothing
else" — this is the only completion-write instruction either driver contains; neither
ever invokes `scripts/set_ticket_status.py`. This is the second door named by the AC, and
it is currently the *only* door actually exercised by a real drive. By contrast,
`templates/agents/status-checker.md`'s own user-gated (`## Closing protocol`, line ~130)
and auto-close (line ~176) paths already correctly invoke
`python scripts/set_ticket_status.py --ticket <path> --status done` and already warn
against `--force` without explicit user authorization. `scripts/set_ticket_status.py`
itself is already correct and matches ADR-046's Decision §2/§7: `_get_needed_agents`
reads only the ticket's own `agents:` map, has no exclusion parameter, and a refusal
(exit 1) performs no write. Blast radius is contained to exactly the 4 `files_touched` —
a repo-wide grep for the offending instruction string found it in only the two named
driver files, and no third caller of the direct-edit pattern exists.

**2. Risks (beyond what the ticket's own Implementation Notes already anticipate).**
The highest-value finding: `set_ticket_status.py`'s unforced `ALLOWED_TRANSITIONS` is
`{(todo, in_progress), (in_progress, done), (in_progress, todo)}`; `(todo, done)` is only
in `FORCE_ALLOWED_TRANSITIONS`. Neither `build-feature.js` nor `build-ticket.js` (grepped
directly) ever transitions a ticket to `status: in_progress` anywhere in the drive. Today
this is invisible because the direct-frontmatter-edit route is a raw string replacement
with no transition validation at all. The moment the completion-write step is routed
through `set_ticket_status.py` as specified, an ordinary ticket sitting at `status: todo`
(the common case — this very ticket is at `status: todo` right now) will have its
`todo -> done` request rejected by the transition allow-list, **not** by the parity
check the AC is actually testing for. That failure mode looks identical to "the checking
mechanism refused" from the outside, but it is a different, mechanical gap, and it
creates exactly the pressure the AC forbids: an implementer under deadline pressure who
sees every ordinary close fail will be tempted to reach for `--force` to make the
`todo -> done` case work, which both bypasses the parity check the AC is testing AND is
the "narrower override wearing a different name" the ticket explicitly rules out.
**This must be fixed by widening the unforced `ALLOWED_TRANSITIONS` set in
`scripts/set_ticket_status.py` to include `("todo", "done")`, not by passing `--force`
and not by adding a new driver-side `in_progress` transition step (out of scope, adds a
fifth location to the n_location_rule).** Widening the transition allow-list is a
data-table change to the one already-in-scope file, does not add a caller-supplied
parameter, and does not touch the parity check (the actual safety property) at all — it
only removes an artificial lifecycle-visitation requirement that the direct-edit route
was silently ignoring anyway. Recommend adding this as an explicit acceptance-criteria
adjustment (see below) so `test-writer` covers it and `python-coder` does not discover it
only when the reachability harness goes red.

**3. Design decisions.** (a) The fix is correctly framed as making the drivers' dispatch
prompt to `status-checker` name the same mechanism `status-checker.md` already uses for
its own closing protocol, rather than inventing a second implementation — prefer wording
that explicitly cites `set_ticket_status.py` and forbids `--force` on the ordinary path,
mirroring the existing closing-protocol prose almost verbatim. (b) The refusal-surfaces-
as-not-closed requirement (AC-5/AC-6) requires the JS driver side (not just the prompt)
to interpret a non-zero/blocker-shaped response from `status-checker` as "not closed" in
its own run report — this is a second sub-location inside each of the two driver files
(the dispatch-prompt text AND the result-interpretation branch), which the ticket's
`n_location_rule: 4` treats as one location; confirm both halves are actually touched.
(c) Because the enforcement here is partly a natural-language instruction followed by an
LLM sub-agent and partly a real script's exit code, `harness_build_ticket_guard.mjs`
(already required by the Test Requirements) is the only artifact that can distinguish "the
prompt says the right thing" from "the prompt is actually obeyed" — this reviewer agrees
with and reinforces the ticket's own "verify by execution, never by grep" instruction.

**4. Acceptance-criteria adjustments.**
- [added] Cover the `todo -> done` unforced-transition case explicitly: drive an ordinary
  ticket that starts at `status: todo` (not `in_progress`) through a real close and assert

- [added] Assert that when `set_ticket_status.py` refuses for a *transition-allow-list*
  reason (not just a parity reason), the run still reports "not closed" rather than
  retrying with `--force` — this closes the exact escape hatch identified in Risk 2 above.
- [added] Assert both driver files' result-interpretation branch (not just their dispatch
  prompt text) treats a `status-checker` blocker/refusal response as "not closed" in the

**5. ADR recommendation.** `ADR-046` (created by sibling ticket `BO-400e-1`, same two

duplicate its reasoning. However, ADR-046 is scoped to *which phases are checked*
