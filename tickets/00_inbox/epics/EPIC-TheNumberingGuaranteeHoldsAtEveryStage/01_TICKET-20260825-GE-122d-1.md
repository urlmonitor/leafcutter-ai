# One rule, evaluated at three stages, cannot give three different answers

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-122d-1` — One rule, evaluated at three stages, cannot give three different answers — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-122d-1`. Component: `guardrail-engine`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given a collection containing exactly one contested number,
When the numbering rule is evaluated at the authoring-time stage, at the commit-time stage,
  and at the shared-build stage, each over that same collection,
Then all three stages identify the same contested number and name the same set of claimant
  paths,

And given the rule is then extended so that a number shape previously accepted is now
  contested, with that extension made in ONE place,
When all three stages are evaluated again, with no edit made to any second or third definition
  of the rule,
Then all three stages report the newly contested case,

And there is no collection for which one stage reports a clean result while another stage
  reports a contested one.

Coverage note: covered only by a test that actually invokes all three stages against one
fixture collection and compares their verdicts, plus a test that makes a single rule change and
re-invokes all three. A test asserting that three registrations point at the same script name
does not cover it — identical registration does not establish identical evaluation, and it
passes on three stages that all silently no-op.
```

- [ ] AC-2: all three stages identify the same contested number and name the same set of claimant
- [ ] AC-3: given the rule is then extended so that a number shape previously accepted is now
- [ ] AC-4: all three stages report the newly contested case
- [ ] AC-5: there is no collection for which one stage reports a clean result while another stage

## Implementation Notes

```yaml
- The shared element is GE-122a-1's evaluation module, imported by all three stage
  entry points. Each stage owns only its own adaptation — reading its input, rendering
  its output and choosing its disposition — and none may hold a copy of the rule.
  A stage-specific special case is the thing this criterion is written to make fail.
- 'THE HARD PART IS DEPLOY-PATH, NOT DESIGN. The three stages run from two different
  deployed layouts: the authoring-time hook from `.claude/hooks/`, the commit-time
  and build-time stages from `.leafcutter/scripts/commit_guardian/`. One shared module
  must be importable from BOTH, which means it must appear in both deploy paths in
  `scripts/build_phases.py` (or be placed where both already resolve). Getting this
  wrong presents as the authoring stage silently emitting nothing while the other
  two work — a three-way disagreement in exactly the shape this criterion forbids,
  and invisible to source-tree unit tests.'
- 'Follow the precedent the `AC store valid` job records: the build stage should invoke
  the commit-time gate THROUGH pre-commit rather than calling the script directly,
  ''so the merge-time and commit-time rule sets are literally the same config and
  cannot drift apart''. That collapses two of the three stages to one configuration
  by construction, leaving only the authoring stage to reconcile.'
- The single-rule-change test needs a real, minimal extension seam — the rule's recognised
  number shapes must be data or a single named constant, so that 'made in ONE place'
  is a meaningful instruction rather than a matter of the tester's judgement about
  which edit counts. Name that seam in the implementation.
- Verify by executing all three stages, never by comparing registrations. Three registrations
  pointing at one script name is satisfied by three stages that all silently no-op
  — and this repository already holds guards that are registered nowhere and guards
  that are deployed and never invoked, so the presence of a name proves nothing.
- Error handling per CLAUDE.md Rules 1-4; the per-stage dispositions on cannot-establish
  and internal-defect conditions come from GE-122d-3 and GE-122d-3-i and are the ONLY
  sanctioned differences between the three stages' behaviour. Any other divergence
  fails this criterion.
```
