# A workspace's supporting material is its own, not another session's

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `BO-4100b-3` — A workspace's supporting material is its own, not another session's — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `BO-4100b-3`. Component: `build-orchestration`. Assigned agent: `python-coder`. Estimated complexity: `L`. Complexity: `high`.

## Acceptance Criteria

```gherkin
Given two workspaces exist at the same time, each created through the normal
  creation path,
When a check running inside the first workspace resolves the supporting
  material it reads,
Then the material it resolves to belongs to the first workspace and not to the
  shared install tree or to the second workspace,
And when the first workspace's supporting material is replaced or repaired,
  the shared install tree's supporting material is byte-identical before and
  after,
And the second workspace's supporting material is byte-identical before and
  after.
```

## Implementation Notes

```yaml
- _establish_pre_commit_config currently prefers os.symlink(<main_repo>/.leafcutter,
  <worktree>/.leafcutter). That symlink IS the structural cause of both harms in BO-4100b
  -- it makes the workspace's supporting material an alias of the shared install tree.
  Replacing it with a per-workspace materialisation is the change. Leaving the symlink
  in place and adding a guard on top of it is not.
- A check running inside a workspace must reach that workspace's own copy through
  the resolution the guardian scripts already share, not through per-hook path logic.
  Today several hooks resolve their root from __file__ of the RESOLVED symlink target,
  which lands them in the shared install tree -- that resolution path is in scope
  and must be fixed at the shared resolution point, not hook by hook.
- The .security-allowlist dual-update workaround documented in CLAUDE.md exists only
  because of this symlink. If the per-workspace copy makes it unnecessary, that instruction
  must be corrected in the same change; a stale workaround for a removed defect is
  a second source of confusion.
- Byte-identity of the shared install tree and of the other live workspace must be
  established by recursive content hashing of the whole tree, never by mtime, size
  or a spot check of a few files.
- The Windows/NTFS fallback branch must keep working. A workspace on a filesystem
  where os.symlink raises must still get its own supporting material, or the fix makes
  those installs unbootstrappable.
- Per-workspace materialisation must not push workspace creation outside its current
  latency budget. A copy-on-write or hardlink arrangement is acceptable provided a
  write inside one workspace is not observable in any other and not observable in
  the shared install tree.
- ADR-031's create-time and pre-drive quality-gate guards must continue to pass against
  the per-workspace copy. This record changes WHERE the material lives, not WHETHER
  the gates run; proof that checks genuinely fire is BO-1700a and must not be re-derived
  here.
- Template and deployed copies of setup_ticket_worktree.py change together and are
  verified in parity via the build.py round-trip (ADR-001).
```
