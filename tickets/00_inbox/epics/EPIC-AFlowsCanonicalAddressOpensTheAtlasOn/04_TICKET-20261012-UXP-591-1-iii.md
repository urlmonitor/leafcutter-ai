## Acceptance Criteria

```gherkin
Given leafcutter/flow-render-pipeline exists and its canonical address is
  /flows/leafcutter/flow-render-pipeline,
When a person opens /flows/leafcutter%2Fflow-render-pipeline (the '/' inside the flow id
  percent-encoded as %2F), or /flows/leafcutter/flow-render-pipeline/ (a trailing slash),
Then the Atlas answers 404 and shows the 'Flow not found' state for each address; it does not
  redirect to /flows/leafcutter/flow-render-pipeline and does not draw that flow,

  /flows/leafcutter/deliver-a-feature, and offers an 'Open the Flows view' link to /flows,
And no flow is drawn, the breadcrumb is empty and the flow selector is shown with Source Real,
  Kind User and Realization All,
And the address bar keeps the address as opened, %2F or trailing slash included, so the link
  can be corrected.
```

## Implementation Notes

```yaml
- 'Build risk carried from the BA: with trailingSlash false (the default) Next.js
  14 answers a trailing-slash path with its own 308 to the slash-less path before
  middleware or routing runs, which would turn /flows/leafcutter/flow-render-pipeline/
  into the flow. Set skipTrailingSlashRedirect: true in leafcutter-web/next.config.mjs
  so the request reaches leafcutter-web/middleware.ts unchanged (owner decision 2026-10-09).'
- skipTrailingSlashRedirect is app-wide by owner decision 2026-10-09. Every request
  path other than '/flows/<one or more characters>/' keeps today's behaviour, a 308
  to the slash-less path (including /flows/ -> /flows and /atlas/ -> /atlas), re-implemented
  in leafcutter-web/middleware.ts; its config.matcher therefore reaches every page
  and API route while still skipping _next/static, _next/image and static files.
- 'leafcutter-web/middleware.ts classifies the raw request path as received, before
  any decoding (the pathname of request.url keeps ''%2F''): a /flows/ path that contains
  an encoded slash (''%2F'' or ''%2f'') or ends in ''/'' is marked not-found and passed
  on with its raw id (e.g. a request header the catch-all route checks before calling
  notFound(), or a rewrite to a path the route always 404s). It is never decoded and
  matched to an existing flow.'
- 'Defence in depth: the catch-all route independently 404s any id that is not exactly
  two path segments, so a ''%2F'' that some layer decodes into one segment still cannot
  resolve to leafcutter/flow-render-pipeline. The two checks are independent and each
  alone is sufficient.'
- 'Middleware runs in the Next.js 14 Edge runtime (no node:fs, no flow store): it
  decides on the shape of the address only, never on whether a flow exists; existence
  stays in the server route.'
- The 404 status, the quoted raw id and the product-and-flow notice wording reuse
  the UXP-591-1-ii not-found boundary and request-scoped id channel; no second not-found
  UI.
- 'leafcutter-web/middleware.ts already holds the UXP-608 mock-mode gate and Next.js
  allows one middleware file: extend it without changing that gate''s behaviour; leafcutter-web/__tests__/route-gating.test.ts
  stays green.'
- Per-request middleware work is constant-time string checks with no I/O.
- Unit tests cannot observe Next.js's own trailing-slash redirect or path decoding,
  so the 404 for both addresses is proven by this AC's Playwright spec in leafcutter-web/e2e/,
  run in CI against `next build` + `next start` (status 404, no Location header, notice
  shown; owner decision 2026-10-09; harness set up under UXP-591-1).
```
