# A component-level declaration block names the criteria the file serves

## Actor / Goal

## Acceptance Criteria

```gherkin
Given a staged screen component file whose leading comment block contains the
  line "@ac UXP-607, UXP-607-1"
When the frontend declaration reader evaluates the file
Then the file's declared criteria are recorded as the ordered list
  ["UXP-607", "UXP-607-1"]
And the file's declaration verdict is "declared"
And the literal comment text is recorded alongside the parsed list so a
  reviewer sees what was written, not only what was parsed

Given a staged screen component file whose leading comment block contains the
  line "@ac UXP-100d-2"
When the frontend declaration reader evaluates the file
Then the file's declared criteria are recorded as the single-item list
  ["UXP-100d-2"]
And the file's declaration verdict is "declared"

Given three staged screen component files whose declaration lines read
  "@ac UXP-607, UXP-607-1", "@ac UXP-607 UXP-607-1" and
  "@ac UXP-607,UXP-607-1" respectively
When the frontend declaration reader evaluates each file
Then all three files record the identical ordered list
  ["UXP-607", "UXP-607-1"]
```

- [ ] AC-2: the file's declaration verdict is "declared"
- [ ] AC-3: the literal comment text is recorded alongside the parsed list so a
- [ ] AC-4: the file's declared criteria are recorded as the single-item list

## Implementation Notes

```yaml
- ONE READER, TWO TIERS. The declaration parse lives in a single new module — canonical
  source templates/scripts/commit_guardian/_frontend_declaration_reader.py, deployed
  twin scripts/commit_guardian/_frontend_declaration_reader.py. Both the commit-tier
  check (GE-124c) and the CI-tier gate (GE-124e) import it; neither may re-parse declarations
  privately. Two parsers of one comment grammar drift, and the user-visible symptom
  is one tier accepting what the other rejects.
- DEPLOY-MANIFEST OBLIGATION. Add the new reader module to the commit-guardian deploy_map
  in scripts/build_phases.py in the SAME change that creates it, and edit the templates/
  source and scripts/ deployed copy together (ADR-001 round-trip). A hook dependency
  absent from the deploy manifest raises ModuleNotFoundError in the deployed layout
  while every source-tree test stays green — done_proof.py shipped exactly that way
  on 2026-07-22.
- Parse the STAGED blob, not the working-tree file. The commit tier must read content
  through git's index (as check_ac_schema Phase 2 does), so a declaration typed in
  the editor but not staged does not clear the check.
- SEPARATOR GRAMMAR IS PERMISSIVE, ORDER IS NOT. Accept any run of commas and/or whitespace
  between ids on the @ac line; preserve the authored order in declares[]; never sort
  and never de-duplicate distinct ids. A reader accepting only one separator form
  emits a false 'missing' verdict, which teaches authors the check is wrong.
- Ids are opaque strings at parse time. This AC must NOT consult the acceptance-criteria
  store — whether an id resolves is GE-124c-2's question, answered by the shared resolver.
  A parser that resolves inline makes the missing-versus-unresolved verdict split
  impossible to keep apart.
- Emit a stable record {path, framework, role, declaration_block, declares[], verdict}
  and keep it structurally parallel to GE-124b-1's pin record, so one reporter formats
  both surfaces and GE-124c-1-i can deduplicate per (subject, code).
- Pure text scan — no JavaScript/TypeScript AST dependency. A Python pre-commit hook
  has no JS toolchain, and the whole staged set must be read within the pre-commit
  latency budget (target under 2s for a typical staged set).
- Must handle errors gracefully per the project error handling policy (CLAUDE.md Rules
  1-4); a single unreadable file is GE-124c-3-i's contract, never a crash.
```
