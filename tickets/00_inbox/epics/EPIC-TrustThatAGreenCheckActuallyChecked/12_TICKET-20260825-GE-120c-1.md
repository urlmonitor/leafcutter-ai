# A harness executes the deployed checks out of process from a real separate working copy

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-120c-1` — A harness executes the deployed checks out of process from a real separate working copy — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-120c-1`. Component: `guardrail-engine`. Assigned agent: `test-writer`. Estimated complexity: `L`. Complexity: `high`.

## Acceptance Criteria

```gherkin
Given a verification harness for the guardrail engine's checks,
When it exercises a check,
Then it creates a real second working copy of the repository, stages real files in it, and
  invokes the check as a separate process in the way the commit path invokes it,
And it asserts on what that process observably produced — its result status and the text it
  wrote for the reader — and on nothing imported from the source tree,
And the source tree is not on the import path of the process under test, so a check that can
  only find its prerequisites via the source tree fails the harness rather than passing in
  it,
And the harness reports, per check exercised, the result status and output text from each of
  the two working copies, so a disagreement can be read directly rather than inferred from a
  failed assertion,
And a harness case that only searches a check's source text for a string is not accepted as
  coverage for any criterion in this tree.

Coverage note: the third clause is the one that distinguishes this harness from the tests
that already exist. Demonstrate it by pointing the harness at a check that resolves its
prerequisites only via the source tree and showing the harness fails — a harness that cannot
be made to fail is not evidence (CLAUDE.md, "Gate / Workflow ACs — Verify Behaviorally, Not
by Grep").
```

## Implementation Notes

```yaml
- 'BINDING CONSTRAINTS (these are the requirement; the mechanism below is a recommendation).
  (1) The process under test must not be able to import from the source tree: scrub
  PYTHONPATH, run the interpreter in isolated mode, and do not set cwd to the source
  tree. (2) The deployed layout must be what the check sees: .leafcutter/scripts/commit_guardian/
  inside the second copy, produced by running ''python scripts/build.py --target-dir
  <copy>'' there. (3) The invocation must match the real commit path in shape — ''python
  .leafcutter/scripts/commit_guardian/run_hook.py .leafcutter/scripts/commit_guardian/<check>.py
  <staged files>'' as .pre-commit-config.yaml declares it (line 294 for check-ac-parent-covered-by)
  — plus the direct-script shape used by precommit-canary.'
- 'OPEN QUESTION ANSWERED — recommended mechanism: ''git worktree add'' into a temporary
  directory at the same commit, then build into it. It matches how people actually
  work, which is the L1''s stated standard, and it gives real staged files via a real
  git index. CAVEAT TO HANDLE: a worktree SHARES the git object store, so the harness
  must not run concurrently with another drive in the same repository, and must clean
  up with ''git worktree remove'' even on failure. A copied tree is acceptable if
  staging can still be exercised; a clone is safest under concurrency and slowest.
  Record which was chosen and why — the behavioural requirement is only that the source
  tree is not importable and the deployed layout is what the check sees.'
- 'THE HARNESS ASSERTS ONLY ON THE SUBPROCESS''S OBSERVABLE OUTPUT: exit status, the
  result value carried in its output, and the text it wrote. It must not import any
  check module, any commit_guardian helper, or _resolve_root.py. Importing anything
  from the source tree reintroduces the exact blindness this harness exists to remove.'
- Per check exercised, record and print result status plus output text FROM BOTH copies,
  side by side, so a disagreement is readable directly rather than inferred from a
  failed assertion. This report is the artifact GE-120b-1, GE-120b-3 and GE-120b-4
  consume.
- A grep or source-text harness case is NOT acceptable coverage for any criterion
  in this tree. Encode that as a rule the harness enforces on its OWN case definitions
  — a review convention will not survive the fourth author.
- 'SELF-DEMONSTRATION IS A DELIVERABLE, not a nice-to-have: point the harness at a
  check that resolves its prerequisites only via the source tree (any of the 19 un-migrated
  files listed in GE-120b-2, before that AC migrates it) and show the harness FAILS.
  A harness that cannot be made to fail is not evidence.'
- 'HOME: unit_tests/portability/, which already holds test_build_deployment.py, the
  existing deployed-layout test. Do NOT place it in unit_tests/commit_guardian/, whose
  tests import from the source tree — that directory is the layout the defect hides
  in, and a harness living there will be tempted into the same import.'
- 'RUNTIME BUDGET: the sweep builds a second copy and spawns one process per manifest
  check (54 today, 108 across both copies). Build each copy ONCE per sweep, never
  per check, and mark the sweep slow rather than letting it quietly narrow its subject
  list to stay fast.'
- 'Error-handling policy applies to the harness''s own subprocess and filesystem calls:
  specific exceptions, logged at WARNING, never swallowed — and per GE-120c-1-i a
  setup failure is a reported failure, not a skipped case.'
```
