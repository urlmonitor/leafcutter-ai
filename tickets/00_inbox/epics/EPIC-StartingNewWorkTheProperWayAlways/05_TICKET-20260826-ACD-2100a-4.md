# A pause record written from inside a worktree is found again by the run that resumes

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `ACD-2100a-4` — A pause record written from inside a worktree is found again by the run that resumes — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `ACD-2100a-4`. Component: `ac-driven-dev`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given a run started with the process working directory set to a git worktree of
  the project that holds no installed copy of the route's own support files,
When the run records that it is waiting for a person's answer,
Then a pause record for that run exists on disk in the project's own store after
  the process has exited,
And no pause record has been created underneath the directory the run started in,
And a second run started from a different working directory -- the project root
  -- finds that same record and reports the run as waiting,
And the run that wrote the record reported the write as failed if and only if no
  record is present on disk.
```

- [x] AC-1: a pause record for that run exists on disk in the project's own store after
- [x] AC-2: no pause record has been created underneath the directory the run started in
- [x] AC-3: a second run started from a different working directory -- the project root
- [x] AC-4: the run that wrote the record reported the write as failed if and only if no

## Implementation Notes

```yaml
- The change must land under templates/. The deployed workflow and the deployed pause-store
  script are both build output.
- All three pause-store sites -- the read, the write and the read-back verification
  -- must resolve through the same repository-anchored resolution. Fixing the write
  alone leaves a run that writes correctly and then cannot find its own record.
- The store location must be a function of the project being operated on, never of
  the caller's working directory, so that a writer in a worktree and a reader at the
  project root address the same location.
- The reported write outcome must be established by observing the record after the
  write, not by the absence of a thrown error. A writer that reports success while
  writing nowhere passes every return-value assertion.
- The write must be durable before the process exits -- a record buffered and lost
  on exit is indistinguishable from a run that never paused.
- 'Must satisfy the repository error-handling policy: the read, the write and the
  read-back are external I/O and each must log at WARNING or re-raise on failure.'
- 'Must be idempotent: pausing the same run twice at the same decision point must
  leave one record, not two.'
```
