summary: "A family of tests checks how many decisions, mockups, tickets and changelog entries the repository contains and compares that to a number written into the test. description: "Files KI-TQ-20261006-corpus-size-assertions-go-red-on-routine-authoring (high) and KI-TQ-20261006-one-validator-run-reports-as-ten-test-failures (low) into docs/known-issues/testing-quality. Both were found while investigating whether the newly sharded CI suite had order-dependent tests; it does not, and these are what the investigation turned up instead. Six tests under tests/knowledge/ assert the size of the live on-disk corpus against a hardcoded integer across eight assertions, all eight currently stale: decisions 9 against 6, mock data 4 against 3, mockups 17 against 15, flows 27 against 25, changelog entries 566 against 551, tickets 1565 against 1560. Four more tests share the shape and happen to agree today, so they go red on the next addition. Sixteen further corpus-derived literals sit behind the first failing assertion in those same files, including a union of frontmatter keys across all tickets that breaks when any ticket introduces a novel key, so fixing only the headline number in each file leaves the fragility in place. The decision corpus drifted from 6 to 9 while the issue was being written up, in ordinary publish commits, which is recorded as evidence rather than a footnote. Two findings make the fix cheap and are both cited: the lower-bound form is already the convention among sibling tests in the same directory, and the identical defect was diagnosed and fixed once before in a protected-diagrams test whose docstring records it breaking twice. The count is also redundant, since the following assertion in each test already proves losslessness by set equality, and the acceptance criterion these cover asks for field-level losslessness and says nothing about census size. Fix directions are given with trade-offs rather than a prescription, including the warning that deriving the expected count from the same glob the production code uses becomes a tautology that proves nothing. The second issue records that ten reported failures in one product-truth test file carry a single identical assertion message from one validator run, so a count that multiplies one cause by ten distorts triage; its local cause could not be reproduced and is left explicitly unexplained. No test was changed: fixing these needs acceptance criteria first, because it retires coverage a completed criterion is credited with."
