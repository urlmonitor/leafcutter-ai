## Actor / Goal

## Acceptance Criteria

```gherkin
Given the store holds 28 flows the Flows view can draw, 25 under Leafcutter and 3 under
  Fern & Fig,
When a person opens /flows from the sidebar 'Flows' link,
Then the finder shows an empty search box and the summary '28 flows',
And all 28 flows are listed, the Leafcutter flows first and the Fern & Fig flows after,
  each product's flows ordered by name with case ignored,
And the Product filter shows Leafcutter 25 and Fern & Fig 3,
And the Actor filter shows Code 23, AI agent 17, Person 12 and Jev 8, Jev being its own
  option and never counted under AI agent,
And the Kind filter shows User 6, Data 20 and Architecture 2, the Realization filter shows
  Built 17, Spec 8 and Sample 3, and the Level filter shows Journey 14, Pipeline 13 and
  Agent 1,
And the 'I/O not yet defined' option shows 9,
And every count is the number of flows that option alone would list, not a number of steps,
And no flow is drawn, no flow is selected, no breadcrumb shows and no drawer is open.
```

## Implementation Notes

```yaml
- 'Finder core is one pure, isomorphic module set in a new folder leafcutter-web/lib/flow-finder/
  (no node:fs, no ''server-only'', no React): index building, search, facet filtering
  and counting, result grouping and ordering, status text, and finder-address parse/build.
  app/flows/page.tsx (server) and the client finder call the same functions, so the
  server HTML and the hydrated client agree (no hydration mismatch).'
- The finder index is built from the flow set lib/data/flows.ts already loads for
  the Flows view (the stored flows plus leafcutter/artifact-knowledge-graph); no second
  loader and no hard-coded flow list. If a node field the finder needs (actor kind,
  screen, entities, AC ids, io_contracts missing_bindings, used/produced field keys)
  is not exposed yet, extend the existing loader. lib/data/ already holds 21 non-markdown
  files, so no new file goes there.
- Facet vocabularies (facet order, stored values, labels, product labels) are declared
  once in leafcutter-web/lib/flow-finder/ and read by the facet panel, chips, address
  builder and counts; no per-component copy. The same declaration is the source the
  UXP-617-5 reference documents.
- 'Every facet count is a flow count: the number of flows the listing function returns
  with that option alone in its facet, q and the other facets kept. Counts reuse the
  listing function; there is no second counting rule that can drift.'
- app/flows/page.tsx renders the finder from its searchParams on the server and answers
  200; the bare-/flows default-entry render and its default flow constant are deleted,
  not left as dead code (UXP-591-1-i).
- 'New finder UI goes in a new folder leafcutter-web/components/flows/finder/: components/flows/
  holds 14 non-markdown files against the 15-file cap. The finder is not grown into
  flow-explorer.tsx (635 lines) or flow-drawer.tsx (438) or flow-nodes.tsx (429),
  all over the 400-line ratchet; flows-view.tsx (210) must stay under 400.'
- 'No server request per search or facet change: the client recomputes from the index
  it received with the page.'
- The result summary sits in one polite live region (role status) that is present
  in the server HTML and is updated in place, not re-mounted.
- Expected values come from the leafcutter/atlas-flows v4 dataset records, replayed
  against a frozen finder-index fixture in leafcutter-web/fixtures/flow-finder/ produced
  by the finder's own index builder from docs/product-truth/flows/ at the dataset's
  measurement commit (provenance recorded in the fixture); tests never pin counts
  against the live store, which grows. fixtures/** is already excluded from vitest
  collection.
```
