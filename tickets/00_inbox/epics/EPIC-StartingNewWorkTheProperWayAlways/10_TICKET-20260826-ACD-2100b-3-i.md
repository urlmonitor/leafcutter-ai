# A registry that holds no agent entries is reported as unusable rather than as a missing agent

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `ACD-2100b-3-i` — A registry that holds no agent entries is reported as unusable rather than as a missing agent — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `ACD-2100b-3-i`. Component: `ac-driven-dev`. Assigned agent: `python-coder`. Estimated complexity: `S`. Complexity: `low`.

## Acceptance Criteria

```gherkin
Given a registry file that can be read and interpreted but does not carry the
  collection of agent entries the startup check expects -- for example it holds
  a single value where a list of agents belongs,
When the startup check runs,
Then the run stops with a report that the registry could not be used and states
  what was found where the agent entries were expected,
And the report does not state that any agent is absent from the registry,
And the report does not state that any agent lacks permission,
And the check itself does not end the run with an unhandled failure.
```

- [ ] AC-1: the run stops with a report that the registry could not be used and states
- [ ] AC-2: the report does not state that any agent is absent from the registry
- [ ] AC-3: the report does not state that any agent lacks permission
- [ ] AC-4: the check itself does not end the run with an unhandled failure.

## Implementation Notes

```yaml
- The change must land under templates/. The deployed workflow is build output.
- 'Fail closed: the run stops.'
- A cause the check did not establish must not be asserted. When the outcome fits
  none of the four named cases the report must say the verdict could not be determined
  and say what was seen -- this is the general rule, and this record is one instance
  of it.
- The report must state what was found where the agent entries were expected, so the
  operator can tell a wrong file from a structurally changed one.
- The outcome must be a recorded report, not an unhandled failure. An unhandled failure
  also stops the run, so a fail-closed assertion alone cannot distinguish the two
  -- the report is the only observable difference.
- 'Must satisfy the repository error-handling policy: the guard must catch by type
  and log at WARNING or higher; it must not be a bare except and must not silently
  substitute an empty collection, which is precisely how this outcome becomes a false
  absence verdict.'
```
