# A document's path-bearing frontmatter entries are resolved whichever of the two accepted shapes they use

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-118d` — A document's path-bearing frontmatter entries are resolved whichever of the two accepted shapes they use — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-118d`. Component: `guardrail-engine`. Assigned agent: `python-coder`. Estimated complexity: `S`. Complexity: `low`.

## Acceptance Criteria

```gherkin
Given a document whose frontmatter carries related_docs with two entries — the
  bare form `docs/explanation/architecture.md` and the labelled form
  `explanation: docs/explanation/architecture.md` — and whose related_code and
  architecture_diagrams each carry one entry in the labelled form,
And every path named by those four entries exists in the repository,
When the document-frontmatter guard checks the document,
Then the guard reports no path error for any of the four entries,
And given one labelled entry is changed to name docs/explanation/absent.md,
  which does not exist,
When the guard checks the document again,
Then it reports exactly one path error, and that error names the field and the
  path string docs/explanation/absent.md — not the whole entry as the parser
  rendered it,
And the guard reaches a verdict for the document on both runs without raising.
```

- [ ] AC-5: the guard reaches a verdict for the document on both runs without raising.

## Implementation Notes

```yaml
- FIX THE TEMPLATE, NOT THE BUILD OUTPUT. templates/scripts/commit_guardian/frontmatter_validators.py
  is the source; scripts/commit_guardian/ and .leafcutter/scripts/commit_guardian/
  are regenerated from it by build_commit_guardian's directory copy. An edit applied
  to a deployed copy alone is reverted by the next build.py run and leaves the template
  broken while the suite reads green.
- ONE ROUTINE, ONE DECLARED ACCEPTED-SHAPE SET, IN EXACTLY ONE PLACE. validate_paths()
  must obtain its path strings by calling the resolver, not by testing element types
  inline. GE-118f proves the sharing by admitting a further shape at that single declaration
  point and observing both consumers move; any second copy of the rule — including
  an inlined 'fast path for the common string case' — makes that proof fail for a
  reason unrelated to GE-118f.
- 'THE RESOLVER''S HOME IS SETTLED: scripts/frontmatter_path_resolver.py, a new top-level
  module in the VERBATIM-COPY tier alongside scripts/knowledge_query.py and scripts/knowledge_frontmatter_reader.py.
  Decided 2026-09-21 by the user on an architect''s recommendation, against the initial
  instinct to place it in the template tree. THREE REASONS, IN ORDER OF WEIGHT. (1)
  TIER. templates/scripts/commit_guardian/ is the COMPILED tier -- build_commit_guardian''s
  docstring states that .py files there ''have config placeholders injected'' (scripts/build_phases_lifecycle.py:330-331)
  -- while build_workflow_tools states ''Files are copied verbatim (no template compilation)''
  (scripts/build_phases_workflows.py:422). This resolver has no config-dependent behaviour,
  so running it through inject_config() is a category error and a latent hazard: any
  {{...}}-shaped text in a docstring or a refusal message naming an example shape
  would be silently substituted. (2) DEPENDENCY DIRECTION. The one existing precedent
  for a gate sharing a leaf module runs the other way -- check_done_proof.py, inside
  the commit-guardian template tree, reaches OUT into scripts/ac_store/ via sys.path.insert(0,
  str(_HERE.parent / ''ac_store'')) (check_done_proof.py:143-146). Hosting the resolver
  in commit_guardian would invert that, making knowledge_query.py -- a standalone
  CLI and library that never touches a commit -- reach INTO commit-guardian''s private
  template directory. (3) OWNERSHIP. This record''s sibling GE-118f declares components:
  [commit_guardian, knowledge_system] precisely because neither component owns ''resolve
  a frontmatter entry to paths''. Filing it under one of them asserts an ownership
  that does not exist. THE COST, ACCEPTED WITH EYES OPEN: the filename must appear
  in TWO deploy lists (see GE-118f it_requirement 1) and that exact two-place drift
  already bit knowledge_frontmatter_reader.py. It is accepted because test_guard_source_paths_match_deployable_set
  fails when the two disagree -- a loud failure, not a silent one.'
- ALL THREE FIELDS, DRIVEN BY THE path_fields LIST RATHER THAN BY NAME. related_docs,
  related_code and architecture_diagrams already share one list and one loop. Apply
  the resolver inside that loop so a fourth field added to the list inherits the rule
  automatically; do not special-case any field name.
- A PATH ERROR NAMES THE PATH AND THE FIELD, AND DOES NOT NAME THE PARSED ELEMENT.
  For a labelled entry pointing at an absent file the message must contain the path
  string and the field name and must NOT contain the mapping's Python repr — the reader
  has to be able to copy the path out of the message and act on it.
- REAL-ARTIFACT FIXTURE, NOT A HAND-INDENTED LITERAL (CLAUDE.md, 'Real-artifact behavioral
  spot-check'; docs/how-to/real-artifact-fixtures.md). At least one test must run
  against a document whose frontmatter was produced by yaml.safe_dump — PyYAML's own
  serialisation, block lists at column 0 — and at least one must run against a document
  already tracked in this repository that uses the bare form. A triple-quoted fixture
  reproduces the author's own indentation bias; that bias has already hidden one defect
  of this class here.
- THE VERDICT FOR EVERY DOCUMENT THAT PASSES TODAY MUST BE UNCHANGED. The bare string
  is the form essentially every tracked document in this repository uses, so any change
  in its verdict is a regression, and the real-artifact arm above is what makes that
  visible rather than assumed.
- 'ERROR-HANDLING POLICY APPLIES UNCHANGED (CLAUDE.md Rules 1-4). No bare except,
  no swallowed exception, and no try/except wrapped around the pure classification
  step: the classification must be total — it returns a refusal for an input it does
  not accept rather than being prevented from raising by a wrapper.'
```
