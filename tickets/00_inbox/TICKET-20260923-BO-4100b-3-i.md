# A workspace's own supporting material carries the same checks as the shared one

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `BO-4100b-3-i` — A workspace's own supporting material carries the same checks as the shared one — so that the acceptance criterion is satisfied.

## Context

## Acceptance Criteria

```gherkin
Given a workspace's own supporting material and the shared install tree's
  supporting material were both derived from the same commit,
When the set of checks each of them defines is enumerated,
Then the two sets contain the same checks,
And each check appears with the same configuration in both sets.
```

- [ ] AC-1: the two sets contain the same checks
- [ ] AC-2: each check appears with the same configuration in both sets.

## Implementation Notes

```yaml
- The equivalence is over the ENUMERATED CHECK SET and each check's configuration,
  not over the raw bytes of the two trees. A copy produced by a different materialisation
  route is still equivalent if it defines the same checks with the same configuration,
  and a byte-comparison would fail it for no reason that matters.
- The enumeration must come from the same place each side's own tooling reads it from
  -- the hooks_manifest as each tree exposes it -- so a copy that omits an entry the
  manifest names is detected, rather than a copy that merely orders entries differently
  being reported as divergent.
- The assertion must be made for the fallback materialisation route as well as the
  preferred one, or a Windows/NTFS install silently receives the reduced copy this
  record exists to forbid.
- This record does NOT assert that the checks fire. That is BO-1700a and must not
  be re-derived here; nor is it BO-1700e's question of the guard working across layouts.
- The comparison must be available as an invocable check, not only as a test, so a
  per-workspace copy that drifts from the shared one later is detectable without re-running
  the suite.
```
