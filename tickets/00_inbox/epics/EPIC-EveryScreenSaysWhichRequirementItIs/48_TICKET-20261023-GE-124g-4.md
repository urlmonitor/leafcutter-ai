## Implementation Notes

```yaml
- EXTEND THE EXISTING COVERAGE-ACCEPTANCE SURFACE, DO NOT BUILD A SECOND ONE. Whether
  a test counts as evidence for a criterion is already decided in scripts/ac_store/done_proof.py
  / test_enforcement.py via the shared covers-tag scan. This AC adds a front-end-specific
  rejection rule to that surface; a parallel acceptance oracle would let the two disagree
  about the same test, which is the drift GE-124c-2-i exists to prevent one namespace
  along.
- 'THE REJECTION RULE MUST BE STATED AS AN ENUMERATED SET OF ASSERTION SHAPES, NOT
  AS A JUDGEMENT OF TEST QUALITY. Reject when the test''s only assertions are: element-exists
  / not-null / toBeInTheDocument on the derived selector; a count of matched elements;
  or an assertion that the element carries the data-ac marker itself. Accept anything
  asserting observable state or behaviour beyond presence. Draw the line explicitly
  — a vaguer rule is either unimplementable or starts rejecting legitimate tests.'
- THIS IS A STATIC ANALYSIS OF FRONT-END TEST SOURCE, and its subject is TypeScript/JavaScript
  while the implementer is python-coder. Keep it to a bounded textual/AST-free inspection
  of assertion calls in the test body — the same class of scan the rest of this tree
  performs on .tsx source. If the rule cannot be drawn without a real JS AST, say
  so and raise it rather than shipping a regex that quietly mis-classifies; a mis-classification
  here either accepts an empty test or rejects a real one, and both are worse than
  the status quo.
- THE THIRD SCENARIO IS THE CIRCULAR ONE AND IS THE REASON THIS IS NOT A SINGLE ASSERTION.
  A test asserting the marker is present is asserting that the DECLARATION exists
  — it tests the guardrail, not the product. It passes every structural check, agrees
  with GE-124f-3's selector rule, and covers nothing. This repo has shipped that exact
  shape before, in tests that grepped for a string rather than executing behaviour.
- THE SECOND SCENARIO IS A REQUIRED ACCEPTANCE CASE, not a courtesy. The rule must
  not be dischargeable by rejecting every front-end test. An assertion about the criterion's
  observable behaviour is accepted, and the worked case is the mock-data record decl-stock-badge
  with its covering test.
- THE REASON NAMES THE MISSING PART — the test locates the element but asserts nothing
  about the criterion — so the author's next move is obvious. A bare 'not accepted'
  invites the author to delete the covers tag instead of writing the assertion.
- NO CONFIGURATION KEY MAY MAKE AN EXISTENCE-ONLY TEST COUNT, and such a key must
  be refused by name if supplied (GE-124g-1-i).
```
