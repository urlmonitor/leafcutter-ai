## Acceptance Criteria

```gherkin
Given a workspace carrying the holds-work verdict,
When its disposal is requested,
Then the disposal is refused,
And the workspace is still listed in the live set afterwards and its files are
  byte-identical to what they were before the request,
And the refusal names each item that produced the verdict -- the modified,
  staged or untracked files by path, the unreached commits by identifier, and
  any stash entry belonging to the workspace.
```

## Implementation Notes

```yaml
- 'The refusal must name items at the granularity the verdict produced them: modified,
  staged and untracked files by path; unreached commits by identifier; the stash entry
  by its reference. A count, a category summary, or ''uncommitted changes present''
  does not satisfy this -- the operator cannot act on any of those, and their only
  route forward is to override.'
- 'The refusal path must be inert: no file in the workspace, no ref, and no registration
  entry may be written while refusing. Byte-identity of the workspace is asserted,
  so a refusal that repairs, prunes or stashes anything on its way out fails.'
- If an override exists at all it must name the workspace explicitly, must not be
  the default, and must not be reachable by repeating the same command. The recorded
  harm is an override habit turning this guarantee off, and a one-keystroke override
  is how that habit forms.
- The verdict and the item list must both come from BO-4100c-1's assessment record.
  Disposal must not re-derive either -- a second derivation can disagree with the
  first, and then the refusal names items the verdict was not based on.
- Error handling follows the project error handling policy. A failure while assembling
  the refusal must not fall through to disposal.
```
