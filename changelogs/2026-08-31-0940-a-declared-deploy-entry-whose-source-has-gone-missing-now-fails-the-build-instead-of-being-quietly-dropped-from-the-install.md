description: "The branch this replaces already did almost everything right. It found the missing source, identified it correctly, and logged it accurately. The only thing it got wrong was the exit code, which made it the purest false-green trap in this area: any test asserting the failure message appears would have been green against the broken code and the fixed code alike, because the broken code emitted exactly the same message. That was confirmed rather than assumed before any test was written — deleting one file the acceptance-criteria deploy map declares produced the warning and an exit code of zero, a build reporting a consumer install it had not produced. Every assertion in the new tests is therefore on the exit code, on the accumulated failure records, or on the set of names in a single report, and none is on log output. The five loops that iterate a declaration have all been changed, not only the one the criterion names, because warn-and-continue on a missing declared source is a pattern rather than a line and a fix scoped to where the defect was found leaves the identical hole in every sibling. Those five are the acceptance-criteria store deploy map, the workflow-tools list, the knowledge-scripts list, the agent-support file list, and the single declared release dependency of the fast lane. Three further sites that look identical were audited and deliberately left alone, because they iterate a directory listing rather than a declaration: a glob cannot have a missing declared entry, the existence check there is filtering out directories, and skipping is the correct behaviour. Flipping those would have manufactured failures for files nothing ever promised to ship. Findings accumulate across the whole run and are raised once at the end through a typed error carrying every record, so a single build hands the author the entire remediation set; halting at the first would turn a set of stale entries into as many build-fix-build cycles, with a green build between each one, and an author who stopped at the first green would ship the rest. A declaration with no entries and a declaration whose entries all resolve are both still successes — nothing promised cannot have been dropped — and that control exists because a fail-closed flip with no empty case is the exact shape of an earlier defect where an empty-list guard was present in one check and absent from its structurally identical twin while every test passed. The pre-existing stale set was enumerated before landing this and is empty, established by running the real build and confirming each of the five loops actually executed and copied its entries rather than by the absence of warnings, so the flip turns no current build red. Two things are deliberately not done. No configuration flag, environment variable or strict mode was added: an opt-in reproduces the defect for everyone who does not set it, and the default is what ships to consumers. And the acceptance criterion itself is left open rather than marked complete, because its technical-constraint child additionally requires that a failed run leave no partial deploy behind, and this change does let the resolvable entries write before it raises. Marking a criterion complete over an unfinished constraint of its own is the precise failure mode this repository exists to prevent, so the note records what landed, what remains, and the design choice the remaining work turns on. One further note for whoever writes tests here next: the obvious fixture does not work. Deleting the first declared file to hand makes an earlier guard abort the build before any deploy phase runs, so the test passes without ever reaching the code under test — verified, and the fixture was chosen to avoid it."
