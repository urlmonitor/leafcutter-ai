# An executable script inside a prose location does not inherit the exemption

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-123d-4-i` — An executable script inside a prose location does not inherit the exemption — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-123d-4-i`. Component: `guardrail-engine`. Assigned agent: `python-coder`. Estimated complexity: `S`. Complexity: `low`.

## Acceptance Criteria

```gherkin
Given the skill-prompt area is one of the five enumerated prose locations,
And that area contains executable Python scripts alongside its Markdown
  prompt text — the secrets scanner's own script among them,
And one of those scripts staged for commit contains a credential-shaped line
  whose quoted value is a run of ordinary words, the same value that is
  exempt in a ticket file,
When the staged file is checked by the pre-commit secrets check,
Then the generic-credential finding IS reported and the commit is blocked,
Because being inside a named prose location is not sufficient on its own: the
  file kind must also be one of the four admitted non-executing kinds, and a
  Python script is not.

Given a Markdown prompt file in that same directory, staged in the same
  commit, contains the identical line,
When the pre-commit secrets check runs over the staged set,
Then exactly one finding is reported — the one in the script — and none for
  the Markdown prompt file,
And the two files differ in nothing but their kind,
Because the kind gate, not the location, is what separates them.
```

- [ ] AC-2: one of those scripts staged for commit contains a credential-shaped line
- [ ] AC-3: the generic-credential finding IS reported and the commit is blocked
- [ ] AC-4: exactly one finding is reported — the one in the script — and none for
- [ ] AC-5: the two files differ in nothing but their kind

## Implementation Notes

```yaml
- 'The location list for the new exemption is copied in spirit from the existing high-entropy
  prose-prefix list, and one entry on that list — the skill-prompt area — holds executable
  Python including the secrets scanner''s own source. The kind gate is what stops
  the new exemption inheriting that shape. It must not be dropped as redundant, and
  it must be observable: removing it has to turn a test red.'
- 'The pre-existing defect this AC guards against is recorded as KI-CG-004 in docs/known-issues/commit-guardian.md,
  with measured evidence — a token of Shannon entropy 5.17 is exempt from the high-entropy
  rule at the scanner''s own source path, at the ticket tree, at the acceptance-criteria
  store and at the retrospectives area, while reported under the build scripts directory.
  That defect is explicitly OUT OF SCOPE here. Do not repair it, do not widen it,
  and do not let this AC be closed as a duplicate of it: KI-CG-004 concerns an existing
  rule''s file-level exemption, this AC concerns the kind gate on a new one.'
- If the location data is shared between the existing high-entropy exemption and the
  new generic-credential exemption, the kind gate must be applied on both sides or
  the sharing must not happen. Reusing the list without reusing the gate is exactly
  the careless line of reuse this AC exists to forbid, and it would silently widen
  KI-CG-004 rather than contain it.
- The kind gate must reject on the file's own extension, so that two files in the
  same directory differing only in extension receive different verdicts in a single
  run. A gate that is short-circuited by a directory-level decision cannot satisfy
  the second scenario.
- The scanner's own source path must be covered explicitly, not merely by implication
  from the extension rule. It is the sharpest instance of the class and the one a
  future reader will check first.
- 'ADR-001 parity: the canonical copies are under templates/; verify through the build.py
  round-trip.'
```
