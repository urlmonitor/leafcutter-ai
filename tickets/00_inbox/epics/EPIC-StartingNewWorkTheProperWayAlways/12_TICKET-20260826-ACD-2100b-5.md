# The startup check reads the registry itself instead of asking an agent to read it

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `ACD-2100b-5` — The startup check reads the registry itself instead of asking an agent to read it — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `ACD-2100b-5`. Component: `ac-driven-dev`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given an environment in which no agent can be dispatched -- every dispatch
  attempt fails immediately with a transport error,
And an agent registry that is present readable and lists the agent the route
  uses to create the authoring worktree with permission to run repository
  commands,
When a run starts and reaches the startup check,
Then the check completes with the permitted verdict and the run proceeds past it,
And the run's record of what it dispatched contains no dispatch made on behalf of
  the check,
And repeating the run with dispatch available reaches the same verdict.
```

- [ ] AC-1: an agent registry that is present readable and lists the agent the route
- [ ] AC-2: the check completes with the permitted verdict and the run proceeds past it
- [ ] AC-3: the run's record of what it dispatched contains no dispatch made on behalf of
- [ ] AC-4: repeating the run with dispatch available reaches the same verdict.

## Implementation Notes

```yaml
- The change must land under templates/. The deployed workflow is build output and
  does not carry this step at all today.
- The verdict must be a function of the registry contents alone. It must be identical
  whether dispatch is available or not -- 'skip the check when dispatch is unavailable'
  is a fail-open regression wearing this record's clothes and is explicitly forbidden.
- The startup path must reach this check and pass it with no network available.
- 'Removing the round-trip must not remove the halt: the four outcomes ACD-2100b-1
  through -3 specify still stop the run, and ACD-2100b-4 still holds over them.'
- If a helper that dispatches for this purpose remains in the source for another caller,
  this behaviour is not satisfied by its absence from the file -- what must be observable
  is that no dispatch is made on the check's behalf during a run.
- 'Must satisfy the repository error-handling policy: the local read replaces a network
  call, so its failure paths are the ones ACD-2100b-1 and ACD-2100b-2 own and must
  not be swallowed.'
- Must not add a per-run cost beyond a single local file read -- this record removes
  latency from startup and must not reintroduce it elsewhere.
```

**What was attempted.** Read the ticket, the AC (`ACD-2100b-5.yaml`), the four
red tests in `unit_tests/workflows/test_acd_2100b_5.py`, and the current
`resolve-workspace-setup-permission` dispatch site in
`templates/workflows-js/plan-feature.js` (~line 2185). Confirmed the red
baseline still holds (4/4 red under `AC_ENFORCE_STRICT=1`, matching
test-writer's report). Traced the only implementation shape that could make
all four tests green: `permitsShell`/`workspaceSetupAgentEntryState` computed
via a literal in-body filesystem read (`require('fs')` +
`require('child_process').execSync('git rev-parse --git-common-dir')`-style
repo-root resolution, replacing the current `agent()` dispatch), since the
tests require the verdict to be correct with EVERY `agent()` call blocked
and with zero calls carrying the `resolve-workspace-setup-permission` label
in either mode.

**Why it was not implemented — architectural conflict, confirmed empirically
just now.** `templates/workflows-js/plan-feature.js`'s top-level body executes
under the E2 engine, which per ADR-030 injects only
`agent/parallel/pipeline/phase/log/args/workflow/budget` — no module loader,
no `fs`. This is not just a documentation claim: I probed it directly against
this repo's own canonical vm-sandboxed E2 harness
(`unit_tests/_workflow_engine_harness.py`, the one built specifically to
reproduce the real engine's sandbox) with a minimal script calling
`require("fs")`, and it throws immediately:
`ReferenceError: require is not defined`. This is the EXACT defect already
found and fixed once in this codebase: `BO-1000c-1a`'s
`appendJournal()` called `require('fs')` inside a `finalize-feature.js`
top-level body, silently swallowed the `ReferenceError` in a try/catch that
logged a WARNING while the run reported success, and was marked
`work_status: done` for eight days before a vm-sandboxed test caught it
(`docs/acceptance-criteria/build-orchestration/BO-1000-live-automation-progress/BO-1000c-1a.yaml`,
2026-08-18 amendment; corroborated in
`docs/known-issues/build-orchestration.md` "Addendum 2026-08-26"). Implementing
`ACD-2100b-5` the only way that satisfies its own tests would reintroduce that
identical failure mode in `plan-feature.js`: green in this ticket's bare-Node
subprocess harness (which does not sandbox `require`), but a `ReferenceError`
on every real invocation — turning the mandated `/plan-feature` entry point
this AC exists to unblock into a harder, less diagnosable failure than the one
it replaces.

**A second, independent problem with the test file itself.**
`_run_plan_feature_blocked(cwd, args)` and `_run_plan_feature_real(cwd,
label_responses, args)` both accept a `cwd` parameter naming the fabricated
fixture repo, but neither ever forwards it to `_run_shim`'s
`subprocess.run(["node", str(tmp_path)], ...)` call (no `cwd=` kwarg is
passed). So even a correct, ADR-030-compliant local-read implementation would,
for all four tests, resolve the registry against the REAL worktree's actual
filesystem location (verified: `git -C <worktree> rev-parse --git-common-dir`
resolves to the main checkout, whose `.leafcutter/config/agent_registry.json`
really does list `worktree-agent` with `permits_shell: true` — matching
`KI-ACD-009`'s own quoted evidence) rather than the constructed
permit/deny/absent fixtures the tests build per-case. The "seam" test in
particular (denies for both blocked and real) could not pass against a
real-fs read for this reason, independent of the ADR-030 conflict.

**Suggested remediation (for the ticket-supervisor / architect / IT-PO):**
1. Re-scope the mechanism: keep a single `agent()`-dispatched raw read (as
   today) but relax the AC's "zero dispatch even under total transport
   failure" criterion to something achievable under E2's no-fs sandbox — e.g.
   require the decision logic to live in the workflow body (already true)
   and consolidate the read into the SAME dispatch used to run
   `setup_ticket_worktree.py`, without requiring a *permitted* verdict when
   dispatch is fully blocked (matching what B0-1000c-1a's own remediation did:
   redefine onto what the engine can actually provide).
2. OR move the read to the host/orchestrator layer, which does have real tool
   access: have `templates/commands/plan-feature.md` `Read` (not dispatch)
   `config/agent_registry.json` before invoking
   `Workflow("plan-feature", { userInput, agent_registry_json })`, and have
   the workflow body consume `args.agent_registry_json` as a pure,
   zero-I/O computation. This is ADR-030-compliant and literally matches "the
   check reads the registry itself" (the top-level orchestrating session
   reads it, not a spawned sub-agent) — but it is out of this ticket's
   `files_touched` scope and needs `test-writer` to rebuild the test harness
   around `args` injection instead of an on-disk fixture + real subprocess.
3. Either way, any redone `test_spec` for this AC should be validated through
   `unit_tests/_workflow_engine_harness.py`'s `run_workflow_under_e2` (the
   vm-sandboxed harness), not a bare Node subprocess, so a `require('fs')`-
   shaped regression is caught the way it should have been for `BO-1000c-1a`.

No changes were made to `templates/workflows-js/plan-feature.js`. Recommend
respawning `python-coder` once IT-PO/architect confirms which remediation
direction to take, or after the AC/test_spec is amended.
