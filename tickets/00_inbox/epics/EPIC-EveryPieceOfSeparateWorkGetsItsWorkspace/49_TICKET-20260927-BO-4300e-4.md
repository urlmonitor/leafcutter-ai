## Acceptance Criteria

```gherkin
Given finalizing a feature needs a temporary copy of the shared main line to
  run a before-and-after comparison,
When it obtains that copy and later clears it, once with the comparison
  succeeding and once with the comparison failing part-way,
Then in both cases the copy was started from the shared main line tip as read
  after fetching,
And in both cases, afterwards, no folder of the copy remains and the project's
  branches, registered workspaces and settings are identical to before,
And in both cases the clearing is reported in finalize's own result.
```

- [ ] AC-3: in both cases the clearing is reported in finalize's own result.

## Implementation Notes

```yaml
- finalize obtains its comparison copy with `ensure --kind scratch` (a detached clone
  at origin/main after a fetch, landing in the one landing place) and always clears
  it with `remove` on both the success and the failure path; the clearing result is
  part of finalize's own result. Nothing is ever registered in the real project (F14);
  /tmp baselines and `git worktree add --detach` are retired.
- 'SCRATCH READINESS (decided by the user at the final gate, 2026-09-25): a detached
  clone has no line of work and nothing is ever committed or merged in it, so the
  branch ingredients AND every protection-stage canary are reported ''n/a'' for kind
  scratch: hooks_pre_commit_fired, hooks_commit_msg_fired, hooks_post_merge_fired
  and their conjunction hooks_canary_rejected (confirmed 2026-09-25: the rule covers
  all three stages of BO-4300c-1-ii, because each stage''s canary is a commit or a
  merge and a comparison copy has neither). The fresh-base, independent-copy and build
  ingredients still apply. ''n/a'' is reported explicitly; no ingredient is silently
  skipped. No other kind may report hooks_pre_commit_fired or hooks_canary_rejected
  as ''n/a''; for other kinds the commit-msg and post-merge checks may be ''n/a''
  only when the project does not declare that stage (BO-4300c-2).'
- 'Workflow bodies run in the E2 engine with no filesystem or process access (ADR-030).
  They reach the maker only through (a) args.workspace -- the maker''s JSON object
  passed verbatim by the entry command or skill (BO-4300a-1-ib) -- or (b) exactly
  one agent() dispatch, carrying a result schema, to an agent whose registry entry
  has permits_shell: true, instructing it to run one exact absolute command unchanged
  and return stdout verbatim. Never status-checker (permits_shell: false), never free-form
  set-up steps.'
- Proof runs the workflow under unit_tests/_workflow_engine_harness.py -- the deployed
  copy the build produces, so the build's workflow transform is exercised -- with
  label-scripted agent replies, and asserts on the RECORDED dispatch list, never on
  workflow source text. The harness must be able to model a workspace step that declines
  its task, answers in prose, answers exit 0 with a non-JSON path, or answers JSON
  without status (F13); extending the harness for this is in scope of the first AC
  that needs it.
- Workflow edits are made in templates/workflows-js/*.js and reach .claude/workflows/
  only through the build; the deployed copy is what the tests run.
```
