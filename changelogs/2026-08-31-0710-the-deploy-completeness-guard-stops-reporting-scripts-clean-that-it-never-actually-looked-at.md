summary: "Fixes three defects in the intra-package closure guard, each of which made it report a script as having no missing dependencies when it had in fact not analysed that script at all, and corrects four known-issue entries — three that were fixed long ago and still read open, and one whose own prescribed fix would have made the guard worse."
description: "The guard added by the deployment-completeness work exists so that a module a deployed script needs cannot silently fail to ship. Its failure mode is not a crash but an empty dependency set, which the containment check reads as nothing missing, so every defect here presented as a passing build. First: a script the guard could not read or could not parse returned an empty closure and was reported clean. That is indistinguishable from a genuine leaf module with no dependencies, and it matters far more than it sounds, because a hundred and seven of the hundred and fifty-two scripts the guard parses live in the templates tree, which the continuous-integration lint run explicitly excludes — the entire commit-guardian hook population, which is the most consequence-bearing deploy set there is. A syntax error there was caught by neither the linter nor the guard, and the guard actively certified the file. It now raises a distinct error naming the file, which the build surfaces as its own kind of finding and aborts on; the read handler also now catches an invalid-encoding failure, which previously escaped it entirely because that exception derives from value errors rather than operating-system errors and so propagated as a raw traceback. Second: the reference lens saw two of the four ways code puts a directory on the import path, and neither of the two dynamic import builtins. A script using the extend form, or a slice assignment, produced no candidate directory, so every plain import depending on it was dropped — and dropped silently, because the skip happened before the disclosure warning that the module's own docstring promised covered every case. That docstring overstated its guarantee and has been corrected to say precisely what it covers. Also added: annotated variable assignments, which the local-name resolver skipped entirely despite this codebase annotating heavily, and relative imports of a subpackage, which offered only a module-file candidate and never the package initialiser. Third: the set of scripts the guard checks against covered eight deploy families while the build has ten, so an entire deployed Python package sat outside the guard with no warning. Two new manifest helpers close that. Two corrections are worth recording because both were mistakes in the analysis rather than in the code. The known-issue entry for the third defect prescribed widening a directory scan from shallow to recursive; doing so would have been wrong, because the phase it mirrors is deliberately non-recursive, and the change would have registered deploy paths for files that phase never writes, adding false entries and producing spurious findings against paths nothing ships. A manifest helper must mirror its phase, not its directory. And wiring the doc-compliance family in immediately produced fourteen phantom findings, every one naming a dependency under the deployed output directory: that family's source directory name differs from its deploy directory name, so path resolution fell through to a fallback that, in any worktree which has installed its shims, resolves a symlink into the deployed tree — meaning the guard analysed build output as though it were source. No unit test caught that; only running the real build did, which is the second time in a week that a green per-file test run has been contradicted by exercising the actual entry point. Finally, four known-issue entries are corrected. Three of them — the doc-types deployment blocker, the acceptance-criteria validator deploy blocker, and the missing components helper — were all fixed some time ago and still read open, which was discovered while choosing what to work on next; one of the three is a particularly good trap, because its fix changed the resolution strategy rather than adding the deploy-map entry the register describes, so grepping for the obvious symptom still finds nothing and reads as never fixed. The register now carries a standing instruction to update an entry in the same change that fixes it, and to confirm a defect is live before starting work on it."
