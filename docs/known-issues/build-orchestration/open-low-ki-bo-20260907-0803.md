# KI-BO-20260907-0803 — `blocked` and `deferred` are valid ticket statuses that no transition can reach, so the only way to park a ticket is to bypass the tool

- **Severity:** medium
- **Status:** open — no AC
- **Occurrences:** 1
- **First seen:** 2026-09-07 · **Last seen:** 2026-09-07
- **Where:** `scripts/set_ticket_status.py` — `ALLOWED_TRANSITIONS` (:49),
  `FORCE_ALLOWED_TRANSITIONS` (:58), `VALID_STATUSES` (:72)

**Symptom.** `set_ticket_status.py` accepts `blocked` and `deferred` on the command line —
`VALID_STATUSES` feeds argparse `choices` (:458), so `--status blocked` parses and the help
text advertises it — but neither value appears as the *target* of any pair in either
transition table. Every attempt is refused from every state, including with `--force`:

```
Invalid transition: todo -> blocked (use --force to override)
Invalid transition: todo -> blocked (not permitted even with --force)
```

The tables contain `("blocked", "todo")` and `("blocked", "in_progress")` — paths *out* of
`blocked` — and no path *in*. `deferred` appears in neither table in either direction. So
`blocked` is an exit-only state that nothing can enter, and `deferred` is entirely inert.

**Why it matters.** These are not decorative vocabulary. `ticket_prioritizer.py:44` lists
both in `EXCLUDED_STATUSES`, so a ticket in either state is correctly held out of the ready
set, and `DONE_STATUSES` (:41) treats `deferred` — but not `blocked` — as satisfying
`depends_on`. The consumer side is fully built and load-bearing; the producer side does not
exist. Parking a ticket without falsely satisfying its dependents is exactly what `blocked`
is for, and it is the one thing the tool cannot do.

The practical consequence is that the sanctioned path forces the wrong answer. The reachable
options are `in_progress` (excluded from the ready set, but claims work is underway) or
`done`/`deferred`-by-hand (both satisfy `depends_on` and will unblock dependents that should
stay blocked). An operator who needs to park one ticket must either mislabel it or hand-edit
the frontmatter — which CLAUDE.md permits for pure lifecycle moves, so the bypass is legal,
but it means the guarded path is routinely stepped around for a routine operation.

**Observed.** Parking ticket 12 (`ACD-2100b-5`) of EPIC-StartingNewWorkTheProperWayAlways
while a design decision on it went to the user, so the other tickets could build. Both
invocations were refused; the status was set by editing frontmatter directly.

**Fix direction.** Add the missing edges rather than removing the statuses — the consumers
justify them. At minimum `(todo, blocked)`, `(in_progress, blocked)` and the `deferred`
equivalents belong in `FORCE_ALLOWED_TRANSITIONS`; parking is deliberate, so requiring
`--force` is right. Whichever way it is resolved, `VALID_STATUSES` and the transition tables
must not be able to disagree about which statuses are settable — the argparse `choices` list
is derived from the wrong one of the two.

**Detection.** For each status in `VALID_STATUSES`, check it appears as the second element of
at least one pair across both transition tables. Today `blocked` and `deferred` fail. No test
asserts this: the suite covers transitions that exist, never the reachability of the declared
vocabulary.

**Re-verified 2026-09-23 against current source before filing.** `ALLOWED_TRANSITIONS` and
`FORCE_ALLOWED_TRANSITIONS` in `scripts/set_ticket_status.py` are unchanged from the state
described above: no pair in either table names `blocked` or `deferred` as its target, and
`VALID_STATUSES` (feeding argparse `choices` at :458) still includes both. The defect is
still live.
