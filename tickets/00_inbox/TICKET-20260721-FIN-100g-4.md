### 2026-08-17 — REOPENED by evidence-based audit (status: blocker)

**One of the AC's four `Then` clauses was never implemented. This ticket was closed
`done` over it, with every phase signed off and its tests green.**

What IS implemented (the 2026-07-21 entry above is accurate about this): the
`step-3-deploy-parity` dispatch, the `build_state_only_failures` filter, and the M-2
`still_failing` contradiction guard. FIN-100g-4-i's core behaviour genuinely holds — a
real failure still survives the exclusion and reaches triage.

**What is missing — the gating clause.** The criterion requires "triage (FIN-100c) runs
only once the deployed layer is verified consistent". The prompt at ~L1198 asks the agent
to return `deploy_consistent` and `redeployed`, and **neither field is ever read**:
`grep -n "deploy_consistent\|redeployed"` over the whole 2383-line `finalize-feature.js`
returns exactly one hit each — the prompt string itself. Only `build_state_only_failures`
and `still_failing` are parsed (~L1208-1213).

**Reproduced behaviourally**, not inferred: feeding
`{"deploy_consistent": false, "redeployed": false, "build_state_only_failures": [],
"still_failing": [...]}` through the E2 harness still dispatches `step-3-changed-files`
and `step-3-triage`. Triage runs on a layout the self-check explicitly reported as
inconsistent — precisely what the AC forbids. Secondary: because `redeployed` is
discarded, the workflow cannot know whether the re-deploy it asked for ever happened.

**Why the green tests did not catch it.** The guarding test is named
`test_triage_runs_only_after_deploy_verified_consistent` — and its assertions are
`"build_state_only_failures" in js` and `"postMergeFailures = postMergeFailures.filter"
in js`. A presence-only scan over the source, testing the adjacent case. All 22 tests in
`unit_tests/workflows/test_finalize_feature_preflight.py` are `read_text()` greps; none
can distinguish shipped behaviour from a matching comment. This is the same pattern as
BP-100i-3, and it is why ticket 09 of EPIC-BuildPipelinePhantomRemediation (BP-1100b-5)
exists.

**Remaining scope — do NOT redo the parts that work:**
1. Read `deploy_consistent` (and `redeployed`) from the parity agent's reply and gate the
   FIN-100c triage dispatch on it. An inconsistent layer must not reach triage.
2. Classify a deploy/build inconsistency as an environment/build-state condition, never a
   test regression (4th `Then` clause — verify it holds once the gate is live).
3. Replace the presence-only guard test with a behavioural one under the E2 harness that
   FAILS when `deploy_consistent: false` still reaches triage. The existing grep test must
   not be left as the proof.

`work_status` on the AC is absent (not `done`), so the store was not itself lying here —
the false claim lived in this ticket's `status` and sign-offs. Both are now reset.
