## Acceptance Criteria

```gherkin
Given the repository's own security allowlist as it stands on disk, containing
  53 entries that are not blank lines or whole-line comments,
When the allowlist is loaded,
Then no unmatchable-entry warning is emitted for any of its lines,
And the set of entries loaded is identical to the set loaded before the
  unmatchable-entry rule existed — all 53,
Because a rule strict enough to fire on the entries this repository already
  lives with would put a warning on every commit anyone makes, which is a
  commit-time outage of its own and would train everyone to ignore the message
  that matters.

Given every security allowlist file present anywhere in the repository's
  working tree, including the copies carried in the package templates and in
  each worktree,
When each of them is loaded in turn,
Then no unmatchable-entry warning is emitted for any line of any of them,
Because the same file is deployed to consumer projects, and a false warning
  there is a defect shipped to every installation.

Given the repository's own allowlist and a scan of the files its entries name,
When the scan completes,
Then every finding those entries suppress today is still suppressed,
Because a rule that satisfies the silence requirement by refusing to load
  anything would pass the two arms above while disabling the allowlist
  entirely.
```

## Implementation Notes

```yaml
- Every allowlist read here is READ-ONLY. The verification must never create, modify
  or delete a .security-allowlist at any real project root, workspace root or worktree
  root — the live file is what the commit hook actually reads, so a stray write would
  disable the real gate as a side effect.
- 'An absent allowlist is a normal checkout state, not a failure: the verification
  skips with a reason rather than failing when the file is missing.'
- The set of allowlist copies to check must be DISCOVERED by walking the working tree,
  never enumerated as a hard-coded list of paths, so a copy added later inherits the
  guard automatically.
- The expected entry count must be DERIVED from the file — the number of lines that
  are neither blank nor whole-line comments — and never written as a literal. A literal
  count goes stale the first time an entry is added and turns a live guard into a
  maintenance chore that gets deleted.
- The third clause is not satisfied by counting warnings. Assert the loaded entry
  set itself, and assert that the findings those entries cover are still suppressed,
  so an implementation that achieves silence by loading nothing fails.
- 'Ignoring the whole file, or falling back to loading nothing, is never an acceptable
  response to an entry the rule dislikes: the disposition is per-line skipping, and
  this criterion is the measurement that the file as a whole survives.'
- Edit the canonical template at templates/skills/security-scanner/scripts/scan_secrets.py
  and propagate with build.py; never edit a deployed copy (ADR-001).
```
