# The set-up path locates its own helper scripts through the shared resolution facility

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-120d-3` — The set-up path locates its own helper scripts through the shared resolution facility — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-120d-3`. Component: `guardrail-engine`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given the set-up command must locate the scripts that verify commit-time protection is
  active and that install the commit-time shims,
When it resolves them,
Then it uses the same shared resolution facility the checks use, rather than a private
  search of its own,
And it locates those scripts from every workspace layout the build actually produces —
  demonstrated by running set-up in each such layout and observing the scripts were found,
And the not-found condition observed while creating a working copy does not arise in a
  workspace that has been built,
And when the workspace genuinely has not been built, the failure is the one described in
  GE-120d-2-i rather than a silent no-op,
And no private root-walking search for these scripts remains in the set-up path.

Coverage note: the load-bearing clause is the one requiring set-up to be RUN in each layout.
Asserting that the set-up path calls the shared facility does not cover it — the observed
defect was a resolution that returned the wrong location, which a call-site assertion cannot
see.
```

## Implementation Notes

```yaml
- 'CONSUME GE-120b-2''s FACILITY: templates/scripts/commit_guardian/_resolve_root.py,
  the existing shared resolver already imported by 27 files in the check family (verified
  2026-08-14). Do not build a second resolver for the set-up path, and do not leave
  a private root walk behind after adoption — a shared facility beside a surviving
  private search changes nothing, because the private path still wins on failure.'
- IMPORT-BOUNDARY CONSTRAINT — the specific technical risk here. setup_ticket_worktree.py
  lives at templates/scripts/ (deployed to .leafcutter/scripts/), one directory ABOVE
  the commit_guardian package that owns the resolver. Confirm the shared resolver
  is importable from that location in the DEPLOYED layout, and extend the deploy manifest
  reach if it is not. An undeployed dependency raises ModuleNotFoundError at set-up
  time, which is a louder version of the very bug being fixed (CLAUDE.md, 'New Hook
  / Gate Dependencies Must Be in the Build Deploy-Manifest').
- SCHEDULE WITH GE-120b-2. This AC cannot land first — it consumes b-2's facility.
  And landing GE-120b-2 without it leaves the set-up path as the LAST private root
  walk in the codebase, which is the position from which the pattern regrows.
- 'ENUMERATE THE LAYOUTS, do not assume them. At minimum: (1) the package''s own dev
  workspace — the leafcutter/ parent holding .leafcutter/ and scripts/ build outputs
  alongside the leafcutter-ai/ git root; (2) a consumer project with leafcutter-ai/
  as a subdirectory, built with ''python leafcutter-ai/scripts/build.py --target-dir
  .''; (3) a git worktree created off origin/main. RUN set-up in each. A call-site
  assertion cannot see a resolution that returns the WRONG location, which is exactly
  the observed defect.'
- The never-built case falls through to GE-120d-2-i's message, not to a silent no-op
  — this AC removes the REASON resolution fails; GE-120d-2 and GE-120d-2-i govern
  what happens when it still does.
- 'ADR-001 deployed/template parity across all three copies of setup_ticket_worktree.py
  (templates/scripts/, scripts/, .leafcutter/scripts/): edit the template, run ''python
  scripts/build.py --target-dir .'', confirm all three match. Callers run the deployed
  copy, so a template-only change is a no-op.'
```
