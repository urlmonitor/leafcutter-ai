# ADR-059: Decision Store — Reviewable YAML Records Now, a Graph Later

## Status

| Field | Value |
|---|---|
| Status | Accepted |
| Date | 2026-10-01 |
| Deciders | BrainCandy |
| Author | Claude Code, recording the user's decisions in [TICKET-20261001-KernelDecisionStore](../../../tickets/00_inbox/TICKET-20261001-KernelDecisionStore.md) |
| Supersedes | None. Deliberately departs from colony concept section 7 and from ADR-057 (see Context) |

## Context

The kernel decides design questions with evidence, a Jev-ranked comparison of options and a human
choice ([ADR-053](ADR-053-intelligence-selection-deterministic-jev-llm-human.md)). It forgets
each answer when the run ends. [ADR-056](ADR-056-colony-memory-evidence-reinforcement.md) wants
the colony to learn from decisions, and the user's Neo4j colony memory concept proposes a graph
database for that
([concept part 2](../../analysis/2026-10-01-neo4j-colony-memory-concept-2-layers-truth-sync.md),
section 7: learned knowledge "may initially live only in Neo4j").

The question "how should Leafcutter file decision records so later runs can reuse them as
precedent" was put to the kernel itself. Run `run-2fbb4ef43b1345f6` (Langfuse trace
`c93592ca1a813365b7d48d5a8363c66d`) resolved decision `dec-ef8ddcb79d668a67`: the human chose
"Kernel-contract YAML per decision". The Stage 0 review of the concept
([delta, part 4](../../analysis/2026-10-01-colony-memory-stage0-delta-4-decisions-needed.md))
had recommended a Null-only memory for Mode 0 and a graph store for learning.

The user then decided (2026-10-01): **no Neo4j yet**; decisions are files in `docs/` behind a
memory interface; precedent works from day one; only human-approved decisions become records.
ADR-057 (a PostgreSQL-first memory store ADR) exists only in another, uncommitted worktree. It is
named here and not linked, and this ADR does not amend it.

## Decision

### 1. One YAML file per approved decision

A decision a human approved MUST be filed as `docs/decisions/<dec-id>.yaml`, one file per
decision, in the format of decision `dec-ef8ddcb79d668a67`: the fields of the kernel `Decision`
contract and of concept section 15 (question, decision type, task context, options, criteria,
evidence references, selected option, assessment, final outcome, corrections), concept section 12
provenance, flat classification filters (component ids, `change_target`, `risk_surface`, roadmap
phase, rule file-type globs, a `repository_wide` flag), an approval block and append-only
corrections. The structure is validated by `config/decision_record.schema.json`.

### 2. The kernel talks to a port, not to files

The kernel MUST reach decisions only through the `ColonyMemory` port (`find_decisions`,
`get_decision`, `stage_decision`; `kernel/memory/port.py`). The backend is `memory.backend` in the
kernel config: `file` (default) or `null`. A graph backend MUST be able to replace the file
backend without any change to the kernel. This is the one place the concept's graph can attach.

### 3. Records are findable through a generated index

`docs/decisions/index.json` is generated by `python -m kernel decisions index` and MUST NOT be
edited by hand. It lets a later run pick candidates by filter and text without opening every
record. The knowledge map reads each record's id, title and component edges with its stdlib
parser through the existing `docs` surface (records use a plain-YAML subset). A dedicated
`decisions` surface in `config/paths.json` would also carry the `supersedes` and `related` edges;
it is deferred because a new `config/paths.json` entry is a package surface and needs an
acceptance criterion with `package_surface: true`, which this work does not carry.

### 4. Validation rides the normal test suite, not a new hook

`python -m kernel decisions validate` checks every record (schema, unique ids, resolvable
supersede links, a human approver, filters drawn from the existing vocabularies) and that the
index is current. It runs in a unit test over the committed store and in CI. No pre-commit hook is
added: a hook is package surface and needs acceptance criteria, which this work does not carry.

### 5. Precedent is evidence from day one

When a decision starts, the kernel MUST look up matching records and let Jev judge whether each
applies. An applicable record becomes `prior_decisions` evidence with its provenance (record path
and approver). Precedent MUST NOT change routing scores or thresholds: that stays behind the
calibration gate of ADR-056 section 9. The approval rules are in
[ADR-060](ADR-060-source-of-truth-and-approval-authority.md).

## Consequences

### Positive

- Decision memory works in every install, with no new service, secret or migration.
- A decision, an approval and a correction are small, reviewable git diffs in one file.
- The graph stays possible: records carry the ids and provenance a graph ingester needs.

### Negative

- File records do not do semantic or graph retrieval. Candidates come from filters and a
  content-word score; Jev, not the score, judges applicability.
- Learned knowledge now lives in Git, which departs from concept section 7. Concept stages that
  assume Neo4j hold learned records need re-reading against this ADR.
- Every published record costs a commit and a review.

### Operational

- `kernel/memory/` holds the port, both backends, the record model, builder, validation, index,
  publication and the `decisions` CLI.
- CI runs `python -m kernel decisions validate` (through `tests/kernel/memory`).

## Alternatives

- **Neo4j now (the concept's plan).** Rejected by the user's decision: new infrastructure, secrets
  and a sharing question, for no precedent benefit a file store cannot give at this size.
- **A single JSON registry file.** Rejected: every decision touches one file, so merges conflict
  and diffs are large.
- **Markdown with YAML front matter, ADR-style.** Rejected in the kernel run itself: it breaks the
  goal's "JSON or YAML files".
- **Component-scoped folders.** Rejected: a flat folder with filters in the record and the index
  needs no move when a record's components change.
- **Reuse the AC store's ids and validators.** Rejected: ids come from the run (ADR-061), and
  extending the AC schema would couple two unrelated stores.
