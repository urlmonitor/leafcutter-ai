## Acceptance Criteria

```gherkin
Given two failing tests that differ in exactly one respect: the first carries a
    tag naming the kind of proof it was written to give, and the second carries
    none,
  And both carry the same existing coverage tag for the same piece of work,
When the run's outcome is decided,
Then both tests are treated identically, and the run's outcome is the one it
  would have had if neither tag were present,
  And the existing coverage tag alone continues to decide which failing tests are
    treated as blocking,
  And a piece of work whose tests all carry kind tags is no closer to being
    counted done than the same work with the tags removed,
  And removing every kind tag from the suite changes no run outcome and no
    completion decision anywhere.
```

### A GREEN FIRST RUN IS THE EXPECTED RESULT — DO NOT TREAT IT AS A TDD-ORDER VIOLATION

This is the one place the standard red-baseline rule inverts, and getting it wrong will
either halt the drive or produce a fabricated failure.

`CLAUDE.md` says a `test-writer` phase that finds the target suite already green is a
TDD-order violation. **That rule does not apply to a negative control.** This AC asserts
an *absence*: that stripping every `# angle:` tag changes no outcome. If `BP-1100g-3` was
implemented correctly — and `2f740cc4` left `_classify_outcomes` and `verify_done_eligible`
byte-for-byte unmodified — then these tests are **green on arrival by construction**. That
is the proof, not a failure of process.

So:

- **`test-writer`:** write the tests, run them, and record the observed result honestly
  whatever it is. Green is a pass here. Do **not** weaken an assertion, invert an
  expectation, or add a temporary production edit in order to manufacture a red baseline.
  State in the sign-off that a negative control is expected green and why.
- **`python-coder`:** you have **no production file to edit**. If every test is green,
  your phase is a no-op — sign off saying so. That is the correct outcome, not a skipped
  phase.
- **If any test goes RED, that is a real defect, not a test bug.** A red here means the
  angle axis leaked into the enforcement or completion path. **Surface it as a
  `status: blocker` naming the leak** — do not adjust the test until it passes, and do
  not "fix" it by editing an out-of-scope file without saying so.

The discriminating power of this ticket comes entirely from the tests being able to fail.
A test rewritten until it passes is worth nothing here.

### The strip-the-tags test must strip from real files on disk

The third test copies a real test subtree to a temp dir and removes every `# angle:` line
**from the files**, then re-runs both decisions. An in-memory version that filters the
`angles` key out of already-parsed records cannot catch a tag consumed anywhere in the
file-reading path, which is most of the surface area. Copy, rewrite on disk, re-read.
