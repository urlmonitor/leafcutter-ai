# No configuration anywhere can turn a declaration into coverage

## Actor / Goal

## Acceptance Criteria

```gherkin
Given the configuration surfaces of the store writer, the reverse-direction
  gate, the coverage reports, and the test-coverage check
When each is loaded
Then none of them exposes a setting that lets a declaration count as coverage,
  satisfy a proof obligation, or be written into `covered_by`
And none of them reads such a setting from the environment or from a
  per-repository override

Given a configuration file that supplies a key asking for a declaration to
  count as coverage
When the configuration is loaded
Then the key is refused and the refusal names the key and states that this
  rule has no configurable form

Given a path that has been placed on GE-124d's warn list, and a file that
  carries an accepted GE-124d opt-out reason
When the four places in GE-124g are evaluated for the criteria those files
  declare
Then neither escape changes any of the four outcomes
```

- [ ] AC-2: none of them reads such a setting from the environment or from a
- [ ] AC-3: the key is refused and the refusal names the key and states that this
- [ ] AC-4: neither escape changes any of the four outcomes

## Implementation Notes

```yaml
- 'SCOPE IS ALL FOUR PLACES, NOT THE STORE. This L3 is filed under GE-124g-1 because
  a parent had to be chosen. Its configuration surfaces are: the store writer (GE-124g-1),
  the reverse-direction gate (GE-124g-2 / check_ui_ac_declared.py''s frontend_ac_declaration
  config), the reports (GE-124g-3 — build output, proof-of-done report, and the Atlas),
  and the test-coverage check (GE-124g-4 / the done-proof surface). Do NOT narrow
  it to the store when implementing.'
- A REFUSED KEY, NOT AN ABSENT FEATURE. Each of those four config loaders must REJECT
  an unknown substitution-shaped key by name rather than ignore it. Absence is indistinguishable
  from 'nobody has asked yet', and the first person to ask will add it; a refusal
  that names the key turns the attempt into a conversation. This requires the loaders
  to reject unknown keys in their own section at all — a permissive loader that silently
  ignores extras cannot implement this AC.
- ENVIRONMENT AND PER-REPOSITORY OVERRIDES ARE PART OF THE SURFACE. The criteria say
  'from the environment or from a per-repository override', and a loader that rejects
  a JSON key while honouring an equivalent environment variable satisfies the letter
  and none of the intent. Enumerate every input each of the four loaders reads.
- THE REFUSAL MUST NOT DISABLE THE AFFECTED CHECK. After refusing the key the check
  continues with the rule in force. Aborting on bad configuration would turn the refused
  key into the bypass it was refused for — the same over-correction GE-124d-1-i guards
  against on the other configuration surface.
- 'THE GE-124d BOUNDARY IS A BEHAVIOURAL CLAIM AND MUST BE TESTED AS ONE: a warn-listed
  path and an accepted opt-out reason change nothing about what a declaration is worth.
  Those escapes govern whether a FILE MUST DECLARE; they never reach these four outcomes.
  This is the third scenario and it is the boundary the PO drew explicitly.'
- This AC is a cross-cutting constraint over four other ACs, so it can only be verified
  once all four surfaces exist. Sequence it last within GE-124g, or accept that it
  is partially red until they land — and say which.
```
