# KI-BO-20260907-0804 — The epic planner omits only `done`, so a parked ticket is re-scheduled every run and halts the drive again

- **Severity:** high
- **Status:** open — no AC
- **Occurrences:** 1 (observed), but structural — it recurs on every run
- **First seen:** 2026-09-07 · **Last seen:** 2026-09-07
- **Where:** the `epic-planner` prompt in `templates/workflows-js/build-feature.js`
  (~:2722, rule 4 of the planner instructions)

**Symptom.** The planner is a `status-checker` agent given a numbered set of rules. The
lifecycle-filtering rule is:

```
(4) Tickets with status 'done', or already recorded complete above, are OMITTED from all batches (resume).
```

`blocked`, `deferred` and `in_progress` are not mentioned, so none of them are omitted. Rule
(2) — "a ticket is ready when every `depends_on` entry names a ticket in the completed set...,
or a ticket whose own frontmatter already reads status: done" — likewise never inspects the
candidate ticket's *own* status, only its dependencies'. A ticket deliberately parked at
`blocked` is planned into a batch on the very next run, dispatched, and — being parked
precisely because it cannot proceed — halts the drive at that batch.

**Observed.** Ticket 12 (`ACD-2100b-5`) was set to `status: blocked` specifically to keep it
out of the ready set so the remaining tickets could build. The next `/build-feature` run
scheduled it as batch 4, dispatched its phases, and halted the epic there. `test-runner`
correctly signed off `failed` rather than false-green, so nothing was corrupted — but the
drive stopped with 11 tickets still `todo` and never reached them.

**Why it matters.** This is the second half of `KI-BO-20260907-0803`. That entry records that
the tool cannot *set* `blocked`; this one records that setting it by hand does not *do*
anything. Together they mean there is currently no way to park a ticket in an epic: not
through the sanctioned tool, and not by the documented lifecycle-edit escape hatch either.
Any epic containing one un-buildable ticket cannot be driven past it, and the operator's only
remaining option is to mark the ticket `done` — a phantom-done write — or to stop driving the
epic.

The severity is high rather than medium because the failure is silent in the direction that
matters: the planner does not report that it scheduled a parked ticket, and the halt it
produces looks identical to a fresh blocker.

**The fix already exists and is not wired up.** `scripts/ticket_prioritizer.py:44` defines
`EXCLUDED_STATUSES = {done, in_progress, blocked, deferred}` — exactly the correct set, with
a docstring describing this dependency-aware selection as its purpose. The planner does not
call it. It re-implements batch selection in an LLM prompt and gets the status vocabulary
wrong by omission.

**Fix direction.** Either have the planner call `ticket_prioritizer.py` and plan over its
output, or — if the prompt must stay authoritative — restate rule 4 to omit every status in
`EXCLUDED_STATUSES` by name, and say what to do with them (report as skipped, do not
dispatch). Prefer the first: a prompt and a script that both encode the same lifecycle
vocabulary will drift, and this is that drift.

**Detection.** Set any ticket in an epic to `status: blocked` and run `/build-feature` on the
epic. If the returned payload lists that ticket in a batch or in `halted_tickets`, this
defect is live. No test covers the planner's status filtering.

**Re-verified 2026-09-23 against current source before filing.** `templates/workflows-js/build-feature.js`'s
epic-planner prompt (rule 4, now ~:2722, reading "Tickets with status 'done', or already
recorded complete above, are OMITTED from all batches (resume)") still omits only `done` and
the run's own completed set — `blocked`, `deferred`, and `in_progress` remain unmentioned, and
the readiness rule (rule 2) still checks only `depends_on` targets, never the candidate
ticket's own status. `scripts/ticket_prioritizer.py`'s `EXCLUDED_STATUSES` (:44, still
`{done, in_progress, blocked, deferred}`) remains uncalled from the planner. The defect is
still live.
