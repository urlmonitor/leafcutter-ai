# Every caller stops on anything but a ready answer

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `BO-4300c-3` — Every caller stops on anything but a ready answer — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `BO-4300c-3`. Component: `build-orchestration`. Assigned agent: `python-coder`. Estimated complexity: `L`. Complexity: `high`.

## Acceptance Criteria

```gherkin
Given each workflow that needs a workspace -- the long-running build, the
  single-ticket build, the quick fix, the requirements-authoring session, the
  fast lane and finalize -- is run with the workspace maker's answer replaced,
  in turn, by: a refusal; an error; a paragraph of prose; an answer that states
  neither ready nor refused; and no answer at all,
When the workflow receives that answer,
Then it ends with a failure that quotes what it received,
And its recorded dispatches contain no authoring, phase, commit or delivery
  step after the workspace step,
And it does not continue in the main copy, in the epic folder, in the folder it
  was started from, or in any location it was not given in a ready answer.
```

- [ ] AC-1: it ends with a failure that quotes what it received
- [ ] AC-2: its recorded dispatches contain no authoring, phase, commit or delivery
- [ ] AC-3: it does not continue in the main copy, in the epic folder, in the folder it

## Implementation Notes

```yaml
- 'Every workflow applies ONE acceptance predicate to the maker''s answer: it parses
  as a single JSON object AND status == ''ok'' AND workspace_path is a non-empty string;
  anything else ends the run with status error, quoting (bounded to 2 KB) what was
  received.'
- 'ONE BUILD-INLINED BLOCK, NOT HAND COPIES (duplication audit C3; KI-BO-20260925-finalize-gate-accepts-agent-answers
  is the hand-copy failure this prevents): the acceptance predicate and the workspace
  dispatch helper live in ONE marker-delimited block (e.g. `// WORKSPACE-ANSWER-START`
  / `// WORKSPACE-ANSWER-END`) with a single tracked source outside the deployed workflow
  set (e.g. templates/workflows-js/_shared/, which the shallow *.js glob in build_workflow_scripts
  does not deploy as a workflow). Each consuming workflow template carries only the
  marker pair; the workflow build phase (scripts/build_phases_workflows.py) fills
  it with the source block, and a template whose marker pair already holds text, or
  a source block that is missing, fails the build rather than being deployed. E2 bodies
  still have no require (ADR-030); inlining happens at build time only.'
- 'Precedent, verified 2026-09-25: the BO-3900-PATH-HELPERS-START/END blocks are the
  marker convention this follows, but they are NOT build-inlined and have NO parity
  test -- build-feature.js and plan-feature.js carry different text between the same
  markers today, and unit_tests/portability/_bo3900a_js_classifier.py and unit_tests/workflows/_bo3900e_resolver_harness.py
  only slice them out for Node execution. This record therefore delivers the build
  inliner and the parity test; moving the BO-3900 block onto the same mechanism is
  a follow-up outside this tree.'
- 'Parity and coverage are tested on the DEPLOYED workflows: the block text in every
  deployed workflow that carries the markers is byte-identical to the source block,
  and every workflow that consumes a workspace (reads args.workspace, or issues a
  workspace dispatch in its BO-4300a-1-ia harness run) carries the block. The consuming
  set is derived, never a hard-coded list.'
- The build inliner is a change to the build pipeline (scripts/build_phases_workflows.py)
  and must keep that phase's compare-before-write idempotency (a second build writes
  nothing) and run before config-placeholder injection.
- 'Remove every fallback that treats ''no workspace'' as a normal state (F2): plan-feature.js''s
  null-worktree mode and every `authoringWorktreePath ? ... : ...` branch, build-epic.js''s
  callerWorktreePath || probe || epicPath fallback, finalize-feature.js''s worktree_root
  ''unknown'' default, fast-lane-ship.js''s `gitReportedPath || claimedWorktreePath`,
  build-ticket.js''s unchecked args.worktree_path. Line numbers in the analysis are
  hints; verify against HEAD.'
- The workflows covered are the long-running build, the single-ticket build, quick
  fix, requirements authoring, the fast lane and finalize; the five hostile answers
  are a refusal, an error, a paragraph of prose, a JSON object with neither ok nor
  refused as status, and no answer at all.
- Entry skills that run the maker stop on a non-zero exit (BO-4300a-1-ib); this AC
  covers the workflow bodies.
- 'Workflow bodies run in the E2 engine with no filesystem or process access (ADR-030).
  They reach the maker only through (a) args.workspace -- the maker''s JSON object
  passed verbatim by the entry command or skill (BO-4300a-1-ib) -- or (b) exactly
  one agent() dispatch, carrying a result schema, to an agent whose registry entry
  has permits_shell: true, instructing it to run one exact absolute command unchanged
  and return stdout verbatim. Never status-checker (permits_shell: false), never free-form
  set-up steps.'
- Workflow edits are made in templates/workflows-js/*.js and reach .claude/workflows/
  only through the build; the deployed copy is what the tests run.
- Proof runs the workflow under unit_tests/_workflow_engine_harness.py -- the deployed
  copy the build produces, so the build's workflow transform is exercised -- with
  label-scripted agent replies, and asserts on the RECORDED dispatch list, never on
  workflow source text. The harness must be able to model a workspace step that declines
  its task, answers in prose, answers exit 0 with a non-JSON path, or answers JSON
  without status (F13); extending the harness for this is in scope of the first AC
  that needs it.
```
