# Tracked-source guard plus truthful broken-reference message (BP-900f + BP-900c-3)

## Actor / Goal

As the leafcutter-ai system, I want the build to fail loudly when any deployable
script's source is present on disk but **not tracked in git**, and I want the
broken-reference report to give a **truthful** suggested action — so that a fresh
clone / CI can never silently build green on leftover untracked working-tree
files, and so the error message points to the real fix.

This is the durability half of the build-resilience work whose first half
(relocating the feedback source to a tracked mirror) shipped as BP-1000a-5.
This branch is stacked on `feat/BP-1000a-5`.

## Acceptance Criteria

### BP-900f-1 (L2) — classify each deployable-script source as tracked/untracked
```gherkin
Given the build has resolved the deployable-script source set (every script
  path the build will ship, as produced by the existing source-resolution step)
And one path in that set, scripts/feedback/submit_feedback.py, is present in the
  working tree but has not been committed to git (untracked)
And another path in that set, scripts/commit_guardian/check_ac_schema.py, is
  committed to git (tracked)
When the tracked-source guard inspects the deployable-script source set
Then it marks scripts/feedback/submit_feedback.py as untracked
And it marks scripts/commit_guardian/check_ac_schema.py as tracked
And it produces a list of zero or more deployable scripts whose source is
  untracked, derived from the git index, not from mere presence on disk
```

### BP-900f-2 (L2) — build fails non-zero and names every untracked source
The guard, when the untracked list is non-empty, makes the build exit non-zero,
writes no partial deployment, and names each untracked source on stderr. An
empty list is a no-op (build proceeds). See `BP-900f-2.yaml` for exact Gherkin.

### BP-900f-3 (L2) — generalizes beyond feedback, fresh-clone reproducible
An untracked source in any deployable directory (not just feedback) is caught
with no directory-specific special-casing; the verdict is reproducible on a
fresh clone. See `BP-900f-3.yaml`.

### BP-900c-3 (L2) — truthful suggested_action when source missing/untracked
When the broken-reference guard reports a missing script whose source directory
(and deploy phase) already exist but the file is missing/untracked, the
`suggested_action` says the source is missing/untracked and must be committed
under `templates/scripts/` — NOT the current "add a deploy phase in
build_phases.py". See `BP-900c-3.yaml`.

### BP-900c-3-i (L3) — directory entirely absent still says "add a deploy phase"
When the source directory itself is absent, `suggested_action` still points to
adding a deploy phase; both action types coexist per-entry in one report. See
`BP-900c-3-i.yaml`.

## Implementation Notes

- Tracked-ness MUST be determined from the git index (e.g. `git ls-files`),
  resolved repository-root-relative, NOT from filesystem presence.
- Wire the new guard so it runs in the build preflight (alongside / within
  `_check_script_reference_guard()`), before any output is written.
- Follow the project Error Handling Policy (Rules 1–3): wrap the git query and
  any file access in specific exception types, log at WARNING+, and surface an
  inability to determine tracked-ness as a determinate guard error — never a
  silent pass.
- Do NOT special-case the feedback directory; the guard must be generic over the
  whole deployable-script source set.
- Keep `_suggest_action()` decision state-based: missing-but-dir-present-or-
  untracked → "commit under templates/scripts/"; dir-absent → "add a deploy
  phase". Both must be emittable in the same report run.
