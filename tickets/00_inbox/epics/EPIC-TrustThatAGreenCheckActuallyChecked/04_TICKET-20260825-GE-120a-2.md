# Each check declares, for itself, whether a cannot-run condition blocks or only announces

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-120a-2` — Each check declares, for itself, whether a cannot-run condition blocks or only announces — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-120a-2`. Component: `guardrail-engine`. Assigned agent: `python-coder`. Estimated complexity: `L`. Complexity: `high`.

## Acceptance Criteria

```gherkin
Given the registry of pre-commit checks that the guardrail engine installs,
When a check is registered,
Then its registration records an explicit cannot-run disposition with exactly one of two
  values — "block", meaning a could-not-check outcome fails the commit, or "announce",
  meaning a could-not-check outcome is reported unmissably and the commit proceeds,
And no value is inferred on the check's behalf when the field is absent,
And when a check reaches a could-not-check outcome, the disposition recorded for that
  check is what determines whether the commit fails — demonstrated by running one check
  under a genuine cannot-run condition once with each disposition and observing two
  different commit results,
And at least the two checks whose cannot-run behaviour was observed carry a recorded,
  reviewable decision with a stated reason: the AC-parent-covered-by check and the
  AC-schema check,
And the recorded disposition is readable without running anything, so the decision for
  every check can be reviewed as a set.

Coverage note: the determining clause is covered by executing the check under both
dispositions and comparing the commit results. Asserting that the disposition field is
present in the registry does not cover it — a field that is read by nothing passes that
assertion.
```

## Implementation Notes

```yaml
- 'OPEN QUESTION RESOLVED — there is no ''mode: error/warn'' field to extend. VERIFIED
  2026-08-14 against templates/scripts/commit_guardian/commit_guardian.json: hooks_manifest.hooks[]
  holds 54 entries whose keys are only id, tier, name, entry, language, stages, pass_filenames,
  plus files on 45, _comment on 39, enabled on 6, types on 5, always_run on 3, and
  fail_open on exactly ONE (check-glossary-coverage). tier is judgment (48) or transform
  (6). The nearest per-check severity axis is the strict boolean inside per-check
  config sections (duplicate_code, diff_coverage). The cannot-run disposition is therefore
  a NEW, DISTINCT manifest key — not a second axis of an existing field.'
- 'Name it so it cannot be confused with the existing fail_open boolean or the tier
  field, and state in the entry _comment that it governs what the check does when
  it cannot LOOK, not what it does when it FINDS a violation. Decide explicitly what
  happens to the single existing fail_open: true entry (check-glossary-coverage) —
  leave it, or express it as a disposition — and state the decision; two overlapping
  fields is the ambiguity this AC exists to remove.'
- 'Every one of the 54 hooks_manifest entries carries an explicit value. No inferred
  default anywhere in the read path: a code-side .get(key, ''announce'') would silently
  defeat both this AC and GE-120a-2-i and must not exist. Absence is an error condition,
  not a value.'
- The disposition must be DATA-DRIVEN from the manifest — never a per-check code branch
  and never a hard-coded id list. A new check inherits the rule by being registered,
  not by being named. Any exemption must derive from a property of the entry (for
  example tier), never from an id.
- Record the reason for each decision beside the value; the manifest already uses
  per-entry _comment for exactly this. At minimum check-ac-parent-covered-by and check-ac-schema
  carry a stated reason.
- 'CANONICAL SOURCE: templates/scripts/commit_guardian/commit_guardian.json. templates/commit-guardian/commit_guardian.json
  is the legacy mirror and the config/ copy is a build output; check_hook_parity compares
  both manifests. Edit the canonical file, then run ''python scripts/build.py --target-dir
  .'' — never edit a build output (ADR-001).'
- The review surface is the manifest JSON itself, read without executing anything.
  Do not introduce a generated index or report as the reviewable surface; a derived
  artifact can go stale relative to the field that actually governs.
- 'The determining clause requires a real two-disposition execution: run one check
  under a genuine cannot-run condition with disposition block and again with announce,
  and observe two different commit results. A unit test over the read path alone does
  not demonstrate that the manifest value governs the commit.'
```
