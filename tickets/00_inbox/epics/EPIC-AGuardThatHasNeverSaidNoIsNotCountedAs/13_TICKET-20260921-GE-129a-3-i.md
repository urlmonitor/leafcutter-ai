## Implementation Notes

```yaml
- RECEIPT IS A PRECONDITION OF A VERDICT, NOT A PROPERTY INFERRED FROM ONE. The run
  must hold positive evidence that a guard received its input before it records anything
  other than never-attempted or blocked. Absence of evidence is never approval, and
  an exit code obtained from a process that read nothing is not an answer to a question
  that was never put.
- THE TWO HONEST VALUES ARE NOT INTERCHANGEABLE AND MUST NOT BE COLLAPSED. config/verification_flow.schema.json's
  `unverified` means the attempt was never made; `blocked` means the attempt could
  not be run to a verdict. They mean different things to a reader — the first is a
  to-do, the second says something is in the way — and collapsing them turns a work
  list into a shrug. Both must also be distinguishable in the run's output from a
  guard that was genuinely asked and allowed the input through, which is a third and
  separate report.
- 'THIS CONSTRAINT IS ABOUT THE RUN''S OWN DISCIPLINE, NOT ABOUT ANY GUARD''S. It
  must hold for a guard that does legitimately read a command line: such a guard invoked
  the wrong way may well answer, and the run must still not count that answer, because
  it is not the answer the protected surface would have got. Do not implement this
  as a check on whether the guard reads argv.'
- ARRIVAL COLOUR IS GREEN AND VACUOUSLY SO — the parent record says this, and it is
  why the injection below is mandatory rather than illustrative. Nothing examines
  these guards today, so nothing currently reports a clean exit as a demonstration.
  A green descriptor that has never been able to go red is not coverage; run the injection.
- 'AC_ENFORCE_STRICT=1 on every pytest invocation below. Error-handling policy applies
  to the subprocess I/O: specific exception types, logged at WARNING or higher or
  re-raised. A swallowed invocation error is `blocked`, never an absent record and
  never a pass.'
```
