## Acceptance Criteria

```gherkin
Given the record's checker is registered among the project's automatic checks,
When a change is offered and the checker does not execute, whether because it was skipped,
  because it was disabled, or because it could not start,
Then the automatic checks report that the record was not checked, naming which of those three
  reasons applied,
And that report is not the report produced when the record was checked and found sound,
And the report names the checker, so a reader can tell which check is missing rather than
  only that one is.
```

Design concern for python-coder/test-writer: the three reasons a checker
"does not execute" — skipped, disabled, could not start — are NOT all the
same layer. "Disabled" and "skipped" are properties of the pre-commit /
commit_guardian configuration and execution wrapper (`run_hook.py`,
`.pre-commit-config.yaml`, `SKIP` env var, `stages:`), observable BEFORE
`validate_product_truth.py` itself ever runs; "could not start" can arise
either at that same wrapper layer (interpreter/script missing) or inside
`run_hook.py`'s own subprocess dispatch. None of these three states are
currently distinguished by any existing report — `check_outcome.py` today
only speaks for a check that DID start but could not complete its own
inspection (`OUTCOME_COULD_NOT_CHECK`), which is a different failure mode
from a checker that never started at all. Do not conflate the two: adding a
new outcome value (or a new "not_run" report emitted by `run_hook.py` itself
before delegating) is preferable to overloading `OUTCOME_COULD_NOT_CHECK`
for a state the check body never got the chance to emit. The test spec's own
entry-point angle is explicitly undeclared ("the AC authored no test_spec, so
the entry point is not declared: resolve it before writing this test") —
test-writer/python-coder must resolve that as `run_hook.py`'s own CLI
invocation (the same one already wired in `.pre-commit-config.yaml` for
`check-product-truth-validate`), not a bare import of `validate_product_truth.py`,
since the "did not execute" states are properties of the wrapper's dispatch,
not of the checker script's internals.

Acceptance-criteria adjustments: none — AC-1/AC-2/AC-3 already correctly
separate the three not-run reasons from the checked-and-sound case; no
rewording needed.
