## Acceptance Criteria

```gherkin
Given the consumer-simulation project from BP-900h-1 — built into a directory that started
  empty and held only a minimal skills_config.json, never a copy of this repository,
And with no opt-in documentation-seeding step performed, so the project holds only what a
  plain install leaves behind,
And that project initialised as a git repository with the deployed commit-time guards active,
When the job stages an ordinary change a new adopter would make and attempts a commit through
  the ordinary commit path — no skip flag, no environment override, no direct invocation of
  any guard script,
Then the commit completes,
And the job fails, naming the guard that blocked and the content it demanded, if any deployed
  guard blocks that commit over an artifact a brand-new project legitimately does not yet
  have,

And the job records which guards actually executed during that commit and reports that record
  as part of its output,
And a commit that completed because no guard ran is reported differently from a commit that
  completed because every guard that ran passed,
And the job fails when no guard executed at all, so a simulation in which the guards were
  never wired is not reported as a successful adopter experience,

And the job carries no continue-on-error, is not skipped on pull request events, and fails the
  pull request when the commit step fails.

Coverage note: this is the clause that separates building an install from using one. A job
that runs the install and inspects the resulting file tree cannot observe a guard that blocks
an adopter, because that guard only speaks when a commit is attempted — and the repository has
shipped seven consumer-install defects and four unregistered guards while every static
deployment check stayed green. Covered by performing the commit and asserting on what the
commit path did, plus a negative case: a deliberately adopter-hostile guard fixture must be
shown to turn this job red, or the job is a green step that proves nothing.
```
