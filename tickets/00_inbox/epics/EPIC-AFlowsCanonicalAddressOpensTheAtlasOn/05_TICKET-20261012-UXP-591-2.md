## Actor / Goal

## Acceptance Criteria

```gherkin
Given 'resolve' is a step of leafcutter/flow-render-pipeline and 'declined' is a branch of
  fern-and-fig/checkout-and-pay,
When a person opens /flows/leafcutter/flow-render-pipeline?step=resolve, or
  /flows/fern-and-fig/checkout-and-pay?step=declined,
Then the Atlas answers 200 and draws that flow with exactly one drawer open: the 'resolve'
  step's drawer for the first address, the 'declined' branch's drawer for the second,
And that drawer shows the same contents a click on that node shows,
And the filters take the flow's own Source and Kind with Realization All
  (Real, Data, All for the first address; Mock, User, All for the second),
And the breadcrumb shows only that flow,
And the address bar keeps the ?step= value as opened.
```

## Implementation Notes

```yaml
- leafcutter-web/app/flows/[...id]/page.tsx reads searchParams.step and passes it
  as the initial drawer id, so the drawer is open in the server-rendered HTML with
  no open-after-mount flicker and no hydration mismatch.
- Resolve ?step= among the flow's steps AND branches with the node keying the explorer
  already uses for clicks (step:<id>), through one lookup shared by deep-link and
  click opening, so a linked drawer renders exactly the click-opened contents (same
  component, same props).
- 'At most one drawer: the view''s drawer state holds a single node id.'
- 'The ?step= value stays verbatim: no normalisation, case-folding or rewrite of the
  address on load.'
- Works for example-product flows under docs/product-truth/flows/fern-and-fig/ as
  well as leafcutter flows; nothing keyed on the product.
```
