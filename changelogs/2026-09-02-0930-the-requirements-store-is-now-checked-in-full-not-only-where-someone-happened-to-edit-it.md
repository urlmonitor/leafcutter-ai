summary: "The automated check on the requirements store only ever looked at the records a single change touched, so a broken record could sit unnoticed indefinitely and some rules spanning several records could never be checked at all. description: "The requirements store has an automated check, and it has been passing. It only ever inspected the records that the change in front of it happened to touch. Two consequences followed. A record that broke a rule before the check existed, and that nobody has edited since, was never once looked at — eight such records were found this week, invalid for twenty-three days while every check reported green. And some rules are about relationships between records rather than about any single one: how many children a parent may have, whether dependencies form a loop, whether a parent and child still point at each other. Two separate changes can each be perfectly valid on their own and together break one of those, and a check that only sees one change at a time is structurally incapable of noticing. A second check now runs whenever work lands on the main line and applies the identical rules to every record in the store. Getting it to actually do that was the hard part, and the first attempt did not. The checks discover which records to examine by asking the version-control system what is pending, so on a fresh copy with nothing pending they examined zero records and reported success — a check that would have passed forever while inspecting nothing, which is precisely the kind of false reassurance the whole exercise exists to eliminate. It was caught before it shipped by the automated review step. The obvious remedy suggested at review — telling version control to mark the files as pending — does not work either, because nothing has actually changed about them and so nothing becomes pending; applying it would have produced something that looked repaired and still inspected nothing. What works is making the system treat the entire store as newly arrived, which is a variation on the trick the existing per-change check already uses. That is now verified by tests that run the real machinery against a temporary repository, including one test whose only job is to record that the plausible-looking remedy does not work, so nobody simplifies it back. A further trap was caught the same way: examining everything also swept in deliberately-broken example records kept as test material, so the check would have failed on its own fixtures. The check reports rather than blocks, for now. Measured honestly against the rules it actually applies, the store has five hundred and twelve outstanding findings — not the eight reported earlier, which had been measured with a different and more lenient tool. Almost all are requirements that describe work without saying how it should be proven. None were introduced by whoever happens to trigger the check. Blocking on the first run would fail everyone's work for a backlog nobody caused, and a check that is always red gets switched off, which would lose the protection entirely. So instead of a five-hundred-line wall of text, the result is grouped by the area that owns each finding, with a plain instruction: clear your own area, or take any ten. A countdown states how many remain and what number turns the check into a blocking one, which is a single line of configuration away."
