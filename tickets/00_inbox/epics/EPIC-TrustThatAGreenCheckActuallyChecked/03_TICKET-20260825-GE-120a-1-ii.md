# A check that falls back to a weaker inspection reports its clean result as unverified

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-120a-1-ii` — A check that falls back to a weaker inspection reports its clean result as unverified — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-120a-1-ii`. Component: `guardrail-engine`. Assigned agent: `python-coder`. Estimated complexity: `S`. Complexity: `low`.

## Acceptance Criteria

```gherkin
Given a check that has an authoritative inspection and a reduced substitute it can fall
  back to when the authoritative one is unavailable,
And the authoritative inspection is unavailable for this run,
And the reduced substitute finds nothing wrong with the staged files,
When the check reports,
Then the clean finding is labelled as produced by the reduced substitute and as not
  authoritative,
And the output names which inspection did not happen,
And the result value is distinguishable from the value produced when the authoritative
  inspection ran and found nothing wrong,
And a reader who sees only the final line can tell the two apart.

Coverage note: cover this by running the check twice on the same staged files — once
with the authoritative inspection available and once without — and asserting the two
results are distinguishable. Asserting only that both exit 0 does not cover it.
```

- [ ] AC-1: the authoritative inspection is unavailable for this run
- [ ] AC-2: the reduced substitute finds nothing wrong with the staged files
- [ ] AC-3: the clean finding is labelled as produced by the reduced substitute and as not
- [ ] AC-4: the output names which inspection did not happen
- [ ] AC-5: the result value is distinguishable from the value produced when the authoritative
- [ ] AC-6: a reader who sees only the final line can tell the two apart.

## Implementation Notes

```yaml
- 'The vocabulary must carry THREE states, not two: ordinary-success (authoritative
  instrument, nothing found), degraded-but-ran (reduced instrument, nothing found,
  NOT authoritative), and could-not-check (never ran). Add the third value to the
  shared outcome module GE-120a-1 introduces. Do not model it as a boolean bolted
  onto success — a boolean read by one caller and ignored by another is how the current
  family diverged.'
- 'An existing flag already models half of this: templates/scripts/commit_guardian/check_ac_schema.py
  carries a schema_validated flag introduced by GE-112 (see that file''s DECISION
  HISTORY, ~lines 29-37, and the manual-validation fallback at ~line 623). Derive
  the degraded-but-ran state FROM that existing flag rather than adding a parallel
  indicator — two flags meaning the same thing is precisely how the GE-112 defect
  arose.'
- The non-authoritative label must appear on the FINAL reader-facing line, not only
  in a mid-run warning that scrolls past. The criterion is that a reader who sees
  only the last line can tell the two runs apart.
- The label must appear even when the reduced instrument found NOTHING at all to report.
  An empty-findings degraded run is the most dangerous of the three states because
  it renders identically to a real pass; it must not print the same closing line.
- 'Generalise, do not special-case: the third state belongs in the shared vocabulary
  so any check with an authoritative/reduced pair inherits it. A change confined to
  check_ac_schema.py would be the fourth point patch in this area (GE-112, GE-118a-1,
  GE-118b were the first three).'
- 'ADR-001 deployed/template parity: edit templates/scripts/commit_guardian/ then
  run ''python scripts/build.py --target-dir .''; scripts/commit_guardian/ and .leafcutter/scripts/commit_guardian/
  must match (check_hook_parity enforces). Any new shared module must also be added
  to deploy_map in scripts/build_phases.py or the hook raises ModuleNotFoundError
  at runtime.'
```
