## Acceptance Criteria

```gherkin
Given a ticket produced by the AC-to-ticket generator whose frontmatter carries a
  traceability block in the two-key form -- the source AC's identifier plus the
  repo-relative path to that AC's store file -- and carries no list-form keys
  (no L2 list, no L3 list, no base-path key),
  And the store AC that block names has work_status "todo", an empty implemented_by
    list and an empty covered_by list,
When the fulfillment gate runs its coverage-resolution step against that ticket,
Then the gate resolves that AC from the traceability block it was actually given,
  And it verifies that AC's work_status, implemented_by and covered_by,
  And it returns a blocking verdict naming that AC and each field that failed,
  And it does not return ok.

Given a ticket whose traceability block is present but yields no resolvable AC in
  any accepted form,
When the fulfillment gate runs,
Then the gate returns a non-ok verdict that names the traceability block as
  uninterpretable and lists the keys it found there,
  And it does not report that the ticket has no AC store fields to verify,
  And it does not return ok on the strength of an empty set of ACs to check --
    an ok verdict requires at least one AC to have been resolved and verified.

Given a ticket whose traceability block uses the list form (an L2 list, an optional
  L3 list, and a base path) and whose named ACs all have work_status "done" with a
  non-empty implemented_by and a non-empty covered_by,
When the fulfillment gate runs,
Then the gate returns ok, and the count of ACs it reports as verified equals the
  number of ACs the block named -- the previously accepted form keeps working
  unchanged.
```

## Implementation Notes

```yaml
- 'THE LOAD-BEARING CONSTRAINT, stated once rather than per-criterion: coverage resolution
  must return an explicit resolved-AC list whose length is observable to its caller,
  and the ok verdict must be conditional on that length being >= 1. An empty resolved
  list must never satisfy the ok condition. Today''s rule -- ok when ''every AC in
  the working list is passed or skipped'' -- is vacuously true over an empty list,
  and that vacuity, not the key names, is the defect.'
- 'TWO ENFORCEMENT POINTS, BOTH MANDATORY, ONLY ONE LOAD-BEARING AT RUNTIME: (a) the
  executable resolver module declared in doc_links, which the tests call, and (b)
  the agent-template prose in templates/agents/ac-fulfillment-gate.md, Steps 1 and
  5, which is what the running gate actually reads. (b) is the point that gates commits;
  (a) is the point that makes the behaviour provable. Changing only (a) leaves the
  live gate vacuous; changing only (b) leaves the AC unprovable and unenforceable.
  Neither alone satisfies this AC.'
```
