# A demanded step nobody accounted for still blocks the finished state, and the block is not lifted by softening what counts

## Actor / Goal

## Context

## Acceptance Criteria

```gherkin
Given a ticket whose record names a phase as needed and carries no sign-off for it,
  And every other phase that record names as needed does carry one,
When a close of that ticket is attempted,
Then the finished state is not written,
  And the ticket's recorded state is left exactly as it was found,
  And the attempt is refused with a message naming the phase that is unaccounted for,
  And the ticket's record still names that phase as needed afterwards -- the refusal is
    not resolved by rewriting the demand away, and the demand is not reclassified as
    not-needed, excluded, or already satisfied as a side effect of being refused,
And given a second ticket carried by the same run, whose record names the same phases as
  needed and carries a sign-off for every one of them,
When its close is attempted,
Then the finished state is written for that second ticket,
So the refusal is a decision taken about the evidence in the record, and not a mechanism
  that has simply stopped writing; and the only way to turn the first ticket into the
  second is to account for the outstanding phase, never to make the check more agreeable.
```

- [ ] AC-7: the finished state is written for that second ticket

config_schema_fragment: null
constraints:
- VERIFY BY EXECUTION, NEVER BY GREP. The parity check already exists in the source,
  so a test that finds it there passes on the broken driver -- the defect is that
  nothing routes to it. Drive both the refused ticket and the control ticket through
  the real workflow via unit_tests/prompt_assembly/harness_build_ticket_guard.mjs
  and assert on the records the run wrote.
- THE REFUSAL IS ROUTED TO, NOT RE-IMPLEMENTED. BO-400a-2-i already specifies this
  refusal for the guarded writer, down to the message string, and is ratified. Do
  not restate it, do not duplicate it in the drivers, and do not add a second implementation
  of the same rule -- a second refusal implementation is a second door under another
  name.
- A REFUSAL MUST NOT MUTATE THE RECORD. Refusing is a read-only outcome. The ticket's
  record must come back exactly as it was found, with the outstanding step still named
  as needed -- not reclassified to not-needed, not marked excluded, not marked already
  satisfied, and not annotated as a side effect of having been refused. Rewriting
  the demand away is the failure mode this clause exists to catch.
- 'THE CONTROL CASE IS PART OF THE CONTRACT, NOT A TESTING STYLE. Every demonstration
  that the mechanism refuses must be accompanied, in the same run, by a ticket that
  IS written finished. BO-400a-2-iii established this the hard way: a driver reverted
  to never writing at all satisfies every refusal clause and looks correct.'
- NO TOLERANCE, THRESHOLD OR GRACE PERIOD. The measured consequence is more halts
  -- roughly 316 tickets whose records demand a step they never got will now be refused
  reliably. That is the correct outcome and it must not be softened by a warn-only
  mode, a percentage allowance, a per-epic opt-out, or an escalating retry that eventually
  writes anyway. The remedy for a record that asks for the wrong thing is to correct
  the record.
- NO OVERRIDE-SHAPED ESCAPE. The blanket override also switches off the allowed-transition
