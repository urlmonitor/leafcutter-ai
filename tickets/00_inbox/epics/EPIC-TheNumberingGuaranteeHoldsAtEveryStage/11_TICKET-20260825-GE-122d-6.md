## Acceptance Criteria

```gherkin
Given a working copy of the project in which the install has been performed by running
  `python scripts/build.py --target-dir .`, so the commit path resolves its checks from the
  deployed layout rather than from the source tree,
And a change staged in that working copy that introduces an artifact claiming a number
  already claimed by a second artifact in the same namespace,
When a commit is attempted through the ordinary commit path — no skip flag, no environment
  override, no direct invocation of the check script,
Then the commit does not complete,
And the output identifies the numbering check by the hook identifier it is registered under,
  and names the contested number and every claimant path,

And given that same built working copy, the deployed registry the commit path reads —
  `.pre-commit-config.yaml` as it resolves in the built working copy — lists that hook
  identifier, so registration is observable where the commit path looks rather than only in a
  source manifest,

And given the check's registration entry is removed from
  `templates/scripts/commit_guardian/commit_guardian.json` — the 55-entry manifest the install
  deploys the registry from — and the working copy is rebuilt,
When the same contested change is staged and the same commit is attempted,
Then the commit completes and no numbering output is produced,

And given the check is registered ONLY in `templates/commit-guardian/commit_guardian.json` —
  the 3-entry file the install does not deploy the registry from — and the working copy is
  rebuilt,
When the same contested change is staged and the same commit is attempted,
Then the commit completes and no numbering output is produced, so registering the check in
  the non-operative manifest does not satisfy this criterion.

Coverage note: covered only by making real commits in a real built working copy and observing
what the commit path does. An assertion that a hook identifier appears in a JSON manifest, or
that a YAML block exists in a configuration file, does not cover any clause here — this
repository already holds four checks that are written, tested, deployed and registered
nowhere, so the presence of a name is evidence of nothing. The last two clauses are the ones
that distinguish a real wiring from a wiring made in the wrong file: both must be executed,
because a registration placed in the manifest the install ignores produces exactly the silent
no-op this criterion exists to detect.
```

```yaml
- 'RESOLVE THE TWO-FILE AMBIGUITY BEFORE WRITING ANY REGISTRATION. There are two files
  named commit_guardian.json and they disagree: templates/scripts/commit_guardian/commit_guardian.json
  holds 55 entries and is the one the install deploys the registry from; templates/commit-guardian/commit_guardian.json
  holds 3 entries and is not. GE-122d''s coverage matrix names .pre-commit-config.yaml
  as the live registry, while GE-120c-3''s it_requirements treat the 55-entry file
  as authoritative. Both are consistent once the direction is stated: the 55-entry
  manifest is the SOURCE the registration is authored in, and the deployed .pre-commit-config.yaml
  is where the registration must be OBSERVABLE. Assert on the deployed side; author
  on the source side.'
- The verification is a real commit, not an invocation of the check script. Invoking
  the script directly proves the script works and proves nothing about whether the
  commit path reaches it — which is the entire defect. Stage real files in a real
  git index in a real built working copy and run the ordinary commit.
- The two negative clauses are the deliverable, not decoration. A test that only exercises
  the positive path passes identically on a check registered in the wrong file, because
  the positive path can be made to pass by invoking the script from the test. Deregistering
  and rebuilding, then observing the commit succeed, is the only construction that
  fails when the wiring is in the file the install ignores.
- 'DEPLOY MANIFEST: every module the check imports must appear in the matching deploy
  list in scripts/build_phases.py, or the deployed hook raises an import error at

  and it applies to every module _uniqueness_scanners.py pulls in as well as to the
  check itself.'

  build stage: do not register this check until GE-122e''s repair has landed. A whole-collection
  uniqueness check registered over a collection that still holds the GE-119 collision
```
