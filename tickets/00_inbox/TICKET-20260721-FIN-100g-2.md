# finalize-feature: pre-flight arg normalization — accept bare string OR object {target}/{target_branch}

## Actor / Goal

As an operator running `/finalize-feature ge-116a-1` (or passing the target via the workflow
engine as `{target: "ge-116a-1"}` or `{target_branch: "ge-116a-1"}`), I want the workflow
pre-flight to resolve my target argument regardless of whether it arrives as a bare string or
an object, so that both invocation forms route correctly into the same worktree resolution step
(FIN-100g-1).

## Context

**FIN-100g-2 (arg normalization):** The current pre-flight at `line 338` of
`templates/workflows-js/finalize-feature.js` reads:

```js
const epicArg = (typeof args === 'string' ? args.trim() : '');
```

When `args` is an object (e.g. `{target: "ge-116a-1"}` from a `/build-feature` dispatch or the
workflow engine), this silently collapses `epicArg` to `""`, causing the pre-flight to fall
through to CWD-based detection instead of resolving the supplied target. This was surfaced in
user-memory [finalize arg is a string + worktree build-layer false-halt].

**FIN-100g-2-i (empty/missing key fallback):** When the object has no `target`/`target_branch`
key (e.g. `{}`), or the value is an empty string (e.g. `{target: ""}`), the pre-flight must
treat this as "no explicit target supplied" and route to the CWD-based detection (FIN-100g-1)
— not produce an empty-target collapse that could trigger the "must be run from a feature
branch" abort.

## Acceptance Criteria

### FIN-100g-2 — bare string and object forms resolve identically

```gherkin
# covers: FIN-100g-2
Given the finalize workflow is invoked with its target supplied as a bare string "ge-116a-1"
When the pre-flight normalizes its arguments
Then it resolves the target branch to "ge-116a-1"
And given the same workflow is instead invoked with {target: "ge-116a-1"} or {target_branch: "ge-116a-1"}
When the pre-flight normalizes its arguments
Then it resolves the target branch to "ge-116a-1" — identically to the bare-string invocation
And the object form does NOT collapse to an empty target (the typeof-string-only check is removed)
And in both forms the pre-flight proceeds into worktree resolution (FIN-100g-1)
```

### FIN-100g-2-i — empty/missing-key object falls back to CWD detection

```gherkin
# covers: FIN-100g-2-i
Given the finalize workflow is invoked with an empty object {} or {target: ""}
When the pre-flight normalizes its arguments
Then it treats the invocation as "no explicit target supplied" and falls back to CWD-based detection
And it does NOT abort with "must be run from a feature branch, not main" solely because the
object argument could not be reduced to a non-empty string
```
