## Implementation Notes

```yaml
- 'Finder and flow view are reachable from one mounted client tree: app/flows/page.tsx
  and app/flows/[...id]/page.tsx mount the same client shell with the data both modes
  need, so opening a result is a pushState that draws the flow client-side, and a
  popstate onto a finder entry shows the finder, with no router navigation, no server
  request and no page reload.'
- 'The mode is decided from the URL on every load and popstate: a path of exactly
  /flows is the finder, read from its query; anything else is a flow entry, restored
  as UXP-591-5-ii states. The finder needs no stored history state.'
- 'Opening a result first flushes any pending finder address write (UXP-617-2), then
  pushes through the UXP-591-5 push path with view state {crumbs: [flowId], filters:
  {source and kind of the flow, realization ''all''}}, at flowHref(flowId) for a card
  or flowHref(flowId, nodeId) for a row.'
- A plain primary click is handled in-app; modified clicks (Ctrl, Meta, Shift, middle
  button) are left to the browser's link behaviour. Enter on a focused row or card
  does the same as a click.
- Search and facet state lives only in the /flows query string; a flow's canonical
  address (/flows/<product>/<flow>[?step=<id>]) never carries finder state, and a
  finder address never carries a flow or step parameter. History is written only with
  window.history.pushState / replaceState through leafcutter-web/components/flows/flow-history.ts
  (view state under 'leafcutter:flows-view', merged beside the App Router's __NA and
  __PRIVATE_NEXTJS_INTERNALS_TREE keys); router.push, router.replace and router.refresh
  are never used for Flows history.
- The explorer does not remount on pops between flow entries (the UXP-591-4 remount
  guard stays green).
```
