## Implementation Notes

```yaml
- 'THE PIN SOURCE IS THE ATTRIBUTE NAME `data-ac`, MATCHED EXACTLY. Not a prefix match,
  not a substring search for an id pattern anywhere in the tag. `className`, `class`,
  `data-testid`, `data-screen` and any `data-ac-*` variant contribute nothing to ac_ids.
  The mock-data invariant is absolute: AcDeclaration.attribute == ''data-ac'' for
  every record.'
- BOTH ATTRIBUTES ON ONE ELEMENT IS THE REAL CASE, NOT THE EDGE CASE. Real pinned
  elements carry class and data-ac together (mock record `decl-stock-badge`), and
  class values contain framework interpolation (`stock--{status}`, `${styles.x}`)
  that must not confuse the attribute scan. Parse the opening tag attribute-wise rather
  than regexing the whole tag for id-shaped tokens.
- 'This constraint applies to the whole pipeline, not just the reader: no report,
  selector or store field may reconstruct a pin from a class name. A class-derived
  marker is mangled by CSS-modules hashing and purged by Tailwind content scanning,
  so it would produce a traceability link that exists in source and not in the built
  product — worse than none.'
```
