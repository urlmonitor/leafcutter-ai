# Several tickets in the identical state, carried by one run, all get the same answer -- and it is the strict one

## Actor / Goal

## Acceptance Criteria

```gherkin
Given one run carrying four tickets,
  And the first three are in the identical state: their records name the same phases as
    needed, every one of those phases carries a sign-off, except one and the same phase
    in all three, which carries none,
  And the fourth ticket's record names those same phases as needed and carries a
    sign-off for every one of them,
When the run reaches the close of each of the four,
Then the first three all receive the same answer as each other,
  And that answer is refusal: none of the three has its recorded state changed, and each
    refusal names the same outstanding phase,
  And the fourth is written finished,
  And the answers do not vary with the order in which the run reached the tickets, nor
    with which of the four was closed first,
And given a second run over the same four tickets in the same state,
When it reaches the close of each,
Then it produces the same four answers as the first run,
So one run cannot give two answers to one question, the answer it gives is the strict
  one, and "the same answer every time" is not obtained by a run that refuses
  everything.
```

## Implementation Notes

```yaml
config_schema_fragment: null
constraints:
- FOUR TICKETS, ONE RUN -- CARDINALITY IS THE WHOLE POINT. A per-ticket assertion
  gathered from four independent single-ticket runs does not reproduce this defect
  and does not satisfy this record. At one ticket the broken driver and the fixed
  driver are indistinguishable, because either branch is defensible in isolation;
  the defect IS the disagreement between tickets inside a single run.
- ORDER-INDEPENDENCE IS A PROPERTY OF THE DECISION, NOT OF THE FIXTURE. No state accumulated
  during a run -- a memo, a cache, a running tally, a set of already-seen phases,
  a batch index -- may influence a later ticket's answer. The observed split correlated
  with position in the run (ticket 01 refused, tickets 03 and 20 written); an implementation
  whose answer depends on how far into the run a ticket sits has not converged, it
  has moved the disagreement somewhere harder to see.
- 'DETERMINISM MUST NOT BE OBTAINED BY REFUSING EVERYTHING. ''All four the same answer''
  is a property a completely broken writer holds trivially. The fourth, fully-signed-off
  ticket is part of the contract, not a testing nicety: only the contrast makes the
  three refusals attributable to the missing sign-off.'
- THE PER-TICKET DECISION MUST BE INDIVIDUALLY OBSERVABLE. The run must expose the
  record write it performed for EACH ticket, separately. A run that reports only an
  aggregate outcome cannot be checked for agreement between its tickets, which is
  exactly the observability gap that made the original defect look like agent caprice
  for a day.
- 'VERIFY BY EXECUTION, NEVER BY GREP. Nothing about this record is visible in the
  source: the broken driver and the fixed one both contain completion code, a phase
  list and a parity check. Only reading back the four records a single run produced
  can tell them apart.'
- BOTH TWINS IN ONE CHANGE, per BO-400a-2-ii's standing constraint.
```
