# The guard this epic keeps citing is examined on the real surface, in the copy the entry that runs it actually resolves to, and is reported as never having refused anything — beside a guard on the same surface that has

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-129a-4` — The guard this epic keeps citing is examined on the real surface, in the copy the entry that runs it actually resolves to, and is reported as never having refused anything — beside a guard on the same surface that has — so that the acceptance criterion is satisfied.

## Acceptance Criteria

```gherkin
Given the guard the project's own records cite as running before every edit and unable to
  refuse anything — readme_read_guard, wired on the settings surface the project ships —
And the copy of that guard the editor runs is not the copy the project edits: the entry's
  own command walks up from where work is happening to an installed hook directory and
  runs what it finds there,
When the liveness run examines the real surface rather than a stand-in for it,
Then that guard is among the subjects the run reports,
And the run states which copy of it the examination loaded, and that copy is the one the
  entry's command resolves to when it is run from where the editor runs it,
And a copy that entry does not resolve to is not examined in its place,
And for as long as that guard allows its declared input to proceed, it is reported as not
  having demonstrated a refusal and is absent from anything the run says is protecting the
  work,
And at least one other guard the same real surface names is reported in that same run as
  having demonstrated its refusal, so being named as unproven is a finding about this guard
  rather than the only thing the run is able to say,
And the state reported for that guard is the state its own examination produced: were it
  changed so that its declared input is stopped, the run would report it as having
  demonstrated its refusal, without anything about the guard being noted in the run itself.
```

## Implementation Notes

```yaml
- 'THE PAIRING CLAUSE COSTS A REAL DECLARATION AND THAT COST IS PART OF THIS RECORD.
  At least one genuine session guard — one that really does deny a tool call — must
  be declared in the section GE-129a-2 establishes and genuinely examined in the change
  that lands this. A fixture cannot stand in; the clause''s whole value is that the
  report distinguishes this tree''s inert guard from a live one standing beside it
  on the same surface, which no fixture pairing can do. Affordable candidates observed
  on this surface: enforce_commit_delegation, wired PreToolUse on the Bash matcher
  and documented in CLAUDE.md as blocking a direct `git commit`; and inline_work_guard,
  wired PreToolUse on Edit|Write and reported in this workspace as hard-blocking file-mutating
  one-liners. VERIFY THE CANDIDATE BEHAVES AS DESCRIBED BEFORE RELYING ON IT — a pairing
  guard that turns out not to deny anything either would make this clause unsatisfiable
  at the last moment, and the two guards above are named here as leads, never as findings.'
- THE COPY EXAMINED IS THE ONE THE ENTRY'S COMMAND RESOLVES TO, AND RESOLUTION IS
  PERFORMED, NOT ASSERTED. The entry walks up from the current directory to an installed
  hook directory, so the target is not a fixed path and must not be written as one.
  Perform the walk-up from where the editor would run, report the absolute path it
  landed on, and assert that path is what was loaded. A test that hard-codes either
  templates/hooks/... or .claude/hooks/... has asserted a constant, not a resolution
  — and resolving through those links is the very mechanism that made the worked example
  inert, so getting this wrong reproduces the defect inside the machinery built to
  find it.
- THE SURFACE READ AND THE GUARD EXAMINED MUST COME FROM THE SAME LAYOUT IN THE SAME
  SWEEP. GE-129a-1 owns which copy of the settings surface is enumerated and states
  the path it read; this record owns which copy of the guard is loaded. Assert the
  two agree rather than assuming it. Enumerating one repository's entries while examining
  another's produces a full, plausible and entirely wrong report, and nothing else
  in the tree would catch it.
- NO VERDICT MAY BE HARD-CODED FOR A GUARD RECOGNISED BY NAME — this is what makes
  naming a real script in a criterion non-expiring, and it is the clause most easily
  defeated by a convenience branch. The implementation must contain no mapping from
  a guard's name to an expected state, no allowlist, and no special case for readme_read_guard.
  The record does not assert that guard is inert; it asserts that whatever is reported
  about it is what its own examination produced, which stays true and stays meaningful
  on the day it is repaired.
- DAY-ONE BLAST RADIUS IS THE CORRECT OUTCOME AND MUST NOT BE PRE-SUPPRESSED. On the
  landing commit most session subjects will report that no attempt has ever been made,
  because none has. Do not seed records, do not write exemptions ahead of the first
  run, and do not add the pairing guard's declaration in a way that quietly also declares
  the others. A postponement is not a ground for an exemption.
- THE REAL-SURFACE SWEEP MUST NOT BE ABLE TO DEGRADE SILENTLY INTO EXAMINING NOTHING
  — ADR-045 §7's governing test applies to this record too, and its in-criteria pairing
  clause is an IN-REGIME guard, which §7 explicitly says is not enough. The independent,
  out-of-regime guard for the non-empty real population lives on GE-129a-1's §7 descriptor;
  this record must rely on that one rather than growing a second, and must not satisfy
  its own non-empty precondition by asking the liveness run.
- 'AC_ENFORCE_STRICT=1 on every pytest invocation below. The sweep must not mutate
  the repository it examines (GE-129a-3''s constraint applies unchanged here, where
  the surface is real rather than a fixture, and matters more for exactly that reason).
  Error-handling policy applies to the resolution walk-up and the subprocess calls:
  specific exception types, logged at WARNING or higher or re-raised. A failed resolution
  is `blocked` and is reported by name; it must never become an absent subject.'
```
