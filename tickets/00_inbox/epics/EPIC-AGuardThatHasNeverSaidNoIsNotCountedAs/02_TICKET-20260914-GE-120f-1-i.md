# A refusal produced by reaching inside a check is not a demonstration — the run states the entry point it used, and only the entry point the protected surface invokes counts

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-120f-1-i` — A refusal produced by reaching inside a check is not a demonstration — the run states the entry point it used, and only the entry point the protected surface invokes counts — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-120f-1-i`. Component: `guardrail-engine`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given a check whose declared rejection can be produced by calling a part of the check
  that is reachable only from within it, while the entry point the protected surface
  invokes does not produce that rejection for the same declared input,
When the liveness run examines that check,
Then the record it writes comes from the entry point the protected surface invokes, and
  that check's record says the rejection was not observed,
And the run states, for every check it examined, which entry point it put the input
  through, taken from the invocation it actually performed rather than from the entry
  point the check's declaration names,
And a rejection produced by reaching inside the check is reported as a refusal obtained
  without using the check's entry point, is named as such, and does not cause that
  check's record to say the rejection was observed,
And a reader of the report can tell which entry point was used for any named check
  without opening the check.
```

- [ ] AC-1: the record it writes comes from the entry point the protected surface invokes, and
- [ ] AC-2: the run states, for every check it examined, which entry point it put the input
- [ ] AC-3: a rejection produced by reaching inside the check is reported as a refusal obtained
- [ ] AC-4: a reader of the report can tell which entry point was used for any named check

## Implementation Notes

```yaml
- 'THE ENTRY POINT IS THE ONE THE PROTECTED SURFACE INVOKES, TAKEN FROM THE INVOCATION
  PERFORMED — never from the declaration, never from a helper import. Adopt config/verification_flow.schema.json''s
  own wording for the field rather than minting a second one: entry_point is "the
  real production way in that this check invokes (CLI, hook, workflow dispatch, deployed
  script). NOT an internal helper import", and the known-bad input is required to
  be fed "through the SAME entry point". Reuse those names.'
- 'THE STATED ENTRY POINT IS A FACT ABOUT THE RUN, NOT ABOUT THE REGISTRY. Build the
  per-check statement of which entry point was used from the invocation the process
  actually performed — the command it executed, captured at the call site — and never
  from the entry point a declaration or a registry entry names. This is the same substitution
  GE-126c-5 forbids one axis over: a statement built from what the author intended
  rather than from what the process did.'
- PROCESS BOUNDARY IS A SMELL, NOT THE CRITERION. Do not implement this as "the invocation
  must cross a process boundary". A check the protected surface legitimately invokes
  in-process would fail such a rule, and a check invoked out of process through a
  way in nobody uses would pass it. The observable is WHICH invocation the protected
  surface performs. The boundary descriptor below exists to make that mis-implementation
  go red.
- THE REPORT MUST BE READABLE WITHOUT OPENING THE CHECK. The entry point used for
  any named check is recoverable from the run's emitted output alone. A reader who
  has to open the check to find out how it was invoked cannot tell a demonstration
  from a reach-inside, which is the condition this record removes.
- 'A REACH-INSIDE REFUSAL IS ITS OWN REPORTED CLASS, NOT AN ERROR AND NOT A DEMONSTRATION.
  Report it under wording distinct from both "rejection observed" and "rejection not
  observed", because its remedy is different from either: the check''s decision logic
  works and its service path does not reach it. readme_read_guard is exactly this
  shape seen from the other side.'
- EXTEND GE-120f-1's RUNNER; ADD NO SECOND OBSERVATION. This record produces no new
  record value — it constrains which invocations may produce one and requires the
  invocation used to be stated. Anything that reads like a second liveness pass beside
  the first is wrong.
- AC_ENFORCE_STRICT=1 on every pytest invocation, and run the DEPLOYED copy out of
  process through GE-120c-1's harness. Any module imported from outside templates/scripts/commit_guardian/
  must be added to the deploy map in scripts/build_phases.py in the same change.
- 'Error-handling policy: specific-exception try/except around subprocess and I/O,
  logged at WARNING or higher or re-raised. A failed invocation is `blocked`, never
  a silent absence and never a `passing`.'
```
