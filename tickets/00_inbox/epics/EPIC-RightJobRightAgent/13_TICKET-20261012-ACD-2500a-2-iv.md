## Acceptance Criteria

```gherkin
Given record R had readiness "draft" when the technical planner's stage began,
  and at the end of that stage R carries readiness "approved",
When the requirement rule check runs at the end of the stage,
Then R's readiness reads "draft" again,
And the report lists one "fixed" entry naming R's file, the value "approved" that was
  removed and the value "draft" that was restored,
And R is not in the buildable queue after the stage,
And, as the paired acceptable input, a record raised from "reviewed" to "approved" by the
  approval step the user runs produces no finding and keeps "approved".
```

## Implementation Notes

```yaml
- The before-state is a snapshot the workflow takes before it dispatches the stage
  (for example the committed state at stage start), passed to the check; never the
  stage agent's self-report.
- The stage identity is passed in by the workflow; the user-run approval step is exempt
  by stage identity, not by inspecting readiness values.
- A record created during the stage that ends at 'approved' is restored to 'draft'
  (the store's authoring default) and reported 'fixed' with its before-state stated
  as absent. See caveat, user to confirm.
- 'Every write is a field-targeted edit: only the named field changes and every other
  byte of the record is preserved (no whole-file YAML load/dump rewrite; see the fast_lane.py
  round-trip hazard in the ac-driven-dev PROJECT_CONTEXT).'
```
