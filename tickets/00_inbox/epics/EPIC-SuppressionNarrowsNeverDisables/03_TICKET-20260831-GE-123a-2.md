# Suppressing the filename finding leaves every content finding in that file reported

## Actor / Goal

## Acceptance Criteria

```gherkin
Given five files whose names mark them as environment configuration, each
  containing the same four content-rule lines — a cloud access key in the
  AWS_KEY form, a private-key header line, a quoted twelve-character value
  assigned to a field named password, and a high-entropy token,
And the allowlist contains exactly one entry, suppressing the filename rule
  across the repository,
When all five files are scanned through the scanner's multi-file entry point,
Then twenty findings are reported — the four content findings for each of the
  five files,
And no filename finding is reported for any of them,
And the run's exit status reports findings present,
Because the one entry the author wrote was an instruction about the filename
  rule and nothing else.

Given the identical five files and the identical single allowlist entry,
When the run completes,
Then the filename finding IS suppressed for every one of the five files,
Because a well-scoped suppression must still do exactly what it says — a fix
  that satisfies this criterion by ceasing to honour the entry is a
  regression, not a fix.

Given the same five files but with all four secret-shaped lines replaced by
  ordinary configuration text that no content rule recognises,
And the same single allowlist entry suppressing the filename rule,
When the files are scanned,
Then no findings are reported and the run exits clean,
Because suppressing the only finding a file genuinely produces is the
  legitimate use of the allowlist and must keep working.
```

## Implementation Notes

```yaml
- The repository-wide suppression must be written with the LITERAL WILDCARD file path
  — the only form that suppresses across the repository per GE-113c-3-v. A zero-segment
  path field is rejected at parse time with a warning and suppresses nothing, which
  would make the whole first arm vacuous while looking correct.
- The allowlist fixture must contain EXACTLY one entry. A second entry, even a harmless
  one, stops the arm distinguishing a correctly-scoped suppression from a broad one,
  which is the reason the criterion says exactly one.
- Findings must be observed BY RULE ID, not by count alone. An implementation that
  suppresses the wrong rule and happens to report twenty other findings must fail,
  and a count-only assertion cannot make it fail.
- The third arm's innocuous configuration text must contain no token of twenty or
  more characters and no keyword-followed-by-quoted-value line, or the clean-exit
  assertion is measuring the fixture rather than the scanner.
- All arms must run through the multi-file entry point scan_files over real files
  in a tempfile-backed directory, with the allowlist written into that same directory
  and passed as the project root. Coverage of the suppression matcher in isolation
  does not discharge any arm — a sibling audit in this family found two criteria verified
  that way which described situations the real entry point can never produce.
- Exit-status arms must run the scanner's CLI entry point in a fresh subprocess with
  the fixture directory as the working directory, and must assert the process exit
  code. A returned list of findings is not an exit status.
- Test fixtures must assemble every credential-shaped string at runtime from concatenated
  fragments rather than writing it as a source literal, so this repository continues
  to need no PRIVATE_KEY or AWS_KEY suppression anywhere. The existing suppression
  test module does this deliberately; do not collapse the fragments back into literals.
- Each of the four content-rule lines must produce exactly one finding, so that twenty
  is an exact expectation rather than a floor. Verify the chosen values do not cross-trigger
  a second rule.
- The module under test must be loaded from the canonical templates/ path via importlib.util.spec_from_file_location,
  never from a deployed copy, which can be stale.
- No test may write a .security-allowlist to any real project root. Every allowlist
  in this criterion's arms lives only inside a tempfile-backed directory.
- Fixture files must not be placed under tickets/, docs/retrospectives/, docs/acceptance-criteria/
  or templates/skills/. The pre-commit consumer post-filters entropy findings for
  those path prefixes, which would silently change the expected counts.
```
