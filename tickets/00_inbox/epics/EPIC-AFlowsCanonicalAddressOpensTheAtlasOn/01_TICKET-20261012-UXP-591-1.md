## Implementation Notes

```yaml
- 'Route: add the catch-all server route leafcutter-web/app/flows/[...id]/page.tsx;
  it joins params.id with ''/'' and resolves the id against the flow set loaded by
  leafcutter-web/lib/data/flows.ts, answering 200 for a known id. leafcutter-web/app/flows/page.tsx
  stays the bare /flows entry. A single optional catch-all app/flows/[[...id]]/page.tsx
  in place of page.tsx is an acceptable alternative, but not both: Next.js 14 rejects
  a page.tsx beside an optional catch-all at the same level.'
- A flow id is exactly two path segments (the leafcutter/atlas-flows invariant ^[a-z0-9-]+/[a-z0-9-]+$);
  a path with any other segment count never resolves to a flow (UXP-591-1-ii, UXP-591-1-iii).
- Flow lookup matches the requested id against the loaded flow set; a URL-supplied
  id is never turned into a filesystem path (no path traversal through lib/data/flows.ts).
- 'The route passes the selected flow, its filters and the one-flow breadcrumb into
  leafcutter-web/components/flows/flows-view.tsx as initial props, replacing today''s
  hard-wired selectedId default. Source and Kind come from the flow record''s own
  source and kind fields, Realization is ''all''; nothing is hard-coded per flow.
  The linked flow is in the server-rendered HTML: no first paint of leafcutter/deliver-a-feature
  and no hydration mismatch.'
- 'One address format: a single edge-safe module (proposed leafcutter-web/lib/flow-url.ts)
  exports flowHref(flowId, stepId?) building ''/flows/<flow id>'' and ''/flows/<flow
  id>?step=<node id>'' with the ''/'' literal, and parses requested paths. It is imported
  by middleware (Edge runtime), server components and client components, so it must
  not import node:fs or ''server-only'' and must not live in lib/data/flows.ts. Every
  producer of a flow address in UXP-591 (route, middleware redirect, history writes,
  AC detail links) uses it; no hand-built ''/flows?flow='' string or encodeURIComponent(flowId)
  remains.'
- Existing suites under leafcutter-web/components/flows/__tests__ and leafcutter-web/lib/data/__tests__
  stay green, and `npm run build` (type-check included) passes.
- 'Documentation companion, outside this AC''s .ts/.tsx surface: the ''The views''
  table in leafcutter-web/README.md must list /flows/<product>/<flow>[?step=<id>]
  and the legacy 308; route it to the generated ticket''s documentation phase.'
- 'Playwright harness (owner decision 2026-10-09), owned here because every UXP-591
  AC with a Playwright descriptor depends on UXP-591-1: add @playwright/test as a
  leafcutter-web devDependency within Next.js 14''s optional peer range ^1.41.2, with
  package-lock.json updated; add leafcutter-web/playwright.config.ts with testDir
  ./e2e, Chromium only, and a webServer that serves the production build with `next
  start` on a fixed port; add an `e2e` npm script running `playwright test`. Specs
  live in leafcutter-web/e2e/ (no e2e convention exists in the repo yet; this sets
  it).'
- vitest must not collect leafcutter-web/e2e/ (its default include also matches *.spec.ts),
  and the atlas-contracts job's `npx tsc --noEmit` must still pass with the Playwright
  config and specs in the tree.
- 'CI (owner decision 2026-10-09): after the leafcutter-web `npm ci` (the setup-node
  v4 + npm ci steps PR #1026 added to the test shards; the atlas-contracts job in
  .github/workflows/ci.yml already runs the same pair in leafcutter-web), add `npx
  playwright install --with-deps chromium`, `npm run build` and `npm run e2e`. They
  run once per CI run, appended to the atlas-contracts job, not inside the 8-leg test-shard
  matrix, which would build the app and run the suite 8 times. A separate job would
  add a concurrency slot that the ci.yml header counts (21 per PR against a cap of
  20 on Free), so that count and any guard test pinning it would then have to change.
  The steps are blocking and upload the Playwright report and traces as an artifact
  on failure.'
- The done-proof gate in CI proves `// covers:` tags in .ts/.tsx files by running
  them with vitest (ci.yml, BO-2500e-6), so a covers-tagged Playwright spec would
  be run under the wrong runner and fail closed. Until that gate can run Playwright
  specs, Playwright specs carry no `// covers:` tag and each AC's coverage proof stays
  on its vitest tests.
```
