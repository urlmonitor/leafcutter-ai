# An agent with nothing to record leaves no record, so silence in the record means silence in the learning

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `INF-700b-1-i` — An agent with nothing to record leaves no record, so silence in the record means silence in the learning — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `INF-700b-1-i`. Component: `infrastructure`. Assigned agent: `llm-expert`. Estimated complexity: `S`. Complexity: `low`.

## Acceptance Criteria

```gherkin
Given a phase agent finishes a piece of work and has learned nothing about
  this project that a later agent would benefit from knowing,
When it executes the shared sign-off knowledge-capture step,
Then no knowledge record is produced for that run,
And in particular no record is produced whose learning text is empty,
  whitespace-only, or a restatement of the run's descriptive fields with no
  learning in it,
And the agent's sign-off completes and its primary output is returned
  unchanged,
And a later count of captured learnings over a period containing only such
  runs reports zero captured and zero failed.
```

- [x] AC-1: no knowledge record is produced for that run
- [x] AC-2: in particular no record is produced whose learning text is empty
- [x] AC-3: the agent's sign-off completes and its primary output is returned
- [ ] AC-4: a later count of captured learnings over a period containing only such

## Implementation Notes

```yaml
- 'INTERFACE CLARIFICATION, load-bearing for INF-700b-3. The prohibition in this AC
  is on the KNOWLEDGE record only. A run that reached the capture step and had nothing
  to record must still leave a durable capture-ATTEMPT record on the operational telemetry
  stream, with an outcome of ''nothing to record''. Without it, INF-700b-3''s third
  case — ''no agent run reached the step at all'' — is not derivable from any artefact,
  and a broken dispatch is indistinguishable from a quiet week. This does not contradict
  the criteria: an attempt record carries no learning and is never a knowledge record.'
- 'The emptiness test applied to `text` must be whitespace-normalised: absent, null,
  empty, or whitespace-only are all ''no learning''. It must additionally reject any
  value that is a template composed from the record''s own descriptive fields (agent,
  component, destination, entry_kind, ticket) — a record that restates its own metadata
  is contentless however long the string is.'
- No default, fallback, placeholder or f-string substitution for `text` may exist
  anywhere on the emit path. This is the emitter-side twin of the substitution INF-700c-1
  deletes on the writer side (harvest_learnings.py line 351); a duplicated default
  is a defect even when one of the two copies is later removed.
- The agent's primary output and its sign-off must be byte-identical whether the no-learning
  branch or the record-produced branch was taken. The capture step must not add a
  sign-off comment, a status change, or a return-value field on the no-learning path.
- Counting must not infer 'nothing to record' from the absence of any record at all.
  Zero-captured-and-zero-failed over a period is only assertable when attempt records
  exist for that period; a period with no attempt records at all is the distinct third
  case owned by INF-700b-3.
```

## Architectural Note (architect-review, 2026-10-20)

**Classification: LARGE.** Always-large trigger: `has_adr_contract_change` (the change adds a contract ADR-034 Amendment 1 does not cover, and narrows how A1.1's "`emit_event.py` is not the knowledge emitter" line must be read). Thresholds also crossed independently: 8 files (> 5), 3 components (`infrastructure`, `knowledge_system`, `agent_telemetry`), and it crosses the `templates/` / `scripts/` package boundary. `requires_adr: true`; `adr-author: needed`. Suggested ADR work: **ADR-034 Amendment 2** (not a new ADR; Amendment 1 was itself recorded as an amendment by BrainCandy's 2026-10-17 decision), titled "Capture-attempt ledger: telemetry, written by emit_event.py". No diagram (`suggested_diagrams: []`): no new component or boundary; the two-stream split is already drawn and INF-700b-5 owns the docs.

**The ticket's premise is partly stale after INF-700b-1 (PR #1278).**
1. Writer choice survives. An attempt record is telemetry, so it belongs on the operational stream, written by the stdlib-only `emit_event.py` that already resolves that stream through ADR-069's declaration with an atomic `O_APPEND` write. ADR-034 A1.1 forbids a second KNOWLEDGE emitter; it does not forbid a telemetry record. Routing it through `emit_knowledge.py` would put a non-knowledge line next to (or in) the sink and breach the INF-400c-4-iii two-stream split. But the ADR text is ambiguous enough to need the Amendment 2 sentence.
2. `files_touched` was wrong. Under INF-700b-1 the emit path is `scripts/knowledge/emit_knowledge.py`, which today accepts ANY `--text`, including empty or whitespace-only, so the AC's "no record whose text is empty / restates metadata" is currently unenforced. The helper must gain the refusal. Also missing: `unit_tests/test_emit_event.py` (line 92 pins the payload key set to exactly `{phase, outcome, retry_count}`), `agent-telemetry/SKILL.md` (documents the record shape), and the ADR-034 amendment. Corrected in frontmatter.
3. The ticket's contract has a hole nobody noticed: `outcome: recorded`. INF-700b-3's partition reads "none recorded, none failed" as the nothing-to-record verdict. If `recorded` rows depend on agent initiative (a second command after the helper), an agent that records a learning but skips that command makes the period read as "nothing to record": a false all-clear, the exact defect this epic exists to close. So `recorded` must be written by code that runs atomically with the knowledge write.

**Recommended design (shared with 03).**
- ONE ledger writer: `emit_event.py`. New event type `capture_attempt`. Payload gains one additive key, `missing_target`, present on EVERY record (null by default), so the documented "every line has the same keys" rule holds; `unit_tests/test_emit_event.py:92` is updated deliberately. For `--event capture_attempt` ONLY, `--outcome` is validated against the closed set `{recorded, nothing-to-record, failed}`; an unknown value writes nothing, warns on stderr, exits 0. Other event types keep free-text outcomes (existing callers use `ok`, `blocked`). `missing_target` is required when the outcome is `failed` and must be null otherwise. That validation is the 03 requirement "outcome must not be overloaded as free text" met once, here.
- Agent-run paths (the helper cannot be relied on to run): the no-learning branch runs `emit_event.py --agent <agent> --event capture_attempt --phase knowledge-capture --outcome nothing-to-record [--ticket <ticket>]` as ONE command with no `--log`. 03 adds the `--outcome failed --missing-target '<literal path>'` variant for the script-missing / import-broken case only the agent can see. Same invocation shape in all four surfaces.
- Helper-run path: `emit_knowledge.py`, after a successful sink append, triggers the `recorded` attempt through `emit_event.py` (subprocess, path derived from the deployed layout, no `--log`, fail open with a stderr warning if it cannot run). The helper stays the only thing that writes the knowledge sink; `emit_event.py` stays the only thing that writes the ledger. The agent-facing `emit_knowledge.py` invocation is UNCHANGED. **Decided by BrainCandy on 2026-10-21: the helper writes the `recorded` attempt itself** (subprocess to the deployed `emit_event.py`, fail open). The helper-to-skill coupling is accepted; the agent-run `recorded` fallback is rejected, so INF-700b-3's verdict (a) needs no sink cross-check. Recorded as ADR-034 Amendment 2, A2.4.
- Helper refusal rule (the emitter-side twin of INF-700c-1): whitespace-normalise `--text`; refuse (nothing appended, stderr reason, exit 0) when it is empty, or when removing every occurrence of the record's own `agent`, `component`, `destination`, `entry_kind` and `ticket` values plus non-alphanumerics leaves nothing. A refused call writes a `nothing-to-record` attempt, not `failed` (the agent had no learning to give). No default or f-string substitution for `text` anywhere on the path (already true; keep a test).

**Does 03 want the same writer? Yes, so 02 and 03 must share this one design.** 03 needs `missing_target` and the closed outcome set. 02 owns the `emit_event.py` change; 03 must NOT touch `emit_event.py` (remove it from 03's `files_touched`) and should add `02_TICKET-20261016-INF-700b-1-i.md` to `depends_on`. They also both edit `signoff/SKILL.md` §7 and the three v3 templates, so they cannot run in parallel anyway. Two caveats for 03: (a) the telemetry stream and the knowledge sink resolve through the SAME `knowledge_sink.json`; an absent or stale declaration drops BOTH writers, so a failure record for "declaration unusable" is unwritable by construction and stays stderr-only; the ledger can only record failures where telemetry is still writable (script missing, `ModuleNotFoundError`, a bad sink key); (b) the three v3 agents run outside any ticket, so "the piece of work" is null `ticket_path` for them; decide an AC-id or request-slug convention before 03.

**Collision with INF-700b-1's single-command invariant: none, if these hold.** The four surfaces keep one identical `emit_knowledge.py` invocation, and `tests/knowledge/test_inf_700b_1_emit_helper.py::test_deployed_section_7_names_emit_helper_and_no_hand_append` only extracts commands containing `emit_knowledge.py ... --text`, so an added `emit_event.py` fenced block is invisible to it. Constraints on the template edit:
- `scripts/ci/check_sink_parity.py` selects the FIRST blank-line-delimited paragraph containing both the word `emit` and `knowledge_captured`. The new no-learning wording (§7 "No path", the PO/BA/IT-PO "On 'no'" lines) MUST NOT put those two together in a paragraph that precedes the existing helper paragraph, or the checker takes the wrong paragraph and reports the surface unparseable. Use "record" / "log" / "capture attempt" instead of "emit".
- The same test's forbidden patterns apply to the whole §7 text and each Emission block: no `>>`, `echo`, standalone `tee`, `debugging/logs`, "append the event", "create the file if it does not exist".
- No `--log` or `--sink` path in any template (ADR-034 A1.2, ADR-069). The `emit_event.py` default resolves the declared stream.
- The new `emit_event.py` command must be byte-identical across the four surfaces except `--agent` and the optional `--ticket`; extend the parity assertion to cover it.
- §7's "capture step must not alter primary output": `emit_event.py` prints nothing on success and always exits 0, so the no-learning branch stays byte-identical to today's from the caller's view.

**ADR conflicts flagged.** (1) ADR-034 A1.1 sentence "`emit_event.py` is not the knowledge emitter" and the Alternatives bullet "Use `agent-telemetry`'s `emit_event.py`. Rejected." are correct for knowledge records but will read as a contradiction once §7 tells agents to run `emit_event.py`; Amendment 2 must scope them. (2) ADR-011's two-stream rule holds: the ledger never touches the knowledge sink. (3) ADR-069: no new copy of the usable-stream rule is introduced; the helper triggers `emit_event.py` rather than re-implementing stream resolution, so the INF-500d-4-ix copy-parity check is not widened. (4) INF-400c-4-iii's "same keys on every line" rule is honoured by the always-present `missing_target`.
