## Implementation Notes

```yaml
- 'THE FINDING CARRIES subject_type: ''ac'' AND tier: ''ci'', AND ITS SUBJECT IS THE
  CRITERION ID. The mock-data artifact states this as an invariant: commit-tier subjects
  are FrontendComponent paths, CI-tier subjects are Ac ids. A finding keyed by the
  wrong subject type is not cosmetic — it collapses the distinction the two-L1 split
  is built on, and a reviewer who cannot tell the direction will try to fix a criterion
  by editing a file.'
- THE CODE IS 'undeclared-done-ui-ac' (mock record gf-ci-uxp-607-2-undeclared), distinct
  from the commit tier's codes. One finding per criterion — the at-most-one-per-(subject,
  code) rule from GE-124c-1-i applies at this tier too, with the criterion id as subject.
- THE MESSAGE MUST STATE THAT BOTH ROUTES WERE ABSENT — no '@ac <id>' in any component-level
  declaration and no data-ac occurrence — so the reader knows the gate looked for
  both and does not assume only the floor was checked.
- 'THE MESSAGE MUST NOT USE PROOF LANGUAGE IN EITHER DIRECTION, per GE-124g-2: failing
  says nothing claims it, never that it is unproven or untested; the corresponding
  pass says declared, never verified or covered. This gate and check_done_proof report
  on the same criterion and their language is what stops a reader merging them.'
- SHARED OUTPUT SURFACE, DISTINGUISHABLE ROWS. When both tiers report in one run,
  the subject_type/tier fields must be rendered, not just stored — a reviewer reading
  the output has to see which direction each row came from. Do not rely on the id
  format alone to imply the direction.
- MIRROR check_done_proof's REPORTING SHAPE rather than inventing one; that gate already
  reports per-criterion failures for the test obligation and the two will appear side
  by side (GE-124e-3-i).
```
