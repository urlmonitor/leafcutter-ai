# An agent that finishes with a learning leaves a durable record of it by following the capture step verbatim

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `INF-700b-1` — An agent that finishes with a learning leaves a durable record of it by following the capture step verbatim — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `INF-700b-1`. Component: `infrastructure`. Assigned agent: `llm-expert`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given a fresh install of the package in which nobody has hand-created any
  directory the knowledge-capture step asks for,
And a phase agent has just finished a piece of work and holds one learning
  about this project that it did not hold when it started,
When that agent executes the shared sign-off knowledge-capture step exactly
  as written, taking no initiative beyond the literal instructions,
Then every artefact the step names — each directory, file or helper it tells
  the agent to load or run — is present at the location the step names, so
  no instruction resolves to a missing target,
And the step's "if unavailable, log a warning and proceed" branch is not the
  branch taken,
And a durable knowledge record exists once the agent's process has ended,
And that record carries the learning as the agent wrote it, in prose a reader
  who was not present in that run can understand from the record alone,
And a reader can recover the learning without opening the agent's console
  output and without opening any other file.
```

### What is genuinely still open: the append is hand-composed

§7 step 2 and the three S9 blocks say "Append the event there (create the file if it does not exist yet)". No tool is named, and none of the agents has a safe append primitive: `Write` overwrites the sink, `Edit` needs a unique anchor, and shell `>>`/`echo` is blocked by the file-mutation hook. A literal-instruction agent cannot reliably produce one clean JSONL line. This is the origin of the bare `</content>` line once seen in the sink. So AC clauses "durable record exists" and "warning branch is not taken" still depend on agent initiative.

### Existing component to extend, not duplicate

`scripts/knowledge/emit_knowledge.py` (INF-400c-5, deployed to `.leafcutter/scripts/knowledge/`) already appends a validated `knowledge_captured` event with `--text` and is documented as "the helper the four shipped emit sites call". No emit site calls it. Extend it; do not add a new emitter. `templates/skills/agent-telemetry/scripts/emit_event.py` is the wrong tool (fixed telemetry record, no `text`, wrong stream).

Three defects block simply pointing §7 at it:

1. `--sink` is required, so a caller must restate a path. Default it to the declared sink via `sink_resolution` (usable-stream rule, ADR-069), keeping "no sink-path literal in any template".
2. The documented sentinel `entry_kind: "unclassified"` is not in `config/entry_kind_vocabulary.json` (members: adr, explanation, glossary, reference, retrospective). The helper would REJECT it and write nothing, so the warning branch would be the only reachable path again. The vocabulary is owned by INF-400c-5, so this AC must not add a member silently. Resolution to be decided by BA/PO: either the helper passes the one declared sentinel through without vocabulary membership (the harvester already retains unknown kinds as unroutable-but-retryable), or INF-400c-5 admits it.
3. `_append_jsonl` calls `mkdir(parents=True)`. ADR-069 (implementation record) requires writers to create only up to the log directory, and only under a live enduring root; a vanished project must be refused, never recreated. The helper must follow the same rule and refuse when the declaration is absent, stale or unusable.
