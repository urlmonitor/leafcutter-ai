# A file recognised by its sensitive filename is also read line by line for its contents

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-123a-1` — A file recognised by its sensitive filename is also read line by line for its contents — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-123a-1`. Component: `guardrail-engine`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given a file named ".env" exists on disk and contains four separate lines that
  the scanner's content rules recognise — a cloud access key in the AWS_KEY
  form, a private-key header line, a quoted twelve-character value assigned to
  a field named password, and a high-entropy token of at least twenty
  characters,
And no suppression entries are in force,
When the file is scanned through the scanner's multi-file entry point (the same
  entry point the pre-commit secrets check calls),
Then five findings are reported for that file: one filename finding recording
  that the name itself marks the file as sensitive, plus one finding for each
  of the four content rules,
And the filename finding and the four content findings are all present in the
  same result — recognising the name adds a finding, it does not replace the
  content scan.

Given a second file named "secrets.py" contains the identical four lines,
And both files are scanned in the same run with no suppression entries in
  force,
When the run completes,
Then "secrets.py" is reported for exactly the same four content rules as
  ".env",
And the only difference between the two files' results is the extra filename
  finding on ".env",
Because a file's contents must be judged the same way whatever the file is
  called.

Given the same two files and no suppression entries in force,
When the run completes,
Then the run's exit status reports findings present,
Because nine findings across two files is not a clean result.
```

## Implementation Notes

```yaml
- The canonical edited source is templates/skills/security-scanner/scripts/scan_secrets.py
  per ADR-001. The deployed copies are build.py outputs and must never be edited directly;
  verify source-to-deployed parity with a build.py round-trip before sign-off.
- templates/skills/security-scanner/SKILL.md must be updated in the same change. Its
  Secrets Detection Rules table presents the rules as applied in order and says nothing
  about the filename rule ending the scan, so after this change the skill body must
  state that a filename match ADDS a finding and the content rules still run.
- Every arm must be exercised through the multi-file entry point scan_files, with
  real files written into a tempfile-backed directory. Coverage of the per-file scan
  called directly, or of the filename-matching logic in isolation, does not discharge
  any arm of this criterion.
- Exit-status arms must run the scanner's CLI entry point in a fresh subprocess with
  the fixture directory as the working directory, and must assert the process exit
  code. A returned list of findings is not an exit status.
- Test fixtures must assemble every credential-shaped string at runtime from concatenated
  fragments rather than writing it as a source literal. unit_tests/commit_guardian/test_scan_secrets_suppression.py
  already does this deliberately so that no PRIVATE_KEY or AWS_KEY suppression is
  needed anywhere in this repository. Do not collapse the fragments back into literals,
  and do not add an allowlist entry so that literals can be committed — suppressing
  the two highest-signal detectors on a real source file would create a genuine blind
  spot in exactly the file most likely to accumulate credential-shaped fixture data.
- 'Each of the four content-rule lines in a fixture must produce exactly one finding.
  Verify the chosen values do not cross-trigger a second rule: a token shorter than
  twenty characters cannot reach the entropy threshold, and the quoted value on the
  password line must stay long enough for the keyword rule while staying short enough
  to avoid the entropy rule.'
- The module under test must be loaded from the canonical templates/ path via importlib.util.spec_from_file_location,
  never from a deployed copy, which can be stale.
- No test may write a .security-allowlist to any real project root. Allowlist fixtures
  live only inside tempfile-backed directories.
- Fixture files must not be placed under tickets/, docs/retrospectives/, docs/acceptance-criteria/
  or templates/skills/. The pre-commit consumer check_secrets.py post-filters entropy
  findings for those path prefixes, so a fixture under one of them would measure the
  exemption rather than the scanner.
- The set of filename forms the sensitive-filename rule recognises must not change
  as a side effect of this work. Any narrowing is a regression, and it is guarded
  by GE-123a-3.
- Content-scan results for ordinary source files must not regress. The existing end-to-end
  arm in unit_tests/commit_guardian/test_scan_secrets_suppression.py that asserts
  four findings on an ordinary .py fixture must stay green.
```
