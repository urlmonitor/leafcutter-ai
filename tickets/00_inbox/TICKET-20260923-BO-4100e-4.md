# Surfacing a leftover does not turn it into a workspace you can be handed

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `BO-4100e-4` — Surfacing a leftover does not turn it into a workspace you can be handed — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `BO-4100e-4`. Component: `build-orchestration`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given a leftover that appears in the listing through discovery rather than
  registration,
When a workspace is requested to start work in,
Then the leftover is not the workspace handed over,
And when work is requested inside the leftover directly, the request is refused
  and the refusal states that it is a remnant awaiting clearing,
And the leftover is never promoted to a registered workspace as a side effect
  of having been listed.
```

- [ ] AC-1: the leftover is not the workspace handed over
- [ ] AC-2: when work is requested inside the leftover directly, the request is refused
- [ ] AC-3: the refusal states that it is a remnant awaiting clearing
- [ ] AC-4: the leftover is never promoted to a registered workspace as a side effect

## Implementation Notes

```yaml
- 'Discovery is a READ with no registration side effect, on every path. Registering
  whatever is discovered is the cheapest way to make BO-4100e-1''s listing complete
  and is precisely forbidden here: a half-created workspace carries no guarantee it
  was rooted at the shared tip (BO-4100a) and no guarantee it holds its own supporting
  material (BO-4100b), so adopting it hands someone a workspace both promises say
  they will never be given.'
- The handover path must select on origin == 'registered'. The filter must read BO-4100e-1's
  origin discriminator, never a name pattern and never a judgement about whether the
  directory 'looks complete' -- a half-created workspace can look complete.
- A request to work inside a leftover directly must be refused with a reason naming
  it as a remnant awaiting clearing, and must not fall through to creating or adopting
  a workspace at that location. ADR-039's discriminated refusal payload is the shape
  to reuse, and its refusal must be distinguishable from the occupied-workspace refusal
  it resembles.
- No code path may write a registration entry for a discovered leftover -- including
  the removal path, which CLEARS registration state (BO-4100e-2) rather than creating
  it, and including any repair or recovery helper added alongside.
- 'Promotion would also defeat BO-4100e-3: a registered workspace is no longer described
  as a remnant, so the misdiagnosis this family removes would return by a different
  route.'
- Error handling follows the project error handling policy; a failure to classify
  an entry must not default to treating it as registered.
```

## Agent Contracts

### Expects From

- **AC:** BO-4100e-1
- **Contract:** The origin discriminator on each listing entry, { path, origin: 'registered' | 'discovered', branch }. Handover filters to origin == 'registered'; the value must be a field, because a rendering difference cannot be filtered on, and it must survive a listing unchanged -- this record forbids listing from flipping it to 'registered'.
