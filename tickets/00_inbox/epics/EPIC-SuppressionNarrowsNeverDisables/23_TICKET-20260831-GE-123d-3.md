# A real credential written into a ticket or a requirement is still caught and still blocks

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-123d-3` — A real credential written into a ticket or a requirement is still caught and still blocks — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-123d-3`. Component: `guardrail-engine`. Assigned agent: `python-coder`. Estimated complexity: `S`. Complexity: `low`.

## Acceptance Criteria

```gherkin
Given a ticket Markdown file staged for commit contains a line made of one of
  the credential keywords the rule recognises, a separator, and a quoted
  sixteen-character value with no whitespace, no placeholder brackets, no
  masking characters, no recognised text-file extension, and no resemblance
  to a project identifier,
When the staged file is checked by the pre-commit secrets check,
Then the generic-credential finding IS reported, naming the file and its
  1-based line number,
And the commit is blocked,
Because a live credential in a ticket is a live credential in the
  repository's permanent history, and the ticket tree being a prose location
  changes nothing about that.

Given a file in the acceptance-criteria store staged for commit contains, on
  one line, a credential-shaped line whose quoted value is a run of ordinary
  words, and three lines later the credential line described above,
When the staged file is checked by the pre-commit secrets check,
Then exactly one finding is reported — the credential line — and the commit
  is blocked,
And the file is still reported after the earlier line was exempted,
Because the exemption is decided per finding and never per file: one exempt
  line must never carry the rest of the file out of scope with it.

Given a ticket Markdown file staged for commit contains a private-key header
  line and a cloud access key in the AKIA form,
When the staged file is checked by the pre-commit secrets check,
Then both findings are reported and the commit is blocked,
Because this feature widens exactly one rule for one closed list of value
  shapes, and every other rule keeps its full strength in prose locations.

Given a retrospective Markdown file staged for commit contains a credential
  line whose quoted value is the sixteen-character value above with a single
  trailing space appended,
When the staged file is checked by the pre-commit secrets check,
Then the finding IS reported and the commit is blocked,
Because the whitespace shape means a value that reads as a run of ordinary
  words, not any value that happens to contain one space character —
  otherwise a single keystroke would be enough to smuggle a credential past
  the check.
```

## Implementation Notes

```yaml
- Every scenario must be verified by the exit status of the real pre-commit check,
  not by the return value of an exemption predicate. A predicate that answers no is
  not evidence a commit was blocked, and this is the arm where that difference matters
  most.
- 'The whitespace shape must be a run-of-ordinary-words test, not a contains-a-whitespace-character
  test. State the invariant the implementation has to hold: adding a single space
  at the start, at the end, or in the middle of an otherwise unrecognised value must
  not change the verdict. Any implementation for which one keystroke flips a report
  into an exemption fails this AC regardless of what the predicate returns.'
- No rule other than the generic-credential rule may be narrowed anywhere by this
  feature. The private-key, cloud-access-key, exchange-API-key and high-entropy rules
  must keep full strength inside every prose location.
- The exemption must never be granted at file level. A staged file holding one exempt
  finding and one reported finding must still block, and the reported count must be
  exactly one — a count of zero and a count of two are both failures, and both are
  reachable from plausible implementations.
- Every scenario must be red before the implementation lands. In particular, each
  must fail against an implementation that grants the exemption per file and against
  one built on a naive contains-whitespace test — those are the two cheapest wrong
  implementations, and a test suite that cannot distinguish them does not discharge
  this AC.
- The pre-existing file-level high-entropy exemption (KI-CG-004 in docs/known-issues/commit-guardian.md)
  is explicitly out of scope. Do not close it, do not extend it, and do not cite it
  as precedent for a file-level generic-credential exemption. The two must remain
  separately tracked.
- 'The exemption must be unreachable for any value the shape vocabulary cannot classify:
  unclassifiable defaults to reported, and that default must be exercised, not merely
  intended.'
- 'ADR-001 parity: any code this AC causes to change lives in the canonical copies
  under templates/; verify through the build.py round-trip.'
```
