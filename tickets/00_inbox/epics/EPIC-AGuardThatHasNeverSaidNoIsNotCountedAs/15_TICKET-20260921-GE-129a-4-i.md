# A guard is examined in the linked working copy the drives actually run in as well as in the main one, and a refusal seen in one layout never stands for the other

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-129a-4-i` — A guard is examined in the linked working copy the drives actually run in as well as in the main one, and a refusal seen in one layout never stands for the other — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-129a-4-i`. Component: `guardrail-engine`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given a guard that lets its declared input proceed in the main working copy and also lets
  it proceed in a linked working copy made for a branch, but for two different reasons —
  in one it gives up while working out where the file it was handed sits, and in the other
  it reaches a decision without difficulty that the file is not one it gates —
When the liveness run examines that guard,
Then it examines it in both layouts and reports a result for each, saying which layout each
  result came from,
And the guard is reported as not having demonstrated a refusal in either, and the two
  results are not merged into one,
And given the guard is then changed so that it stops the declared input in the main working
  copy while still letting it proceed in the linked one,
When the run repeats,
Then it is reported as having demonstrated its refusal in the main working copy and as not
  having demonstrated one in the linked working copy, and it is not reported as established
  on the strength of the layout in which it now refuses,
And in that same run a guard that stops its declared input in both layouts is reported as
  having demonstrated its refusal in both, so a report of two different results is something
  the run produces rather than something it always says.
```

## Implementation Notes

```yaml
- THE LAYOUT IS A SWEEP DIMENSION, NOT A SECOND RUNNER — the one-runner decision on
  GE-129a applies here unchanged. The sweep iterates its subjects across layouts;
  it does not grow a second runner, a second population reader or a second report
  format for the linked copy. Every subject carries the layout its result came from,
  and results are never merged, never reduced to a best case, and never reduced to
  a worst one.
- 'THE LINKED LAYOUT MUST BE A REAL ONE, BUILT THE WAY THE DRIVES BUILD IT. A directory
  that merely looks like a worktree does not reproduce the behaviour: what differs
  is where the walk-up lands relative to the installed hook directory, and that is
  a property of the real arrangement. Extend the second-working-copy machinery ADR-045
  §5 already binds this family to (unit_tests/portability/_deployed_check_harness.py)
  rather than growing a parallel fixture, and build each layout ONCE per sweep, never
  once per subject.'
- RESOLUTION IS PERFORMED PER LAYOUT, WHICH IS THE ONLY REASON THIS RECORD IS NOT
  ITS PARENT'S THIRD CLAUSE. GE-129a-4 requires the examined copy to be the one the
  entry's command resolves to; here that resolution is re-run inside each layout,
  from a directory inside that layout, and each result states the layout AND the resolved
  path it examined. A single resolution reused across layouts silently examines the
  main workspace's copy twice.
- DO NOT LET A FLAKY SECOND LAYOUT BE DROPPED — this is the clause hardest to keep
  true over time and the parent record says so. A layout that could not be built or
  in which resolution failed is reported as `blocked` for every subject in it, by
  name, and must make the sweep's verdict non-clean. It must never become an absent
  layout, which reads exactly like a layout where everything was fine. The cheapest
  repair for an unreliable second layout is to stop sweeping it, and that repair reinstates
  the defect this record exists to prevent.
- THE TWO-MECHANISM CASE IS A REQUIREMENT ON THE EXAMINATION, NOT A CLAIM ABOUT ANY
  GUARD. The observed instance — an error while resolving a path in the main workspace,
  a plain failed prefix match inside a linked copy — is the motivation, not the assertion.
  No test may encode which mechanism applies to which guard in which layout; assert
  only that both layouts are examined, both results are reported with their layout,
  and neither stands for the other.
- 'AC_ENFORCE_STRICT=1 on every pytest invocation below. The sweep must leave every
  layout it examined byte-identical. Error-handling policy applies to the layout construction
  and the per-layout resolution: specific exception types, logged at WARNING or higher
  or re-raised; a swallowed construction error must never become a missing layout.'
```
