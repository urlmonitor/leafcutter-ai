summary: "When a batch of work items was assembled into a group, each requirement recorded where its work item now lived using a full machine-specific location rather than a location relative to the project. The reference was therefore meaningless to everyone except the person who generated it, and would have carried their home directory into the shared record."
description: "When several requirements are assembled into a group of work items, each requirement records where its own work item ended up, so a reader can trace from what was asked for to what delivered it. That recorded location was being written as a full path on the machine that generated it — including the generating user's home directory. For anyone else, and on any other machine, the reference points at nothing; but it still looks populated, which is worse than blank, because a reader treats it as evidence and only discovers otherwise when they try to follow it. Committing one would also have put a personal directory into a record the whole team reads. The cause was a small asymmetry rather than a missing feature. The assembly step rewrites the reference twice over: once to find the old entry, once to write the new one. The lookup half was carefully converted to a project-relative form so it would match what was stored earlier; the replacement half was passed straight through unconverted. A sibling piece of code doing the same job a few hundred lines away converts both, correctly — so one route through the assembly was right and the other was not, and the explanatory comment mentioned only the half that was handled, which is exactly why the omission read as deliberate to anyone skimming. Two things were verified as innocent before anything was changed: the helper that works out the project root returns the right answer when given the exact input that triggered this, and the helper that writes the reference faithfully records whatever it is handed. The machinery was never broken; one caller simply did not use it. A second, quieter problem is closed at the same time. If the project root could not be worked out at all, the code fell through in silence and recorded the machine-specific path anyway — meaning a run that could not do the job right produced output indistinguishable from a run that did. It now says so plainly, naming the affected item and the remedy. That silent-fallback shape has already had to be repaired three times elsewhere in this project, each time because something reported success from a check that had examined nothing. The regression test drives the real assembly from end to end rather than calling either helper, because both helpers are individually correct and a test against either passes on the broken code. It was confirmed to fail before the change, pass after it, and fail again when the change was temporarily removed. One detail is recorded because it nearly caused a wrong conclusion: the passing run finished fifty times faster than the failing one, which looks precisely like a test that has quietly stopped doing its work. Measured properly, the test body takes about the same time in both states; the difference was one-off start-up cost. The gap was checked rather than assumed."
