# A registry the startup check cannot read is reported as unreadable and names what it tried to read

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `ACD-2100b-1` — A registry the startup check cannot read is reported as unreadable and names what it tried to read — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `ACD-2100b-1`. Component: `ac-driven-dev`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given a run in which the agent registry the startup check resolves to cannot be
  read -- the location holds no file, or the process is refused permission to
  open it,
When the startup check runs,
Then the run stops and reports that the registry could not be read,
And the report states the location that was tried and the reason the read
  failed,
And the report contains no statement about whether any agent is permitted to run
  repository commands,
And the report does not direct the reader at a permission setting.
```

- [x] AC-1: the run stops and reports that the registry could not be read
- [x] AC-2: the report states the location that was tried and the reason the read
- [x] AC-3: the report contains no statement about whether any agent is permitted to run
- [x] AC-4: the report does not direct the reader at a permission setting.

## Implementation Notes

```yaml
- The change must land under templates/. The deployed workflow is build output and
  today carries no charter gate at all (see ACD-2100d-3).
- 'Fail closed: the run still stops. The objection is to the diagnosis, not to the
  caution -- relaxing this outcome to a warning reintroduces the hazard the BO-1500f-1
  gate was built for, and that AC is work_status: done.'
- The reported location must be the location actually attempted, taken from the resolution
  that ran -- not a constant reproduced in the message. A hard-coded path in the message
  is wrong the moment the resolution changes and is exactly what made the current
  message misleading.
- The reported reason must distinguish 'no file at that location' from 'permission
  refused'; these have different remedies and collapsing them recreates the defect
  one level down.
- The report must not name a permission setting, and must not assert anything about
  any agent's permission. This is a negative constraint on observable output and must
  survive as one -- a test that asserts only that some message was printed restates
  the bug.
- 'Must satisfy the repository error-handling policy: the failed read is external
  I/O and must be logged at WARNING or higher before the halt.'
- Must not emit the registry's contents or the process environment in the report --
  the location and the failure reason only.
```
