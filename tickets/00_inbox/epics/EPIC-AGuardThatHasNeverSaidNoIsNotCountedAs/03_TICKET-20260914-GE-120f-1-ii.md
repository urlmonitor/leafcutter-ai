# A check that also refuses the work it is meant to accept has demonstrated nothing — refusing everything is as inert as refusing nothing, and is reported under its own wording

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-120f-1-ii` — A check that also refuses the work it is meant to accept has demonstrated nothing — refusing everything is as inert as refusing nothing, and is reported under its own wording — so that the acceptance criterion is satisfied.

## Context

## Acceptance Criteria

```gherkin
Given a check declares, beside the known-bad input it must reject, an input of the same
  kind that it is required to accept,
When the liveness run examines that check,
Then it puts both declared inputs through the entry point the protected surface invokes,
And that check's record says the rejection was observed only when the declared bad input
  produced the declared rejection and the declared acceptable input did not,
And a check that produced the declared rejection for both inputs is named as a check that
  refuses without discriminating, its record does not say the rejection was observed, and
  the run fails,
And a check whose two declared inputs are the same, or differ in no way the check can act
  on, is named as a check whose pair cannot discriminate, and the run fails,
And a check that produced the declared rejection for neither input is reported as a check
  whose declared rejection was not observed, under different wording from a check that
  refused both — the first has a refusal that never fires, the second has one that never
  stops firing, and they are repaired differently.
```

- [ ] AC-2: that check's record says the rejection was observed only when the declared bad input
- [ ] AC-3: a check that produced the declared rejection for both inputs is named as a check that
- [ ] AC-4: a check whose two declared inputs are the same, or differ in no way the check can act
- [ ] AC-5: a check that produced the declared rejection for neither input is reported as a check

## Implementation Notes

```yaml
- 'THE ACCEPTABLE INPUT IS ONE DATUM IN ONE PLACE, NEVER A SECOND DECLARATION STORE.
  DECIDED HERE, AS THE doc_link ON config/verification_flow.schema.json ASKS: the
  schema already carries both sides of the pair — a check''s ordinary `command` with
  its observable `pass_criteria` for the case it must accept, and `negative_control`
  for the case it must reject. Model the acceptable input as the check''s ordinary
  case in the SAME registration entry as the negative control. Do not add a parallel
  declaration record; two records will disagree about which checks are enrolled, which
  is the failure GE-126b-5''s doc_link warns about in this exact spot.'
- BOTH INPUTS GO THROUGH THE SAME ENTRY POINT, IN THE SAME RUN. The observed value
  is conditional on the two invocations DIFFERING, so a single invocation can never
  produce it. An implementation that records the rejection as observed the moment
  the bad input is refused — one invocation instead of two — is the obvious efficiency
  and is the whole defect; the mandatory injection below exists to make it red.
- THREE OUTCOMES, THREE WORDINGS, AND THEY ARE NOT INTERCHANGEABLE. A check that refuses
  both inputs is "refuses without discriminating". A check that refuses neither is
  "declared rejection not observed". A check whose two declared inputs are identical
  or differ in no way the check can act on is "pair cannot discriminate". The first
  two have OPPOSITE remedies — narrow the guard, or widen it — so one shared message
  lets an implementer discharge both findings with a repair that makes one of them
  worse.
- A PAIR THAT DOES NOT DISCRIMINATE IS A FINDING, NOT A MALFORMED-INPUT ERROR. The
  run must report it and continue examining the remaining checks. A run that refuses
  to proceed on a bad declaration leaves those checks unexamined, which is the never-attempted
  state wearing an error message — and an unexamined check is exactly what this tree
  exists to make visible. Assert the continuation, not only the report.
- DO NOT FORCE A PAIR ONTO A CENSUS-SHAPED CHECK. A check that counts or measures
  rather than accepts or rejects has no acceptable-versus-unacceptable pair at all
  and is handled by GE-126b-5-i's grounded exemption (`negative_control.not_applicable`
  + `reason`, already in the schema). Consume that disposition; do not re-derive it,
  and do not let the exemption be used to escape a pair that simply fails to discriminate.
- EXTEND GE-120f-1's RUNNER AND ITS SINGLE RECORD PER CHECK. This record adds a second
  observation and makes the parent's observed value conditional on the two differing.
  It does not add a second record, a second report, or a second population.
- AC_ENFORCE_STRICT=1 on every pytest invocation; execute the DEPLOYED copy out of
  process through GE-120c-1's harness; any module imported from outside templates/scripts/commit_guardian/
  goes into the scripts/build_phases.py deploy map in the same change.
- 'Error-handling policy: specific-exception try/except around subprocess and I/O,
  logged at WARNING or higher or re-raised. A failed second invocation is `blocked`
  for that check, not a silent fallback to the single-invocation verdict.'
```
