# A blocking build and type-check check runs on every web-app pull request and fails on any build or type error

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `BP-1400a-1` — A blocking build and type-check check runs on every web-app pull request and fails on any build or type error — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `BP-1400a-1`. Component: `build-pipeline`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given the continuous-integration configuration for the repository,
When a pull request is opened or updated with one or more changed files under
  the web-app directory (leafcutter-web/),
Then a dedicated web-app check builds the web app and runs its type-check
  automatically,
And the check reports a failing (non-passing, blocking) result whenever the
  build fails or any type error is reported,
And the check reports a passing result only when the web app builds and
  type-checks with no errors,
And the check is a hard, blocking check — not an advisory or informational one
  that a pull request can be merged despite.
```

## Implementation Notes

```yaml
- 'Add a NEW web-app build/type-check job to the existing .github/workflows/ci.yml
  alongside the current Python jobs (lint, component-vocab, test, typecheck). The
  job MUST be blocking: do NOT set continue-on-error — a build or type error fails
  the job and the check (contrast the existing informational typecheck job).'
- 'Scope the job to web-app changes via a `paths:` filter on `leafcutter-web/**` (or
  an equivalent changed-files guard) so it runs only when a PR touches the web app
  — the trigger contract owned by BP-1400a-2. Match ci.yml conventions: actions/checkout@v4,
  runs-on ubuntu-latest, triggered on pull_request targeting main (and push to main).'
- The job MUST use Node via actions/setup-node (with npm caching keyed on leafcutter-web/package-lock.json)
  and run `npm ci` then `next build` in the leafcutter-web/ working directory. `next
  build` runs the TypeScript compiler (tsc), so a type error fails the build and therefore
  the check — no separate tsc invocation is required, though one may be added.
- Pin the check NAME deterministically (a stable `name:` on the job). This exact name
  is a cross-AC contract consumed by the merge-gate/required-status-checks wiring
  in BP-1400a-4 — if the name changes, branch protection silently stops requiring
  it (mirrors the BP-1200b-1 -> BP-1200c-1 name contract).
- Errors in the npm ci / build prepare step must fail the job loudly (non-zero exit)
  rather than skipping to a misleading green; the blocking guarantee must not be defeatable
  by a silently-skipped preparation step.
- 'PREREQUISITE: `next build` must already succeed on leafcutter-web/ from a clean
  `npm ci` (no pre-existing build break) before this check is made blocking, or every
  web-app PR is blocked. Verify a clean baseline first (analogous to the BP-1200a-1
  fresh-clone-green prerequisite for the Python test gate).'
```
