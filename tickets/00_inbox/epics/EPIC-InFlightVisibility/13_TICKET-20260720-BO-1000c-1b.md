# The /finalize-feature launcher polls the run-progress journal and relays it into the main conversation

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `BO-1000c-1b` — The /finalize-feature launcher polls the run-progress journal and relays it into the main conversation — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `BO-1000c-1b`. Component: `build-orchestration`. Assigned agent: `llm-expert`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given the finalize-feature workflow is running in the background and appending
  progress lines to the run-progress journal as they happen,
When the /finalize-feature launcher has started that background run,
Then the launcher polls the run-progress journal while the run is in flight and
  relays each new progress line into the main conversation where the user
  already is,
And the user receives the progress in the conversation without having to open
  or watch the separate live-workflows view.
```

- [ ] AC-1: the launcher polls the run-progress journal while the run is in flight and
- [ ] AC-2: the user receives the progress in the conversation without having to open

## Implementation Notes

```yaml
- 'Surface: the /finalize-feature launch contract — templates/commands/finalize-feature.md
  (the command doc) plus the instruction to the invoking main loop to poll and relay.
  This is prose/launch-contract work (llm-expert), NOT a finalize-feature.js edit:
  a background workflow cannot inject into the main conversation, so the relay must
  be driven by the launcher/main loop.'
- 'The command doc must instruct the launcher: after starting the background finalize
  run, poll the run-progress journal (the path/convention delivered by BO-1000c-1a)
  at a bounded interval while the run is in flight, and surface each new line into
  the main conversation in emission order.'
- Relay must be incremental (new lines only, no duplicates) and must stop cleanly
  when the run terminates (success or halt), then present the end-of-run recap.
- The relay must not require the user to open the separate live-workflows view; the
  live-workflows view remains available but is not the delivery path.
- Locate the journal exactly as BO-1000c-1a delivers it (same path convention / run
  key); do not invent a second location. If the journal is absent or unreadable, degrade
  gracefully (report that live progress is unavailable) rather than erroring the launch.
- Keep the /finalize-feature command doc and its deployed copy in parity via build.py
  (ADR-001).
```
