# The harness reports its own setup failure instead of passing vacuously

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-120c-1-i` — The harness reports its own setup failure instead of passing vacuously — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-120c-1-i`. Component: `guardrail-engine`. Assigned agent: `test-writer`. Estimated complexity: `S`. Complexity: `low`.

## Acceptance Criteria

```gherkin
Given the harness cannot complete the creation of its separate working copy — for example
  the copy is created but the deployed layout it needs was never built,
When the harness runs,
Then it states that no check was exercised and names the setup step that did not complete,
And it reports a failure rather than reporting that every check passed,
And a run in which zero checks were exercised is never reported as a successful sweep, even
  when no assertion failed,
And the count of checks actually exercised appears in the harness output, so a reader can
  see that the number is not zero without reading the assertions.

Coverage note: exercise this by running the harness against a deliberately incomplete setup
and asserting on the observed failure and message. This case must be run, not reasoned
about — the whole point is that the vacuous path produces no failing assertion of its own.
```

## Implementation Notes

```yaml
- VACUOUS SUCCESS IS THE TARGET STATE. Zero checks exercised with zero failing assertions
  must be a FAILURE. Assert on the exercised COUNT, not on the absence of assertion
  failures — the whole defect is that the vacuous path produces no failing assertion
  of its own, so a test that waits for one will never fire.
- The exercised-check count must appear in the harness output on EVERY run, including
  successful ones. A hard failure catches a harness that breaks loudly; the printed
  count catches a harness that silently narrows its own subject list, which is the
  slower and more common decay. Compare the count against the manifest set (GE-120c-3)
  rather than against a constant.
- The setup step that did not complete must be named SPECIFICALLY — for example 'build.py
  did not produce .leafcutter/scripts/commit_guardian in <copy>' — not reported as
  a generic setup error. A generic message sends the reader to the wrong layer.
- 'Exercise this against a DELIBERATELY INCOMPLETE SETUP: a second copy created but
  never built. Do not simulate it by stubbing the harness''s own counter or by raising
  a synthetic exception — a stub reproduces the author''s belief about how setup half-fails,
  and a harness that stands up infrastructure has far more ways to half-fail than
  a check does.'
- 'PRECEDENT TO ENCODE, not merely to remember: this project has shipped this exact
  shape twice. fast-lane-build.js passed its grep-only structural tests while never
  executing its red/green gates, and the phantom-done files_touched hook passed its
  unit tests while being a no-op on every real ticket. Both were green sweeps over
  nothing. The interlock must be mechanical.'
- 'The harness is itself subject to GE-120a: a harness that cannot run reports a could-not-check
  outcome, distinguishable from a clean sweep. Reuse the shared outcome vocabulary
  rather than inventing a second one for the test layer.'
```
