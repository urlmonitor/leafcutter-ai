# KI-BO-20260922-0500 — the fast lane renders a crashed resolver as an empty build set

> Filed 2026-09-22, observed on the first `fast-lane-ship` run against `BP-1500g-2`.
> Index: [build-orchestration.md](../build-orchestration.md).

- **Severity:** high — the run reports success, so nothing downstream questions it
- **Status:** open
- **Occurrences:** 1
- **Where:** `templates/workflows-js/fast-lane-ship.js` — the Resolve phase, where the
  `resolve-connected` agent's result feeds the `nothing_to_build` early return

**Symptom, verbatim from the run payload:**

```json
{"status":"ok",
 "message":"Nothing to build: the connected set for BP-1500g-2 is empty (already done,
            or the id resolved to no not-done leaves), with structural-parent
            prerequisites excluded from the dependency walk.",
 "ac_ids":[], "nothing_to_build":true, "created":true,
 "base_commit":"fa2a46eda8bfd5d8a007c5f18643aaef575caf96",
 "base_matches_origin_main":true}
```

and, separately, in the run's `<failures>` block:

```
[resolve-connected] failed: API Error: Can't reach the API server
                            — check your internet or DNS (EAI_AGAIN)
```

**The set was not empty.** Running the lane's own resolver by hand, at the same commit:

```
$ python scripts/build_orchestration/fast_lane.py select_connected \
    --ac BP-1500g-2 --ac-root docs/acceptance-criteria --exclude-structural-parent
["BP-1500g-2", "BP-1500g-2-i"]
```

Both `readiness: approved`, `work_status: todo`, and `check_producibility` returns
`{"producible": true, "unproducible": []}`. There was a full build's worth of work to do.

**Cause.** The `resolve-connected` agent died on a transient network error. Its result was
absent or empty, and the Resolve phase treats an empty result as an empty connected set —
which is a legitimate, expected outcome for an AC whose subtree is already done. The failure
took the same path as the success and produced the same verdict.

**Why this is worse than a crash.** A crashed run gets re-run. This run said `status: ok` and
explained itself in confident prose — "already done, or the id resolved to no not-done leaves"
— which is a *diagnosis*, and a wrong one. Nothing downstream re-examines a lane that reported
success with nothing to do, so the AC would simply have been recorded as needing no work. It
was caught only because the operator happened to read the `<failures>` block, which sits below
the payload and is easy to skip when the status says ok.

**A second instance, same run family, different input.** Three runs later the same lane
returned a structured refusal blaming "a symlink at
`/home/henzeh/projects/leafcutter/.leafcutter`" that "interferes with locating the git
repository root", citing the operator's own memory file as corroboration. That path is a plain
directory; no symlink exists; the cited memory entry describes a different path already fixed.
The underlying failure was real — the deployed script genuinely crashes,
`KI-BP-20260922-0620` — but every stated cause was invented, and the suggested remediation
("remove the parent symlink") would have deleted a directory roughly eighty live worktrees
resolve through.

The two instances share a mechanism: **the lane composes a verdict from an agent's
unverified claim and publishes it in the same structured shape it uses for verified facts.**
An empty result becomes "nothing to build"; a confabulated explanation becomes a `reason`
code. A reader cannot tell either from a checked answer. The second instance is also an
instance of `KI-BO-20260921-fastlane-worktree-agent-acts-on-leaked-conversation` — the phase
agent drawing on the parent session's context — reached by reading rather than by acting.

**What the lane got right, so it is not mistaken for the fix.** Between those two runs the
occupancy guard refused twice, correctly: it named the occupied path, reported whether the
workspace was pushed, distinguished `uncommitted_changes: true` from `false` across the two
attempts, and marked which remedy was destructive. Faced with genuine uncertainty about a
workspace it might damage, it refused and said why. That is the disposition the Resolve phase
lacks, in the same file. The contrast is the useful part: the machinery for an honest
uncertain answer already exists here and is simply not applied to the resolver's result.

**Fix direction.** The Resolve phase must distinguish "the resolver ran and returned an empty
set" from "the resolver did not return". An agent error should halt the lane rather than fall
through to the empty-set branch; at minimum the `nothing_to_build` early return should require
a successful resolver result, and the payload should never claim `status: ok` when any phase
agent errored. The run already *has* that information — it is recorded in `<failures>` — it is
simply not consulted before the verdict is composed.

A cheap independent check is also available: `select_connected` is a plain CLI needing no
model, so the lane could re-run it as a subprocess and compare. That would have caught this in
one call. More generally, a phase agent's claim about the *environment* should be verified
before it is rendered as a `reason` code, or labelled as unverified when it cannot be.

**Related.** `KI-TQ-20260914-1050` (same shape — a non-answer rendered as a specific claim —
in the done-proof gate) · `KI-BO-20260921-fastlane-worktree-agent-acts-on-leaked-conversation`
(explains the second instance) · `KI-BP-20260922-0620` (the real failure underneath it) ·

**Pattern:** a failure path and a legitimate success path that produce byte-identical output,
so the runner cannot tell them apart and picks the reassuring one.
