## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-120e-2-i` — A check whose recorded change-set source disagrees with what it actually inspects is named by running it, not by believing it — so that the acceptance criterion is satisfied.

## Acceptance Criteria

```gherkin
Given a check whose manifest entry records that the commit path hands it the files to
  inspect, so it is outside the set GE-120e-2 governs,
And a commit whose staged tree holds carried-in work that would trip that check, and whose
  author wrote nothing that would,
When that check is executed as a process against that commit,
Then it raises no objection,
And a check that does raise one is named, together with the content it objected to and the
  state that content came in from, and the determination reports a failure,
And the same is asserted for every manifest entry recorded as being handed its files, so a
  recorded source that is not what the check does is caught by running the check rather
  than by reading the record.

Coverage note: the record is a claim, and this AC is the only thing that tests the claim.
Cover it by planting a check whose entry claims it is handed its files while it derives
its own change set, and asserting the sweep names that check and fails. A sweep that
cannot be made to fail this way is not evidence.
```

## Implementation Notes

```yaml
- THE SWEEP EXECUTES CHECKS AS PROCESSES. Reuse GE-120c-1's out-of-process harness
  (unit_tests/portability/) so each check runs from the deployed layout with the source
  tree off its import path. The record is a claim about runtime behaviour; importing
  the check module to inspect it is exactly the reading-the-record move this AC exists
  to replace.
- SELF-DEMONSTRATION IS A DELIVERABLE. Plant a check whose manifest entry claims it
  is handed its files while it derives its own change set, and show the sweep FAILS
  on it. A sweep that has never been observed to fail is not evidence — the same standard
  GE-120c-1 sets for its harness. The planted check must be a fixture the sweep discovers
  through the manifest, not a special case coded into the assertion.
- SUBJECT SET IS THE COMPLEMENT, DERIVED NOT LISTED. Iterate every manifest entry
  recorded as handed-its-files, read from GE-120e-2's manifest reader at run time.
  No hand-written check list and no hard-coded entry count — a new hook joins the
  sweep by being registered, not by anyone remembering.
- 'THE FAILURE REPORT MUST NAME THREE THINGS: the check, the content it objected to,
  and the state that content arrived from. ''Check X failed'' is not actionable and
  does not distinguish this defect from an unrelated check failure.'
- RUNTIME. Roughly fifty processes per sweep today. Build the fixture repository ONCE
  per sweep, never per check, and mark the sweep slow rather than letting it quietly
  narrow its subject list to stay fast.
- DO NOT DUPLICATE GE-120e-3. That AC's differential pair covers the GOVERNED set;
  this sweep covers the complement. If the two ever iterate the same entries, one
  of them is reading the record wrongly — surface that as a failure rather than tolerating
  the overlap.
- IF A SHARED REGISTRY-CONFORMANCE MECHANISM EMERGES from GE-120a-2-i or GE-120c-3,
  use it rather than adding a fourth private manifest sweep. Record which was chosen.
- 'Error-handling policy applies to the sweep''s own subprocess and filesystem calls:
  specific exceptions, logged at WARNING, never swallowed, and a setup failure is
  a reported failure rather than a skipped case (GE-120c-1-i).'
```

**The failure is real, and it is in the test, not in the checks it accuses.** The sweep
reports six handed-its-files checks as having "objected to carried-in content". None of them
did. Every one failed to *run*:


Two are argument-shape failures (one is a `commit-msg`-stage hook given no message file);
two need a product-truth store the second working copy does not contain; two need a fuller
layout than the fixture provides.

**The defect is the sweep's predicate: it treats `exit != 0` as "objected".** That conflates
*could not check* with *found something* — precisely the distinction `GE-120a-1` was built to
establish and that `check_outcome.py` exists to express. The AC's own criterion is that a
check "raises no objection"; a check that never ran raised nothing.

**Fix direction.** The harness already exposes `_looks_like_could_not_check(output)`. The
sweep should classify each non-zero outcome as *objection* or *could-not-check* and fail only
on the former — while still failing loudly if a check could not be exercised at all, since
`GE-120c-1-i` forbids silently skipping. Narrowing the subject list to the checks that happen
to run cleanly is NOT acceptable: this AC's Implementation Notes forbid it explicitly, and it
would reintroduce the hand-written-list defect `GE-120e-2` just removed.

**Also note the `_MANUAL` suffix** added to the test name during the drive. It does not
exclude the test from collection — pytest still runs it and it still fails. If the intent was
to mark a slow test, that needs a marker and an explicit exclusion, not a naming convention;
as it stands the suffix reads as an exemption that has no mechanical effect.
