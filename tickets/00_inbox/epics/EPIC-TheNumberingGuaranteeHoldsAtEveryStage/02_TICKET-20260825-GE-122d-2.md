## Acceptance Criteria

```gherkin
Given an author commits a record claiming a contested number with the commit-time guards
  bypassed, so the commit-time stage never ran at all,
And the resulting change is proposed for merge into the shared branch,
When the shared build's numbering gate runs on that proposed change,
Then the gate fails,
And its output names the contested number and every claimant path,
And the gate's name appears in the set of checks the shared branch requires to pass before a
  merge is permitted, so the failing gate actually prevents the merge rather than merely
  reporting on it,

And given a proposed change that contests no number,
Then the gate passes and states, per namespace, how many artifacts it inspected.

Coverage note: covered by executing the gate's own command against a checkout that really
contains the contested pair and asserting the failing result and the named paths — plus a check
that the gate's name is present in the shared branch's required-check set. A gate that fails
correctly but is not required is a report, not a backstop, and this criterion is not met by
either half alone.
```

## Implementation Notes

```yaml
- 'THE REQUIRED-CHECK HALF IS AN OUT-OF-REPOSITORY OPERATION AND MUST BE PLANNED AS
  ONE. The shared branch''s required-check set lives in a GitHub ruleset, not in any
  file in this repository — verified 2026-08-17: no settings-as-code script exists
  here, so BP-1200c-1''s settings-as-code decision was in practice carried out by
  hand. Adding this gate means a `gh api` call against the ruleset under the non-EMU
  `urlmonitor` account with an admin-scoped token. Budget it as a deliberate ops step
  with recorded evidence, not as something the coder does incidentally.'
- Because the required-check set is not in the repository, a unit test CANNOT assert
  it, and a test that silently skips when no token is present is a false green of
  exactly the kind this tree exists to eliminate. Satisfy the second half with a recorded
  `gh api` query of the ruleset's required-check names, captured as evidence on the
  implementing ticket, and treat a skipped or unavailable query as NOT DONE rather
  than as passed.
- The gate's job NAME in ci.yml is the string the ruleset matches, and the match is
  exact. Choose it at implementation time and never rename it afterwards — the existing
  test job carries the same warning in its own comment, and a renamed job silently
  becomes a non-required job that still reports green.
- 'ORDERING IS LOAD-BEARING: do not make this gate required until GE-122e''s repair
  has landed and GE-122e-3 passes. A required whole-collection gate over a collection
  that still holds the GE-119 collision and the five twice-held work items fails every
  merge in the repository on day one, and the documented response to that situation
  in this codebase has twice been to defer or diff-scope the gate.'
- 'REPRODUCE THE STAGED-INDEX HANDLING OR THE GATE VALIDATES NOTHING. The `AC store
  valid` job documents the trap in full: hooks reading from `git diff --cached` see
  an empty index in a CI checkout, where the PR''s files are committed rather than
  staged, so invoking them naively passes. Its answer is `git reset --soft origin/<base>`,
  and its comment records verifying both ways — with the reset a malformed record
  fails, without it the same record passes. Any gate reusing a staged-index reader
  inherits this, and a false pass here defeats the entire backstop.'
- Verify the gate by executing its own command against a checkout that genuinely contains
  the contested pair — not by asserting the job exists in ci.yml. This repository
  already contains a written, tested, deployed decision-number collision guard that
  is registered nowhere and has never run; a job block in a YAML file is the same
  class of evidence.
- The inspected-count output on the passing path is not decoration. A CI gate that
  passes over an empty or unreadable checkout looks identical to one that passed over
  the whole collection, and this is the stage where nobody is watching the output.
- 'DEPLOY MANIFEST: the CI job runs `python scripts/build.py --target-dir .` before
  invoking the gate, as the existing AC-store and done-proof jobs do. Every module
  the gate imports must be in the matching deploy list, or the required gate crashes
  with ModuleNotFoundError and blocks every merge — the done_proof.py precedent, and
  the reason this it_requirement appears on every AC in this tree that touches a gate.'
```
