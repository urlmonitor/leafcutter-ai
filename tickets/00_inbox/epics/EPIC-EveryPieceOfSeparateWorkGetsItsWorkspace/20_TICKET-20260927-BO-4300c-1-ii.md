# Every protection the project declares must fire; one that is present but does not fire produces a refusal

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `BO-4300c-1-ii` — Every protection the project declares must fire; one that is present but does not fire produces a refusal — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `BO-4300c-1-ii`. Component: `build-orchestration`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given a test project that declares three kinds of protection -- checks that
  run when a commit is made, a check on the commit message, and a check that
  runs after a merge -- and a test fixture that can leave exactly one of those
  kinds declared and in place in a new workspace but not firing,
When the workspace maker answers,
Then it answers ready only when every kind of protection the project declares
  was shown to fire inside the workspace, each by a real operation that it
  rejects: a commit of a known-bad file for the commit-time checks, a commit
  with a known-bad message for the commit-message check, and a merge that
  brings in a known-bad change for the after-merge check, which reports that
  merge as failing,
And when any one declared kind does not fire, the answer is a refusal naming
  that kind,
And the presence of the protection settings, or of the files meant to run a
  kind of protection, never on its own produces a ready answer.
```

## Implementation Notes

```yaml
- 'STAGE SET FROM THE PROJECT''S OWN DECLARATION (KI-CG-20260914-post-merge-stage-registers-but-installs-no-shim):
  ensure installs a shim into the clone''s own .git/hooks for EVERY stage the workspace''s
  own hook declaration names -- in practice the union of `stages:` in the workspace''s
  generated .pre-commit-config.yaml, the same source commit_guardian''s install_pre_commit_shims.collect_stages
  reads (today pre-commit, commit-msg and post-merge). The stage list is never hard-coded
  in the maker, and no new copy of the stage-derivation logic is written: the maker
  uses the install''s own shim installer (run as a separate process from the workspace''s
  install, so the maker stays stdlib-only) or an equivalent single shared source.
  Clones have their own hooks directory, unlike worktrees.'
- 'ONE CANARY PER DECLARED STAGE, each a real operation the stage rejects: pre-commit
  -- a commit of a known-bad file is rejected; commit-msg -- a commit with a known-bad
  message is rejected; post-merge -- a merge that brings in a known-bad change is
  reported as failing by the post-merge hook (non-zero exit; a post-merge hook cannot
  undo the merge). Each canary''s known-bad input is taken from the install''s own
  declaration, never hard-coded to one hook; a declared stage with no declared canary
  input cannot be shown to fire and counts as not firing.'
- 'Canaries leave nothing behind: commit canaries never land in the branch, the index
  or the working tree; the after-merge canary runs against a disposable ref, and afterwards
  the line of work''s branch tip, index and working tree are exactly as before and
  the disposable ref is gone -- confirmed by the tree_clean ingredient (BO-4300c-1-iii)
  evaluated after the canaries.'
- 'ANSWER FIELDS (aligned with BO-4300c-1 and BO-4300c-2): checks.hooks_pre_commit_fired,
  checks.hooks_commit_msg_fired, checks.hooks_post_merge_fired, each true|false|''n/a'';
  checks.hooks_canary_rejected is their conjunction (true only when every declared
  stage fired); hooks_stages_declared lists the stages the declaration names. When
  any declared stage does not fire, the answer is refused with code HOOKS_INACTIVE,
  its message names the stage(s), and inactive_stages lists them; no workspace_path.'
- '''n/a'' RULE: for kind scratch ALL three stage checks and the conjunction are ''n/a''
  (BO-4300e-4 -- nothing is committed or merged in a comparison copy). For every other
  kind the pre-commit check is never ''n/a'' (a project that declares no commit-time
  stage gives HOOKS_INACTIVE naming pre-commit), and the commit-msg and post-merge
  checks are ''n/a'' only when the project''s declaration does not name that stage
  -- never because a declared stage was skipped.'
- Presence of .pre-commit-config.yaml (or any .leafcutter copy), or of a shim file
  for a stage, is recorded (precommit_config_present) but never on its own produces
  ok. The fail-open OR-probe (setup_ticket_worktree.py AC-5, CLAUDE.md's ls ... ||
  ls ... check, verify_precommit_active.py's check_b_config fallback) is not reproduced.
- 'Git spelling (KI-CG-20260925-commit-delegation-hook-misses-git-dash-c): canary
  commits and the canary merge run with git''s working directory set to the workspace,
  never as `git -C <path> commit`; the same holds in the tests and fixtures.'
- The real install must declare a canary input for each stage it declares; commit_guardian's
  declaration carries only a manual-stage precommit-canary today (verified 2026-09-25),
  so adding per-stage canary declarations to the install is in scope of this record's
  ticket (flagged to the user as a cross-component touch on commit_guardian).
- Proof runs the DEPLOYED maker -- the copy an install delivers, resolved through
  the shared test locator delivered by BO-4300f-4 -- as a separate process against
  real temporary git repositories with a real bare hub. No mock of git, no import
  of the maker module, no grep of its source (CLAUDE.md 'Gate / Workflow ACs -- Verify
  Behaviorally, Not by Grep'); a test never falls back to the templates/ source copy.
- 'Tests must not spawn the package''s own scripts/build.py (CLAUDE.md ''Tests must
  not spawn their own build.py''): the deployed maker comes from the shared deployed
  layout, and fixture projects carry a minimal stub build entry point that installs
  a real, rejecting hook in well under a second. A test that must mutate the package
  and build its own copy says so and justifies it in its ticket.'
- All temporary projects, hubs and workspaces live under the test's temp directory
  and run git with an isolated global and system config; afterwards the developer's
  own repository's branches, registered worktrees and local git config are unchanged
  (BO-4300f-4-i, F14, KI-TQ-012).
```
