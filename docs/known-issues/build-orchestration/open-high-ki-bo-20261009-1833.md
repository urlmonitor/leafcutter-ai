# KI-BO-20261009-1833 — /build-feature's red-baseline gate outlives the relaying agent's 120s Bash timeout, and the agent returns {output: "", exit_code: 0} from a stale empty read, so a gate that PASSED halts the drive as unverifiable

- **Severity:** high. The driver's fail-closed parse did its job and nothing wrong was
  committed. The defect is upstream of it: the envelope the driver received was fabricated. It
  paired an exit code taken from one source with an output taken from an earlier, empty read of
  another. The halt message then says the gate "could not be verified" for a gate that passed.
  Any ticket whose red-baseline pytest run takes longer than 120s cannot reach its coder on a
  first run.
- **Status:** open. No AC. The gate dispatch is TQ-500f-3-ii; the reuse path is F2 in
  `scripts/build_orchestration/_fl_heavy_lane_gate.py`.
- **Occurrences:** 1 (2026-10-09, run `wf_0648a71b-2ac`, `/build-feature
  EPIC-OneDurableLogRootForEveryWorkspace`, ticket `01_TICKET-20261009-INF-500d-4-iii`, after
  `adr-author` and `test-writer` both returned `ok`).
- **First seen:** 2026-10-09 · **Last seen:** 2026-10-09
- **Where:** `templates/workflows-js/build-feature.js` on origin/main `282117ab5`: the gate
  command (:2159-2163); the dispatch to `agentType: "status-checker"` with the prompt "Run the
  following command and return ONLY its raw stdout" and no timeout or no-background instruction
  (:2164-2168); the envelope parse (:2169-2172); the fail-closed refusal (:2173-2177). The
  deployed copy (`.claude/workflows/build-feature.js`, built 2026-10-08) has the same logic at
  :2134-2143 (dispatch), :2144-2147 (parse) and :2148-2155 (refusal, still as an inline `return
  { status: "blocked", ... }` rather than main's `refuse()`; the behaviour is identical).

  The command exists in the deployed install tree: `.leafcutter/scripts/build_orchestration/fast_lane.py`
  dispatches `heavy_lane_gate` at :490, and both it and `_fl_heavy_lane_gate.py` are
  byte-identical to `scripts/build_orchestration/` on origin/main. The deployed workflow is
  older than main (`git diff --no-index --stat`: 91 insertions, 153 deletions), but none of that
  difference touches this gate. Not fixed on origin/main; this is not a stale deploy.

## Symptom

```text
The red-baseline gate reply could not be verified for ticket .../01_TICKET-20261009-INF-500d-4-iii.md:
not a parseable {output, exit_code} envelope carrying a real heavy_lane_gate verdict (raw reply:
{"output":"","exit_code":0}). Fail closed — the coder is never dispatched on an unverified
red-baseline gate reply.
```

The tests were red. Running the test file by hand shows real assertion failures.

## Cause

The journal's `red-baseline-gate` step (agent `ab7c6a2f4e435b364`, `agentType: status-checker`)
ran exactly the command it was given:

```text
python <worktree>/.leafcutter/scripts/build_orchestration/fast_lane.py heavy_lane_gate
  --source-ac INF-500d-4-iii --test-root <worktree> --ac-root <worktree>/docs/acceptance-criteria
  --ticket <worktree>/tickets/00_inbox/epics/EPIC-OneDurableLogRootForEveryWorkspace/01_TICKET-20261009-INF-500d-4-iii.md
```

Its transcript, in order (UTC):

1. 18:15:40 — the Bash call starts. No `timeout` is passed, so the 120s default applies.
2. 18:17:41 — "Command did not complete within its 120s timeout and was moved to the
   background (ID: bdz3b8lil)."
3. 18:17:43 to 18:19:23 — `sleep 100; cat <output file>` returns nothing.
4. ~18:19:28 — a `sleep 240` and a Read of the output file are issued together. The Read
   returns "the file exists but the contents are empty".
5. 18:21:40 — the background command finishes. The completion notice reads `Background
   command "Run heavy lane gate script" completed (exit code 0)`.
6. 18:23:27 — the sleep ends and the agent returns `{"output": "", "exit_code": 0}`, without
   re-reading the file.

The output file was still on disk afterwards. It holds the real verdict:

```text
{"gate_passed": true, "reason": null, "interpreter": "/usr/bin/python", "red": [ ...9 entries,
 every one INF-500d-4-iii, outcome FAILED... ], "green_at_baseline": [], "inconclusive": [],
 "preexisting": [], "refused": [], "applicable": true, "verified": true, "recorded": true}
[exited with code 0]
```

So the gate ran correctly, took about six minutes, passed, and recorded its verdict in the ticket:
the ticket's frontmatter now carries `red_baseline_gate: {"passed": true, "recorded_at":
"2026-10-09T18:21:40+00:00", ...}` with the same nine red tests. Three
things combined to lose it:

1. **The workflow gives a long-running command to a relayer with a 120s default.** The prompt
   names no timeout and does not forbid backgrounding. A pytest run over a fresh test file can
   take minutes.
2. **The relaying agent assembled an envelope from two different moments.** `exit_code` came
   from the completion notice; `output` came from the empty read before it. Nothing in the
   prompt or in `status-checker`'s charter tells it to read the output after completion, or to
   refuse rather than answer when it does not have the output.
3. **`status-checker` is the wrong agent for this.** It is registered `permits_shell: false`
   (see `KI-BO-20260927-status-checker-runs-workflow-shell-commands`, which lists this
   driver's other shell dispatches). The fast lane already moved its command steps to
   `command-step-runner` (`templates/workflows-js/fast-lane-ship.js:1052`), but that template
   says nothing about timeouts or backgrounding either, so moving the dispatch alone would not
   close this entry.

The pytest node ids in the verdict are rooted at the workspace parent
(`worktrees/EPIC-OneDurableLogRootForEveryWorkspace/unit_tests/...`). That suggests the gate's
pytest ran from above the worktree, which may explain part of the six minutes. Not confirmed.

## Detection

A refusal whose raw reply is `{"output":"","exit_code":0}`. In the step's agent transcript, look
for "moved to the background". Then read the task output file it names. If that file holds a
JSON verdict, the gate ran and the reply lost it.

## Workaround

Re-run `/build-feature`. The gate recorded its pass in the ticket's `red_baseline_gate`
frontmatter line, and F2's reuse path returns a recorded verdict without running pytest when the
`source_ac` matches and every recorded red test is still newly added. So the re-run should be
fast. Expected from the code (`_fl_heavy_lane_gate.py` module docstring); not yet confirmed by a
re-run.

## Fix direction

1. Dispatch the gate to an agent whose charter covers running a command
   (`command-step-runner`), and pass a Bash timeout that covers a full red-baseline run.
2. Make the relaying contract explicit for slow commands: if the command is backgrounded, wait
   for completion, then read the output; never return an `exit_code` without the output that
   goes with it. If the output cannot be obtained, return a reply the parse rejects as a
   failed relay, not an empty success.
3. Better still, have the gate write its verdict to a file whose path the workflow chooses, and
   read that file back in a separate bounded step. Then the verdict does not depend on an
   agent relaying stdout at all. This is the same remedy as
   `KI-BO-20261009-setup-reply-truncated-on-new-worktree`.
4. Have the refusal message say which half was missing (empty output with exit 0), so the
   operator looks at the relay and not at the tests.
