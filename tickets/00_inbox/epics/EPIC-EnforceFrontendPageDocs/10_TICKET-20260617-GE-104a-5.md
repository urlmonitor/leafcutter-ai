## Acceptance Criteria

```gherkin
Given a ticket whose files_touched contains a newly added frontend page at
  site/app/<route>/page.tsx
And files_touched does NOT contain the matching reference doc at
  docs/reference/frontend/<name>.md
When agent selection runs during ticket creation (the real ticket-creation path
  that reads the agent registry to resolve each agent's status)
Then the documentation-expert agent actually resolves to "needed"
And the trigger condition genuinely evaluates to a firing result — it does not
  silently fall back to its default_status of "not_needed"

---

Given a ticket whose files_touched contains BOTH a newly added frontend page at
  site/app/<route>/page.tsx AND its matching reference doc at
  docs/reference/frontend/<name>.md
When agent selection runs during ticket creation
Then this trigger does NOT fire on that basis
And the documentation-expert agent is not forced to "needed" by this trigger
  (no false positive when the doc is already part of the planned work)

---

Note: This AC is an enablement/spike. It defines the OUTCOME — the planning-time
trigger must genuinely evaluate and fire — but leaves the MECHANISM to the IT PO.
The two candidate mechanisms are: (a) wire the LLM-evaluation path so the existing
llm-type trigger condition (authored in GE-104a-2 / GE-104a-2-i) actually evaluates
instead of raising and falling back to not_needed; or (b) extend the
selection-criteria DSL grammar with a derived-missing / negation primitive so the
condition can be a dsl-type expression that evaluates deterministically. Either
mechanism must produce the observable outcomes above. The commit-time hook
(GE-104a-1) remains the authoritative backstop regardless of which mechanism is
chosen.
```
