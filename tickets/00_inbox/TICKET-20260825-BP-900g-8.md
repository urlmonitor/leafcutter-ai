## Acceptance Criteria

```gherkin
Given any script the build deploys into a consumer install,
And that script resolving, importing, or executing another module belonging to the
  same package — whether by import statement, by path construction relative to its
  own location, or by dynamic loader,
When the build runs its deploy-completeness preflight,
Then every such intra-package dependency is itself deployed, or the build exits
  non-zero naming the deployed script, the dependency it needs, and the deploy
  phase that would have to carry it,
And the dependency set is DERIVED from what the deployed script actually resolves,
  so a module added to a deployed script tomorrow is covered without anyone editing
  a list — a hand-maintained manifest of dependencies does not satisfy this
  criterion even when it happens to be complete on the day it is written,
And the closure is transitive: a dependency of a dependency is subject to the same
  rule, so a chain that is correct at its first hop and broken at its second fails
  the build rather than passing it,
And the demonstration runs the build into a temporary target directory and then
  exercises the DEPLOYED copy in a fresh subprocess, with a negative control that
  withholds one dependency from the deploy and must be shown to fail the build —
  a check performed against the source tree does not satisfy this criterion,
  because the source tree contains every module by construction and is therefore
  structurally blind to the defect,
Because at HEAD 339b0981c scripts/ac_store/generate_ticket_from_ac.py is deployed
  by the build_ac_store phase and resolves its sibling
  scripts/ac_store/_component_migration_map.py, which that phase does not deploy —
  so in every consumer install the sibling is absent. That deploy map already
  carries THREE separate comments warning about this exact ModuleNotFoundError
  failure mode, for done_proof.py, test_enforcement.py and ac_parent_id.py, and
  still contains a live fourth instance. A hand-maintained list annotated with
  warnings about the way it fails is not a mechanism; it is a record of the
  mechanism's absence.
```

config_schema_fragment:
  description: The three sets this AC and BP-900g-5 together govern, named explicitly
    so an implementer cannot satisfy one by collapsing it into another. The whole
    defect class is these three being assumed equal while never being compared.
  properties:
    deploy_declaration:
      description: 'SET B — the deploy_map: what a phase declares it ships. Remains
        an explicit, human-readable declaration. It is CHECKED against set A, not
        generated from it.'
      items:
        type: string
      type: array
    guard_manifest:
      description: 'SET C — _manifest_ac_store_scripts: the guard''s model of what
        has been deployed. Per BP-900g-5''s fifth it_requirement this must derive
        FROM set B. It must never be the source set B is derived from.'
      items:
        type: string
      type: array
    invariant:
      description: B must contain closure(A), enforced by a build failure; C is derived
        from B. Deriving B from A automatically, or deriving C from anything other
        than B, does not satisfy this AC.
      type: string
    resolved_closure:
      description: SET A — the transitive set of intra-package modules a deployed
        script actually resolves, DERIVED from the code by static analysis of imports,
        relative path construction, and dynamic loader calls. Never hand-maintained.
        This is the new artifact this AC introduces.
      items:
        type: string
      type: array
  required:
  - resolved_closure
  - deploy_declaration
  - guard_manifest
  type: object
constraints:
- 'THE BINDING DIRECTION RULE (resolves the conflict the BA escalated). Three sets,
  two edges, and the direction of each edge is fixed. Edge 1: B must CONTAIN closure(A)
  — checked at build time, failing the build when it does not. Edge 2: C DERIVES FROM
  B — this is BP-900g-5''s fifth it_requirement and it stays. What is FORBIDDEN: (a)
  generating B from A, which silently deploys whatever a typo''d import names and
  leaves BP-900g-9 with no declaration to check; (b) deriving the checker''s view
  from B, which makes the guard and the thing it polices agree by construction and
  detect nothing — this is the failure the AC''s own criteria name; (c) deriving C
  from A, which restores the divergence BP-900g-5 was closing. Full rationale in this
  AC''s notes under IT-PO RULING.'
- 'DERIVED MEANS DERIVED FROM THE CODE. The closure must be computed from what the
  deployed script resolves — import statements, paths built relative to __file__,
  and dynamic loader calls — not read from any list, map, allowlist, or annotation.
  The test that proves this is the newly-added-module case in BP-900g-8-i: add a module
  inside the test, have an already-deployed script resolve it, edit NO list, and require
  the build to either deploy it or fail naming it. An implementation that passes every
  other test and fails that one is an enumeration wearing the word ''derived''.'
- TRANSITIVE, AND SAY SO IN THE FAILURE. The closure follows dependencies of dependencies.
  When it fails at the second hop the message must name the module that is actually
  missing, not only the top-level deployed script, or the author fixes the wrong hop.
- 'EVERY DEPLOY PHASE, NOT ONLY build_ac_store. n_location_rule is ''all'': the live
  instance is in build_ac_store, but any phase in scripts/build_phases.py that ships
  intra-package Python modules is subject to the same closure. A fix scoped to the
  one phase where the defect was found reproduces the history the criteria cite —
  three prior instances, each fixed individually, each annotated with a warning comment,
  and a fourth still live.'
- DO NOT SATISFY THIS BY ADDING _component_migration_map.py TO THE DEPLOY MAP. That
  makes the live symptom disappear and leaves the mechanism exactly as it was. Adding
  it is necessary and is not sufficient; the closure check must independently fail
  on a tree where it is withheld.
- OUT-OF-PACKAGE MODULES ARE NOT OURS TO SHIP. The standard library, installed third-party
  distributions, and host-project paths the consumer owns must produce no finding.
  A closure that demands the build ship the standard library gets an allowlist, and
  an allowlist is a hand-maintained list wearing a different name. Respect BP-900g-5's
  narrowed output-root prefix bound and keep BP-900g-6's negative-control tests green
  — that bound exists because BP-900g-4 mis-normalised a host-project path (debugging/scripts/...)
  into a deploy key.
- STATIC ANALYSIS HAS A KNOWN BLIND SPOT AND IT MUST BE DECLARED, NOT PAPERED OVER.
  A dynamic loader that builds a module path from a runtime value cannot always be
  resolved statically. Where the closure cannot decide, it must report the unresolvable
  reference for a human rather than assume it is external — an unknown silently classified
  as not-ours is the same fail-open in a new place. BP-900g-10 is the runtime backstop
  for whatever the closure still misses; it is not a licence for the closure to guess.
- IDEMPOTENCY AND BUDGET. The closure computation must be deterministic and byte-stable
  across runs on an unchanged tree, and must run inside the existing build preflight's
  budget — static analysis of the package's own Python files, no network, no per-module
  subprocess.
