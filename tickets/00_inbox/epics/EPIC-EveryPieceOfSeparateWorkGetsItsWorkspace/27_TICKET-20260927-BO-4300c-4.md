## Acceptance Criteria

```gherkin
Given a ready answer naming location L, relayed by an agent that also states in
  its own words that the workspace is at a different location M,
When the workflow proceeds,
Then every step it dispatches is directed to work in L,
And the contents of M are identical before and after the run,
And given a ready answer that carries no location, the workflow ends with a
  failure instead of using any other location.
```

## Implementation Notes

```yaml
- The only source of a working location is workspace_path of an ok answer; prose from
  the relaying agent is ignored for location purposes (retires fast-lane-ship's claimed-path
  fallback and the verify-reply trust).
- Every later dispatch names that location as its working location; an ok answer without
  workspace_path is treated as a failure.
- 'Every workflow applies ONE acceptance predicate to the maker''s answer: it parses
  as a single JSON object AND status == ''ok'' AND workspace_path is a non-empty string;
  anything else ends the run with status error, quoting (bounded to 2 KB) what was
  received. The predicate is the one in the build-inlined WORKSPACE-ANSWER block delivered
  by BO-4300c-3 (byte-identical in every consuming workflow, parity-tested); no workflow
  hand-copies or re-implements it.'
- Proof runs the workflow under unit_tests/_workflow_engine_harness.py -- the deployed
  copy the build produces, so the build's workflow transform is exercised -- with
  label-scripted agent replies, and asserts on the RECORDED dispatch list, never on
  workflow source text. The harness must be able to model a workspace step that declines
  its task, answers in prose, answers exit 0 with a non-JSON path, or answers JSON
  without status (F13); extending the harness for this is in scope of the first AC
  that needs it.
- Workflow edits are made in templates/workflows-js/*.js and reach .claude/workflows/
  only through the build; the deployed copy is what the tests run.
```
