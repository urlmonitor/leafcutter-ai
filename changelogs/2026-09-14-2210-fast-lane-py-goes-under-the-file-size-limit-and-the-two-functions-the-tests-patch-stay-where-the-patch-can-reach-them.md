description: "scripts/build_orchestration/fast_lane.py was 3.5x over the 400-line limit for .py files. It is now 343 content lines, measured with the gate's own count_content_lines rather than wc -l, which counts the docstrings the gate strips and would have misreported the file in both directions. The extracted code went into eight siblings -- _fl_lifecycle (369), _fl_cli (231), _fl_red_baseline_support (185), _fl_changelog (126), _fl_producibility (122), _fl_selection (97), _fl_common (69), _fl_coverage (61) -- so the overflow is genuinely distributed rather than relocated into one new oversized file. Siblings in scripts/build_orchestration/ rather than a package directory was deliberate: build_build_orchestration_scripts() copies every .py from that directory, so the new modules deploy with no entry added to build_phases.py, which is itself 6.7x over its own limit and effectively frozen by the ratchet -- the trap that made the previous file-size split require a justified hook skip. The deploy was verified by simulating it into a fresh temp target and running the deployed fast_lane.py --help there as a real subprocess. One decision was not mechanical. resolve_connected_build_set and verify_red_baseline stay physically defined in fast_lane.py instead of moving out and being re-exported, because the suite patches module attributes -- mock.patch('fast_lane._load_ac'), mock.patch.object(fast_lane, 'traverse_ac_tree'), patch('fast_lane._run_pytest_and_parse') -- and a patch on a module attribute only reaches code whose __globals__ is that module's dict. Re-exporting those two would have left their __globals__ pointing at the sibling module, so every such patch would silently miss and the tests would have kept passing while exercising the real implementation instead of the double: green tests that had quietly stopped testing anything, which is the exact failure mode this component's ACs exist to prevent. Their bare-global callees are patched nowhere, so those moved freely; main() stays alongside them to avoid an import cycle, and _build_cli_parser moved out cleanly. No logic, signature, error-handling or public-name changes: every name previously importable from fast_lane, including the private ones tests import and patch, is still importable and patchable from fast_lane. Ruff required two mechanical additions, __all__ on the re-export hub _fl_common.py and one noqa F401 on _update_ac_work_status. Verification: 217 passed and 4 xfailed in unit_tests/build_orchestration/ under AC_ENFORCE_STRICT=1, 22 passed in test_fast_lane_ship_structure.py, and 46 passed across the seven build-guard tests that touch fast_lane -- those seven failed while the new modules were untracked, because build.py's TRACKED-SOURCE GUARD refuses to run against an untracked source tree, and were re-run after committing to confirm the cause rather than assume it. The CLI was exercised in fresh processes against the real on-disk AC store. templates/workflows-js/fast-lane-ship.js remains over its own limit at 1573 lines against 1000 and is deliberately untouched: workflow .js files deploy flat, and sharing a helper across them has previously broken the isolation harness in a way whose recorded fix was to bundle rather than split, so it needs a different technique and its own change."
