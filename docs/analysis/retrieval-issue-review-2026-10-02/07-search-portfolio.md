## Truthful method offering and execution

The offer should distinguish **implemented mechanism**, **eligible now**, and **why unavailable**, against one pinned source. It must not derive eligibility from a string in the user's question or from `capabilities.semantic=true` alone (`knowledge/adapters/neo4j_backend.py:151`). A read-only availability description may list unavailable methods for diagnosis, but Jev's executable option set must contain only eligible methods. Missing user input can be marked preparable; missing mapping/index/provider cannot be relabeled as missing keywords.

For native keyword search, eligibility needs authorized configured roots/categories, supported file reads and available result/budget capacity. A source restriction to graph alone does not authorize adding repo-text roots. Keep skipped/denied roots, oversized files, binary content and unjudged/cut candidates visible. Native reads use current filesystem bytes while `resolve_source_version` can accept a caller revision label (`kernel/capabilities/retrieval/versioning.py:44`); a pinned SHA alone does not freeze those bytes. Comparisons requiring the same revision need immutable materialization or verified byte identities. The default-source route needs its own test; the graph-only canary cannot prove it.

For semantic and existing hybrid search, check all of these before offering and recheck at execution:

1. Authorized repository/revision resolves to a retained ready generation; requested kind and source fields have an approved mapping. Active Decision support and absent Lesson support stay distinct from zero matching records.
2. Embeddings are enabled with an authorized provider; generation semantic readiness is true; the generation/kind index is ONLINE; the provider model and dimensions match the generation. The service should expose a checked availability description rather than force the planner to use writer credentials or arbitrary Cypher.
3. Entity content hashes, generation, embedding text/normalization versions and index identity are compatible. Query/provider identity must be recorded precisely enough to detect model-alias drift; the current checks compare declared model strings and dimensions, not an independently resolved immutable model build.
4. The method's real input/filter schema fits the request, and the shared budget can fund query embedding, retrieval, bounded expansion/disclosure and any agreed Jev judgment. Ingestion costs are not hidden inside query startup.

`knowledge/semantic.py:54` rejects missing readiness/provider and model/dimension mismatch before embedding. `neo4j_vectors.py:103` checks ONLINE and generation/model scope at query time. A later readiness loss must produce its own unsuccessful attempt and preserve siblings. The existing `NotReady` maps to `unsupported` (`knowledge/errors.py:42`); retain a reason such as missing mapping, absent index, or incompatible provider rather than calling all of them no-match. `KnowledgeService.retrieve` initializes requested/executed mode to the requested value (`knowledge/service.py:93`); that field alone is not evidence the vector query actually ran. An attempt receipt needs a separate stage/execution outcome.

Retain existing hard bounds: neutral results 1..100, candidates 1..200, neighbors 1..50, hops 0..2, rounds 1..10, bytes 1..128 KiB, estimated tokens 256..16000 and deadline at most 30 seconds (`knowledge/contracts.py:83`). Query text is nonblank and at most 4000 characters. The embedding gateway allows dimensions 1..4096, batches at most 32 and each text at most 32 KiB, with bounded response/deadline (`knowledge/adapters/http_embeddings.py:29`). These are per-request ceilings, not additional allowances for every new sibling. All calls, retries, variants, candidates and rerank work must spend the original kernel budget, preserving the caller's Jev reserve. ANN postfilters may reduce recall; bounded semantic results cannot prove an exact population count or absence.

## Caller terms, generated five suggestions, and attempt identity

RS-07 must work with useful caller terms and **zero term-generation calls**. It may still use Jev for selection, sufficiency or relevance. Preserve the original terms and origin, plus the normalized execution terms, selected contract/version, source and any accepted filters. Existing `ResearchRequestPayload` has no dedicated caller-keyword field; `RetrievalRequestPayload.query_hints` only carries goal/criteria/option text (`kernel/contracts/payloads.py:102`, `:134`). Public input plumbing and its producer-to-consumer behavior need an explicit compatible contract owned with S1/S2.

For RS-08, generation is optional. The generation owner supplies exactly five distinct nonempty suggestions, bound to question/context and selected method/query/version/source; System validates the matching response and Jev judges usefulness before search. Do not require generation for a semantic contract that can accept the original question directly. Terms are proposed search inputs, never answer evidence or authority to widen source scope.

**Five suggestions do not imply five mandatory network calls.** Two defensible execution shapes need an explicit choice:

- One validated term set per selected method: cheaper and closest to current native extraction/scoring. Record all five suggestions and their normalization. The comparison can say which method/set worked, but cannot identify which suggestion caused a unique result.
- Bounded separately attributed query variants: Jev chooses useful variants from the accepted suggestions; each executed variant has its own attempt identity, normalized query, cost and evidence. This can compare which query worked, but multiplies search/rerank/embedding work. Budget or sufficiency may stop before all five; record non-execution reasons without manufacturing empty attempts.

Recommend the first as the minimum default and the second as an explicit offered capability when query-level comparison is useful. Preserve per-selected-method/query attempts, as the target flow requires. Do not concatenate variants and later invent per-term credit. Normalize before claiming distinct executable variants: case/whitespace, stopwords and token truncation can collapse apparently different suggestions. The S2 owner defines validation/correction; S3 consumes only accepted inputs and reports the actual execution shape.

RS-09's current fixture promises keyword ADR evidence plus a vector schema locator (`docs/analysis/2026-10-02-retrieval-scenarios.md:91`). A schema is not currently a semantic seed kind. A real supporting declared path from an approved Decision may supply context if it actually exists; otherwise this fixture needs a new approved mapping/contract before it can run as written. It must not be made green with an arbitrary schema vector or by silently replacing its required evidence. A narrower Decision/keyword example can prove a useful portfolio slice while RS-09 remains pending.
