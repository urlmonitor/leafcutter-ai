# A check that works out its own change set works out the author's change, not everything the staged tree happens to hold

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-120e-1` — A check that works out its own change set works out the author's change, not everything the staged tree happens to hold — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-120e-1`. Component: `guardrail-engine`. Assigned agent: `python-coder`. Estimated complexity: `L`. Complexity: `high`.

## Acceptance Criteria

```gherkin
Given a commit whose staged content includes work the author did not write — carried in
  from another line of development where it is already recorded,
And a check that works out for itself which changes to inspect, because the commit path
  hands it no list of files,
When that check runs on the commit,
Then the change set it inspects holds only content that differs from every state this
  commit is built on, so the carried-in work is absent from it,
And the check reaches its verdict from that change set alone,
And a check whose verdict was previously driven by the carried-in work now raises no
  objection to it, while its verdict on the same commit's own content is unchanged,
And every check that works out its own change set takes it from one shared source rather
  than computing a private one, so the answer to "what did the author change" is the same
  for all of them.

Coverage note: cover this by executing the check as a process against a real repository
standing in that state and asserting the result status and the text it wrote for the
reader; reading the check's source does not cover this criterion (CLAUDE.md, "Gate /
Workflow ACs — Verify Behaviorally, Not by Grep"). The observed case to reproduce is a
large mainline merge into a working branch whose own change set touched none of the files
the check objected to.
```

## Implementation Notes

```yaml
- 'TEMPLATE/DEPLOYED PARITY (ADR-001). The change lands in templates/scripts/commit_guardian/
  and must be deployed by build.py. build_commit_guardian() in scripts/build_phases.py
  rglob-copies the WHOLE templates/scripts/commit_guardian/ directory, so a new shared
  module placed there is deployed with no deploy_map edit. A module placed anywhere
  else (e.g. scripts/ac_store/) needs an explicit deploy_map entry in scripts/build_phases.py
  or the deployed hook dies with ModuleNotFoundError at commit time — the failure
  mode CLAUDE.md records for done_proof.py. Never edit the deployed copy: the next
  build.py overwrites it and the fix silently disappears.'
- MIGRATE BOTH OBSERVED CONSUMERS IN THE SAME CHANGE. templates/scripts/commit_guardian/check_contract_shrinking.py
  line 180 runs git diff --cached; templates/scripts/commit_guardian/check_doc_frontmatter.py
  line 287 runs git diff --cached --name-status. Migrating one and leaving the other
  produces exactly the split verdict the last criterion forbids — one check blocking
  a commit the other passed.
- THE SHARED SOURCE MUST SERVE BOTH DIFF SHAPES. git diff --cached is HEAD-to-index,
  i.e. it compares against ONE state. The two known consumers need different shapes
  (full text diff, and name-status). If the shared source offers only one shape, the
  other consumer is driven straight back to a private git call and the single-source
  clause is defeated in the first week. Serve both from the one derivation.
- RETURN THE DERIVATION, NOT JUST THE PATHS. The result must carry the change set
  AND the states it was derived against, so a consumer's objection text can name what
  it inspected. GE-120e-3's last clause compares WHAT each arm objected to, not only
  whether it objected, and it cannot do that if the shared source discards the provenance.
- SHAPE IT LIKE _resolve_root.py. templates/scripts/commit_guardian/_resolve_root.py
  is the family's existing precedent for one shared facility with many importers (27
  today). One module in the same package, imported by the checks. Do not satisfy this
  AC by pointing at _resolve_root.py itself — that facility resolves PREREQUISITES,
  this one derives the CHANGE SET (see the AC notes).
- ERROR-HANDLING POLICY APPLIES TO THE GIT CALLS. Wrap the subprocess calls in specific
  exceptions, log at WARNING or higher, never swallow. A git failure must NOT degrade
  to using the whole staged tree — that silently restores the defect on the exact
  commits where git is under stress. A derivation that cannot be computed is a could-not-check
  outcome in GE-120a-1's vocabulary, not a wider change set.
- NO BEHAVIOUR CHANGE ON THE ORDINARY COMMIT. Where the commit is built on exactly
  one state, the derived change set must equal today's git diff --cached output byte
  for byte. This is the regression budget for the other manifest checks and for every
  ordinary commit in the repository.
- LATENCY BUDGET. This runs inside every pre-commit. Derive once per process and memoise;
  do not issue one git invocation per consuming check. On a staged tree of ~500 changed
  files (the observed merge was 479) the shared source must add under 500 ms to the
  commit.
- WORKTREE-SAFE. Drives in this repository run inside git worktrees, where there is
  no .git DIRECTORY. Resolve the git directory with git rev-parse --git-dir (or equivalent
  plumbing) rather than assuming <root>/.git; a hard-coded path is a silent no-op
  in a worktree, which is where the observed defect was hit.
```
