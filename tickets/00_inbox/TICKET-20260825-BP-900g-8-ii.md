# The deployed-dependency closure covers the data and configuration files a script reads, not only the modules it imports

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `BP-900g-8-ii` — The deployed-dependency closure covers the data and configuration files a script reads, not only the modules it imports — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `BP-900g-8-ii`. Component: `build-pipeline`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given a script the build deploys into a consumer install,
And that script reading a NON-CODE file at runtime to do its job — a schema that
  defines the rule it applies, a vocabulary of permitted values, a registry of
  records it looks up, or a data table it maps through — in addition to any modules
  it imports,
When the build derives the set of files that must ship alongside that script,
Then the derived set contains those non-code files as well as the imported modules,
And any file in that set that is absent from the deploy manifest fails the build,
  naming the file, the script that reads it, and the deploy phase that would have
  to carry it,
And a missing non-code file fails the build with the same force as a missing
  module, so a guard that only detects an unimportable module leaves the data case
  live,
And the non-code half of the set is DERIVED from what the deployed script actually
  reads, on the same terms as the module half — a hand-maintained list of data
  files does not satisfy this criterion even when it is complete on the day it is
  written,
And the guard is demonstrated against a dependency introduced AFTER the guard
  exists: adding a new non-code read to a deployed script, without adding that file
  to the deploy manifest, fails the build,
And a file the script reads from outside the install — an operating-system path, or
  data owned by an external tool the package does not ship — is not added to the
  set, so the guard does not demand the build deploy things it does not own.

Because the closure as it stands, and the written rule and guard test behind it,
are all expressed in terms of Python module imports and the import error a missing
module raises. A configuration JSON is therefore not a dependency as far as any of
them can tell. On 2026-08-18 four configuration files and one helper module were
confirmed absent from a deployed output root with the build green throughout: two
type vocabularies, the AC-store schema, and the agent registry — none of which is
a module, and none of which any existing guard was capable of noticing.
```

## Implementation Notes

```yaml
config_schema_fragment:
  description: The dependency record the closure emits, widened so that a non-code
    read is the SAME kind of thing as an import rather than a second notion bolted
    alongside it. The defect is that a JSON file is not a dependency as far as any
    existing guard can tell; if the widening produces two record shapes, two code
    paths follow, and the data path is the one that ends up logging a warning while
    the module path raises. One record, one discriminator, one verdict path.
  properties:
    dependency:
      description: The intra-package file the deployed script needs - a module it
        imports or a non-code file it reads. Recorded as the path the build would
        have to ship, so a red build hands the author a remediation list rather than
        a diagnosis.
      type: string
    deploy_phase:
      description: The phase in scripts/build_phases.py that would have to carry it.
        Without this the failure names a gap and no owner.
      type: string
    enforcement_point:
      description: Which gate consumes this verdict and fails the build on it. Present
        so a sign-off cannot claim enforcement while the verdict is routed only through
        the branch that logs and continues.
      type: string
    kind:
      description: 'One of: module, data, unresolvable. Three values, not two. ''unresolvable''
        is required because a data read is an ordinary call against a path that may
        be constructed, so the static half will not always decide - and an unknown
        silently classified as not-ours is the same fail-open in a new place.'
      type: string
    read_by:
      description: The deployed script that imports or reads it. Demanded by the criterion's
        naming clause, and necessary because the second hop of a transitive chain
        is the hop the author actually has to fix.
      type: string
    resolution:
      description: derived or underivable. The field that keeps the underivable set
        visible; a closure that drops what it could not resolve looks exactly like
        a closure that found nothing to complain about.
      type: string
  required:
  - dependency
  - kind
  - read_by
  - deploy_phase
  - resolution
  - enforcement_point
  type: object
constraints:
- 'VERIFY FROM THE DEPLOYED LAYOUT, IN A COLD PROCESS, WITH THE PACKAGE SOURCE TREE
  OFF sys.path. Every existing unit test in this family imports from scripts/, which
  is exactly why all five prior instances of this defect stayed green: the source
  tree contains every sibling and every config by construction, so the assertion is
  structurally incapable of failing there. A test that imports from the source tree

  <ac>.yaml` raised ModuleNotFoundError for _ac_components, and `python .leafcutter/scripts/commit_guardian/check_doc_frontmatter.py
  <doc>.md` raised FileNotFoundError for the doc_types declaring file. Both must be
  red before the change and green after, observed from that layout and never from
  the package repo.'
- 'ADDING THE NAMED MODULE OR FILE IS NECESSARY AND NOT SUFFICIENT. Stated as the
  register states it: treat ''add the module to deploy_map'' as a fix for the instance,
  never for the defect. That map has been patched four times for this same class (done_proof.py,
  test_enforcement.py, ac_parent_id.py, ac_coverage_resolver.py), five of its eleven
  entries now carry a comment explaining why that particular module must not be forgotten,
  and a sixth instance was found on 2026-08-25 - check_ac_parent_covered_by.py cannot
  import derive_parent_id in a deployed layout and exits 0 silently. A list that needs
  a warning per entry is a record of the mechanism''s absence. Reachability must hold
  by construction or by a gate that fails the build, never by someone remembering.'
- 'STAY LOUD; A SILENT FALLBACK IS A REGRESSION EVEN WHEN IT MAKES THE ERROR DISAPPEAR.
  The fail-closed posture on the document type vocabulary was established deliberately
  by GE-118c, which removed precisely such a narrowing. The sibling _find_diagram_types_json
  in templates/scripts/commit_guardian/diagram_type_validators.py is the identical
  walk and still returns None, degrading silently to a built-in constant - the next
  instance, already waiting, and the shape a lazy fix here will reach for. No change
  may reinstate a silent fallback to a narrower built-in list on either side. Note
  the second-order consequence: a silently-degrading reader is invisible to any startup
  or verdict sweep because it produces an answer, so if this change leaves one in
  place, name it in the sign-off as a blind spot rather than counting it as covered.'
- DEPLOY WHERE THE EXISTING WALK ALREADY REACHES, AND WHERE A WORKTREE STILL SEES
  IT. `.leafcutter/config/` already exists and is git-tracked in a consumer install
  (it carries commit_guardian/ and feedback_categories.yaml), so a declaring file
  placed there is reachable by the ancestor walk as written and survives into a git
  worktree. A destination that requires the walk to grow another hardcoded candidate
  trades this defect for the next one. Neither `<consumer>/config/` nor `<consumer>/leafcutter/`
  exists in a genuine adopter install - confirmed by direct inspection on 2026-08-25
  - which is why the two existing candidates in _find_doc_types_json both miss.
- 'PACKAGE-DIRECTORY NAME INDEPENDENCE IS OWNED BY BP-900h-4-i AND IS NOT RE-SPECIFIED
  HERE. That AC owns the layout matrix and the prohibition on spelling a package-directory
  name in any candidate path. This AC must not contradict it: any path this change
  constructs must derive the location rather than name the directory, because the
  same lookup fails differently under the two adopter directory names - with the package
  at `leafcutter/` the second hardcoded candidate resolves in a main checkout and
  fails inside a git worktree, and with it at `leafcutter-ai/` it fails everywhere,
  main checkout included. Both adopter reports were correct. Reference h-4-i for the
  proof; do not build a second layout matrix here.'
- WHATEVER THE GATE SURFACES ON FIRST RUN MUST BE ENUMERATED, NOT SKIPPED. Turning
  a derived closure on will reveal a pre-existing set of undeclared dependencies well
  beyond the files named in this AC's doc_links. That is the intended effect. The
  full set must be listed in the sign-off and each entry either resolved or explicitly
  deferred with a date. Parking the remainder behind a skip list reintroduces, inside
  the mechanism built to remove it, the hand-maintained list that is the defect.
- IDEMPOTENT AND WITHIN THE PREFLIGHT BUDGET. The derivation must be deterministic
  and byte-stable across runs on an unchanged tree, use static analysis of the package's
  own files only, and add no network call and no per-file subprocess to the build
  preflight.
n_location_rule: 'all — every deploy phase that ships a file a deployed script reads,
```
