# An answer that did not come from the person is refused even when it is well formed

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `ACD-2100c-4` — An answer that did not come from the person is refused even when it is well formed — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `ACD-2100c-4`. Component: `ac-driven-dev`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given a run waiting at a decision point with drafted work on disk,
And an answer that is well formed and names one of the choices the decision
  offers but that did not originate from the person running the route,
When the run evaluates that answer,
Then it is not treated as the person's decision and the choice it names is not
  carried out,
And the run stays at the decision point and stays waiting with its record on
  disk,
And the reason it records is that the answer did not come from the person -- not
  that the answer could not be understood,
And an answer identical in every respect except that it did come from the person
  is accepted and carried out.
```

- [ ] AC-1: an answer that is well formed and names one of the choices the decision
- [ ] AC-2: it is not treated as the person's decision and the choice it names is not
- [ ] AC-3: the run stays at the decision point and stays waiting with its record on
- [ ] AC-4: the reason it records is that the answer did not come from the person -- not
- [ ] AC-5: an answer identical in every respect except that it did come from the person

## Implementation Notes

```yaml
- The change must land under templates/. The deployed workflow is build output.
- 'Provenance -- where the answer came from -- must be the discriminator. The answer''s
  content must not be inspected to decide whether to accept it. Any content-based
  test is re-implementing the defect with a longer regex: the agent gets better at
  sounding like a user and the bug returns.'
- Hardening the answer parser does not satisfy this record and must not be offered
  as satisfying it. resolveGate already pauses on a null or unparseable answer; the
  observed loss came from a well-formed answer that passed every shape check.
- A refused answer must leave the run waiting, not failed, and must leave the record
  on disk. The person is still owed the question.
- The recorded reason must name provenance. Recording 'could not understand the answer'
  for an answer that was perfectly well formed is how this defect stayed invisible
  for a whole run -- the journal showed a clean decision.
- The accept-and-refuse pair must differ only in origin. If accepting an answer requires
  it to carry anything the refused answer could not also carry, the pair is not a
  controlled comparison and the record is not proved.
- Must satisfy the repository error-handling policy on the channel interaction.
```
