## Acceptance Criteria

```gherkin
Given the command that prepares a fresh working copy for a drive,
When it finishes,
Then it presents exactly one recorded outcome for each protection step it attempted —
  established, or not established with the reason,
And a step recorded as not established names the specific artifact it could not find or
  create, not the general activity that failed,
And the closing summary states how many protection steps were not established,
And a run in which any protection step was not established is not presented as a completed
  set-up,
And each attempted step appears exactly once in the report, on every path through the
  command, including paths where a step was skipped.

Coverage note: cover this by running the real set-up command and asserting on the report it
produced, including at least one run in which a step genuinely cannot be established. The
final clause needs a run per path, not a source inspection — a per-step record added inside
a skip branch while an unconditional record remains after the branch produces a duplicate
entry that no static check sees (CLAUDE.md, "Skip-Branch Side-Effects").
```

```yaml
  running verify_precommit_active.py and install_pre_commit_shims.py (both present
  under templates/scripts/commit_guardian/), and establishing .pre-commit-config.yaml
  / the .leafcutter layout in the new copy.'
- ENUMERATE THE STEPS FROM A DECLARED LIST that the reporter iterates — not from scattered
  print statements. Both the exactly-once clause and the not-established count are
  unenforceable over ad-hoc prints, and a report that miscounts is a report the reader
  stops trusting, at which point it protects nothing.
- 'EXACTLY ONCE ON EVERY PATH, INCLUDING SKIP PATHS. This project has already shipped
  the inverse defect: per-step records were added inside skip branches while the pre-existing
  UNCONDITIONAL record after the if/else was left in place, so every skipped step
  double-recorded, and the structural test''s regex was blind to the template-literal
  call. CONDITIONALIZE the pre-existing unconditional call — move it into the execute
  branch or guard it — do not merely add a second one (CLAUDE.md, ''Skip-Branch Side-Effects
  — Conditionalize, Don''t Add'').'
- A not-established step names the SPECIFIC ARTIFACT by path that it could not find
  or create, never the general activity ('could not set up hooks').
- The closing summary states the NOT-ESTABLISHED COUNT, and a run with a non-zero
  count is not presented as a completed set-up. The refusal itself is GE-120d-2; this
  AC is the visibility half, and reporting comes first because a set-up that refuses
  without saying which step failed just moves the opacity.
- 'Error-handling policy: each step''s failure is a caught SPECIFIC exception, logged
  at WARNING, and recorded as a not-established outcome. No bare except, and no swallowed
  failure that leaves the step unrecorded — an unrecorded step breaks the exactly-once
  invariant in the quiet direction.'
```
