# The harness is shown to fail against the behaviour that was actually observed

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-120c-2` — The harness is shown to fail against the behaviour that was actually observed — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-120c-2`. Component: `guardrail-engine`. Assigned agent: `test-writer`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given the harness case for the AC-parent-covered-by check,
When it is run against the behaviour observed before this feature — the check exiting
  successfully after printing "cannot import derive_parent_id: ac_parent_id.py not found via
  package import, script-relative, or project-root walk.; skipping check (fail-open)" from a
  working copy without the deployed layout,
Then the harness case fails,
And when it is run against the corrected behaviour, it passes,
And the failing result is captured and recorded before the corrected behaviour is
  implemented, so the harness is demonstrated capable of catching the defect rather than
  assumed to be,
And the same red-then-green evidence exists for the AC-schema degradation case of GE-120b-3,
And a harness case for which no failing result was ever observed is reported as unproven
  rather than counted as coverage.

Coverage note: the recorded red result is the deliverable here, not a passing test. A green
harness proves the harness runs; only the red result proves it constrains anything.
```

- [ ] AC-3: the failing result is captured and recorded before the corrected behaviour is
- [ ] AC-4: the same red-then-green evidence exists for the AC-schema degradation case of GE-120b-3

## Implementation Notes

```yaml
- THE DELIVERABLE IS THE RECORDED RED RESULT, not a passing test. Capture it as a
  durable artifact — the harness's own output, together with the commit SHA of the
  pre-fix tree — BEFORE any GE-120b implementation begins, and reference it from this
  AC's sign-off. A green harness proves the harness runs; only the red result proves
  it constrains anything.
- 'TWO RED BASELINES ARE REQUIRED, not one: (a) check_ac_parent_covered_by exiting
  0 after printing the cannot-import-derive_parent_id fail-open line from a copy without
  the deployed layout; (b) the check_ac_schema degradation to manual field validation,
  which is GE-120b-3''s case. One red result does not license the other case.'
- 'SEQUENCING IS THE SUBSTANCE OF THIS AC: GE-120c-1 and this AC land FIRST, red is
  recorded, THEN GE-120b is implemented. If the harness is written after the fix,
  or by the same agent in the same pass, the evidence is worth much less. Per CLAUDE.md
  ''TDD Order — test-writer Must Precede python-coder'', a harness found already green
  before the coder phase is an ORDERING VIOLATION to be documented, not a pass.'
- A harness case with no observed red result must be REPORTED AS UNPROVEN — a distinct,
  machine-readable state, not an ordinary green. Reuse the shared outcome vocabulary
  from GE-120a-1 rather than inventing a second three-state model for the test layer;
  this is the same distinction GE-120a draws for the checks themselves.
- The pre-fix behaviour must be reproduced from the REAL pre-fix code at a real commit,
  never from a hand-written stub that imitates it. A stub reproduces the author's
  belief about the defect, which is how this defect class survived a full suite of
  passing tests for its entire life.
- This AC's own value is destroyed if it is scheduled after GE-120b. Record the ordering
  constraint wherever the build sequencer reads it, not only here.
```
