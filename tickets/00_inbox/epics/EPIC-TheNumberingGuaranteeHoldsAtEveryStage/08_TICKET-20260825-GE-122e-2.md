## Acceptance Criteria

```gherkin
Given the work-item collection holds five identifiers that each exist as a file in two
  lifecycle folders — four of them as a copy in the intake folder alongside a copy in the
  completed folder, and one as a copy in the intake folder alongside a copy in the active
  folder,
When the repair is complete,
Then each of those five identifiers exists as exactly one file,
And the surviving file sits in the lifecycle folder that matches the lifecycle state declared
  in that work item's own content, so folder position and declared state agree,
And where the two copies declared different states, the resolution taken and the reason are
  recorded on the surviving file, rather than one copy being deleted silently,
And where the two copies differ in content beyond their declared state, the surviving file
  retains the content of whichever copy records the later work, so no completed work is
  discarded by the repair,
And no work-item identifier anywhere in the collection is held by more than one lifecycle
  folder,
And the five are exactly the five this record already enumerates, not a set re-derived at
  implementation time: an identifier the repair believes is twice-held but which is not among
  them is reported and left alone, and an enumerated identifier the repair cannot confirm is
  twice-held is reported and left alone,
And every reference to any of the five identifiers resolves to the surviving file.

Coverage note: covered by executing the work-item uniqueness pass over the repaired collection
and asserting zero findings, plus asserting for each of the five that exactly one file exists
and that its folder agrees with its declared state. Counting files alone does not cover it —
deleting the correct copy also yields one file.
```

## Implementation Notes

```yaml
- The survivor is chosen by computing declared-state-versus-folder agreement from
  `tickets/ticket_lifecycle.json`, the same data `_check_status_folder` reads — not
  by a rule of thumb that the completed folder wins. Four of the five will very likely
  resolve to the completed copy, but that is an outcome to be arrived at per pair,
  not an assumption to implement; assuming it is precisely how the wrong copy gets
  deleted.
- THIS IS A DELETION AND IT IS NOT REVERSIBLE FROM THE STORE. Before deleting either
  copy, diff the two and record the diff on the surviving file. Two copies that have
  drifted may each hold something the other lacks — sign-off comments, a status history,
  a comment stream — and the point of the repair is that one identifier means one
  thing, not that half the record disappears.
- 'SCOPE IS THESE FIVE IDENTIFIERS AND NO OTHERS — measured 2026-08-17, listed here
  because an irreversible deletion must not act on a set re-derived at implementation
  time. Intake + completed: TICKET-20260603-ConfigDrivenBuildPaths, TICKET-20260603-FeedbackAnalysisPipeline,
  TICKET-20260604-PullRequestAgentProjectContext, TICKET-20260605-ContractShrinkingSelfExclusion.
  Intake + active: TICKET-20260629-BP-1200a-1-ii. If a fresh scan of the collection
  disagrees with this list in either direction, STOP and report the difference — do
  not repair the difference. The list, not the scan, is the scope.'
- GE-122a-2's whole-collection pass will also surface `EPIC-MoveOnMainOnly`, which
  is held by BOTH `tickets/99_done/` and `tickets/99_rejected/` — one identifier in
  two TERMINAL folders that flatly disagree, with Master_Plan.md and four sub-items
  duplicated inside. It is not in the five and it is NOT repaired under this AC. Report
  it and stop; expanding scope silently is the mirror image of the re-expansion GE-122e-3
  fails an implementer for.
- Sixteen loose `TICKET-*.md` files sit at `tickets/` root outside any lifecycle folder.
  They are not twice-held and are out of scope here; do not tidy them while in the
  area.
- 'ORDERING: this repair must land before the work-item stage of the uniqueness guard
  becomes blocking, or every commit is stopped by five pre-existing conditions the
  author did not create. GE-122e-3 is the check that the ordering worked.'
- Use `git mv` / `git rm` so the deletions and moves are tracked; a ticket file removed
  with a plain filesystem delete loses the history that would let the decision be
  reviewed. Note that `templates/hooks/check_ticket_no_branch_move.py` blocks `git
  mv` of ticket files on non-main branches — it is currently registered nowhere, so
  it will not fire today, but if it is wired during this tree's work this repair collides
  with it. Perform the repair on a branch with that interaction understood, not discovered.
- 'Idempotency: re-running the repair over the repaired collection makes no further
  change.'
```
