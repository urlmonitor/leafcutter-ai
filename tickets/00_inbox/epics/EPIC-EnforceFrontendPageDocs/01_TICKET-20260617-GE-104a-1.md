# Commit-time guardrail blocks a new frontend page that ships without its reference doc

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-104a-1` — Commit-time guardrail blocks a new frontend page that ships without its reference doc — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-104a-1`. Component: `guardrail-engine`. Assigned agent: `python-coder`. Estimated complexity: `M`.

## Acceptance Criteria

```gherkin
Given a commit stages a frontend page file at site/app/<route>/page.tsx that
  did NOT exist in the previous commit (a newly added page)
And a reference doc at the deterministic path docs/reference/frontend/<name>.md
  that corresponds to that page is also staged in the same commit
When the page-documentation guardrail runs at pre-commit time
Then the guardrail treats the page as documented and allows the commit to proceed

---

Given a commit stages a frontend page file at site/app/<route>/page.tsx that
  did NOT exist in the previous commit (a newly added page)
And the matching reference doc already exists on disk at the deterministic
  path docs/reference/frontend/<name>.md (added in an earlier commit)
When the page-documentation guardrail runs at pre-commit time
Then the guardrail treats the page as documented and allows the commit to proceed

---

Given a commit stages a frontend page file at site/app/<route>/page.tsx that
  did NOT exist in the previous commit (a newly added page)
And no reference doc exists at the deterministic path
  docs/reference/frontend/<name>.md — neither staged in this commit nor present on disk
When the page-documentation guardrail runs at pre-commit time
Then the guardrail blocks the commit
And it emits a FIX message that names the exact expected reference doc path
  docs/reference/frontend/<name>.md the author must create

---

Given a commit stages changes to a frontend page file at
  site/app/<route>/page.tsx that already existed in the previous commit
  (a pre-existing / legacy page being edited)
When the page-documentation guardrail runs at pre-commit time
Then the guardrail does NOT require a reference doc for that page
And it allows the commit to proceed regardless of whether a matching doc exists

---

Given two consumer projects, one with the page-documentation guardrail
  configured in "block" mode and one configured in "warn-only" mode
And both stage a newly added frontend page with no matching reference doc
When the guardrail runs at pre-commit time in each project
Then in "block" mode the commit is blocked with a non-zero result and the FIX message
And in "warn-only" mode the commit is allowed to proceed while the same
  FIX message is surfaced as a warning
```
