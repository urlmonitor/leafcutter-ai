# KI-BO-20260908-1151 — An agent hand-authoring the Agent Contracts block bypasses the generator that knows the required format, and nothing validates the result until documentation-verifier refuses it

> Observed 2026-09-07 on `GE-122d-1`, with a second instance cross-referenced in
> another epic. Filed 2026-09-28. **Scope corrected before filing** — see
> "What this is NOT" below; the first draft of this entry blamed a
> producer/consumer contract split that does not exist.

- **Severity:** low — narrow trigger, fails closed, and the repair is mechanical
- **Status:** open — no AC
- **Occurrences:** 2 confirmed, in different epics
- **First seen:** 2026-09-07 · **Last seen:** 2026-09-07
- **Where:** `templates/agents/documentation-expert.md` §v2 behaviour ·
  `templates/agents/documentation-verifier.md` Step 2 (~lines 147-169) ·
  `scripts/ac_store/_gtfa_contracts.py:181` (the correct producer)

**Symptom.** `documentation-verifier` halts with a Step 2 parse failure and the ticket cannot
reach `commit`. Its contract requires the target path to be the second pipe-delimited field
(`genre | target_path | content_constraint`). `GE-122d-1` carried instead:

```text
- [x] AC-1: [component-diagram] docs/architecture/components/commit-guardian.md — all three stages ...
```

Bracketed genre, em-dash constraint, zero pipes. Fail-closed parse failure, ticket blocked.

**WHAT THIS IS NOT, because the obvious diagnosis is wrong.** This is not a producer/consumer
format split. The generator emits the required form correctly:

```python
# scripts/ac_store/_gtfa_contracts.py:181
lines.append(f"- [ ] AC-{i}: {genre} | {doc_path} | {constraint}")
```

Any ticket produced by `generate_ticket_from_ac.py` is conformant. Checking
`templates/agents/documentation-expert.md` for the pipe convention and finding it absent —
which it is — proves nothing, because that template *reads* the Agent Contracts block (its
documented v2 behaviour is "read the AC block and use it as the doc spec"); it does not
normally author one.

**The actual trigger is narrow.** `documentation-expert`'s own sign-off on `GE-122d-1` records
that the `Agent` tool was unavailable in that session, so it authored the Agent Contracts block
**directly** instead of dispatching its specialist. That hand-authored fallback path does not
know the format the generator would have applied, and nothing between authoring and
verification checks it. So the defect is: *a degraded-session fallback writes a structured
block by hand, and the structure is only validated at the far end by an agent that can only
refuse.*

**Why it is worth recording despite being narrow.** A Step 2 parse failure is not a small
delay. It halts before Steps 3-7, so the required-docs-present and placeholder checks — the
substance of the phase — never run at all. On `GE-122d-1` those steps executed for the FIRST
time only after the lines were reformatted and the verifier re-run, three weeks later. A
blocked run and a run that checked nothing look identical from outside.

**Countermeasure, smallest first:**

1. State the required line form in `documentation-expert.md` beside the v2 behaviour block, as
   a constraint on the fallback authoring path — cheap, and it closes the observed trigger.
2. Better: have Step 2 emit a malformed line as a REPAIRABLE finding routed back to
   `documentation-expert`, rather than a terminal halt. It already prints an exact remediation
   string; nothing consumes it.
3. Do NOT add a lenient parse. The fail-closed posture is what surfaced this at all, and a
   parser accepting both conventions would let the two forms drift apart across epics
   indefinitely.

**The general shape, which is the transferable part.** Whenever an agent has a degraded-mode
fallback that writes a STRUCTURED artifact normally produced by a generator, the fallback
inherits none of the generator's format knowledge and the structure goes unvalidated until
something downstream refuses it. Worth checking which other agents have such fallbacks before
treating this as one ticket's bad luck.

**Related.** `KI-BO-20260901-1052` (`handoff_target` — a genuine producer/consumer contract
split, which is what this entry was first mistaken for; the distinction is that there the
producing template really was silent about a field the driver required).
