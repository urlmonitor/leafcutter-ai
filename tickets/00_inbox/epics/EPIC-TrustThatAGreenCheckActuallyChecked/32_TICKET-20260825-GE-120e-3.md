# The same authored content reaches the same verdict whether it is committed ordinarily or brought in alongside a mainline merge

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-120e-3` — The same authored content reaches the same verdict whether it is committed ordinarily or brought in alongside a mainline merge — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-120e-3`. Component: `guardrail-engine`. Assigned agent: `test-writer`. Estimated complexity: `L`. Complexity: `high`.

## Acceptance Criteria

```gherkin
Given a body of authored content and a check that works out its own change set,
When the verification runs that check twice against real repositories — once on an
  ordinary commit that introduces the authored content on its own, and once on a merge
  commit that introduces the identical authored content alongside a large incoming
  changeset the author did not write —
Then it executes the check as the commit path executes it in both arms and records the
  result status and the reader-facing text from each,
And it reports a failure when the two arms disagree on the result status,
And it prints both arms' output side by side, so a disagreement is read directly rather
  than inferred from an assertion message,
And the pair is run for every check the manifest records as working out its own change
  set,
And an arm that objects names the content it objected to, so a pair that agrees on status
  while objecting to different content is also reported as a disagreement.

Coverage note: the pair is the unit of evidence. A verification that runs only the merge
arm cannot tell a check that now ignores carried-in work from a check that objects to
nothing at all, which is why the ordinary arm is in the criterion rather than in a
separate test. Both arms execute the check as a process against a real repository standing
in the corresponding state; source inspection covers neither arm (CLAUDE.md, "Gate /
Workflow ACs — Verify Behaviorally, Not by Grep").
```

## Implementation Notes

```yaml
- EXTEND GE-120c-1'S HARNESS WITH AN OPERATION-SHAPE DIMENSION; DO NOT FORK IT. Home
  is unit_tests/portability/, where the out-of-process harness already stands up a
  real working copy, builds the deployed layout into it and runs a check as a subprocess.
  GE-120b-4 sweeps the same manifest on the LAYOUT axis; this sweep adds the OPERATION
  axis. Two dimensions of one harness, not two harnesses.
- ONE AUTHORED-CONTENT FIXTURE FEEDS BOTH ARMS. Build the ordinary arm and the merge
  arm from a single authored-content definition so the arms cannot drift. Two hand-written
  fixtures that were meant to be identical is how a differential test quietly stops
  being differential.
- THE MERGE ARM MUST BE A REAL git merge. Perform the merge as a repository operation
  producing a real staged merged tree with a large incoming changeset — the observed
  case was 479 files. A hand-staged approximation of a merge does not reproduce the
  two-parent state that the whole L1 turns on.
- 'ASSERT ONLY ON THE SUBPROCESS''S OBSERVABLE OUTPUT: exit status and the text it
  wrote. Never import a check module, a commit_guardian helper, or _resolve_root.py
  into the verification — importing from the source tree reintroduces the blindness
  the harness exists to remove.'
- PRINT BOTH ARMS SIDE BY SIDE UNCONDITIONALLY, not only on failure. The criterion
  is that a disagreement is READ directly; output produced only inside a failure branch
  is unavailable to the reader diagnosing a pass that looks wrong.
- COMPARE OBJECTED-TO CONTENT, NOT ONLY STATUS. Two arms that both block for different
  reasons is a disagreement. Status-only comparison would have called the observed
  merge 'agreement', because contract-shrinking would also have blocked the ordinary
  arm had the author really deleted a test.
- ITERATE THE MANIFEST-DERIVED SET FROM GE-120e-2 at run time. No hand-written check
  list, no hard-coded entry count. A self-deriving check registered tomorrow must
  join this sweep by being registered.
- RUNTIME. Two arms per self-deriving check, each a subprocess, on top of a real merge
  fixture. Build each repository ONCE per sweep and mark the sweep slow. Narrowing
  the subject list to keep the suite fast turns this AC into the always-green assertion
  it exists to eliminate.
- A SETUP FAILURE IS A REPORTED FAILURE, NEVER A SKIPPED CASE (GE-120c-1-i), and never
  an xfail. This repository has a recorded history of xfail-masked AC enforcement
  where CI under-reported failures; a pair that could not be run must be loud.
- 'Error-handling policy applies to the harness''s own subprocess, git and filesystem
  calls: specific exceptions, logged at WARNING, never swallowed. Clean up any worktree
  or temporary repository even on failure.'
```
