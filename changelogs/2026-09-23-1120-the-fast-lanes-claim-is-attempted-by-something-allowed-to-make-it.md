description: "Observed on a fast-lane run aimed at BO-3500. The run cleared the worktree, verification, resolve and producibility steps -- further than any run that day -- then halted at the claim step reporting the connected set was already claimed and owned by a concurrent run, while the same payload carried an empty claimed list and an empty excluded list. Nothing was held by anyone. Two faults produced that. First, the claim command mutates the AC store but was dispatched to status-checker, whose declared charter is investigating and reporting state, restricts edits to ticket files and forbids code edits; it declined, correctly and in detail. The file's own comment already recorded status-checker as a structural charter mismatch under KI-BO-020, but that reasoning had been applied only to the release path, leaving the claim path -- the inverse operation on the same state -- untouched in the same file. Second, the claim step's instructions treated a non-zero exit OR a refusal flag as meaning the set was held elsewhere, so an agent declining the task was indistinguishable from genuine contention and an operator reading the halt would go looking for a concurrent run that did not exist. The single branch is now three, all driven off the one dispatch that already existed: a reply carrying neither usable array, or a refusal with nothing excluded, halts as NEVER ATTEMPTED and avoids every contention word; a refusal with a non-empty excluded set reports contention and names the members held. A payload asserting contention while naming nothing held is now unreachable, which is the shape the original halt had. A third case surfaced by the tests rather than by the incident is also closed: a refusal-shaped reply carrying no target_refused key at all, and a null reply, previously fell through the halt entirely and the run proceeded having claimed nothing -- worse than the reported bug, since it is silent. Both now take the not-attempted branch. The performer is worktree-agent and the reasoning is deliberately narrow: per the registry schema, permits_shell false OR ABSENT means read-only, and worktree-agent is the only registry entry declaring it true. python-coder, which the release path switched to, declares nothing and is therefore read-only by the schema's own definition -- KI-BO-20260901-1620 exists precisely because that earlier fix reasoned from 'does not explicitly forbid' and wrote the mistaken justification into a comment for future readers to copy. The comment added here states the one true fact and names the weakness instead of claiming safety: worktree-agent's charter is worktree lifecycle rather than AC-store claims, so it may itself decline, and if it does the not-attempted branch now reports that honestly rather than inventing contention. No registry or schema file was edited and KI-BO-20260901-1620 remains open. Two sibling tests changed, both drift from an intentional behaviour change rather than collateral damage: one pinned the claim performer to status-checker under a docstring scoping that guard to the release-path change, and the other supplied no claim response at all and rode the harness's generic stub, which the pre-fix code read as an implicit success -- it was passing because of the defect. Mutation-proven: reverting the workflow to its pre-fix content turns the suite red again and reproduces the original payload verbatim, contention language with an empty held set included. The whole unit_tests/workflows/ suite is green at 777 passed. The file is over its size limit, so the change is net-neutral at 1655 content lines before and after, with the rationale in JSDoc blocks the ratchet's counter strips."
