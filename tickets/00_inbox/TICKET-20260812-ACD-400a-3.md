## Acceptance Criteria

```gherkin
Given the AC store contains an approved, active, todo L2 AC "X-100a-1"
  whose only depends_on entry is its own parent L1 "X-100a",
And "X-100a" is an L1 composite whose work_status is not done
  (an L0/L1 parent is never built as a leaf, so it never reaches done),
When the scanner is invoked with leaf and todo filters,
Then "X-100a-1" appears in the ready list,
And "X-100a-1" does NOT appear in the blocked list,
And no blocked entry names "X-100a" as a blocker of "X-100a-1"
  (an AC's own ancestor is excluded from the dependencies that gate readiness).
```

## Implementation Notes

```yaml
- The fix must live in the scanner's classification path (_classify_ac / the dependency-blocking
  logic); do not add a second, parallel blocking codepath.
- Ancestor detection must reuse the existing derive_parent_id() helper applied transitively
  (walk parent -> grandparent -> ... to the root); do not re-implement parent-id parsing.
- An AC's own ancestor at ANY depth must be excluded from the blocking set, not merely
  its immediate parent.
- Only genuine non-ancestor depends_on entries may gate readiness; a leaf whose only
  depends_on entries are its own ancestors must classify as ready, never blocked.
- scripts/ac_store/ac_prioritizer.py must produce results consistent with the scanner's
  classification (share or mirror the same ancestor-exclusion logic; no divergent
  blocking rules between the two).
- The scanner must remain read-only (never mutate any AC YAML), run in O(n) over the
  store, and be idempotent (repeated invocations on an unchanged store yield identical
  ready/blocked lists).
- Must handle malformed or missing depends_on / parent-id derivation gracefully per
  the project error handling policy (no bare except; log or raise typed).
```
