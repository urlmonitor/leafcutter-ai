# The finder's search and filters travel in the /flows address, so a shared link reopens the same results

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `UXP-617-2` — The finder's search and filters travel in the /flows address, so a shared link reopens the same results — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `UXP-617-2`. Component: `ux-prototyping`. Assigned agent: `frontend-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given /flows is open in a tab with one history entry,
When the person types 'selected option' and then ticks 'Person' under Actor,
Then the address bar becomes /flows?q=selected+option and then
  /flows?q=selected+option&actor=human,
And the tab still has one history entry, because each change rewrote the current entry
  rather than adding one,
And opening /flows?q=selected+option&actor=human in a new tab answers 200 and shows the same
  search 'selected option', the 'Actor: Person' chip and the same '2 flows, 5 steps match'
  results,
And the address names each filter by its stored value, actor=human, never by its label
  'Person',
And the address never carries a flow or a step parameter, so opening it never triggers the
  legacy-link redirect and never opens a drawer,
And clearing the search box and unticking 'Person' returns the address to /flows.
```

## Implementation Notes

```yaml
- 'One finder-address module in leafcutter-web/lib/flow-finder/ builds and parses
  the address: ''/flows'', then q first (form-encoded, spaces as ''+''), then one
  parameter per chosen value, facets in the order product, actor, kind, realization,
  level, uses, produces, io, entity, screen, values in option order and field keys
  sorted; ''/flows'' with no ''?'' when nothing is chosen. build(parse(url)) == url
  for every FlowFinderQuery.url in the dataset.'
- Search and facet state lives only in the /flows query string; a flow's canonical
  address (/flows/<product>/<flow>[?step=<id>]) never carries finder state, and a
  finder address never carries a flow or step parameter. History is written only with
  window.history.pushState / replaceState through leafcutter-web/components/flows/flow-history.ts
  (view state under 'leafcutter:flows-view', merged beside the App Router's __NA and
  __PRIVATE_NEXTJS_INTERNALS_TREE keys); router.push, router.replace and router.refresh
  are never used for Flows history.
- Search and facet edits rewrite the current entry with replaceState, never pushState,
  and make no server request. Writes from typing are coalesced so they stay inside
  browser rate limits on the history API, while results update on every keystroke;
  a pending write is flushed before any push (UXP-617-2-i).
- 'Parameter names and stored values are a public contract (shared and bookmarked
  links): renaming one is a breaking change and needs the UXP-617-5 reference updated
  in the same change.'
- Unknown parameters and unknown values are ignored for results and produce no chip;
  the address is not rewritten on load (UXP-591-1-i), and the next edit writes the
  canonical form.
- leafcutter-web/middleware.ts keeps keying the legacy 308 on the 'flow' parameter
  alone, so no finder address is redirected.
- A shared finder address renders its results in the server HTML from searchParams
  with a 200.
```
