# A repair that is missing from the source an installed file is generated from is reported as not delivered

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `ACD-2100d-2` — A repair that is missing from the source an installed file is generated from is reported as not delivered — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `ACD-2100d-2`. Component: `ac-driven-dev`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given a working copy in which an installed route file carries a repair that the
  source it is generated from does not carry,
When the check that decides whether a change is delivered runs over that working
  copy,
Then it reports the installed file as carrying behaviour its source does not and
  names the file,
And the change is not reported as delivered while that remains true,
And running the installer over that working copy leaves the installed file
  without the repair -- confirming the report rather than contradicting it.
```

- [ ] AC-1: it reports the installed file as carrying behaviour its source does not and
- [ ] AC-2: the change is not reported as delivered while that remains true
- [ ] AC-3: running the installer over that working copy leaves the installed file

## Implementation Notes

```yaml
- The check must derive the source-to-installed relationship from the installer's
  own mapping, not from a hand-maintained list of file pairs. A second list of pairs
  goes stale the first time a file is added and the check then reports clean on the
  file it cannot see.
- The check must name the file. 'Something is out of sync' cannot be acted on and
  cannot be distinguished by a test from a check that found nothing.
- The check must not fire on a generated file that merely differs from its source
  in a way generation explains -- template expansion, header injection, path rewriting.
  Comparing raw bytes across a transform produces a check that is always red and is
  therefore always ignored.
- The check must be usable from the point where 'delivered' is decided, and its result
  must be consumed there. A check that computes a correct verdict nobody reads is
  inert -- the phantom-gate failure mode this repo keeps rediscovering.
- 'Must satisfy the repository error-handling policy: reading both copies is external
  I/O.'
- 'Must be idempotent and side-effect free: running the check must not modify either
  copy.'
- This is not a ban on touching an installed copy while debugging. The requirement
  is that a repair living only in build output is visible as undelivered before someone
  reports it as done.
```
