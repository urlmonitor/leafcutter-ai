# Every unresolved outcome of the startup check still stops the run before any authoring work begins

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `ACD-2100b-4` — Every unresolved outcome of the startup check still stops the run before any authoring work begins — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `ACD-2100b-4`. Component: `ac-driven-dev`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given four runs set up so that the startup check meets a different condition in
  each -- a registry it cannot read; a registry it cannot interpret; a readable
  registry that does not list the agent the route would use; and a readable
  registry that lists the agent with repository commands withheld,
When each run reaches the startup check,
Then each of the four runs stops at the check,
And in none of them is an authoring agent dispatched,
And in none of them does an authoring worktree or branch exist on disk
  afterwards,
And each run reports an outcome that says the run did not proceed rather than an
  outcome that says the run succeeded.
```

## Implementation Notes

```yaml
- The change must land under templates/. The deployed workflow carries no charter
  gate at all today, so this guard is also what stops a future build shipping a gate
  that halts selectively (see ACD-2100d-3).
- The halt must hold for every outcome in which the check did not establish a permitted
  verdict -- including outcomes not enumerated by ACD-2100b-1 through -3. A guard
  written as a list of four conditions is satisfied by an implementation that fails
  open on the fifth.
- Absence of dispatch must be established from the run's own record of what it dispatched,
  and absence of a worktree from the filesystem after the process exits. Reading the
  source to confirm a return follows the check proves nothing about whether the check
  is reached.
- The recorded outcome must not be a success outcome. This constrains only the success/non-success
  distinction -- it does not specify the status vocabulary and does not touch the
  cancellation return path, which is out of scope for this tree (KI-ACD-006).
- Must not weaken the halt to a warning for any outcome. Three of the four causes
  are not permission problems, and the tempting conclusion that three of the four
  should therefore not block is the specific regression this record exists to prevent.
- Must satisfy the repository error-handling policy on every one of the four paths.
```
