## Acceptance Criteria

```gherkin
Given the security allowlist's fourth line is
  "ENTROPY_HIGH:src/config/foo.py:*  # noisy keyword argument, not a secret" —
  a recognised rule id, a real file path, the wildcard that means every line,
  and a trailing explanatory note,
And the file "src/config/foo.py" contains a high-entropy token that the
  ENTROPY_HIGH rule reports,
When the file is scanned through the multi-file entry point the pre-commit
  secrets check calls, with that allowlist in force,
Then the ENTROPY_HIGH finding is still reported — the entry suppressed nothing,
And a warning is emitted on the error stream naming the allowlist file, the
  1-based line number 4, and the verbatim text of that line,
And the entry is skipped rather than loaded,
Because everything after the second separator is read as the field that names
  which line of the target file is exempt, so the entry as loaded asks to exempt
  a line identified as "*  # noisy keyword argument, not a secret", which is
  neither the wildcard nor any line number and therefore can never match — the
  author reads their own file back, sees their note, and believes a suppression
  is in force that is not.

Given the security allowlist contains, on separate lines, the entries
  "GENERIC_SECRET:secrets.py:twelve" and "GENERIC_SECRET:secrets.py:12a",
And "secrets.py" contains a quoted twelve-character value assigned to a field
  named password on line 12, which the GENERIC_SECRET rule reports,
When the allowlist is loaded and the file is scanned,
Then the GENERIC_SECRET finding is reported,
And each of the two entries produces its own warning naming the allowlist file,
  its own 1-based line number, and its own verbatim text,
And neither entry is loaded,
Because a line-number field that is neither the wildcard nor a decimal line
  number cannot equal the line number of any finding, so the entry is incapable
  of matching whatever the scanner later reports.

Given the security allowlist contains the entries
  "ENTROPY_HIGH:src/config/foo.py:*" and "GENERIC_SECRET:secrets.py:12",
And "src/config/foo.py" contains a high-entropy token and "secrets.py" contains
  the password assignment on line 12,
When the allowlist is loaded and both files are scanned,
Then both findings are suppressed,
And no warning is emitted for either line,
Because the wildcard and a decimal line number are exactly the two things the
  field is allowed to contain, and a rule that reports them would make every
  well-formed suppression in the repository noisy.
```

## Implementation Notes

```yaml
- Edit the canonical template at templates/skills/security-scanner/scripts/scan_secrets.py
  and propagate with build.py; the deployed copies are build outputs and must never
  be edited directly (ADR-001).
- Reuse the single allowlist-diagnostic convention already established for this file
  — a message on the error stream carrying the allowlist file path, the 1-based line
  number and the verbatim line text, one message per offending line. Do not introduce
  a second message shape for the new class.
- 'Classification is never fatal: an unmatchable entry must not raise and must not
  change the scan''s exit status, which stays determined by the surviving findings
  alone.'
- Allowlist diagnostics go to the error stream only. The findings report on the standard
  output stream, which the pre-commit check parses, must stay free of them.
- 'The decision must be reachable from the entry text alone, with no filesystem access
  per entry: an entry is judged on what it says, never on whether the file it names
  exists.'
- The value classified must be exactly the value the loader stores for that field,
  so the accepted/rejected boundary is the same one the matcher later compares against
  — a divergence between the value validated and the value stored reintroduces the
  defect in a new place.
- Do not repair, strip or otherwise guess at the author's intent for a rejected value;
  the entry is reported and skipped.
- 'This code runs on every commit: classification must remain a single linear pass
  over the allowlist with no per-entry I/O, and must not measurably lengthen the hook''s
  runtime for an allowlist of a few hundred entries.'
- Load-time rejection must not weaken the matcher's own independent guard against
  directly-constructed allowlist tuples (GE-113c-3-v); both layers stay in force.
- Tests must never create, modify or delete a .security-allowlist at any real project
  root, workspace root or worktree root — the live file is what the commit hook actually
  reads, so a stray write would disable the real gate as a side effect. Every fixture
  allowlist lives under tmp_path/tempfile.
- Fixture files must use ordinary source filenames. The per-file scan short-circuits
  environment-named files to a single filename-based finding and never reads their
  content, so such a fixture cannot produce the content findings these criteria depend
  on.
```
