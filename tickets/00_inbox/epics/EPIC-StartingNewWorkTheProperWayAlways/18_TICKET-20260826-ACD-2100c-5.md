## Acceptance Criteria

```gherkin
Given a run holding drafted work at a decision point,
When the run ends for any reason other than the person choosing to stop -- no
  answer arrives, the answering channel is unavailable, or an answer arrives that
  cannot be attributed to the person,
Then the drafted work is still present on disk after the process has exited,
And the run does not record the outcome as the person having chosen to stop,
And when the person does choose to stop the drafted work is discarded and the
  run records the person as the source of that choice.
```

## Implementation Notes

```yaml
- The change must land under templates/. The deployed workflow is build output.
- State this as an invariant over every exit path, not as a repair to the one known
  destructive default at line 2086. That path is unreachable today, which is exactly
  why a test written against the line would be deleted with it at the next refactor
  and the invariant would silently lapse.
- Discarding must remain reachable from an explicit person's choice -- the feature
  is not being removed, only its use as a fallback.
- The run's record must attribute a discard to the person who chose it. Attribution
  is what makes a legitimate discard distinguishable from a fallback discard afterwards,
  and without it this invariant is unverifiable in production.
- The survival of the drafted work must be observed on disk after the process has
  exited. A run that returns a non-destructive result and then removes the worktree
  or resets the branch on the way out satisfies every in-process check and still loses
  the work.
- This record does not specify the status vocabulary of a cancelled run and must not
  change the cancellation return path (KI-ACD-006 is out of scope for this tree).
  It constrains only the attribution and the on-disk outcome.
- 'Must satisfy the repository error-handling policy: a failure on the way out must
  not become an unattributed discard.'
```
