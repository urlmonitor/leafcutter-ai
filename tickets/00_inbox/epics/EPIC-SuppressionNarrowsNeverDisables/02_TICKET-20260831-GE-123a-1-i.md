# Every sensitively-named file in the same run is read, not just the first one, and no finding is lost between the per-file scan and the run's report

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-123a-1-i` — Every sensitively-named file in the same run is read, not just the first one, and no finding is lost between the per-file scan and the run's report — so that the acceptance criterion is satisfied.

## Acceptance Criteria

```gherkin
Given five files whose names mark them as environment configuration — the same
  five-file set the measured baseline used — each containing the same four
  lines the scanner's content rules recognise: a cloud access key in the
  AWS_KEY form, a private-key header line, a quoted twelve-character value
  assigned to a field named password, and a high-entropy token of at least
  twenty characters,
And no suppression entries are in force,
When all five files are scanned in a single run through the scanner's
  multi-file entry point — the same entry point the pre-commit secrets check
  calls,
Then twenty-five findings are reported: for EACH of the five files, one
  filename finding plus the four content findings,
And the run's exit status reports findings present,
Because the measured collapse was total across all five files, so an
  implementation that reads the contents of the first sensitively-named file
  it meets and short-circuits the rest still leaves four files unprotected
  while satisfying the parent criterion, whose scenario contains only one
  such file.

Given the same five environment-configuration files interleaved with three
  ordinary source files, one of which is scanned before any of the five and
  one of which is scanned after all of them,
And no suppression entries are in force,
When the same set is scanned again in reverse order in a second run,
Then each of the five environment-configuration files reports the same five
  findings in both runs, and each ordinary source file reports the same
  findings in both runs,
Because nothing about a file's position in the run, or about which files
  preceded it, may decide whether that file's contents are read.

Given the same five environment-configuration files and no suppression
  entries in force,
When the run completes,
Then the run's report contains every finding produced for every file — findings
  that differ only in which file they came from are all present, none is
  dropped and none is collapsed into another,
Because coverage demonstrated on the per-file scan alone does not reach the
  author: a run that produces five findings per file internally but reports
  one of each rule for the whole run is the same coverage loss one level up.
```

- [ ] AC-3: the run's exit status reports findings present
- [ ] AC-4: no suppression entries are in force

## Implementation Notes

```yaml
- All fixture files must exist as distinct real files in one tempfile-backed directory
  and be scanned in a SINGLE scan_files call. A test that calls the per-file scan
  five times in a loop asserts nothing this criterion is about and specifically cannot
  fail the aggregation arm.
- The aggregation arm must assert on the multiset of (rule_id, file_path) pairs, never
  on a total count alone. An implementation that de-duplicates by rule id across files
  must fail this arm rather than pass on a coincidental total.
- Order independence must be asserted by comparing the PER-FILE finding sets between
  a forward run and a reverse run of the same file list, never by comparing run totals
  — an order-dependent implementation can produce the same total from a different
  distribution across files.
- The five env-named fixtures must not be five copies of one filename in five directories.
  Use five distinct names drawn from the forms the sensitive-filename rule recognises,
  so the arm cannot be satisfied by behaviour that is specific to one name.
- The three ordinary source files must use ordinary .py filenames, and in the forward
  run one must precede all five env-named files and one must follow all of them, so
  the reverse run genuinely inverts their relative positions.
- Exit-status arms must run the scanner's CLI entry point in a fresh subprocess with
  the fixture directory as the working directory, and must assert the process exit
  code. A returned list of findings is not an exit status.
- Test fixtures must assemble every credential-shaped string at runtime from concatenated
  fragments rather than writing it as a source literal, so this repository continues
  to need no PRIVATE_KEY or AWS_KEY suppression anywhere. The existing suppression
  test module does this deliberately; do not collapse the fragments back into literals.
- Each of the four content-rule lines in a fixture must produce exactly one finding,
  so that twenty-five is an exact expectation rather than a floor. Verify the chosen
  values do not cross-trigger a second rule.
- The module under test must be loaded from the canonical templates/ path via importlib.util.spec_from_file_location,
  never from a deployed copy, which can be stale.
- No test may write a .security-allowlist to any real project root. Every arm of this
  criterion runs with no allowlist present in the fixture directory.
- Fixture files must not be placed under tickets/, docs/retrospectives/, docs/acceptance-criteria/
  or templates/skills/. The pre-commit consumer post-filters entropy findings for
  those path prefixes, which would silently change the expected counts.
```
