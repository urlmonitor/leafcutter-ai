# The liveness run states how many checks it actually put an input through, that figure moves when the population moves, and a run that put an input through none fails as unresolved

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-120f-3` — The liveness run states how many checks it actually put an input through, that figure moves when the population moves, and a run that put an input through none fails as unresolved — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-120f-3`. Component: `guardrail-engine`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given the population of protective checks the run examines is the population established
  by whichever record owns the enumeration of that family, read at the moment the run
  executes rather than written into the run,
When the run finishes,
Then it states how many checks it examined, and that figure counts the checks whose
  declared input it actually put through an entry point, not the checks it set out to
  examine,
And given one further check joins that population and nothing else in the repository
  changes,
When the run repeats,
Then the stated figure is greater than the figure stated before, and the newly joined
  check appears in one of the run's reported classes,
And given a check leaves that population and nothing else changes,
When the run repeats,
Then the stated figure is smaller than the figure stated before, and that check appears
  in none of the run's reported classes,
And a run that put an input through no check at all fails as a run that reached no
  verdict, states that it examined none, and does not report that no check was found
  wanting,
And the figure the run states never exceeds the number of checks it put an input through
  plus the number it reports as unresolved.
```

- [ ] AC-1: it states how many checks it examined, and that figure counts the checks whose
- [ ] AC-2: given one further check joins that population and nothing else in the repository
- [ ] AC-3: the stated figure is greater than the figure stated before, and the newly joined
- [ ] AC-4: given a check leaves that population and nothing else changes
- [ ] AC-5: the stated figure is smaller than the figure stated before, and that check appears
- [ ] AC-6: a run that put an input through no check at all fails as a run that reached no
- [ ] AC-7: the figure the run states never exceeds the number of checks it put an input through

## Implementation Notes

```yaml
- 'THE POPULATION IS THE INVOKED SUBSET OF BP-1600a-2''s CENSUS, READ AT RUN TIME
  — AND THAT RESOLVES THE BOUNDARY THE criteria LEAVE TO "whichever record owns the
  enumeration". BP-1600a-2 (approved) partitions the gate scripts on disk into invoked-at-commit-time,
  registered-and-deliberately-switched-off, and invoked-by-nothing. This run''s population
  is the FIRST class only: a check reached by no entry line has no entry point the
  protected surface invokes, so there is nothing to put an input through and its absence
  here is not a gap. A script the registry never mentions stays BP-1600a-2''s finding
  and must NOT be reported by this run as never-demonstrated — reporting it in both
  places is the fork this family has already had to unpick once (GE-120c-6 / BP-1600a-2,
  2026-09-07).'
- DO NOT GROW A SECOND CENSUS. Consume BP-1600a-2's enumeration; do not list the gate-script
  directory here and do not carry a population of your own. Two independently-derived
  populations will disagree about how many guards exist, and this record's whole subject
  is a figure that can be trusted.
- THE STATED FIGURE COUNTS INVOCATIONS PERFORMED, NEVER INTENTIONS. It counts checks
  whose declared input the run actually put through an entry point — not the checks
  it set out to examine, not the size of the population it read. A check in the population
  that could not be invoked at all is reported as unresolved and is excluded from
  the examined figure.
- 'THE FIGURE MUST MOVE IN BOTH DIRECTIONS OR THE REQUIREMENT IS VACUOUS. A requirement
  to state a number is satisfied by printing one, and a number written into the run
  stays correct-looking on a run that examined nothing. Requiring it to MOVE when
  the population moves is the only form a literal cannot satisfy, and it is required
  both ways: an implementation that adds newly-found checks to a base constant grows
  correctly and never shrinks. Both directions are asserted in one descriptor below
  for that reason.'
- DERIVE THE VERDICT FROM THE EXAMINATION, NOT FROM THE FINDINGS LIST — THIS IS THE
  MOST LIKELY WAY THIS SHIPS BROKEN. A run that put an input through nothing has an
  empty findings list, and an empty findings list is the greenest possible result.
  Reporting nothing wrong is not the same statement as finding nothing wrong. A run
  that examined none fails as a run that reached no verdict, states that it examined
  none, and does not report that no check was found wanting. Follow GE-126e-2's empty-run
  wording rather than diverging from it.
- REBUILD THE FINDINGS FROM THIS RUN'S OBSERVATIONS EVERY TIME. Never carry findings
  forward from a previous run, a cached artifact, or a committed rollup. A finding
  that survives its subject is how a stale figure gets quoted as current, and it makes
  the leaving-the-population clause unfalsifiable.
- NO FIGURE MAY BE ENCODED IN THE IMPLEMENTATION OR IN ANY TEST EXPECTATION, AND THE
  VARYING-POPULATION CLAUSES MUST BE WRITTEN AS FIXTURES, NEVER AS AN EXPECTED LIST.
  An assertion that today's population is fully demonstrated passes forever and catches
  nothing on the day the next check is added — which is the day this run exists for.
  That is GE-120c-6's standing instruction and it applies here unchanged. The parent
  records the count as disputed and forbids one below it.
- THE SCHEMA ALREADY MODELS THE ROLLUP AND SAYS TO REGENERATE IT RATHER THAN HAND-EDIT
  IT. config/verification_flow.schema.json carries a derived per-state rollup over
  the four values; reuse those names and that rule rather than minting a second summary
  vocabulary.
- AC_ENFORCE_STRICT=1 on every pytest invocation; the figure must be stated by the
  DEPLOYED copy out of process. Any module imported from outside templates/scripts/commit_guardian/
  goes into the scripts/build_phases.py deploy map in the same change.
- 'Error-handling policy: specific-exception try/except around directory listing,
  registry reads and subprocess calls, logged at WARNING or higher or re-raised. A
  swallowed read error must never become an empty population — that is precisely the
  examined-none case, and it must reach the caller as a refusal rather than as a clean
  small number.'
```
