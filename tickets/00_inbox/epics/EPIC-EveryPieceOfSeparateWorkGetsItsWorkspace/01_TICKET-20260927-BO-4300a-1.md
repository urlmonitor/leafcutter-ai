# Every route that asks gets the same kind of workspace from the same maker

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `BO-4300a-1` — Every route that asks gets the same kind of workspace from the same maker — so that the acceptance criterion is satisfied.

## Context

## Acceptance Criteria

```gherkin
Given a test project with a shared project it was copied from, whose shared main
  line is at commit S,
And a workspace is requested once from each of these routes -- a long-running
  build, a quick fix, a requirements-authoring session, an agent following the
  workspace skill, and a person at a terminal -- each for its own piece of work,
When each request is answered ready,
Then every one of the five workspaces carries the record the workspace maker
  leaves in each workspace it makes, and that record agrees with the answer the
  route received,
And each of the five is an independent copy of the project, started from S as
  read at the time of its request, with its tools installed inside it from its
  own contents, with its protections shown to fire, and located in the
  project's one landing place for workspaces,
And each route receives its answer in the same form, stating ready and the
  workspace's location,
And no route's workspace lacks any of those properties that another route's
  workspace has.
```

## Implementation Notes

```yaml
- Deliver the one maker as a stdlib-only Python file at templates/scripts/worktree.py
  (name provisional; once built, that path is the contract every caller names), exposing
  the verbs ensure, locate, list, verify, remove and where, plus the separate project-root
  resolver module described below. After BO-4300f-2 no other code path in the package
  creates, clones, locates or removes a workspace.
- 'ROOT RESOLUTION LIVES IN ITS OWN MODULE (duplication audit C4, KI-CG-20260925-shared-root-resolver-accepts-non-repo-workspace-parent):
  project resolution is delivered as a separate importable module (see delivers_to),
  separate from the maker''s CLI file, stdlib-only, with its own named deploy-manifest
  entry. The maker imports it; it never re-implements resolution inline. It must not
  reuse, import, wrap or copy templates/scripts/commit_guardian/_resolve_root.py (that
  module walks up from __file__ looking for .git or CLAUDE.md and caches its answer
  in a module global -- both forbidden here). The resolution order and exclusions
  are BO-4300b-1''s.'
- 'NO SECOND TRACKED COPY (KI-TQ-20260831-mutation-probe-lands-in-the-wrong-copy,
  KI-TQ-004): the only tracked source of the maker and of the resolver module is templates/scripts/.
  No tracked copy exists under scripts/ or anywhere else in the package repository
  (today scripts/setup_ticket_worktree.py and templates/scripts/setup_ticket_worktree.py
  are both tracked and differ -- that shape must not recur). Tests run the DEPLOYED
  copy only.'
- 'ensure follows the decision memo''s order (''Consequences for the standalone script''s
  contract'', step 1): resolve the main checkout; read the hub from its origin (NO_HUB
  when absent); compute the landing place; if the location exists, verify then repair
  or refuse; otherwise a hardlinked local-path clone with --no-checkout (no --shared,
  no --reference); re-point origin at the hub; fetch origin main (FETCH_FAILED unless
  --allow-stale-base); check out the line of work from origin/main, or resume origin/<branch>
  (BO-4300d-4); when --ticket was given, locate the ticket inside the workspace (BO-4300a-1-ii);
  set gc.auto 0 and maintenance.auto false in the workspace; copy .env and .mcp.json;
  run the install build inside the workspace with an explicit config path; install
  the shim for every hook stage the workspace''s own hook declaration names (BO-4300c-1-ii);
  clean-tree check; one canary per declared stage; write the marker; emit the answer.'
- 'GIT INVOCATION SPELLING (KI-CG-20260925-commit-delegation-hook-misses-git-dash-c):
  the maker runs git as a subprocess with its working directory set to the target,
  or with -C <path> for verbs other than commit only. Any commit the maker makes (the
  canaries) runs with the working directory set, never as `git -C <path> commit`.
  The same holds for every recipe, skill text and test in this family, because the
  commit-delegation hook matches only the literal "git commit" and the -C spelling
  slips past it.'
- No os.symlink, ln -s, mklink or junction anywhere in the maker or in the install
  path it drives (decision 2).
- The build entry point and its config are derived from the main checkout's own install
  config (the memo's --config-path derivation, stripping the top_level_packages prefix).
  NO_CONFIG when that is impossible; never the build's default config, never the maker's
  own location.
- 'Work identity and naming live in ONE table inside the maker (Q4 open): callers
  pass kind plus the raw work identity they hold, the maker normalises it, and the
  same identity from any route yields the same landing location and the same line
  of work. The table must accommodate whichever scheme the user picks, including an
  alias for legacy spellings (BO-4300a-2).'
- The marker record is the maker's registry under clones (no git command lists clones).
  It holds schema_version, kind, slug, branch, hub, project_root (absolute path of
  the main checkout the workspace was made from -- the ONLY way a workspace identifies
  its project, BO-4300b-1), base_commit, maker_version, state ('creating'|'ready')
  and created_at; it is written atomically (temp file plus replace), state 'creating'
  immediately after the clone exists and 'ready' as the last step; it lives outside
  version control and outside anything the install build rewrites or cleans. The memo's
  .leafcutter/workspace.json is acceptable only if a test shows the build leaves it
  intact.
- 'BUILD DEPLOY MANIFEST (CLAUDE.md ''New Hook / Gate Dependencies Must Be in the
  Build Deploy-Manifest''): the maker is added as a NAMED entry to the standalone-scripts
  deploy (build_template_standalone_scripts in scripts/build_phases_script_deploy.py
  -- its docstring list -- and the matching manifest helper in scripts/build_deploy_manifest_helpers.py),
  not left to the shallow glob alone. The resolver module gets its OWN named entry
  in both places, deployed beside the maker in <install-root>/scripts/; that phase
  is non-recursive, so any further helper module the maker imports needs a named entry
  too. Verified by running the DEPLOYED copy''s `where` verb after the build and importing
  the DEPLOYED resolver module in a separate process, not by the unit suite importing
  the source.'
- 'docs/components.json -> worktree_manager: its description (''Git worktree lifecycle
  management for isolated epic and ticket branch environments.'') and primary_code
  ([''scripts/worktree/'']) become wrong under decision 1. Update the description
  to per-feature clone workspaces made, found, listed and cleared through one maker,
  and add templates/scripts/worktree.py and the resolver module to primary_code; drop
  setup_ticket_worktree references when BO-4300f-2 deletes that script. (IT PO recorded
  this here and did NOT edit components.json.)'
- Excluding the install build, an ensure on a project of the leafcutter-ai size (about
  8,500 tracked files) completes within 30 s on the reference Windows host (the decision
  memo measures about 11 s clone plus about 1 s fetch); read-only verbs complete within
  5 s.
- The maker never reads stdin and never prompts; every decision it needs arrives as
  an argument of the request, so an unattended caller can never stall on it.
- 'Must handle errors per the project error handling policy: a condition the maker
  cannot classify is an error answer (code INTERNAL_ERROR) whose message names it
  -- never an ok answer, and never a traceback on stdout.'
- The workspace skill that agents run the maker from is llm-expert work and is delivered
  by BO-4300a-1-ib; this AC delivers the command that skill runs.
- Proof runs the DEPLOYED maker -- the copy an install delivers, resolved through
  the shared test locator delivered by BO-4300f-4 -- as a separate process against
  real temporary git repositories with a real bare hub. No mock of git, no import
  of the maker module, no grep of its source (CLAUDE.md 'Gate / Workflow ACs -- Verify
  Behaviorally, Not by Grep'); a test never falls back to the templates/ source copy.
- 'Tests must not spawn the package''s own scripts/build.py (CLAUDE.md ''Tests must
  not spawn their own build.py''): the deployed maker comes from the shared deployed
  layout, and fixture projects carry a minimal stub build entry point that installs
  a real, rejecting hook in well under a second. A test that must mutate the package
  and build its own copy says so and justifies it in its ticket.'
- All temporary projects, hubs and workspaces live under the test's temp directory
  and run git with an isolated global and system config; afterwards the developer's
  own repository's branches, registered worktrees and local git config are unchanged
  (BO-4300f-4-i, F14, KI-TQ-012).
```
