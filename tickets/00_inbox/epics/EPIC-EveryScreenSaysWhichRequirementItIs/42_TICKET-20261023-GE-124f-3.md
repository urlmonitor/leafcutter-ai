# A test's selector and the criterion it claims to cover are checked against each other

## Actor / Goal

## Acceptance Criteria

```gherkin
Given an element pinned to the criterion UXP-100d-2
When the selector for that element is derived
Then the derived selector matches elements whose criterion pin includes
  UXP-100d-2, and matches no element that does not carry that pin
And the derived selector is the same string for every element pinned to that
  criterion

Given a front-end test that declares it covers UXP-100d-2 and locates its
  element with the selector derived from UXP-100d-2
When the test and the element are checked against each other
Then they are reported as agreeing

Given a front-end test that declares it covers UXP-100d-2 and locates its
  element with the selector derived from UXP-607
When the test and the element are checked against each other
Then a finding is reported naming the test, the criterion it claims, and the
  criterion its selector actually reaches
```

## Implementation Notes

```yaml
- THE SELECTOR IS THE MEMBERSHIP FORM `[data-ac~="<id>"]`, EXACTLY AS THE MOCK-DATA
  INVARIANT STATES. The `~=` operator matches a whitespace-separated token within
  the attribute value; an exact-match `[data-ac="<id>"]` selector silently fails on
  every multi-valued pin such as `data-ac="UXP-607-1 UXP-607"`, which is the common
  case. This is also why GE-124b-1's value grammar is whitespace-only — a comma in
  the value would make every derived selector match nothing.
- DERIVATION IS A PURE FUNCTION OF THE ID, exposed as ONE function that both the check
  and the documentation (GE-124b-5) read. Same id in, same string out, every time,
  for every element pinned to that criterion. A per-element or per-file selector would
  defeat the whole point, which is that the selector a test writes and the id in its
  coverage tag are the same thing.
- THE CLAIMED CRITERION COMES FROM THE TEST'S EXISTING COVERAGE TAG. Reuse the repo's
  established covers-tag convention and its existing parser (COVERS_TAG_RE, shared
  between scripts/ac_store/done_proof.py and test_enforcement.py) rather than introducing
  a second way for a front-end test to declare what it covers. Two coverage-tag conventions
  would be a new drift surface in a tree whose entire point is removing them.
- AGREEMENT IS CHECKED STATICALLY, NOT BY RUNNING THE TEST. Extract the selector literals
  a test uses and compare their embedded ids against the ids in its coverage tag.
  This is a text-level comparison of two declared things and does not require a browser,
  a test run, or a rendered DOM — keeping it static is what makes it affordable to
  run over every front-end test.
- 'THE FINDING NAMES THREE THINGS: the test, the criterion it claims, and the criterion
  its selector actually reaches. A finding that says only ''mismatch'' leaves the
  author to work out which of the two is wrong, and either could be.'
- HARD BOUNDARY — THIS AC CHECKS AGREEMENT ONLY. It says nothing about whether the
  test asserts anything. An existence-only test that locates the element and stops
  AGREES perfectly and must still not count as covering the criterion; that is GE-124g-4,
  which guards this outcome directly. Do not let agreement be recorded anywhere as
  coverage.
- A test that uses a non-derived selector (a CSS class, a text matcher, a testid)
  is NOT a finding — this check applies to tests that use the derived selector form.
  Reporting every front-end test that does not use data-ac would make the pin compulsory
  by the back door.
```
