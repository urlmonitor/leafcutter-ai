# Undoing or replaying someone else's recorded change is treated the same way as merging it in

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-120e-4` — Undoing or replaying someone else's recorded change is treated the same way as merging it in — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `GE-120e-4`. Component: `guardrail-engine`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given a commit that stages the undo of a large changeset already recorded in the project's
  history, and a commit that stages a copy of a change already recorded elsewhere, in each
  case with a record of the operation in progress naming the change it came from,
When a check that works out its own change set runs on each of them,
Then the content that is present only because it reproduces or undoes the named recorded
  change is absent from the change set the check inspects, and the check raises no
  objection to it,
And content the author wrote on top of that operation is present in the change set and the
  check reaches its verdict on it,
And on an ordinary commit, with no operation in progress and one state to compare against,
  the change set is the author's entire staged content, so the rule narrows nothing on the
  common path,
And the change set is worked out from the states the commit is built on and the record of
  the operation in progress together, so it is never decided by asking whether a merge in
  particular is under way.

Coverage note: cover each operation by performing it as a real repository operation and
executing the check as a process against the resulting staged state. The last clause is
the load-bearing one and cannot be covered by any merge fixture — cover it by running an
operation in which no merge marker exists, and asserting the carried-in content is still
absent from what the check objects to.
```

## Implementation Notes

```yaml
- TWO SIGNALS, COMBINED — NEVER A MARKER SWITCH. The derivation takes the states the
  commit is built on AND the record of the operation in progress. REVERT_HEAD and
  CHERRY_PICK_HEAD are the operation records this AC is about; MERGE_HEAD is a third
  of the same kind. Branching on 'is a merge in progress' is explicitly forbidden
  by the fourth criterion — the question is 'what states is this commit built on',
  and the operation record is one input to that answer, not a mode selector.
- EXTEND GE-120e-1'S SHARED SOURCE, DO NOT ADD A SECOND DERIVATION for these operations.
  Two derivations will disagree, and the disagreement surfaces as one check blocking
  what another passed — the defect this L1 removes.
- RESOLVE THE GIT DIRECTORY WITH PLUMBING. The operation records live in the git directory,
  and drives in this repository run inside git worktrees where there is no .git DIRECTORY.
  Use git rev-parse --git-dir (or equivalent) rather than assuming <root>/.git; a
  hard-coded path makes the whole derivation a silent no-op in exactly the environment
  the observed defect was hit in.
- THE ORDINARY-COMMIT CLAUSE IS A NEGATIVE CONTROL AND MUST STAY TRUE. With no operation
  in progress and one state, the change set is the author's entire staged content,
  byte-identical to today's git diff --cached. The cheapest way to satisfy the first
  two clauses is a narrowing that also quietly exempts ordinary commits, and nothing
  else in this L1 would catch that.
- 'SCOPING JUDGMENT — CONFIRMED, WITH A CONSTRAINT ON HOW TO REVISE IT. Treating a
  straight undo as not-the-author''s is accepted here: being blocked on deletions
  that are inherent to reversing someone else''s decision is precisely what teaches
  the override reflex this L1 exists to remove. If a specific check needs the opposite
  answer, record it as that check''s own behaviour on its manifest entry; do not weaken
  this rule and do not delete this AC — the copy-of-a-recorded-change half stands
  regardless.'
- PERFORMANCE. At most one additional git invocation beyond GE-120e-1's derivation,
  memoised per process. The derivation must not walk history — an undo of a large
  mainline merge is precisely the case where a history walk turns a pre-commit into
  a coffee break.
- 'TEMPLATE/DEPLOYED PARITY (ADR-001): the change lands in templates/scripts/commit_guardian/
  and must be verified in the deployed layout after build.py, not only in the source
  tree.'
- 'Error-handling policy applies to the git calls: specific exceptions, logged at
  WARNING or higher, never swallowed, and never degrading to ''attribute everything
  to the author''.'
```

guidance for `python-coder`:

1. **Combine the probe, don't branch on it (per the ticket's own
   Implementation Notes, "TWO SIGNALS, COMBINED — NEVER A MARKER SWITCH").**
   The three operation-record files (`MERGE_HEAD`, `REVERT_HEAD`,
   `CHERRY_PICK_HEAD`) all live in the same git directory
   (`git rev-parse --git-dir`, already how `_resolve_root.py` and this
   module's worktree-safety precedent resolve it — never `<root>/.git`). The
   *scoping semantics* this AC requires ("content differing from the
   operation's own incoming state") are identical for all three refs — so
   the natural shape is one small ordered list of candidate op-record names,
   checked for existence, with the *first present one* (there is normally at
   most one at a time; git does not allow overlapping in-progress operations)
   feeding the same `_build_authored_change(scoped_paths, ["HEAD", <ref>],

   "one shared source, one general predicate over which state pair applies"

   is the shape the AC's fourth clause (never decided by "is a merge in
   particular under way") is written to forbid.
2. **Stay inside the ticket's own performance budget with file-existence
   checks, not three subprocess probes.** The Implementation Notes cap this
   at "at most one additional git invocation beyond GE-120e-1's derivation."
   Today's single `git rev-parse -q --verify MERGE_HEAD` subprocess call can
   be replaced by resolving the git directory once (already necessary for
   worktree-safety) and checking for the presence of the `MERGE_HEAD`,

**Design concern (one paragraph).** The single largest risk here is
representational, not algorithmic: `AuthoredChange.states` is documented as
provenance ("the states the commit is built on") and consumers may reasonably

amendment (below) should say explicitly that `states` values are not to be
