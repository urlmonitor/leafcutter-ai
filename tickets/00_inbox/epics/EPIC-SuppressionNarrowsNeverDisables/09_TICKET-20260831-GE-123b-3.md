## Acceptance Criteria

```gherkin
Given a file "settings.py" containing only ordinary configuration text that no
  content rule recognises,
And the allowlist contains exactly one entry naming the high-entropy rule, the
  path "settings.py", and every line,
When the file is scanned through the scanner's multi-file entry point — the
  same entry point the pre-commit secrets check calls,
Then no findings are reported, the run exits clean, and no lost-coverage
  warning is emitted about "settings.py",
Because the file's other five rules remain able to report on it: what is
  counted is the rules still capable of firing on a file, not the findings the
  file happens to produce today.

Given a file "notes.py" whose only recognised line is a quoted
  twelve-character value assigned to a field named password,
And the allowlist contains exactly one entry naming the single rule that
  recognises that line, the path "notes.py", and every line,
When the run completes,
Then that finding is suppressed, no findings are reported, the run exits
  clean, and no lost-coverage warning is emitted,
Because suppressing the only finding a file currently produces is the
  ordinary, intended use of the allowlist; it becomes a collapse only when no
  rule is left able to report on that file at all.

Given a file the scanner cannot read,
And no allowlist entry names it,
When the run completes,
Then no finding is reported for that file and no lost-coverage warning is
  emitted about it,
Because no suppression took anything away — this guarantee is about coverage
  removed by an allowlist entry, and it must not manufacture coverage where
  none was ever offered. Whether an unreadable file should be announced on its
  own account is GE-120a's question, which this criterion neither answers nor
  repeals.
```

## Implementation Notes

```yaml
- 'THIS IS THE OVER-REACH GUARD and its whole content is a silence-and-inertness constraint:
  on anything that is not a collapse, the new decision point must change nothing and
  say nothing. No lost-coverage warning may be emitted for a file that merely has
  nothing to report, and no well-scoped narrowing may be declined. On a check that
  runs on every commit, over-reach here is its own outage.'
- 'THE COUNTED QUANTITY IS RULES-STILL-ABLE-TO-REPORT, file-independent, exactly as
  GE-123b-1 defines it. Stated here as a prohibition rather than a definition: the
  implementation must NOT decide by looking at how many findings a file produced.
  Both green arms below are files that produce zero findings after suppression and
  are nonetheless fully covered, so a findings-based implementation fails them immediately
  — which is precisely what they exist to catch.'
- SCOPE THE SILENCE ASSERTION TO THE LOST-COVERAGE WARNING SPECIFICALLY. Tests must
  assert the absence of THAT warning, not an empty error stream. An empty-stream assertion
  would forbid GE-120a from ever announcing an unreadable file on its own account,
  and would collide with GE-113c-3-v's malformed-entry warnings, neither of which
  this criterion touches. Emit the lost-coverage warning with a stable, greppable
  marker so its absence can be asserted without asserting global silence.
- 'THE UNREADABLE-FILE ARM IS ABOUT WHAT DRIVES THE DECISION, not about unreadable
  files. `scan_file` swallows the read error and returns no findings, so a file that
  cannot be read is indistinguishable from a clean file at the findings level. The
  decision must be driven by the allowlist entries in force for that file: no entry
  names it, so nothing was taken away, so there is no decline and no warning. Do not
  manufacture coverage where none was ever offered, and do not use ''this file produced
  zero findings'' as the trigger for anything.'
- COMPATIBILITY WITH GE-123a-2 IS A HARD CONSTRAINT, not a nicety. Its third arm requires
  that suppressing the only finding a file genuinely produces keeps working. Under
  a findings-based reading of GE-123b that arm becomes a contradiction; under the
  rules reading the two agree exactly. Any implementation that breaks arm 2 below
  has put the two L1s in conflict.
- 'REAL-ARTIFACT FALSE-POSITIVE GUARD IS MANDATORY: loading this repository''s own
  on-disk `.security-allowlist` and scanning a real repository file that it names
  must emit no lost-coverage warning. That file has at most two of six rules silenced,
  so it is nowhere near a collapse; a rule strict enough to warn on the real artifact
  would be a commit-time nuisance on every commit. Read-only — the test must never
  write to the repository''s allowlist, and must skip if the file is absent.'
- 'VERIFICATION STANDARD, non-negotiable: every arm through `scan_files` with real
  files on disk and a real `.security-allowlist` in the same temporary root. Calling
  `_is_suppressed` with hand-built tuples discharges nothing.'
- 'Fixture reachability: ordinary `.py` filenames throughout. `scan_file` short-circuits
  an environment-named path to a single name-based finding and returns before any
  content rule runs. The environment-filename collapse is GE-123a''s subject, not
  this one''s.'
- 'ADR-001 parity: edit the canonical `templates/skills/security-scanner/scripts/scan_secrets.py`
  only and let `build.py` propagate. Never hand-edit the copies under `.claude/`,
  `.gemini/`, `.leafcutter/`, `EPIC-*/` or `worktrees/**`.'
- 'RED-FIRST LABELLING, and this record is the exception in the batch: arms 1 and
  2 are declared REGRESSION GUARDS and are GREEN ON ARRIVAL by design (both measured
  0 findings, clean exit, no warning). They are the guard rails on this L1, not the
  change it asks for — green here is expected and is not a TDD-order violation. They
  fail only if an implementation of GE-123b-1, GE-123b-2 or GE-123b-4 over-reaches,
  which is exactly what they exist to catch. Do not let a red-baseline gate reject
  this record for lacking a red arm.'
```
