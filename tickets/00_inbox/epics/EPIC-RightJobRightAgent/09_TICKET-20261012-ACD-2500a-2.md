```gherkin

Then every record is evaluated against each of these rule families:
  parent-to-child back-links,
  non-empty graph component list,
  readiness never raised to approved by an authoring agent,
  producer/consumer contract symmetry,
  documentation trigger to documentation requirement mapping,
And for the three families that have exactly one correct repair (parent back-links,
  graph component list when the namespace maps to a single graph id, and readiness
  raised to approved by an authoring agent) the check applies the repair and lists each

  finding with disposition "needs a decision",
And after applying repairs the check evaluates the repaired records again, and reports
  passed only when that second evaluation produces no finding,
And each family's rule is read from the same rule source the store's existing record
  checks read, so changing a rule in that source changes this check's verdict with no
  second edit.
```

```yaml
- Each family's rule is read from the one rule source the existing record checks read
  (config/ac_store_schema.json, docs/components.json, docs/acceptance-criteria/index.yaml
  and the documentation-trigger map); no rule, id list or trigger table is restated
  inside the check. A duplicated rule source is a defect to delete.
- The documentation-trigger-to-specialist map (5 triggers) lives in exactly one machine-readable
  config location read by this check; the it-po.md S7b table and ACD-200b-1's 4-entry
  table are not sources.
- 'Every write is a field-targeted edit: only the named field changes and every other
  byte of the record is preserved (no whole-file YAML load/dump rewrite; see the fast_lane.py
  round-trip hazard in the ac-driven-dev PROJECT_CONTEXT).'
- 'Repairs are idempotent: a second run immediately after the first changes no file
  and reports no ''fixed'' entry.'
- A repair is applied only when fully determined by data already in the store; any
  ambiguous case is reported 'needs a decision', never guessed.
- After repairs the check re-evaluates the repaired records and reports passed only
  when that second evaluation yields no finding.
- Contract symmetry asserts presence and mutual pointing only; description text is
  never compared (semantic compatibility stays with the technical planner, TKT-300a-3).
- Namespace-to-graph-id resolution reuses the store's existing namespace-to-graph
  mapping (the one backfill_components.py applies); no second mapping.
```
