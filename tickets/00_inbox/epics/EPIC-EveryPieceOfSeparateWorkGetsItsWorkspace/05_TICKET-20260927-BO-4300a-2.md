# The same piece of work is always recognised as the same workspace

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `BO-4300a-2` — The same piece of work is always recognised as the same workspace — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `BO-4300a-2`. Component: `build-orchestration`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

**Field note (2026-10-02): the naming table also needs a rule for ticket files.** This
record's criteria only test epic spellings, and BO-4000 does not define the identity of a
ticket-file target either. Today the same single ticket gets a different identity on each
route:
- **`build-feature.js`** names the worktree and branch after the ticket file's last path
  segment, `.md` included. Example: worktree
  `worktrees/TICKET-20261002-KernelRunnablePublishCommand.md` on branch
  `ticket/ticket-20261002-kernel-runnable-publish-command.md`.
  - Claude Code now lists that worktree's skills as `worktrees/TICKET-...md:<skill>`.
- **`setup_ticket_worktree.py create-only <name>`** produces `feature/<name>`.
- **The `worktree-agent`** once chose `feature/ticket/...md` on its own.

When the maker's naming table is settled (Q4), it should give a ticket file one identity
that every route agrees on, without the `.md` extension. The tests for this record should
then include a ticket-file case next to the epic cases. If that changes the criteria, amend
BO-4300a-2 through the AC flow, because the YAML is canonical.

```gherkin

  through the long-running build route, and its line of work carries two

When the same epic is asked for again through the feature skill's epic route,
  which today names epics differently, and again through the long-running
  build route,
Then both requests are answered ready with the location of the existing
  workspace,
And afterwards exactly one workspace and exactly one line of work exist for
  that epic,
And the two commits are still on the line of work the workspace is on,
And given a different epic, "Files Stay Portable", is requested, it is answered
  with a workspace of its own, at a different location from the first.
```

## Implementation Notes

```yaml
- Identity normalisation is owned by the maker's single naming table (Q4 open). Whatever
  scheme is chosen, spellings of the same work used by today's routes -- EPIC-<Name>
  (feature skill), epic/<kebab> (build-feature), the epic's display title -- normalise
  to one identity, and distinct works never collide.
- Matching is on the exact normalised identity, never a prefix or substring (the '_worktree_exists'
  prefix table and finalize's branch-substring match are retired).
- A re-request never abandons an existing line of work for a freshly named twin and
  never moves or resets its commits (F10, KI-BO-20260921 'abandons the epic worktree
  branch').
- Answers conform to the result contract delivered by BO-4300c-2 (one JSON object
  on stdout, status/code/exit mapping, workspace_path absent on every non-ok answer).
- Proof runs the DEPLOYED maker -- the copy an install delivers, resolved through
  the shared test locator delivered by BO-4300f-4 -- as a separate process against
  real temporary git repositories with a real bare hub. No mock of git, no import
  of the maker module, no grep of its source (CLAUDE.md 'Gate / Workflow ACs -- Verify
  Behaviorally, Not by Grep'); a test never falls back to the templates/ source copy.
- 'Tests must not spawn the package''s own scripts/build.py (CLAUDE.md ''Tests must
  not spawn their own build.py''): the deployed maker comes from the shared deployed
  layout, and fixture projects carry a minimal stub build entry point that installs
  a real, rejecting hook in well under a second. A test that must mutate the package
  and build its own copy says so and justifies it in its ticket.'
- All temporary projects, hubs and workspaces live under the test's temp directory
  and run git with an isolated global and system config; afterwards the developer's
  own repository's branches, registered worktrees and local git config are unchanged
  (BO-4300f-4-i, F14, KI-TQ-012).
```
