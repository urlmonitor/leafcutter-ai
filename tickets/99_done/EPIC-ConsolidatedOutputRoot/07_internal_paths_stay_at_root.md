# 07: Keep Internal-Only Build Outputs at target_root

## Goal
In order to avoid unnecessary symlinks and ensure a seamless upgrade for
existing installs, we need to distinguish between **externally-referenced**
build outputs (which must go into `.leafcutter/` and be shimmed) and
**internal-only** outputs (which should stay at their current locations in
`target_root` because nothing outside our own code references them by path).

## Context
Ticket 03 moved ALL artifact phases to write into `output_root`. But many of
those outputs are only read by our own scripts — not by external tools that
hardcode paths. These don't need to move into `.leafcutter/` or get shimmed.

Moving them adds complexity (extra shims) and breaks existing installs on
upgrade (old files left behind with no benefit). The simpler approach: only
move what external tools require at fixed paths.

### What MUST go into .leafcutter/ (external tools hardcode these paths):
- `agents/` — Claude Code reads `.claude/agents/`
- `skills/` — Claude Code reads `.claude/skills/`
- `commands/` — Claude Code reads `.claude/commands/`
- `hooks/` — Claude Code reads `.claude/hooks/`
- `settings.json` — Claude Code reads `.claude/settings.json`
- `gemini/` — Gemini reads `.gemini/`
- `pre-commit-config.yaml` — pre-commit reads `.pre-commit-config.yaml`

### What should STAY at target_root (only our code reads these):
- `scripts/commit_guardian/` — referenced in `.pre-commit-config.yaml` entry
  lines, but those entry lines are also generated by us and can point anywhere
- `scripts/doc_compliance/` — internal hook scripts
- `scripts/feedback/` — internal feedback pipeline
- `scripts/sync_platforms/` — internal sync tooling
- `config/feedback_categories.yaml` — internal config
- `.agents/rules/` — internal rules (if applicable)
- `build_propagation_audit` output — internal audit

### Special case: scripts/commit_guardian/
Pre-commit hooks reference `scripts/commit_guardian/run_hook.py` in their
`entry:` field. Since we also generate `.pre-commit-config.yaml`, we control
both the scripts AND the references to them. The simplest fix: keep writing
scripts to `target_root/scripts/commit_guardian/` (no move, no shim). The
generated `.pre-commit-config.yaml` (which IS shimmed) already references
the correct path.

## Acceptance Criteria

```gherkin
Given build.py runs on a fresh consumer project
When examining the filesystem after build
Then .leafcutter/ contains ONLY: agents/, skills/, commands/, hooks/,
  settings.json, gemini/, pre-commit-config.yaml
And scripts/commit_guardian/ exists at target_root (not inside .leafcutter/)
And scripts/doc_compliance/ exists at target_root
And scripts/feedback/ exists at target_root
And config/feedback_categories.yaml exists at target_root

Given build.py runs on an existing consumer project (pre-consolidation layout)
When examining the filesystem after build
Then scripts/commit_guardian/ is unchanged (not deleted, not symlinked)
And .claude/agents/ is now a symlink to .leafcutter/agents/
And no shim entries exist for scripts/commit_guardian, scripts/doc_compliance,
  scripts/feedback, or scripts/sync_platforms

Given the shim_map in install_shims()
When inspecting the shim entries
Then only external-tool paths are shimmed:
  .claude/agents, .claude/skills, .claude/commands, .claude/hooks,
  .claude/settings.json, .gemini, .pre-commit-config.yaml
```

## Risk & Safety
- Touches money? No.
- Touches data? No.
- Reversibility? Fully reversible — just moves phases between lists.
- This is a fix for ticket 03 that prevents breakage on upgrade for existing
  installs. Without this, existing `scripts/commit_guardian/` dirs would be
  deleted and replaced with symlinks (surprising, potentially destructive if
  user had local modifications to hook scripts).
