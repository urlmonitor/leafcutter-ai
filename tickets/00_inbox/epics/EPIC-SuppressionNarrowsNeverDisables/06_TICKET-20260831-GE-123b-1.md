## Acceptance Criteria

```gherkin
Given a file "secrets.py" on disk containing four lines the scanner's content
  rules recognise — a cloud access key in the AWS_KEY form, a private-key
  header line, a quoted twelve-character value assigned to a field named
  password, and a high-entropy token of at least twenty characters,
And the allowlist contains exactly one entry, which names every rule (the rule
  field written as the wildcard), the path "secrets.py", and every line (the
  line field written as the wildcard),
When the file is scanned through the scanner's multi-file entry point — the
  same entry point the pre-commit secrets check calls,
Then all four findings for "secrets.py" are still reported,
And the run's exit status reports findings present,
Because that one entry would leave "secrets.py" with no rule still able to
  report anything about it, and a suppression may narrow what a file is
  reported for but may never take it to nothing.

Given the identical file and the identical single entry,
And a second file "helpers.py" containing the same four recognised lines,
  named by no allowlist entry,
When both files are scanned in the same run,
Then eight findings are reported — four for each file,
Because refusing an entry for the one file it would have left unprotected
  changes nothing about any other file in the run.

Given the same file "secrets.py",
And the allowlist instead contains exactly one entry naming the single rule
  that recognises the password assignment, the path "secrets.py", and every
  line,
When the run completes,
Then exactly three findings are reported for "secrets.py" — the cloud access
  key, the private-key header and the high-entropy token — and the
  password-assignment finding is not reported,
Because five of the scanner's six rules remain able to report on that file, so
  this entry is a narrowing, and narrowing must go on working exactly as
  written.

Given the same file "secrets.py",
And the allowlist instead contains exactly one entry naming every rule, the
  path "secrets.py", and the single line number of the cloud-access-key line,
When the run completes,
Then exactly three findings are reported — the private-key header, the
  password assignment and the high-entropy token — and the cloud access key
  is not reported,
Because an entry that names every rule is not forbidden in itself; what is
  refused is an entry whose effect is to leave the file with nothing able to
  report on it.
```

## Implementation Notes

```yaml
- 'ENFORCEMENT POINT, named before implementation because the wrong one is a no-op:
  the decision belongs in `scan_files` in the canonical `templates/skills/security-scanner/scripts/scan_secrets.py`,
  taken once per scanned file after the whole allowlist has been loaded and before
  the findings list is returned. `_is_suppressed` cannot host it — it sees one finding
  against one entry set and has no notion of what would remain able to report on the
  file. A guard added only to `_is_suppressed` satisfies no arm of this criterion.
  `check_secrets.main` calls `scan_files`, so this is also the point the real pre-commit
  path reaches.'
- 'WHAT EFFECTIVE COVERAGE IS COUNTED IN — the definition the whole L1 turns on; do
  not re-derive it and do not soften it. Coverage is the set of RULES still able to
  report on a file after every allowlist entry in force has been applied, never the
  findings the file happens to produce. A rule counts as silenced FOR A FILE only
  when some entry matches that rule id (literally or through the rule wildcard), matches
  that file path (through the literal path wildcard or the GE-113c-3 exact / segment-suffix
  forms), AND carries the wildcard in its line field. An entry pinned to a specific
  line number never removes a rule''s ability to report on that file. A collapse is
  exactly: every declared rule silenced for that file.'
- 'THE RULE INVENTORY MUST HAVE ONE DECLARED SOURCE. The scanner has six rule ids:
  the four regex rules held in `_RULES`, plus the entropy rule and the env-filename
  rule, both of which exist today only as inline literals inside `scan_file`. The
  collapse check must count against a single declared inventory that all six come
  from. A hard-coded list, or a hard-coded count, inside the check is a defect: a
  seventh rule added later would silently stop being counted and the guarantee would
  weaken without anything failing. Counting is file-independent — do NOT compute which
  rules could match this particular file''s content, which is precisely the findings
  reading this criterion exists to reject.'
- Disposition is REFUSE AND ANNOUNCE, never raise and never block. A declined entry
  must not abort the scan, must not by itself change the exit status, and must leave
  the exit status determined by the reported findings alone. The announcement contract
  belongs to GE-123b-1-i; reuse it rather than inventing a second one.
- Arm 4 must be satisfied by RESULTING COVERAGE, never by the shape of the line. Do
  not reject the rule wildcard, and do not reject any entry judged too broad, at parse
  time or by pattern. An entry naming every rule but pinned to one line number is
  safe and must keep working; the only trigger for refusal is the state the allowlist
  would leave the file in. This arm exists specifically to block that cheap fix.
- Refusal is scoped to the file it would have emptied. No other file in the same run
  may change its outcome, and no other entry in the same allowlist may be withdrawn
  — the per-line-not-per-file precedent established by GE-113c-3-v holds unchanged.
- 'VERIFICATION STANDARD, non-negotiable: every arm must be exercised through `scan_files`
  with real files on disk and a real `.security-allowlist` written into the same temporary
  root. Calling `_is_suppressed` with hand-built tuples discharges nothing — an audit
  in the sibling GE-113c-3 family found two criteria that passed unit-level tests
  while describing scenarios the real entry point can never produce.'
- 'Fixture reachability: use ordinary `.py` filenames. `scan_file` short-circuits
  an environment-named path to a single name-based finding and returns before any
  content rule runs, so a four-findings-across-four-rules fixture at such a path is
  unreachable. The environment-filename collapse is GE-123a''s subject, not this one''s.'
- Commit hot path. This code runs on every commit. The check must add at most one
  pass over (scanned files x allowlist entries), must not re-read or re-scan any file,
  and must not add any filesystem access beyond the single allowlist read `scan_files`
  already performs.
- 'SCOPE BOUNDARY so the coder does not chase the wrong surface: `check_secrets._filter_prose_findings`
  can still drop every entropy finding for a file AFTER `scan_files` has returned.
  That is a downstream prose exemption, not an allowlist suppression, and it is out
  of scope here. This guarantee is defined at the `scan_files` boundary.'
- 'ADR-001 parity: edit the canonical `templates/skills/security-scanner/scripts/scan_secrets.py`
  only and let `build.py` propagate. Never hand-edit the copies under `.claude/`,
  `.gemini/`, `.leafcutter/`, `EPIC-*/` or `worktrees/**`.'
- 'Doc parity: `templates/skills/security-scanner/SKILL.md` documents the suppression
  modes and must gain a short note that an entry which would leave a file with no
  rule able to report is declined for that file and announced, and that this is judged
  on effect and not on the shape of the line. Kept inside this AC because it is a
  two-sentence addendum to a section this change invalidates; if it grows beyond that,
  raise a follow-up documentation AC rather than expanding scope.'
- 'RED-FIRST LABELLING, so a TDD-order check does not misread the batch: arms 1 and
  2 are the red ones (measured 0 and 4 today; target 4 and 8). Arms 3 and 4 are declared
  REGRESSION GUARDS and are GREEN ON ARRIVAL by design (measured 3 findings each today).
  Green on arrival for those two is expected and is not a TDD-order violation; without
  them the criterion is satisfied by an implementation that stops honouring suppressions,
  or that bans the rule wildcard outright.'
```
