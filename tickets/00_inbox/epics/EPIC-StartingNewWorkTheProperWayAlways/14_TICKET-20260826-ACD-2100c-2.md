# A run that cannot reach a person waits with a durable record instead of proceeding or discarding

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `ACD-2100c-2` — A run that cannot reach a person waits with a durable record instead of proceeding or discarding — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `ACD-2100c-2`. Component: `ac-driven-dev`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given a run started with no channel by which a person can answer -- an unattended
  invocation with no interactive session attached,
And the run is started with its process working directory set to a git worktree
  of the project,
And drafted work from the steps before the decision point is present on disk,
When the run reaches a decision point,
Then no step after that decision point runs,
And a record naming the run and that decision point is present on disk after the
  process has exited,
And the run reports that it is waiting for an answer,
And the drafted work is still present on disk unchanged.
```

- [ ] AC-1: the run is started with its process working directory set to a git worktree
- [ ] AC-2: drafted work from the steps before the decision point is present on disk
- [ ] AC-3: no step after that decision point runs
- [ ] AC-4: a record naming the run and that decision point is present on disk after the
- [ ] AC-5: the run reports that it is waiting for an answer
- [ ] AC-6: the drafted work is still present on disk unchanged.

## Implementation Notes

```yaml
- The change must land under templates/. The deployed workflow is build output.
- The pause record must be durable before the process exits and must be written to
  the project's own store, not beside the caller. Both properties come from ACD-2100a-4;
  until it lands this behaviour degrades to a persist failure when run from a worktree,
  which is where the original loss was observed.
- '''Waiting'' must be established by the record on disk, not by the reported outcome.
  A run that reports waiting while having written nothing is not paused, it is lost,
  and it satisfies every assertion made against the return value.'
- No step after the decision point may run on any path out of an unreachable channel
  -- including a timeout path. A timeout that proceeds is the same loss with a delay.
- The drafted work must be left byte-identical. The pause must not normalise, rewrite
  or relocate anything the earlier steps produced.
- 'Must satisfy the repository error-handling policy: the record write is external
  I/O; a failed write must be logged at WARNING or higher and must not be reported
  as a successful pause.'
- 'Must be idempotent: reaching the same decision point twice for the same run leaves
  one record.'
```
