# KI-BO-20260908-1006 — A cross-epic `depends_on` is resolved against the worktree root instead of the ticket's own directory, so a satisfied prerequisite reads as unsatisfiable and withholds the ticket

> Found 2026-09-07 during the second `/build-feature` drive of
> `EPIC-TheNumberingGuaranteeHoldsAtEveryStage`. Filed 2026-09-28 after
> re-confirming against `origin/main` at `89613071` — 511 commits later, still
> unfixed.

- **Severity:** high
- **Status:** open — no AC
- **Occurrences:** 1 observed (`BP-900h-6`), but see "blast radius" — the condition
  is structural, not incidental
- **First seen:** 2026-09-07 · **Last seen:** 2026-09-28 (re-verified present)
- **Where:** `templates/workflows-js/build-feature.js` — the eligibility /
  prerequisite resolution backing `BO-100e-1-i`

**Symptom.** Ticket 10 (`BP-900h-6`) was withheld as ineligible, naming this prerequisite:

```text
/home/henzeh/.../worktrees/ge122-epic/../EPIC-DeploymentCompleteness/12_TICKET-20260817-BP-900h-1.md
```

Resolve that and you get `worktrees/EPIC-DeploymentCompleteness/…`, a sibling of the worktree
that has never existed. The ticket's frontmatter reads
`depends_on: [../EPIC-DeploymentCompleteness/12_TICKET-20260817-BP-900h-1.md]`, which is
relative to **the ticket's own directory** (`tickets/00_inbox/epics/EPIC-…/`). The correct
resolution is `tickets/00_inbox/epics/EPIC-DeploymentCompleteness/12_…md`. That file exists
and reads `status: done`. The prerequisite is satisfied; the driver cannot see it.

**Why it appeared only on the second drive, which matters for blame.** The first drive
dispatched this ticket normally. The eligibility gate that consumes resolved prerequisite
paths (`BO-100e-1` / `BO-100e-1-i`) landed on `main` between the two runs. So the path bug is
older than the gate and was harmless until something started reading the resolved path. A new,
correct guard made a latent defect load-bearing. **The gate is not at fault and should not be
reverted** — that is the tempting wrong fix, because reverting it would restore the appearance
of working while removing a real protection.

**It fails CLOSED, which is why this is high and not blocker.** An unresolvable prerequisite
withholds the ticket rather than releasing it. That is the right default. But the outcome is
indistinguishable in the run output from a genuinely unmet prerequisite: the operator reads
"waiting on BP-900h-1" and has no way to tell that BP-900h-1 is done. A stall that looks like
ordinary waiting is a stall nobody investigates.

**Blast radius.** Any `depends_on` entry that is relative and crosses out of its own epic
folder. The `../` form is the documented way to express a cross-epic edge and
`EPIC-TheNumberingGuaranteeHoldsAtEveryStage`'s own `Master_Plan.md` uses it. Every such edge
is currently unresolvable and every ticket carrying one is permanently withheld — silently,
and with a message that reads like normal scheduling.

**Countermeasure.**

1. Resolve `depends_on` entries against `dirname(ticket_path)`, not the worktree root.
2. Then add the distinction that would have surfaced this immediately: a prerequisite path
   that resolves to a **non-existent file** must be reported as UNRESOLVABLE, separately from
   "resolved, and not yet done". Those are different operator actions — fix the reference
   versus build the prerequisite — and the run currently renders them identically.

**Verification note for whoever picks this up.** Confirmed still present on `origin/main` at
`89613071` on 2026-09-28: `grep -c "dirname(ticket_path)\|path.dirname"` against
`templates/workflows-js/build-feature.js` returns 0. Check `build-ticket.js` too before
assuming this is build-feature-only — the two are declared twins and have already diverged
once (`KI-BO-20260907-0850`).

**Pattern:** a relative path resolved against the wrong base, silently, with a fail-closed
outcome that is indistinguishable from ordinary waiting.

**Related.** `BO-100e-1-i` (the eligibility criterion whose implementation surfaced this).
`KI-BO-20260907-0850` (twin-driver divergence — check `build-ticket.js` for the same bug).
