## Acceptance Criteria

```gherkin
Given a leftover that appears in the listing only because it was discovered on
  disk, with no registration entry referring to it,
When its removal is requested,
Then the request is accepted rather than rejected for want of a registration
  entry,
And afterwards no directory remains at the location it occupied,
And any partial registration state referring to it is gone,
And a second listing of the set does not contain it.
```

- [ ] AC-2: afterwards no directory remains at the location it occupied

## Implementation Notes

```yaml
- Absence of a registration entry must not be a disqualifying condition anywhere on
  the removal path. git worktree remove refuses for exactly that reason, so removal
  of a discovered entry cannot simply delegate to it -- and the alternative route
  must still run BO-4100c-1's verdict check (BO-4100e-2-i), not skip straight to deletion.
- Partial registration state referring to the leftover must be cleared too. A half-created
  workspace can leave an administrative record behind with no directory, and that
  record is itself a leftover that reproduces the symptom.
- Removal must be addressed to the discovered entry's resolved path and must not widen
  to siblings. BO-4100c-4-i's blast-radius constraint applies here unchanged and must
  not be re-derived.
- The second-listing assertion must be satisfied against a FRESHLY computed listing,
  not a cached one, since the discovery route reads the filesystem and a cache would
  report the removed leftover as still present or vice versa.
- Residual processes and open handles must be handled as in BO-4100c-4; a half-created
  workspace is not less likely to have one.
- Error handling follows the project error handling policy. A removal that partially
  completes must report failure, not success.
```
