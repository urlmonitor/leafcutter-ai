## Acceptance Criteria

```gherkin
Given a project with 19 workspaces made the old way -- some holding work that
  has not reached the shared project and some holding none -- and 2 entries in
  the project's workspace register that were started from a Linux shell and
  never finished,
When the cut-over is run,
Then each old workspace holding nothing unsent is retired: its folder is gone
  and its register entry is gone,
And each old workspace holding unsent work is either brought over as a
  workspace the one maker recognises, with that work intact, or left untouched
  and listed as needing a decision,
And the 2 unfinished entries are gone from the register, and nothing else is
  changed by their removal,
And afterwards the register of old-style workspaces lists only those left for a
  decision.
```

## Implementation Notes

```yaml
- 'The cut-over is reachable through the same door: a maker verb (e.g. `worktree.py
  migrate-legacy`) rather than a second script; if a separate script is chosen it
  must be a named deploy-manifest entry. It is the ONLY place allowed to run `git
  worktree` commands, and only against legacy entries.'
- 'Per legacy workspace, the BO-4100c-1 holds-work verdict decides: nothing unsent
  -> remove its folder and its registration; unsent work -> bring over as a marker-bearing
  clone ONLY when provably lossless (every commit sha present on the new line, uncommitted
  and untracked content byte-identical), otherwise leave untouched and list for a
  human decision (Q10: never retired while it holds unsent work).'
- Stuck registration entries made from another platform (the WSL 'locked initializing'
  admin entries) are removed individually; nothing else is touched by their removal.
- Offers a no-change preview of what it would do; its report is one JSON object listing
  retired, brought_over and needs_decision entries.
- The maker never reads stdin and never prompts; every decision it needs arrives as
  an argument of the request, so an unattended caller can never stall on it.
- 'Must handle errors per the project error handling policy: a condition the maker
  cannot classify is an error answer (code INTERNAL_ERROR) whose message names it
  -- never an ok answer, and never a traceback on stdout.'
- Proof runs the DEPLOYED maker -- the copy an install delivers, resolved through
  the shared test locator delivered by BO-4300f-4 -- as a separate process against
  real temporary git repositories with a real bare hub. No mock of git, no import
  of the maker module, no grep of its source (CLAUDE.md 'Gate / Workflow ACs -- Verify
  Behaviorally, Not by Grep'); a test never falls back to the templates/ source copy.
- 'Tests must not spawn the package''s own scripts/build.py (CLAUDE.md ''Tests must
  not spawn their own build.py''): the deployed maker comes from the shared deployed
  layout, and fixture projects carry a minimal stub build entry point that installs
  a real, rejecting hook in well under a second. A test that must mutate the package
  and build its own copy says so and justifies it in its ticket.'
- All temporary projects, hubs and workspaces live under the test's temp directory
  and run git with an isolated global and system config; afterwards the developer's
  own repository's branches, registered worktrees and local git config are unchanged
  (BO-4300f-4-i, F14, KI-TQ-012).
```
