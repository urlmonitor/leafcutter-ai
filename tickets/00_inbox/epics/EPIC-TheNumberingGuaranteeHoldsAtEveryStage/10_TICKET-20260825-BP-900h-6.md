## Acceptance Criteria

```gherkin
Given the consumer-simulation project from BP-900h-1 — built into a directory that started
  empty and held only a minimal skills_config.json, never a copy of this repository,
And with no opt-in documentation-seeding step performed, so the project holds only what a
  plain install leaves behind,
And that project initialised as a git repository with the deployed commit-time guards active,
When the job stages an ordinary change a new adopter would make and attempts a commit through
  the ordinary commit path — no skip flag, no environment override, no direct invocation of
  any guard script,
Then the commit completes,
And the job fails, naming the guard that blocked and the content it demanded, if any deployed
  guard blocks that commit over an artifact a brand-new project legitimately does not yet
  have,

And the job records which guards actually executed during that commit and reports that record
  as part of its output,
And a commit that completed because no guard ran is reported differently from a commit that
  completed because every guard that ran passed,
And the job fails when no guard executed at all, so a simulation in which the guards were
  never wired is not reported as a successful adopter experience,

And the job carries no continue-on-error, is not skipped on pull request events, and fails the
  pull request when the commit step fails.

Coverage note: this is the clause that separates building an install from using one. A job
that runs the install and inspects the resulting file tree cannot observe a guard that blocks
an adopter, because that guard only speaks when a commit is attempted — and the repository has
shipped seven consumer-install defects and four unregistered guards while every static
deployment check stayed green. Covered by performing the commit and asserting on what the
commit path did, plus a negative case: a deliberately adopter-hostile guard fixture must be
shown to turn this job red, or the job is a green step that proves nothing.
```

constraints:
- 'ATTEMPT A REAL COMMIT. Invoking a guard script directly, or running the hook framework
  against a file list, does not cover this: both prove the script works and neither
  proves the commit path reaches it. Initialise a git repository in the built project,
  stage a real file, and run the ordinary commit.'
- The staged change must be something a new adopter would actually have — the project's
  own skills_config.json, or a README the adopter writes. Do not stage an artifact
  from one of the numbered namespaces; that tests the guard's subject rather than
  the adopter's first commit.
- The project must be built from an empty directory and must NOT have the opt-in documentation-seeding
  step run. Copying this repository, or seeding it, reintroduces exactly the content
  whose absence is the condition under test.
- THE EXECUTED-GUARD RECORD IS NOT OPTIONAL AND IS THE HARD PART. A commit that completes
  because every guard is unregistered looks identical to a commit that completes because
  every guard passed, and that is the state four guards in this repository are in
  today. Capture which guards the commit path actually ran — the hook framework's
  own per-hook reporting is the natural source — and fail the job on an empty record.
- 'Demonstrate the job can go red before accepting it green: introduce a guard fixture
  that blocks over content a new project lacks and confirm a non-zero result. A green
  step that would stay green on an adopter-blocking guard is the phantom-done failure
  this branch exists to prevent, and the repository has shipped that exact shape in
  its own gate code.'
- No continue-on-error, and no condition that skips the step on pull_request events.
  Registering this job among the required checks is BP-900h-3's scope and is not re-decided
  here; this AC only requires that the new step cannot pass while the commit fails.
- 'ONE ENTRY POINT FOR THE JOB AND ITS TEST (IT-PO 2026-08-25). The workflow step
  must not inline the logic as a shell block: put the stage-and-commit-and-record
  behaviour in a single invocable script (scripts/ci/ is the established home for
  merge-gate-only tooling and is correctly source-only per BP-1000d-1), and have the
  ci.yml step call it with no logic of its own beyond arguments. Otherwise every unit
  test written for this AC exercises a COPY of the job rather than the job, and the
  step itself stays unverified — which is the same one-surface-tested-other-surface-shipped
  shape as a guard registered in the manifest the install ignores. The workflow step
  and the test must reach the same code.'
- THE EXECUTED-GUARD RECORD IS A CAPTURED OBSERVATION, NOT A DERIVED ONE. Read which
  guards ran from what the commit path itself reported during the commit — never by
  re-parsing the deployed registry and assuming everything listed executed. A record
  derived from the registry is exactly as green on an unwired install as on a wired
  one, which reproduces the defect the record exists to detect. If the hook framework's
  per-hook reporting is unavailable in the job's environment, that is a blocker to
  raise, not a licence to derive the record.

  that ran passed, no guard ran at all, and a guard blocked — must be three visibly
  distinct job outputs, with the guard names printed in the first two cases. A job

  diagnostic the criterion is actually asking for.

  surrounding job behave differently, and must not be mistaken by BP-900h-2's idempotency
  comparison for install drift. Sequence the step after the idempotency assertions
  or isolate its artefacts explicitly — do not leave the interaction unstated.
