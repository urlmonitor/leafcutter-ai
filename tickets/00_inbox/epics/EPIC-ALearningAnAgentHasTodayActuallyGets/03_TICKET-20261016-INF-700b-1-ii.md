# A capture step that cannot complete leaves a countable failure record, not only a warning

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `INF-700b-1-ii` — A capture step that cannot complete leaves a countable failure record, not only a warning — so that the acceptance criterion is satisfied.

## Context

Scope decision (epic refinement, 2026-10-16): the emitter extension that the Implementation Notes defer to "a python-coder follow-up" is IN SCOPE for this ticket. python-coder adds one additive `missing_target` payload field to `templates/skills/agent-telemetry/scripts/emit_event.py` (existing callers and records stay valid; `outcome` is not overloaded); llm-expert changes the signoff section 7 proceed-anyway branch to call that writer.

Superseded 2026-10-21 by the INF-700b-1-i architect-review (ticket 02): ticket 02 owns the `emit_event.py` change (event `capture_attempt`, closed outcome set `{recorded, nothing-to-record, failed}`, additive `missing_target` key on every record). This ticket no longer edits `emit_event.py`. It only adds the agent-run variant `--outcome failed --missing-target '<literal path>'` to the capture step, and it depends on 02. A failure record is writable only while the telemetry stream is; when the shared declaration is unusable, both writers refuse and the failure stays stderr-only. Ticketless v3 agents emit a null ticket path.

## Acceptance Criteria

```gherkin
Given a phase agent holds a learning and reaches an instruction in the
  knowledge-capture step whose target is missing at the moment it runs,
And the step is specified to let the agent proceed rather than fail its run,
When the agent takes that proceed-anyway branch,
Then a durable failure record is written that names the agent, the piece of
  work it was finishing, and the specific target that was missing,
And that record survives the end of the agent's process and can be read by a
  later count without replaying the run's console output,
And the agent still returns its primary output and its sign-off is not
  blocked,
And a run in which capture completed produces no such failure record,
And a period containing one such failed run is distinguishable from a period
  containing one run that simply had nothing to record.
```

## Implementation Notes

```yaml
- SINK BOUNDARY (preserves INF-400c-4-iii's invariant). The failure record must NOT
  be written to the knowledge-emission sink. It carries no learning, so a reader that
  finds it there would either count it as backlog or bucket it as no-learning-text
  — both wrong, and the second would make it invisible to INF-700c-2's resting-state
  rule. It belongs on the operational telemetry stream alongside the capture-attempt
  records of INF-700b-1-i.
- 'The record must be written by a deployed, tested writer, never composed free-hand
  by the agent in an ad-hoc shell append. Evidence that free-hand appends corrupt
  the stream: line 19 of debugging/logs/agent_telemetry.jsonl is the bare fragment
  `</content>` and four further lines are `{"probe": "pre-drive-check"}` writability
  probes, all produced by hand-composed appends into the same file.'
- 'SURFACE CONSTRAINT — read before estimating. The only writer currently deployed
  for this stream, templates/skills/agent-telemetry/scripts/emit_event.py, emits a
  fixed payload of exactly { phase, outcome, retry_count } and has no field that can
  carry the name of the missing target. `outcome` must not be overloaded as a free-text
  field. Satisfying this AC therefore needs either an additive payload field on that
  writer or a second writer — either way a Python surface that llm-expert does not
  own. See the caveat recorded in amended_by: do not silently widen this AC into a
  Python change; the emitter extension is a python-coder follow-up.'
- One failed attempt produces at most one failure record. A retried attempt is a new
  record with its own timestamp, not an amendment to the previous one, so a count
  over a period is a count of attempts rather than of distinct agents.
- The failure-record write is itself best-effort and must never block the agent's
  sign-off or alter its primary output. Its own failure must be reported on stderr
  — a silent failure to record a silent failure is the same defect one level up.
- 'The record must name the missing target specifically enough to act on: the literal
  path or skill name the instruction asked for, not a category such as ''skill unavailable''.
  The 2026-06-to-08 silence is exactly the failure this clause exists to make legible,
  and ''a warning was logged'' is what it produced.'
- Distinguishability is a property of the record's outcome field, not of a count.
  The failed record and the nothing-to-record record must differ by a value from the
  closed outcome set defined in INF-700b-1-i's delivers_to contract, so INF-700b-3
  partitions rather than infers.
```
