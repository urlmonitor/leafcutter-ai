# The startup check reads the registry itself instead of asking an agent to read it

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `ACD-2100b-5` — The startup check reads the registry itself instead of asking an agent to read it — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `ACD-2100b-5`. Component: `ac-driven-dev`. Assigned agent: `python-coder`. Estimated complexity: `L`. Complexity: `high`.

## Acceptance Criteria

```gherkin
Given an environment in which no agent can be dispatched -- every dispatch
  attempt fails immediately with a transport error,
And an agent registry that is present readable and lists the agent the route
  uses to create the authoring worktree with permission to run repository
  commands,
When a run starts and reaches the startup check,
Then the check completes with the permitted verdict and the run proceeds past it,
And the run's record of what it dispatched contains no dispatch made on behalf of
  the check,
And repeating the run with dispatch available reaches the same verdict.
```

- [x] AC-1: an agent registry that is present readable and lists the agent the route
- [x] AC-2: the check completes with the permitted verdict and the run proceeds past it
- [x] AC-3: the run's record of what it dispatched contains no dispatch made on behalf of
- [x] AC-4: repeating the run with dispatch available reaches the same verdict.

## Implementation Notes

```yaml
- The check must land as a real executable pre-flight script invoked by the plan-feature
  skill BEFORE the workflow is invoked -- not as prose instruction in SKILL.md, and
  not in the workflow body. The E2 engine contextifies the workflow body with exactly
  the injected globals agent, parallel, pipeline, phase, log, args, workflow and budget,
  with no module loader and no filesystem primitive reachable (ADR-030; canonical
  statement in the unit_tests/_workflow_engine_harness.py docstring, ENGINE FIDELITY
  section). A workflow body therefore cannot read config/agent_registry.json at all
  -- the agent round-trip exists precisely because the sandbox has no filesystem.
  The skill runs in the main agent loop with real Bash and Read access, so a script
  invoked from there can perform the local read.
- All source changes must land under templates/ and scripts/. The deployed workflow
  and the deployed skill are build output.
- The verdict must be a function of the registry contents alone. It must be identical
  whether dispatch is available or not -- 'skip the check when dispatch is unavailable'
  is a fail-open regression wearing this record's clothes and is explicitly forbidden.
  There must be no code path anywhere in the check that branches on dispatch availability.
- The startup path must reach this check and pass it with no network available.
- 'Removing the round-trip must not remove the halt: the four outcomes ACD-2100b-1
  through -3 specify still stop the run, and ACD-2100b-4 still holds over them. Moving
  the check into the skill must additionally not open a bypass -- the workflow must
  fail closed when no pre-flight verdict reaches it. A caller that invokes the workflow
  directly, for example Workflow({scriptPath: ''.leafcutter/workflows/plan-feature.js''}),
  which is a real and currently-used invocation path, supplies no verdict and must
  be stopped before any authoring agent is dispatched, with a report that names the
  missing pre-flight rather than asserting a permission cause the run never established.'
- The verdict must cross from the pre-flight into the workflow through args -- the
  only injected global that carries caller-supplied data -- and must carry enough
  structure to keep the outcomes ACD-2100b-1, -2 and -3 own distinguishable from one
  another. A single boolean collapses them and re-creates the defect those records
  exist to fix.
- The registry-location semantics must not fork. The pre-flight must resolve the registry
  the same way ACD-2100a-1 and ACD-2100a-3 already established -- repository-anchored,
  so it reaches the project's real registry when the run starts inside a linked git
  worktree that holds no .leafcutter/ of its own -- rather than a second, independent,
  cwd-relative resolution.
- If a helper that dispatches for this purpose remains in the source for another caller,
  this behaviour is not satisfied by its absence from the file -- what must be observable
  is that no dispatch is made on the check's behalf during a run.
- 'Must satisfy the repository error-handling policy: the local read replaces a network
  call, so its failure paths are the ones ACD-2100b-1 and ACD-2100b-2 own. Those are
  external I/O and must be wrapped, must name a specific exception type, and must
  never be swallowed into an unqualified denial.'
- A new script under scripts/ that the DEPLOYED skill invokes must be added to the
  build deploy manifest in the same change. The deployed skill runs against the deployed
  layout, so a script that exists only in the source tree makes the pre-flight fail
  at runtime while every source-tree test passes.
- Must not add a per-run cost beyond a single local file read -- this record removes
  latency from startup and must not reintroduce it elsewhere.
```
