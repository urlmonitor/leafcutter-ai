## Acceptance Criteria

```gherkin
Given the contested requirement identifier and the five twice-held work items have been
  repaired,
When the whole-collection uniqueness pass is run over the repaired collection with no
  exemption list, no allowlist, and no known-bad entries configured for any namespace,
Then it terminates with a passing result for all four namespaces,
And it states, per namespace, the number of artifacts it inspected, and each count equals the
  number of artifacts actually present in that namespace,
And no configuration exists anywhere that would cause a contested number to be reported as
  acceptable,

And the artifacts that carry no number at all are unchanged in name and in location — they are
  not ambiguous, they break no reference, and they are deliberately outside the repair,

And when a contested number is then reintroduced into any one of the four namespaces, the same
  pass over the same collection terminates with a failing result naming it — so the passing
  result above is evidence that the collection is clean, not evidence that the pass is inert.

Coverage note: the final clause is the load-bearing one and must be executed, not reasoned
about. A pass that reports success over the repaired collection proves nothing on its own,
because a pass that inspects nothing reports the same thing. Only the reintroduce-and-re-run
pair distinguishes a clean collection from a dead check.
```

## Implementation Notes

```yaml
- Run the REAL gate, in the deployed layout, by the same entry point the commit-time
  and build-time stages use. A bespoke audit script written for this verification
  would prove that a script can count correctly, not that the guard that will hold
  the line afterwards works — and the guard is the artifact under test.
- The reintroduce-and-re-run pair must be executed as one test, in all four namespaces,
  with the reintroduced collision REMOVED afterwards. It is the only clause here that
  a broken implementation cannot satisfy, and it is the mutation check for the whole
  tree. Running it in one namespace leaves the other three unproven, which is the
  same gap as a pass that inspects nothing.
- The inspected counts must be asserted as EQUAL to independently-computed artifact
  counts for each namespace, not merely as non-zero. A non-zero assertion passes on
  a pass that reads one file per namespace, and the whole point of the count is to
  detect a partial walk.
- '''No configuration exists anywhere that would excuse a contested number'' must
  be checked against the actual configuration surfaces, enumerated: the enrolment/identifier
  rule data GE-122b-1 introduces, the `hooks_manifest.hooks` entry (an `enabled: false`
  flag there silently removes a hook from `.pre-commit-config.yaml` at build time),
  the ci.yml job''s own conditions, and any skip or exemption argument on the gate''s
  command line. An `enabled: false` manifest entry is the most plausible way this
  clause is violated without anyone writing an allowlist.'
- The unchanged-artifacts clause must be asserted by NAME AND LOCATION over the eleven
  unnumbered diagrams, not by count. A count is preserved by renaming one of them,
  which is exactly the tidy-up the clause exists to fail.
- This AC is the tree's exit gate and must run AFTER GE-122e-1 and GE-122e-2, and
  BEFORE GE-122d-2 makes the CI gate required — that ordering is what stops a required
  gate from failing every merge on pre-existing drift.
- The verification must be re-run at merge time, not only when it is written. The
  collection moves continuously; a pass recorded three weeks before the merge is evidence
  about a different collection.
```

**[H-1] `scripts/build_placeholder_detection.py` — case-sensitive PLACEHOLDER/"Replace
with"/FIXME patterns miss lowercase and mixed-case genuine markers (false negative).**

`_MARKER_RULES` compiles `\bTODO\s*:` and `<!--\s*QUESTION\s*:` with `re.IGNORECASE`, but
`\bPLACEHOLDER\b`, `\bReplace with\b`, and `\bFIXME\s*:` are compiled with **no**
`re.IGNORECASE` flag at all — confirmed by direct read of the `_MARKER_RULES` list (lines
121-139) and confirmed behaviourally: a file whose sole content is `placeholder: fill this in`
(lowercase) or `fixme: this needs attention` (lowercase) returns `[]` from
`scan_for_placeholders` — zero hits, even though both are structurally exactly the shape
(bare marker + immediate colon) the validators are designed to accept. Since this helper backs
`documentation-verifier`'s Step 6a fail-closed placeholder gate — the mechanism that exists
specifically to catch a doc that was announced but never written — a scaffold left in lowercase
("please placeholder: fill in your value", "fixme: needs owner review") sails through silently.

This is not merely undiscovered: `docs/known-issues/build-orchestration.md`'s KI-BO-3 entry
(marked **FIXED**) explicitly names "selective case-sensitivity" as one of the mechanisms that
"pins **both** directions" of the false-positive/false-negative tension, and claims verification
"in both directions" — but the six MUST-DETECT regression cases it lists
(`TODO: write this`, `PLACEHOLDER`, `<!-- PLACEHOLDER -->`, `TODO: Replace with…`,
`<!-- QUESTION: … -->`, `FIXME: broken`) are all written in the exact uppercase casing the
selective-case-sensitivity change requires to match at all. No lowercase or mixed-case variant
was ever tried, in that verification or in
`unit_tests/test_build_placeholder_detection_context_discrimination.py` (whose own SCOPE NOTE
explicitly limits itself to the false-positive/precision direction and does not test this floor).
The doc's "verified in both directions" claim is not actually true for the case-sensitivity
mechanism — case-sensitivity can only ever narrow (help precision), never widen (help recall);
narrowing to a specific case is a new avenue for exactly the false-negative failure the same
paragraph says is "strictly worse."
