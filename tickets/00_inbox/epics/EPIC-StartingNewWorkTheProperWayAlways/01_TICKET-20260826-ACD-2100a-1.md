# The worktree step runs the copy of the setup script that belongs to the repository being worked on

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `ACD-2100a-1` — The worktree step runs the copy of the setup script that belongs to the repository being worked on — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `ACD-2100a-1`. Component: `ac-driven-dev`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given two copies of the worktree setup step exist on the machine -- one inside
  the repository the run will operate on, and one in an untracked parent
  directory that is not itself a repository,
And the two copies differ in an externally observable way, so which one ran can
  be told from the run's output alone,
And the run is started with the process working directory set to that untracked
  parent directory,
When the route creates the authoring worktree,
Then the copy that executes is the one inside the repository being operated on,
And the authoring worktree exists on disk afterwards as a working copy of that
  repository with the expected branch checked out,
And the run's own record of the command it issued names an absolute location
  inside that repository rather than a location relative to the working
  directory.
```

- [x] AC-5: the run's own record of the command it issued names an absolute location

## Implementation Notes

```yaml
- The change must land under templates/. A repair applied to the deployed copy under
  .leafcutter/ is regenerated away by the next build and does not count as delivered
  (see ACD-2100d).
- The resolved script location must be absolute at the point it is handed to the process
  launcher -- the run must not rely on the caller's working directory to complete
  the path.
- The run's own diagnostic record must carry the resolved absolute location it invoked
  so a wrong-copy execution is diagnosable after the fact without re-running.
- The resolution must be shared with the other four cwd-relative sites (ACD-2100a-3
  and ACD-2100a-4) rather than patched here alone; a per-site fix is what left three
  sites standing after the known issues were filed.
- 'Must satisfy the repository error-handling policy: the resolution is external I/O,
  so a failure to resolve must raise a typed error or log at WARNING and re-raise
  -- never be swallowed into a silent fallback.'
- Must not change the setup step's existing command-line contract; callers that already
  pass an explicit location must behave exactly as they do today.
- The startup path up to and including this step must complete with no network available.
```
