# The rooted commit is checked after the workspace exists, not predicted before it

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `BO-4100a-2` — The rooted commit is checked after the workspace exists, not predicted before it — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `BO-4100a-2`. Component: `build-orchestration`. Assigned agent: `python-coder`. Estimated complexity: `M`. Complexity: `medium`.

## Acceptance Criteria

```gherkin
Given a staleness check run before creation has reported the starting point
  as current,
And creation has then produced a workspace whose branch is rooted at a commit
  other than the shared main-line tip that creation targeted,
When creation finishes,
Then creation reports failure rather than success,
And the workspace is not offered to the caller as ready to work in,
And the failure states both the commit the branch is actually rooted at and
  the shared main-line tip it was required to be rooted at.
And given the branch is rooted at exactly the targeted shared main-line tip,
  When creation finishes, Then creation reports success.
```

- [ ] AC-1: creation has then produced a workspace whose branch is rooted at a commit
- [ ] AC-2: creation reports failure rather than success
- [ ] AC-3: the workspace is not offered to the caller as ready to work in
- [ ] AC-4: the failure states both the commit the branch is actually rooted at and
- [ ] AC-5: given the branch is rooted at exactly the targeted shared main-line tip

## Implementation Notes

```yaml
- The verdict must be computed from the CREATED WORKSPACE's own HEAD, read back after
  creation, never from the commit-ish handed to git worktree add. _compute_base_commit_report
  already does this read on the fast-lane path (BO-2400f-13-iv) but only REPORTS it;
  here the same read must GATE the outcome.
- No pre-creation staleness check may be added, strengthened or relied on to satisfy
  this record. An existing pre-check may remain, but it must not be what produces
  the verdict -- a check that runs before the thing it checks exists can only ever
  verify an input.
- The post-condition must run on every creation path, including the reconnect/reuse
  path where an existing branch is checked out or force-reset rather than freshly
  cut. That is the path on which a stale root is most likely and the one the fast-lane
  reconnect already demonstrates.
- On failure the success payload must not be emitted and the workspace must not be
  offered as ready to work in. Whether the failed workspace is removed or left for
  BO-4100e to account for is the implementer's call; emitting success is not.
- Both commits must be carried as separate machine-readable values (actual rooted
  commit, required shared tip), not only embedded in a sentence, so a caller can act
  without parsing prose.
- Both the canonical template and its scripts/ build output must carry the change
  (ADR-001).
- Error handling follows the project error handling policy; the post-condition itself
  failing to read HEAD is a failure, never a pass.
```
