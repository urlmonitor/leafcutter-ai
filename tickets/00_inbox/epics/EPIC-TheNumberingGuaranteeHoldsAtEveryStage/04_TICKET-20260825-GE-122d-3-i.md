# A defect in the guard itself is announced but does not hold an unrelated commit hostage

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `GE-122d-3-i` — A defect in the guard itself is announced but does not hold an unrelated commit hostage — so that the acceptance criterion is satisfied.

## Acceptance Criteria

```gherkin
Given the uniqueness pass raises an internal error that is NOT a failure to read the
  collection — a defect in its own reporting code, raised after every artifact in every
  namespace has been successfully read and compared,
When the pass runs at the commit-time stage,
Then it does not report an ordinary clean success,
And its output states that the check terminated abnormally and names the point it reached,
And the commit is nonetheless permitted to complete, because a defect in the guard must not
  hold an unrelated change hostage,

And when the same internal error occurs at the shared-build stage, the build fails, because
  there the guard's own health is in scope and no author is waiting on it,

And given instead the condition described in GE-122d-3 — an artifact in the collection that
  could not be read — the commit-time stage BLOCKS, and this criterion's permission to proceed
  does not apply to it.

The line this criterion draws: the pass either did or did not manage to inspect the whole
collection. If it did and then fell over on the way to reporting, the collection has been
examined and the author may proceed. If it did not, nothing has been established and the author
may not. Both cases are announced; only the second blocks at commit time.

Coverage note: covered only by a test that induces each of the two conditions distinctly and
asserts the two different dispositions at the commit-time stage. A test that induces only one
cannot show the boundary holds, and a boundary is what this criterion is.
```

## Implementation Notes

```yaml
- The disposition must be DERIVED FROM THE READ COUNTS GE-122d-3 already requires,
  not from the exception type. 'Every namespace completed its read, then something
  failed' is a state the pass knows; 'this exception class means internal defect'
  is a guess that a new exception type silently invalidates. Deciding on exception
  class is the way this boundary quietly inverts eighteen months from now.
- Four outcome values are now in play — clean, contested, could-not-establish, terminated-abnormally
  — and the commit-time disposition differs between the third (block) and the fourth
  (proceed). The return type must express all four; a boolean or an exit-code-only
  contract cannot, which is why GE-122d-3 requires a value-typed outcome.
- The abnormal-termination path must name the point the pass reached, which means
  the pass has to record progress as it goes rather than reconstructing it from a
  traceback. A traceback is not a statement of what was established, and this criterion's
  whole purpose is to say what was established.
- This is the exact place where two standing rules of the component meet, so the implementation
  must not collapse them into a single try/except at the top of the entry point. A
  blanket handler makes every failure look like an internal defect and lets the unreadable-collection
  case through — the precise inversion the BA's notes warn about.
- 'Reproduce the component''s established fail-open tail shape for the proceed path
  — specific exception type, `noqa: BLE001` where the blanket catch is deliberate,
  stderr-prefixed announcement, clean stdout so the announcement is never mistaken
  for a violation — rather than inventing a new one. `check_ac_governance.py`''s tail
  is the reference implementation.'
- Error handling per CLAUDE.md Rules 1-4 applies to the guard's own code as much as
  to the collection it reads; a handler on this path must log at WARNING or above,
  never pass silently.
```
