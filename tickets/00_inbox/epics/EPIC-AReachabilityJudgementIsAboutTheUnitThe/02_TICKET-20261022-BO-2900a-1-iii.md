# A refusal is armed only after the rule has been shown to return the right verdict on every proof shape the store already contains

## Actor / Goal

## Acceptance Criteria

```gherkin
Given a reachability rule that announces its findings without refusing,
  And a corpus of proofs assembled from the proof files the store already
    records as covering criteria — not written for the occasion — containing
    every shape those proofs are actually written in, including a proof that
    drives the unit as a separate program it launches and a proof whose test
    needs something supplied by the suite that normally runs it,
When the rule is exercised over every proof in that corpus,
Then for each proof the rule either runs it and returns the verdict a reader of
  that proof would give, or returns no verdict for it,
  And no proof in the corpus is answered with a refusal the rule reached
    without having watched that proof run,
  And the rule keeps announcing without refusing for as long as any proof in
    the corpus is still answered wrongly, so arming the refusal is a
    consequence of the corpus being satisfied and not a separate decision
    anyone can take,
  And the exercise reports how many proofs the corpus held and how many were
    answered each way, so a corpus that examined nothing cannot be mistaken
    for a corpus that found nothing,
  And a corpus that resolves to no proofs at all is reported as a failure of
    the exercise, never as the corpus being satisfied.
```

## Implementation Notes

```yaml
- CORPUS MEMBERSHIP IS DERIVED, NEVER AUTHORED. Members are resolved by walking the
  AC store and collecting the proof files named by covered_by / covers-tagged functions
  that already exist on disk. No member may be a file the exercise itself creates,
  and no member may be reached through a hand-maintained list of paths. A member is
  identified by (proof file path, test function name) — the same pair the covers tag
  records.
- 'SHAPE COVERAGE IS A GATE, NOT A STATISTIC. The corpus must resolve at least one
  real member in each of the five measured shapes: unittest method taking no arguments
  (698 in the store), module-level function taking pytest fixture arguments (91),
  unittest method taking fixture arguments (38), module-level function taking no arguments
  (35), and the subprocess-CLI shape. A shape that resolves zero members is a FAILURE
  of the exercise, identical in effect to an empty corpus — not a shape reported as
  trivially satisfied.'
- ZERO RESOLVED MEMBERS EXITS NON-ZERO AND PRINTS NO SUCCESS SHAPE. This repository
  has three recorded cases of a defence that examined nothing and reported clean (a
  bare-directory glob matching no files for eight days, a pre-drive check reading
  a path that never existed, a merge audit comparing against a stale ref). Model the
  reporting on scripts/ac_store/validate_ac_schema.py, which states the count it inspected
  in its own success line for exactly this reason.
- THE EXPECTED VERDICT PER MEMBER MUST COME FROM SOMETHING OTHER THAN THE RULE UNDER
  TEST. Each member carries a declared expectation — reached / not reached / no verdict
  — recorded in a corpus manifest authored by a reader of that proof. An exercise
  that derives the expectation from the rule's own output is tautological and satisfies
  itself on a rule that is wrong in both directions, which is the state the rule is
  in today.
- THE ARMING CONDITION MUST BE DERIVED FROM THE REPORT AT RUNTIME, NOT A CONSTANT
  AN AUTHOR CAN FLIP. The refusal path in _done_proof_entry_point_gate.py must be
  reachable only when the exercise's own persisted artifact records a non-empty corpus,
  every shape represented, and zero wrong verdicts. An env var, config key, boolean
  literal or code comment that arms the refusal independently of that artifact is
  a violation of this AC's central clause — arming is a consequence of the measurement,
  not a decision anyone takes.
- 'THE REPORT STATES ABSOLUTE COUNTS PER SHAPE: members resolved, answered correctly,
  answered with no verdict, answered wrongly — plus the totals. Percentages alone
  are not acceptable; a percentage of an empty denominator is the failure shape this
  clause exists to exclude. The counts for the report-only population BO-2900a-1-ii
  announces must reconcile against the corpus, so the two measurements can be compared.'
- NO VERDICT IS AN ACCEPTABLE ANSWER; A REFUSAL REACHED WITHOUT WATCHING IS NOT. A
  member the observation reports as unwatched (BO-2900a-2-ii) counts as 'no verdict'
  and does not block arming. A member answered with a refusal while its observation
  record says the run was unwatched or the question was undecidable counts as WRONG,
  however plausible the refusal looks.
- THE EXERCISE IS A STANDALONE SWEEP, NOT A GATE. It must be runnable as its own command
  and must NOT be added to the per-AC done-proof path, the check_done_proof pre-commit
  hook, or the required CI done-proof job — at 862 candidate covers-tagged functions
  it cannot run per commit. Two runs over an unchanged tree must produce byte-identical
  report output so a diff between runs is meaningful.
- READ-ONLY AGAINST THE STORE. The exercise must not write work_status, readiness,
  covered_by or implemented_by on any AC, must not modify any proof file, and must
  write nothing outside its own report and manifest paths. Re-running it must be safe
  on a dirty tree.
- DEPLOY MANIFEST. Any new module this exercise adds that done_proof.py or _done_proof_entry_point_gate.py
  imports must be added to build_ac_store's deploy_map in scripts/build_phases_ac_store.py
  in the same change, or the deployed check_done_proof hook and the required CI done-proof
  job crash with ModuleNotFoundError.
```
