# No workflow body asks an agent to make a workspace in its own words

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `BO-4300a-1-ia` — No workflow body asks an agent to make a workspace in its own words — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `BO-4300a-1-ia`. Component: `build-orchestration`. Assigned agent: `python-coder`. Estimated complexity: `L`. Complexity: `high`.

**Field note (2026-10-02, single-ticket `/build-feature` runs).** Two defects seen today come
from the free-form worktree prompt this ticket removes. `build-feature.js` still tells the
`worktree-agent`: "Open a NEW git worktree at the EXACT location ... Bootstrap it (copy/symlink
.leafcutter so hooks are present)".
- **The agent chose its own location.** Once, the agent opened the worktree on a different
  branch and path (`feature/ticket/...md`). The run correctly aborted with
  `worktree-location-mismatch` (BO-4000a), but the agent's empty worktree and branch were left
  behind and had to be removed by hand.
- **The bootstrap never builds.** The "copy/symlink .leafcutter" step never runs
  `scripts/build.py --target-dir <worktree>`, which is the step `setup_ticket_worktree.py`
  runs. As a result:
  - there is no `scripts/commit_guardian` and no `scripts/feedback`;
  - phase sign-offs record `feedback-id: (submit-failed)`;
  - the commit phase fails until build.py is run by hand.
- **The copy spreads stale files.** The copy also carries the main checkout's stale gitignored
  outputs (`.claude/commands/leafcutter.md`, `.gemini/workflows/leafcutter.md`) into the new
  worktree, so `check-output-drift` fails with `gaps=2`.

With this ticket, the maker becomes the only way to make a workspace, and BO-4300c-1 adds the
check that the build finished successfully. Together they remove all three defects, so no
separate ticket was filed for them.

## Acceptance Criteria

```gherkin
Given each workflow that needs a workspace is run with a recording stand-in in
  place of every agent it dispatches,
When the workflow reaches the point where it needs a workspace,
Then it either receives the workspace maker's answer as part of its input, or
  issues exactly one request, which asks for the workspace maker to be run
  unchanged and its answer relayed word for word,
And no dispatched request asks an agent to create, copy, set up, link or
  repair a workspace by steps of the agent's own choosing,
And no workspace request is dispatched to an agent that is not permitted to
  run commands.

Given every workflow the project delivers, and the agents' permissions to run
  shell commands as they stand when the check runs,
When every step of every workflow that asks an agent to run a shell command is
  checked -- including steps that a single run of the workflow does not reach --
Then no such step is sent to an agent that is not permitted to run shell
  commands, and an agent with no stated permission counts as not permitted,
And each offending step is reported by workflow, step, agent and the command it
  asks for,
And a workflow added later, or a change to an agent's permission, is covered
  by the same check without anyone editing a list,
And when an agent asked to run a shell command declines, answers in prose, or
  answers without a result, the workflow ends with an error that quotes the
  answer received, and no later step of that workflow is dispatched -- a
  refusal is never taken as the step having run.
```

## Implementation Notes

```yaml
- 'Workflow bodies run in the E2 engine with no filesystem or process access (ADR-030).
  They reach the maker only through (a) args.workspace -- the maker''s JSON object
  passed verbatim by the entry command or skill (BO-4300a-1-ib) -- or (b) exactly
  one agent() dispatch, carrying a result schema, to an agent whose registry entry
  has permits_shell: true, instructing it to run one exact absolute command unchanged
  and return stdout verbatim. Never status-checker (permits_shell: false), never free-form
  set-up steps.'
- 'Remove every free-form workspace instruction from the workflow bodies: build-feature.js''s
  ''Open a NEW git worktree ... Bootstrap it (copy/symlink .leafcutter ...)'' prompt,
  the resolver and branch-check steps plan-feature.js sends to status-checker, finalize-feature.js''s
  `git worktree add/remove` and `rm -rf` prompts, and fast-lane-ship.js''s create
  prompt. Line numbers in the analysis are hints; verify against HEAD.'
- A workspace dispatch's prompt carries only the exact absolute maker command and
  the instruction to run it unchanged and relay stdout verbatim; the agent's reply
  is parsed with the BO-4300c-2 schema.
- 'ONE SHARED DISPATCH HELPER (duplication audit C3/C2): the workspace dispatch is
  issued only through the dispatch helper in the WORKSPACE-ANSWER block delivered
  by BO-4300c-3 (build-inlined, byte-identical in every consuming workflow). No workflow
  builds its own workspace dispatch or its own reply parsing.'
- 'Reply handling applies to EVERY step in every workflow that asks an agent to run
  a shell command, not only workspace dispatches: the dispatch carries a result schema;
  a decline, a prose reply, a non-JSON reply, or a reply without the result the step
  asked for (for the workspace dispatch: JSON without status) is an error that ends
  the workflow, and the error quotes the reply received. No later step of that workflow
  is dispatched after such a reply, and a refusal is never taken as the step having
  run. For the workspace dispatch there is additionally no fallback to the current
  checkout, the epic folder or the start folder. The rule is enforced in one shared
  place in the workflow runtime (not re-implemented per workflow), so a new workflow
  inherits it.'
- 'REPO-WIDE SHELL-DISPATCH LINT (duplication audit C2; covers EVERY workflow, not
  only workspace dispatches): a test fails when any agent dispatch in any templates/workflows-js/*.js
  whose prompt instructs the agent to run a shell command names an agentType whose
  config/agent_registry.json entry does not have permits_shell: true (absent counts
  as not permitted). The workflow set is enumerated from the directory and the registry
  is read at test time -- no hard-coded lists. What counts as "a prompt that runs
  a shell command" is one declared, reviewed rule held in one place in the test (e.g.
  the prompt, including template-literal fragments, names a command line starting
  with git, gh, python/python3, node/npm, pytest, rm, mv, cp, bash/sh or pwsh), and
  the test carries a self-check proving the rule catches a known status-checker git
  dispatch. Each failure names the workflow, the dispatch label or location, the agentType
  and the command seen.'
- 'Blast radius of the lint (verified 2026-09-25): 62 dispatches target status-checker
  (permits_shell: false), and only worktree-agent has permits_shell: true -- commit,
  test-runner, python-coder and others have no permits_shell field at all. The lint
  therefore goes red on today''s tree. Making it green is in scope of this record:
  each offending dispatch is moved to a shell-permitted agent, or the registry entry
  of an agent that genuinely runs shell by charter gains permits_shell: true with
  that charter change reviewed; no dispatch is exempted by name.'
- 'Commit spelling (KI-CG-20260925-commit-delegation-hook-misses-git-dash-c): no workflow
  prompt this record touches spells a commit as `git -C <path> commit`; commits go
  through the commit agent per CLAUDE.md Commit Delegation.'
- 'The set of workflows under test is every workflow in the deployed workflow set,
  and the set of shell-permitted agents is read from config/agent_registry.json (permits_shell:
  true) at test time -- neither is a hard-coded list, so a new workflow or a changed
  registry entry inherits the check.'
- Workflow edits are made in templates/workflows-js/*.js and reach .claude/workflows/
  only through the build; the deployed copy is what the tests run.
- Proof runs the workflow under unit_tests/_workflow_engine_harness.py -- the deployed
  copy the build produces, so the build's workflow transform is exercised -- with
  label-scripted agent replies, and asserts on the RECORDED dispatch list, never on
  workflow source text. The harness must be able to model a workspace step that declines
  its task, answers in prose, answers exit 0 with a non-JSON path, or answers JSON
  without status (F13), and any other shell-running step that declines, answers in
  prose or answers without its result; extending the harness for this is in scope
  of the first AC that needs it.
- 'Must handle errors per the project error handling policy: a condition the maker
  cannot classify is an error answer (code INTERNAL_ERROR) whose message names it
  -- never an ok answer, and never a traceback on stdout.'
```
