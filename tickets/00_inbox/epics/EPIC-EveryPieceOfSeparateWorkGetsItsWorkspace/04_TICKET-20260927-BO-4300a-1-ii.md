## Acceptance Criteria

```gherkin
Given a test project whose main copy holds the ticket
  "tickets/TICKET-20260925-demo.md",
And a workspace is requested for that ticket, naming the ticket by its
  location in the main copy,
When the workspace maker answers ready with workspace location L,
Then the answer states the ticket's location inside L,

  and holds the content of the ticket named in the request,

  other location outside L, as the workspace's copy of the ticket,
And a ready answer never states a ticket location at which no file exists.
```

## Implementation Notes

```yaml
- The in-workspace location is the ticket's project-relative path (computed against
  the resolved project, never against cwd) re-rooted under workspace_path. The request's
  path must lie inside the resolved project; one outside it is a usage error (code
  USAGE) naming it, and --ticket with --kind scratch is a usage error.
- 'Existence and identity are checked on the finished workspace immediately before
  the answer is emitted: a regular file exists at ticket_path_in_worktree, and its
  bytes equal the ticket named in the request as it exists on the base the workspace
  was made from. An ok answer is never emitted with a ticket field that fails either
  check.'
- 'Decision 3 governs content: the workspace takes the ticket only from its own base
  (origin/main for a new line, the resumed line for a resumed one). The maker never
  copies, writes or edits a ticket file from the main copy into a workspace.'
- 'UNPUSHED TICKET (DECIDED, user 2026-09-27): when the requested ticket is absent
  from the workspace''s base (reason ''absent'') or present there with bytes that
  differ from the main copy''s (reason ''differs''), the maker refuses with code TICKET_NOT_ON_BASE
  (status refused, exit 2). The message names the ticket''s project-relative path
  and tells the caller to push it and ask again; the answer carries ticket_path (the
  path as requested) and reason, and -- like every non-ok answer -- neither workspace_path
  nor either ticket_path_in_worktree field. The maker never copies unpushed or uncommitted
  content in, and never treats ''differs'' as ok with a warning.'
- 'Order and clean-up for TICKET_NOT_ON_BASE: the check runs after the workspace''s
  fetch and before its install build, so no build runs for a refused request. When
  the clone was made by THIS request it holds no work by construction, and the maker
  clears it before emitting the answer: the refusal leaves no folder at the workspace
  location and no INCOMPLETE remnant. A resumed line compares against the resumed
  line, not origin/main, and a pre-existing workspace is never cleared by this check.'
- The answer fields are named ticket_path_in_worktree and ticket_path_in_worktree_posix
  (BO-4300c-2); the retiring set-up script's ticket_path_final and the charter's ticket_path_new
  are not emitted by the maker, not even as aliases, because both have been read as
  "the ticket inside the workspace" while meaning the input path.
- 'Caller fixes land in the SAME change set as this record (KI fix direction: "Fix
  the two prompt sites in the same change"): build-single-ticket''s step-1 prompt
  via BO-4300a-1-ib and worktree-agent''s ticket_path_new parsing via BO-4300f-2-ia.
  This record is not signed off while either caller still reads another field.'
- Proof runs the DEPLOYED maker -- the copy an install delivers, resolved through
  the shared test locator delivered by BO-4300f-4 -- as a separate process against
  real temporary git repositories with a real bare hub. No mock of git, no import

  Behaviorally, Not by Grep'); a test never falls back to the templates/ source copy.
- 'Tests must not spawn the package''s own scripts/build.py (CLAUDE.md ''Tests must
  not spawn their own build.py''): the deployed maker comes from the shared deployed
  layout, and fixture projects carry a minimal stub build entry point that installs
  a real, rejecting hook in well under a second. A test that must mutate the package
  and build its own copy says so and justifies it in its ticket.'
- All temporary projects, hubs and workspaces live under the test's temp directory
  and run git with an isolated global and system config; afterwards the developer's
```
