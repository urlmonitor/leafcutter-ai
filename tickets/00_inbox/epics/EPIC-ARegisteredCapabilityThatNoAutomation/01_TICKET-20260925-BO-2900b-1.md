## Acceptance Criteria

```gherkin
Given the product's operator-facing command surface registers four actions —
  `claim`, `release`, `mark-done` and `report`,
  And the automation that drives builds invokes `claim`, `release` and `mark-done`,
  And no automation invokes `report`,
When the connection from registered capabilities to the automation that runs them
  is checked,
Then `report` is reported as a registered capability that nothing runs, naming the
  capability and the command surface it is registered on,
  And `claim`, `release` and `mark-done` are not reported,
  And the change is refused rather than passing with an advisory note,
  And the set of capabilities checked is the set the command surface actually
    registers when it is built — obtained by asking the built surface what it
    accepts — so a capability that appears in the source but is never registered is
    not checked, and a capability registered only under a condition that is false
    when the surface is built is not checked.
```
