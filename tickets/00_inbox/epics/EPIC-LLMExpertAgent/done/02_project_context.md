# 02: Create PROJECT_CONTEXT.md for llm-expert

## Goal

Create the leafcutter-internal knowledge file `docs/agents/llm-expert/PROJECT_CONTEXT.md` that documents shell conventions, agent/skill frontmatter schemas, signoff protocol, nesting rules, and the expanded Prompt-Quality Checklist with examples. This file is NOT deployed to consumer projects — it remains in leafcutter-internal docs/.

## Context

Stub generated by create-epic. Harden with create-ticket (depth 2).

The llm-expert agent requires a PROJECT_CONTEXT.md file analogous to `docs/agents/python-coder/PROJECT_CONTEXT.md`. This knowledge base enables the agent to:
- Understand and enforce the shell convention (single-command rule from CLAUDE.md)
- Validate agent frontmatter schema (required fields, build-injected vs hand-authored)
- Validate skill frontmatter schema
- Enforce signoff protocol (parity guard, timestamps, phase-agent choreography)
- Apply nesting/spawn-allowlist rules (depth-3 cap, spawn_allowlist contract)
- Run the expanded Prompt-Quality Checklist with concrete examples of good and bad patterns

The PROJECT_CONTEXT.md is leafcutter-internal (docs/, not templates/) and must NOT be deployed to consumer projects.

## Acceptance Criteria

```gherkin
Given docs/agents/llm-expert/PROJECT_CONTEXT.md is created
When the file is read
Then it contains all six sections in order:
  1. Shell convention
  2. Agent frontmatter schema
  3. Skill frontmatter schema
  4. Signoff protocol
  5. Nesting / spawn-allowlist rules
  6. Prompt-quality checklist (expanded)

Given the "Shell convention" section is read
When it describes the single-command rule
Then it explains the rule from CLAUDE.md: every Bash tool call must be a single command
And it lists detection heuristics for violations: &&, ; (outside quotes), ||, cd followed by another command, pipes to commands that produce side effects
And it includes examples of wrong patterns (compound commands) and right patterns (single commands with absolute paths)
And it notes that environment variable syntax (ENV=val command) is allowed as a single command

Given the "Agent frontmatter schema" section is read
When it lists required fields
Then it includes: name, description, model, tools, portable, signoff, requires_verification, spawn_allowlist (for agents spawning sub-agents)
And it documents which fields are build-injected (e.g., inject_registry, config_keys) vs hand-authored
And it notes that domain can be null for portable agents
And it explains the purpose of each field

Given the "Skill frontmatter schema" section is read
When it lists required fields
Then it includes: name, description, allowed-tools
And it explains the purpose of allowed-tools (whitelist of tools the skill code may call)

Given the "Signoff protocol" section is read
When it describes the protocol
Then it references signoff SKILL.md §2 and §4
And it explains the parity guard (all needed agents sign off before ticket leaves phase)
Then it explains timestamps and their role in enforcing ordering
And it documents why signoff protocol matters for ticket-supervisor choreography

Given the "Nesting / spawn-allowlist rules" section is read
When it describes the depth cap
Then it states the hard limit is depth 3 (depth 0 = user, depth 1 = first agent, depth 2 = second agent, depth 3 = third agent)
And it explains why depth is capped (prevent unbounded recursion, ensure deterministic execution)
And it explains spawn_allowlist: every agent that spawns sub-agents must declare which agents it may spawn
And it explains spawned_by: how ticket-supervisor uses spawned_by to determine who can invoke an agent
And it documents the contract: if an agent spawns sub-agents, it must declare spawn_allowlist; if an agent can be spawned by another agent, it must list spawned_by

Given the "Prompt-quality checklist (expanded)" section is read
When it lists the 6+ checklist items
Then it includes:
  1. No compound bash commands (&&, ;, ||, chained pipes)
  2. Tool allowlist matches tools used
  3. No tools used that are absent from allowlist
  4. spawn_allowlist declared for agents spawning sub-agents
  5. Signoff protocol section present for signoff: true agents
  6. Stop-and-ask rules present for scope boundaries
And each item includes detection heuristics and concrete examples of violations
```
