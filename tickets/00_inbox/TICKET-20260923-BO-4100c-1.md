# Every live workspace carries a definite verdict on whether it still holds something

## Actor / Goal

As the leafcutter-ai system, I want to implement AC `BO-4100c-1` — Every live workspace carries a definite verdict on whether it still holds something — so that the acceptance criterion is satisfied.

## Context

This ticket was generated from AC store entry `BO-4100c-1`. Component: `build-orchestration`. Assigned agent: `python-coder`. Estimated complexity: `L`. Complexity: `high`.

## Acceptance Criteria

```gherkin
Given 150 live workspaces, some holding work that has not reached the shared
  main line and some holding none,
When the live set is assessed,
Then every one of the 150 carries exactly one of two verdicts: holds work not
  on the shared main line, or holds nothing not on the shared main line,
And no workspace is left without a verdict,
And a workspace carries the holds-work verdict when any one of these is true
  of it on its own: it has modified tracked files; it has staged changes; it
  has untracked files that are not ignored; its branch carries a commit not
  reachable from the shared main line; or a stash entry belongs to it.
```

- [ ] AC-1: every one of the 150 carries exactly one of two verdicts: holds work not
- [ ] AC-2: no workspace is left without a verdict
- [ ] AC-3: a workspace carries the holds-work verdict when any one of these is true

## Implementation Notes

```yaml
- 'The verdict must be produced by an invocable program, not by an agent following
  a procedure. templates/workflows/close-worktree.md is today''s only disposal surface
  and it is a prompt: it judges one workspace a human already chose, so it structurally
  cannot carry the clause that all 150 receive a verdict. It must not be the thing
  this record changes.'
- The five triggers are independently sufficient and must be evaluated as a disjunction
  over a DECLARED set, so a sixth trigger is added by extending the set rather than
  by editing the verdict logic. A hard-coded chain of conditions reproduces the count-coupling
  defect this family is full of.
- 'Reachability from the shared main line must be decided by PATCH CONTENT, not by
  commit identity: after a squash merge the pre-squash SHAs are absent from main''s
  history while their diffs are on it, and treating them as unreached makes every
  delivered workspace read as holding work. The existing close-worktree procedure
  already uses git cherry for exactly this reason and records why.'
- Untracked-file detection must honour the project's ignore rules as git itself resolves
  them -- nested .gitignore files and the worktree's own exclude file included --
  or every workspace with a build cache reads as holding work and the accumulation
  half of BO-4100c never improves (see BO-4100c-1-i).
- A stash entry must be attributed to the workspace it was made in. Git's stash list
  is per-repository and shared across every workspace, so an attribution rule is required.
  An entry that cannot be attributed to any workspace must not be silently dropped
  -- it is itself an unaccounted holding and must be surfaced rather than discarded.
- An assessment that raises or cannot read must yield the no-verdict outcome, never
  holds-nothing. The natural implementation reads an unanswerable question as an empty
  finding set; that path must be closed here, because BO-4100c-3 can only act on an
  outcome this record produces.
- Assessing the whole live set must be fast enough for routine use at the recorded
  scale -- on the order of seconds for 150 workspaces -- so per-workspace git invocations
  must not be issued serially without bound.
- The assessment is a READ. It must not fetch, prune, reset, stash, or write any ref
  or file in any workspace it inspects.
- Any new module must be registered in the build deploy manifest (scripts/build_phases*.py).
  The hook and CLI layers run from the DEPLOYED layout, so a module present only in
  the source tree raises ModuleNotFoundError at runtime while every source-tree unit
  test passes.
```

## Agent Contracts

### Delivers To

- **Agent:** python-coder
- **Contract:** One assessment record per live workspace: { path: str, verdict: 'holds_work' | 'holds_nothing' | 'no_verdict', items: [{kind: 'modified' | 'staged' | 'untracked' | 'unreached_commit' | 'stash', ref: str}], reason: str | null }. `items` is non-empty exactly when verdict is holds_work, and is the set BO-4100c-2's refusal names item by item. `reason` is non-null exactly when verdict is no_verdict, and is what BO-4100c-3's refusal states. The three verdict values are a closed machine-readable discriminator, so BO-4100c-3's two refusals are distinguishable without parsing prose. BO-4100e-2-i consumes the same record for a workspace reached by discovery rather than by registration.
